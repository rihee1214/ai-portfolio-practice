# P08-D 모의 결제·결과 조정·예약 만료 — 구현 작업 계획

> **For agentic workers:** 구현 요청 시 `superpowers:executing-plans`로 작은 작업을 순서대로 수행한다. 개발 전체 통과 후 지정 검토세션에서 독립 검토한다. 이번 문서 작성은 구현/커밋 승인이 아니다.

**Goal:** 확정 성공·확정 실패·결과 불명확과 만료 경쟁을 안전하게 처리한다.

**Architecture:** payment가 시도/제공자 결과를 소유하고 order 공개 계약으로 주문 잠금과 전체 예약 결과를 같은 거래에 반영한다. B worker가 지속 조회/만료/보상 작업을 실행한다.

**Tech Stack:** Java/Spring Boot·Spring JDBC·PostgreSQL·JUnit/ArchUnit·React/TypeScript·Vitest/Playwright.

**Spec:** [설계](../shop-design.md) §4·7~11·13~16, [요구사항](../requirements.md) F05/F09/F10/F11·AC01~04/07/08/13, [구현 계획](../implementation-plan.md) §10, [P08 전체 계약](P08.md).

상태: 구현·개발 전체 검증 완료 / 독립 전체 검토 대기 (2026-10-28). 선행: **C 및 B 완료**. 아래 계획 문구와 초기 기록은 작성 당시 이력이다.

## Interfaces와 세부 계약

생산: PaymentAttempt CREATED→PROCESSING→SUCCEEDED/FAILED/UNKNOWN, order와 별도 상태. 승인 전 주문 소유권·저장금액·유효예약 확인/활성시도1개를 거래로 기록한다. 외부 모의 제공자 호출은 거래 밖, 응답 저장·주문 상태·전체 재고/쿠폰·Outbox는 결과 거래. 주문 잠금은 승인 시작/결과/만료 경로에서 공통이며 stale worker token만으로 상태를 확정하지 않는다.

PROCESSING/UNKNOWN은 정각이 와도 해제/새 승인 금지. 조회로 확정 실패일 때만 전체 release/expire. 성공 확인 시 기한/예약 확정이 불가능하면 고객 PAID로 선반영하지 않고 보상 취소를 기록·재조회, 실패 시 운영 확인으로 남긴다. 이미 해제 후 늦은 승인의 보상도 동일하다. 임의 기한 연장이나 내부 reserve/commit 검증 우회 금지. 실제 환불/클레임 전체 기능은 P09지만 늦은 승인 보상 취소의 멱등 시도·UNKNOWN·운영 조회는 D 필수다.

초기 제안은 결제 조회 최대5회/최대15분, 이후 REVIEW_REQUIRED 작업 표식과 재대사 명령(권한·감사 필수)이다. B의 재시도 소진과 구분해 D에서 수치/상태 계약을 고정하고 무한재시도 금지. mock은 정상/거절/응답유실/지연성공/조회실패를 결정적으로 제공한다. 0원은 외부호출0이며 동일 검증 후 결제 이력·모든 예약 확정1회. 사용자 승인 POST는 CSRF/소유권 확인, fixture 전용 모의 결과 설정은 운영 공개 API에 노출하지 않는다.
