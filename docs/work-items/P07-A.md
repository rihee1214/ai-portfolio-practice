# P07-A 공개 상품·배송 행사 — 구현 작업 계획

> **For agentic workers:** 구현 요청 시 `superpowers:executing-plans`를 사용해 아래 작업을 순서대로 수행한다. 단계 전체 개발 통과 후 지정 검토세션에서 독립 검토한다. 이 문서 작성만으로 구현·다음 단계·커밋을 시작하지 않는다.

**Goal:** 판매자가 자기 매대의 공개 행사를 관리하고 회원·비회원이 같은 조건으로 조회하도록 한다.

**Architecture:** 설계의 promotion 모듈이 혜택 데이터와 계산을 소유한다. 기존 identity/seller/catalog 공개 API로 권한과 판매 정보를 확인하고, React는 서버 결과와 입력 상태를 표시한다. 거래 경계·정수 계산·현재 권한 검사를 서버에서 보장한다.

**Tech Stack:** 기존 Java·Spring Boot·Spring JDBC·PostgreSQL·Flyway·JUnit·ArchUnit, React·TypeScript·Vitest·Playwright. 새 프레임워크를 도입하지 않는다.

**Spec:** [요구사항](../requirements.md), [설계](../shop-design.md), [구현 계획](../implementation-plan.md), [P07 공통 계약/검증 절차](P07.md). F08·F03, AC03·AC04·AC05, requirements §8, shop-design §4·7·8.

상태: 개발 전체 및 독립 전체 검증 완료. 상세 결과·제한·실패 이력은 아래 최종 기록과 P07-A-review.md 참조.

## 입력·출력·실패 계약

계획 공개 계약은 `Promotions.save(UUID actor, UUID id, Input input): Promotion`, `published(UUID id): PublicPromotion`, `candidates(UUID storeId, List<UUID> productIds, Instant at): List<Candidate>`다. Input은 제목·상품/배송 종류·대상 상품 IDs·시작/종료·정액/정률·상한·상태·version을 포함한다. Candidate는 행사 ID/version/기간/대상/할인 조건만 가지며 C가 계산에 사용한다. ID를 임의 소유권으로 신뢰하지 않는다.

예정 경로는 판매자 `/api/seller/promotions`의 생성/목록 및 `/{id}` 조회/수정/보관, 공개 GET `/api/events`와 `/{id}`, 화면 `/seller/promotions`, `/events/:id`다. 대상 상품은 자기 매대 여부를 catalog 공개 API로 검증한다. 기존 API가 충분하지 않으면 catalog.api에 좁은 검증 계약을 추가하고 타 모듈 JDBC를 참조하지 않는다.

기간은 start < end, 정확한 종료에는 적용하지 않는다. 공개 조회는 현재 판매자·매대·상품 공개 조건을 재확인한다. 관리 권한은 MANAGE_CATALOG, 실제 행사 적용은 NEW_SALES 및 판매 가능 조건을 사용한다. 정지/숨김 상태에서 새 행사가 할인 적용을 우회하지 못한다. C 전에는 행사 안내/후보/할인 규칙까지만 제공하며 최종 배송비·결제 금액으로 표시하지 않는다.

## 실행 기록 — 2026-10-26

- V26 행사·대상·감사 테이블, promotion API/순수 규칙/JDBC/HTTP, 판매자 관리 및 공개 목록/상세를 추가했다. 외부 모듈 쓰기는 없으며 공개조건은 기존 catalog와 같은 원칙의 명시적 읽기 projection이다.
- API의 Candidate/PublicPromotion 별도 DTO 예정은 Promotion 값 DTO 공유로 구체화했다. 공개 필드는 id/storeId/title/scope/productIds/startsAt/endsAt/kind/value/cap/state/version/storeSlug/storeName/targets의15개다. 소유자/감사 행위자/개인정보는 제외한다. 현재 공개인 target만 공개 응답에 포함하며 매대·상품 안내 링크에 사용한다.
