## R-A01 — P2: 정렬·필터 계약을 판별하는 assertion 부족

근거: `backend/src/test/java/com/example/marketplace/dbtest/PostgresJdbcIT.java`의 `browseSearchFiltersSortAndPages`는 22개 상품을 모두 100원으로 만들고 `price_asc`만 조회한다. 중복 없는 페이지와 응답 반복 일치는 검사하지만 가격이 다른 상품의 오름차순·내림차순, 이름순, 등록시각순을 구별하지 않는다. 현재 `price_asc`가 UUID순으로 잘못 구현되어도 이 DB 검사는 통과할 수 있다. 브라우저는 서로 다른 가격의 오름차순 일부를 확인하지만 `price_desc`·`name`·`newest`의 순서 assertion은 없다.

카테고리·매대·가격·재고 조건도 한 요청에 결합하고 유일한 재고 보유 상품을 기대하므로 카테고리나 매대 조건이 빠져도 그 assertion은 통과할 수 있다. 또한 활성 옵션이 여러 개인 상품에서 최저가(품절 옵션 포함), 비활성 옵션 제외를 판별하는 fixture가 없다.

보완: 서로 다른 가격·제목·명시적 생성시각과 동률을 가진 상품으로 네 정렬의 실제 순서를 검사한다. 각 필터가 없을 때만 포함되는 대조 상품을 두고 필터별 배제를 확인한다. 여러 활성/비활성·품절 옵션의 가격 및 가용량으로 표시 최저가/가격 필터/재고 필터 계약을 확인한다. 기존 검사를 유지하고 필수 검사 목록·A01/A02 매핑에 연결한다.

## R-A02 — P2: 카테고리 페이지 이동 중 미적용 선택 유실 경로

근거: `frontend/src/pages/BrowsePages.tsx`의 `CategoryOptions`(29~39행)는 uncontrolled select의 `defaultValue={selected}`를 사용한다. 선택 변경은 상태에 저장하지 않고, 현재 페이지의 옵션만 렌더링한다. 목록 로딩 중에는 `useResource`가 이전 옵션을 제거하며, 보존하는 추가 옵션도 사용자가 방금 선택한 값이 아니라 URL의 `selected`다.

예상 재현: 필터 미적용 상태에서 카테고리 A 선택 → 다음 카테고리 클릭 → 로딩/다음 목록에서 A option 제거 → 검색 적용. 선택값이 전체 또는 기존 URL의 값으로 바뀌어 의도한 A 필터를 잃을 수 있다. 이는 정적 분석으로 찾은 경로이며 이번에는 실행 재현하지 않았다.

보완: 미적용 카테고리 선택을 상태로 보존하고 옵션 페이지/로딩/오류 중에도 해당 option을 유지한다. 카테고리 21개 이상의 컴포넌트 또는 브라우저 회귀 검사에서 선택 → 옵션 페이지 이동 → 선택 유지 → 적용 URL 및 실제 요청의 category를 확인한다. 뒤로 가기/URL 변경 시에는 새 URL 선택값을 복원해야 한다.

## R-A03 — P2: A04의 실제 필터 제출·페이지 초기화 검증 누락

`frontend/tests/unit/Browse.test.tsx`의 URL 검사는 `{ ...query, q: '다른 상품', page: 0 }`을 직접 만들어 직렬화한다. 이는 `BrowseList.submit`이 페이지를 초기화한다는 근거가 아니다. 브라우저 검사도 페이지 1에서 돌아온 뒤 필터를 바꾸므로 비영 페이지의 필터 적용을 검증하지 않는다. 현재 submit이 기존 page를 유지하는 회귀가 생겨도 해당 검사들은 놓친다.

보완: page=1 이상에서 실제 폼을 변경·제출해 page=0과 나머지 조건/매대 고정값이 요청 및 URL에 유지되는지 검사한다. 뒤로 가기 때 폼과 결과의 조건 복원을 함께 확인한다. R-A02 회귀와 묶어 작성해도 된다.
