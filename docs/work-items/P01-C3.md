# P01-C3 JDBC 조회·매핑·트랜잭션·테스트 DB 보호

2026-10-23 / 상태: 구현·검증·지정 세션 검토 완료

## 범위와 실행 계획

설계의 NamedParameterJdbcTemplate, RowMapper, 공개 서비스의 @Transactional(checked exception 포함) 계약을 테스트 전용 fixture로 구현한다. 미정 업무 도메인·API·운영 migration은 추가하지 않는다. D1의 JUnit/MockMvc와 D2의 Failsafe/Testcontainers 체계는 시작하지 않는다. C3 전용 Java 실행 검사를 사용하며 JUnit 실행 수와 구분한다.

1. 기존 서버·컨테이너·개발/테스트 DB 덤프 해시 기록.
2. 보호 장치와 조회/이체 계약 검사부터 작성하고 실패 확인.
3. 보호 장치 → 새 전용 DB → 기존 V1 + 테스트 전용 V2 → Spring 프록시를 통한 서비스 실행 순서로 구현.
4. 파라미터 바인딩·금액/NULL 매핑·성공 커밋·중간 제약 실패·checked exception·REQUIRED 참여 롤백을 독립 연결에서 확인.
5. 격리 빌드·회귀 확인, 보존 비교, 문서 및 지정 세션 검토.

결정: 이전 단계와 지정 검토 세션이 공유하는 현재 작업 공간에서 진행하고 빌드는 .local-tools/c3-build에 격리한다. 기존 프로세스의 JAR/출력과 DB 컨테이너는 대체하지 않는다. 테스트용 코드/SQL은 src/test에만 두어 배포 JAR에 포함하지 않는다. 모든 SQL 초기화는 대상 검증 이후에만 수행하며 drop/truncate/delete/reset/clean 경로를 제공하지 않는다.

대상은 고정 loopback 테스트 포트15433의 새 c3_verify_<32자리 UUID> DB만 허용한다. 일반 marketplace_dev/test, 운영 이름, 관리자 앱 계정, URL 옵션/다중 호스트를 거부한다. 실제 연결의 DB·사용자·관리자 권한도 검사한 뒤 이행한다. 실행마다 새 DB를 만들고 보존한다. 로컬 설정과 DB 관리자 자격을 가진 사용자를 격리하는 보안 경계가 아니라 검증 도구의 오접속 방지 장치다.

## 검증 결과

- [보호 검사 RED](evidence/P01-C3-guard-red.txt): 구현 전 12개 거부 조건 실패 확인. [최종 보호 검사](evidence/P01-C3-guard.txt): 12개 거부 + 허용 1개, 총 13개 통과. 이 검사가 실패하면 스크립트는 DB 생성 전에 종료한다.
- [계약 RED](evidence/P01-C3-red-results.txt): 조회/이체 미구현 상태에서 실제 DB 검사 26개 중 12개 실패. [최종 계약](evidence/P01-C3-results.txt): 26개 통과. 인용부호·한글·SQL 주입 문자열 바인딩, BigDecimal/NULL/문자열 매핑, 없는 행, 정상 커밋, 양쪽 잔액 변경 이후 중복키 실패 롤백, 출금 이후 checked 예외 롤백, 잔액 CHECK·FK, REQUIRED 내부 실패와 바깥 rollback-only를 확인했다.
- [실행 로그](evidence/P01-C3-runtime.txt): PostgreSQL 18.6, 기존 V1 + 테스트 전용 V2 최초 이행과 재실행 0건. Spring 컨텍스트의 실제 프록시·JdbcTransactionManager를 사용했다. 새 연결로 잔액/이체 기록을 읽으므로 테스트 전체 자동 롤백으로 성공을 가장하지 않는다.
- [Maven verify](evidence/P01-C3-build.txt): Checkstyle·테스트 소스 컴파일·패키징 성공. JUnit은 0건이며 13+26 계약 검사는 Java main으로 별도 실행했다. D1/D2의 JUnit/MockMvc/Failsafe는 미착수다.
- [배포 JAR 확인](evidence/P01-C3-package.txt): 테스트 fixture 클래스와 V2 SQL 미포함. production 코드·V1·pom·React 코드는 변경하지 않았다.
- [기존 프런트 회귀](evidence/P01-C3-frontend-tests.txt): 68개 통과, 실패/skip 0. 화면 변경이 없어 브라우저 검증은 반복하지 않았다. 이번에는 React 타입·린트·빌드를 반복하지 않았다.
- [종료 상태](evidence/P01-C3-after.json): 기존 8080/5174 PID, DB 컨테이너 ID/healthy 유지. 기존 marketplace_dev/test의 덤프에서 무작위 restrict 토큰만 제외한 SHA256이 시작 시점과 동일하다. 기존 두 health는 HTTP200 status-only UP. 기존 JAR가 계속 실행 중이며 C3를 그 서버에 배포했다는 뜻이 아니다.

## 잔여 데이터와 실패 이력

새 테스트 DB 두 개를 보존했다. [RED DB](evidence/P01-C3-red-target.txt)는 `c3_verify_5aaff9ff870e41e883136dc31ab25c25`, [최종 DB](evidence/P01-C3-target.txt)는 `c3_verify_51b5e587565343ca8abbfbbc5afce7cf`다. 모두 marketplace_test 소유이며 marketplace의 Flyway 이력과 c3_fixture.account/transfer_entry의 가상 데이터를 포함한다. 기존 개발/공용 테스트 DB와 C2 검증 DB는 초기화하지 않았다. 이 작업에서 컨테이너 재시작·볼륨 삭제·DB drop/clean/reset은 하지 않았다. 검사에는 HTTP 앱 프로세스가 없다.

초기 빌드에서 보호 utility 이름 TestDatabaseTarget이 Surefire 기본 Test* 검색에 걸려 JUnit3 provider 오프라인 누락으로 [실패](evidence/P01-C3-initial-build-failure.txt)했다. 실제 JUnit 테스트가 아닌 utility를 DedicatedDatabaseTarget으로 바꾸고 격리 출력의 이전 class 한 개만 제거해 해결했다. Maven 전체 테스트를 skip하지 않았다. [제한 실행의 TCP 거부](evidence/P01-C3-sandbox-failure.txt)는 승인된 실행에서 해소됐다. 이 두 실패는 제품 검사의 RED와 구분한다.

## 한계·인수인계

현재 남은 실행 차단 항목은 없다. 사용자 직접 실습, 새 PC/다른 OS, 운영 보안·백업 복원·분산 트랜잭션·동시성은 미검증이다. C3는 테스트 전용 SQL/서비스 패턴이며 쇼핑몰 업무 기능·운영 데이터 스키마 구현 완료를 뜻하지 않는다. 테스트 도구는 고정된 로컬 포트와 프로젝트 로컬 JDK/cache를 사용한다. 기존 캐시가 없으면 오프라인 빌드가 실패한다.

지정 검토 및 반영세션의 [검토](P01-C3-review.md)를 완료했다. 제품 코드 수정 지적은 없고 로그 마스킹 시점의 문서 설명 1건을 보정했다. 사용자 이해·실습 완료는 미확인이다. 다음 P01-D 단계와 원격 push는 진행하지 않는다.

증거 텍스트는 Git 공백 검사에 맞춰 줄 끝 공백과 마지막 빈 줄만 정리했다. 원본 실행 출력은 .local-tools/c3-*에 보존한다.

구현·검증 커밋: 5dae1675e4e787435efe378b549061e42b6036c2. 후속 검토 문서와 상태 변경은 별도 로컬 커밋으로 보관한다. 검토 후 코드 변경은 없으며 서버·DB를 추가 조작하지 않았다.
