# P01-D3 개발 검토

2026-10-23 / 대상: `9630fae..da54ed8641d994e163e1991eebf344945bc50a40`

판정: D3 범위 검토 통과. 필수 수정 결함은 발견하지 않았다. 제품 코드·테스트 코드·패키지·상태 문서는 변경하지 않고 이 검토와 증거 요약만 추가했다. 사용자 직접 실습은 미확인이고 D4 이후는 진행하지 않았다.

## 독립 확인

[검토 실행 요약](evidence/P01-D3-review-checks.json): test:unit은 2개 파일·14개 통과, 타입 검사·린트 종료 코드 0이다. npm ls와 설치 패키지의 engines/peerDependencies를 대조했다. Node24.22.0은 Vitest5.0.5/jsdom30.1.3/jest-dom7.0.1의 범위에 들고 Vite8.3.4·React19.3.1도 해당 peer 범위에 든다. lockfile과 정확한 버전 고정, 별도 Vitest include 설정을 확인했다. 새 PC에서 npm ci를 재현한 결과나 포괄적 보안 감사를 의미하지 않는다.

git diff의 frontend/src 범위는 비어 있어 제품 소스의 최종 변경이 없음을 확인했다. 기존 Node68개·빌드·mutation은 개발세션 로그를 검토했으며 이 세션에서 반복하지 않았다. 실행 중 서버·DB 연결/쓰기/생성/재시작은 하지 않았다. DB 보존은 개발세션의 P01-D3-preservation.json 증거이며 이 검토에서 덤프를 다시 생성하지 않았다.

| 대상 | 판단 |
| --- | --- |
| 실제 컴포넌트 사용 | HomePage/HealthPanel과 실제 health/http 모듈을 사용하고 fetch만 대체한다. 내부 상태값을 직접 변경하지 않고 역할·접근 가능한 이름·사용자 입력과 클릭으로 관찰한다. |
| 입력 | 이름 변경/초기화, 공백 안내, maxLength30, 재마운트 초기화를 확인한다. 영속 저장이나 실제 새로고침·라우팅 검증과 구분한다. |
| 비동기 상태 | deferred Promise로 응답 시점을 제어하고 act로 갱신을 기다린다. 임의 sleep 없이 로딩·성공·오류·재시도를 관찰한다. 실패 후 내부 오류 원문이 표시되지 않는지도 확인한다. |
| 오래된 응답 | 두 요청의 AbortSignal과 최신 요청 로딩 중/성공 후의 옛 응답 도착을 모두 검사한다. 모의 fetch는 abort를 무시하지만 실제 requestJson은 중단 신호를 다시 검사하므로 옛 응답 결과가 cancelled가 될 수 있다. 순번 보호를 제거한 실험에서 최신 상태가 취소 안내로 덮여 두 검사가 실패한 증거가 있다. 이는 유효한 회귀 탐지이며 옛 DOWN 본문이 그대로 표시된 실험이라고 설명하지 않는다. |
| StrictMode·정리 | HealthPanel은 StrictMode로 렌더링하며 사용자 동작 전 요청 없음과 effect 정리 후 요청 가능 여부를 확인한다. afterEach에서 cleanup 후 global/spy 복원을 수행하고 각 테스트가 pending 요청을 자체 관리한다. |
| 범위 분리 | Vitest는 jsdom과 테스트용 React 플러그인만 사용하며 Vite API 프록시를 로딩하지 않는다. DOM 통과는 실제 브라우저 레이아웃·네트워크·Boot/DB 연동·스크린리더 발화 성공을 뜻하지 않는다. |

## 비차단 관찰과 남은 범위

1. **재마운트 검사의 보장 범위:** unmount 시 신호 중단과 새 화면 상태를 확인하지만, 해제된 인스턴스의 publish가 전혀 호출되지 않는다는 것까지 DOM만으로 입증하지는 못한다. 새 인스턴스는 원래 별도 React 상태를 갖는다. 기존 node:test의 createHealthCheck 검사는 dispose 이후 publish 횟수 불변을 직접 확인하므로 해당 보장은 두 검사를 함께 근거로 삼는다. 이를 이유로 추가 추상화나 제품 코드 변경은 필요하지 않다.
2. **기본 fetch 모의의 역할:** setup의 예외는 실제 네트워크 접근을 막지만 requestJson이 예외를 network 결과로 처리하므로 예상 밖 호출을 무조건 테스트 실패로 만드는 장치는 아니다. HomePage의 일부 검사와 HealthPanel 초기 검사는 호출 0건을 명시적으로 단언한다. 향후 모든 화면에서 불필요한 자동 요청 금지까지 공통 계약으로 삼는다면 기본 fetch mock의 호출 횟수를 별도 확인해야 한다. 현재 구현의 결함으로 판정하지 않는다.
3. Node 테스트에 있는 본문 스트림 단절·프록시 timeout을 jsdom에서 모두 중복 검증하지 않아도 된다. 이 단계의 UI 연결 목적과 기존 통신 검사 역할을 유지한다. 실제 브라우저·Router 이동·취소 중 본문 읽기·네트워크 연동·모바일 표시 등은 D3 DOM 결과로 확대하지 않는다.

개발세션의 최종 기록에서는 현재 작업 문서의 ‘구현·검증 진행, 지정 세션 검토 대기’를 이 결과에 맞춰 갱신할 수 있다. 검토 문서 2개와 완료 기록은 개발세션의 최종 로컬 문서 커밋에 포함한다. 프런트 단순화와 D4 이후, 원격 push는 수행하지 않았다.
