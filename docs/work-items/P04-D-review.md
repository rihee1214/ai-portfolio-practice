# P04-D 독립 검토

2026-10-25 / 기준33d5427 / 계약 사전 검토. 구현·실행 판정 전.

개발세션의 실제 최신 사용자 메시지에서 P04-D 진행·독립 검토와 P04-E 보류를 직접 확인했다. 검토세션은 이 문서와 evidence/P04-D-review-*만 수정한다. 기존 서버·DB·검증 DB·미디어를 보존하며 개발 종료/포트 반환 후 새 DB·새 media 루트로 독립 실행한다. 제품/검사 파일 변경 및 커밋·푸시는 하지 않는다.

## 계약 대조

보유·예약·가용 수량, version, 조정 사유/원인 이력은 설계9절 및 P04-D 계획과 일치한다. 예약 잔액을 표현하고 하한을 지키는 것과 P04-E의 예약 생성/확정/해제를 구분한 범위도 적절하다. 신규 SKU의 미생성 잔액을0/version0으로 읽고 첫 조정에서 생성하는 방식은 모듈 의존을 분리하지만 아래 경합/조회 검증이 필요하다.

## 구현·검증 조건

1. **멱등 키 계약:** UUID requestId의 유일 범위를 전역 또는 actor별 중 무엇으로 정하는지 명시한다. 같은 키/다른 actor·SKU·수량·사유·version의 동작과 본문 정규화 규칙을 확정한다. 성공 응답 유실 후 동일 요청 재전송은 현재 version이 달라져도 최초 결과를 반환하되, 이후 다른 조정까지 되돌리거나 이력을 추가하면 안 된다. 재전송에도 현재 인증·대상 접근 권한을 검사한다. 잠금 이후 조정 금지 상태가 된 경우 재전송 처리 우선순위도 명시한다.
2. **실제 경쟁과 원자성:** 동일 키 동시 제출은 이동1건, 다른 키/같은 version은1승자, 빈 balance 최초 생성 경쟁도1승자여야 한다. balance 갱신 후 movement 삽입 실패 시 수량/version/키 모두 롤백하고 같은 키로 정상 재시도가 가능해야 한다. 서로 다른 SKU에 같은 키가 동시에 들어와도 DB 유일 제약과 충돌 매핑으로500을 만들지 않아야 한다.
3. **예약 하한·엄격 타입:** HTTP에서 소수·숫자 문자열·boolean·null·범위 초과를 거부한다. reserved는 이번 API로 변경할 수 없으며 reserved≤onHand와 available=onHand-reserved를 유지한다. reserved가 양수인 fixture에서 하한과 같은 값은 허용, 그 아래는 거부를 검증하되 예약 API는 추가하지 않는다.
4. **운영자 잠금/권한:** CONTENT를 가진 운영자 자신의 상태/권한과 대상 판매자의 회원·매대·상품 상태를 구분한다. 두 회원을 잠그는 경우 전역적으로 일관된 순서가 필요하다. 대상 잠금 대기 중 CONTENT 회수/계정 정지/매대 제한/보관 후 권한·상태 재검증을 실제 대기 관측으로 검사한다. 판매자·운영자 동시 수정과 상품/SKU 소속 불일치도 확인한다.
5. **초기화·이력:** V16에 기존 SKU를 넣고 V17로 올리는 보충 검사와 신규 SKU의 LEFT JOIN/기본0 조회를 구분한다. 이력 순서는 시각 역행·동률에도 실제 변경 순서를 유지하도록 SKU version 등으로 결정한다. 페이지는 안정된 순서와 hasMore를 제공하며 각 이력이 해당 SKU/대상에 속하는지 확인한다.
6. **화면 재시도:** 수동 재시도 시 응답 유실된 동일 의도에는 같은 requestId를 유지하고, 수량/사유/version을 바꾼 새 의도에는 새 키를 사용한다. 이전 성공 결과 재전송 후에는 최신 balance/이력을 다시 조회해 과거 잔액으로 화면을 되돌리지 않는다. 인증/상품/SKU 변경 시 늦은 응답과 이전 폼·요청 키를 폐기하며401/403은 기존 인증 오류 처리와 일치시킨다.

API 경로/요청·응답·오류와 위 멱등 우선순위를 작업 문서에 구체화하도록 요청했다. 구현 전 확인 조건이며 아직 발견된 구현 결함을 뜻하지 않는다. 실행 결과와 보존 비교 전까지 최종 통과 판정은 보류한다.

## 문서 정합성

implementation-plan의 단계 요약 행에는 P04-C 미착수가 남아 있으나 본문에는 완료가 기록되어 있다. 또한 P04-C 마감 당시 P04-D 이후 보류 문장도 남아 있다. 개발세션은 최신 P04-D 작업 상태를 갱신할 때 과거 기록과 현재 상태를 구분해 정리해야 한다. 검토세션은 해당 개발 소유 문서를 수정하지 않는다.

## 구현 중간 정적 검토

Inventory/JdbcInventory/InventoryController/InventoryErrors, V17, Skus.inventoryAccess와 InventoryPanel을 직접 대조했다. 현재 읽은 소스에서 확정된 필수 수정 결함은 발견하지 않았다. 개발 중인 검사·화면 연결의 완료나 독립 실행 통과를 뜻하지 않는다.

- 전역 requestId 및 actor/SKU/정규화 사유/onHand/입력version 일치 비교, 현재 권한·쓰기 상태 검사 후 replay→version 순서가 작업 문서와 일치한다. 성공 재전송은 movement의 최초 snapshot을 반환하며 balance를 다시 쓰지 않는다.
- 상품 잠금으로 현재 조정 경로를 직렬화하고 balance 최초 생성/행 잠금/조건부 갱신과 movement 삽입을 같은 트랜잭션에서 수행한다. 서로 다른 대상의 키 중복은 거래 밖 DuplicateKeyException409 변환이 있다. 기존 SKU0 보충과 신규 SKU LEFT JOIN0 조회를 구분한다.
- 운영자는 CONTENT 확인 후 대상판매자의 회원→매대→상품 잠금을 취하고 CONTENT를 재확인한다. actor행 잠금을 추가하지 않는 계약이며 권한 회수 후 실제 잠금 대기 종료 시 거부를 최종 검사에서 확인해야 한다. reserved 양수 하한, version 기반 이력 순서, HTTP 정수/UUID 형식 검사가 존재한다.
- 화면 폼은 수량/사유/version에 대해 requestId를 보관하고 CatalogStore 저장 뒤 최신 조회를 사용한다. version별 폼 재생성과 SKU별 이력 컴포넌트가 있다. 응답 유실 후 실제 같은 키 재전송, 입력 변경 후 새 키, 선택/인증 변경 후 늦은 응답 폐기는 별도 실행 증거가 필요하다.

최종 확인 요청: 같은 requestId를 **서로 다른 판매자/상품/SKU**에 동시에 보내는 경우 한쪽만 적용되고 다른 쪽409·잔액/이력 불변을 검증한다. 동일 상품/동일 SKU 검사는 공유 잠금에 직렬화되므로 전역키 unique 충돌 경로를 대신하지 못한다. 운영자 실제 HTTP 조정/CONTENT 회수, V16기존SKU→V17, 이력 시각 역행·페이지, lost-response UI 재전송 검사도 최종 증거와 맞춘다. 독립 실행은 종료 신호 전이므로 수행하지 않았다.
