## 목적과 접근 판단

기능 이름의 체크 목록이 아니라 실제 사용자 명령이 화면→HTTP→업무 서비스→DB→후속 화면으로 이어지는지 증명한다. 역할별 시연 기록과 자동 제약 검사를 같은 요구사항 행에서 찾을 수 있어야 한다. 새 금융 정책·권한·제품 기능·MSA·공개 배포를 설계 범위에 넣지 않는다.

기존 검사 전부를 새 시연 테스트로 복제하는 방안은 실패 원인과 유지보수 지점을 늘린다. 기존 통과 수만 모아 마감하는 방안은 기능 누락·교차 업무 연결·다른 환경 재현을 증명하지 못한다. **기존 assertion과 원보고서를 추적표로 연결하고, 누락된 실제 연결만 보완하는 접근**을 채택한 설계 제안이다. 구현 계획의 순서·승인 정책은 그대로 둔다.

### AC16 권고 재현안과 판정

권고안은 **같은 호스트의 별도 깨끗한 checkout**이다. 실행 승인 후 확정 커밋에서 추적 파일만 새 경로에 준비하고 기존 작업트리·`.local-tools`·`.env`·`node_modules`·빌드 산출물을 복사해 성공 조건을 숨기지 않는다. 런타임 도구 버전과 설치/의존성 준비 명령을 기록한다. Offline에 필요한 캐시는 출처·버전·무결성 및 준비 절차를 명시한 별도 경로에서 사용한다. 캐시 공유가 불가피하면 그 의존성을 공개하고 완전 독립 재설치 성공이라고 하지 않는다.

DB는 새 인스턴스/포트·새 볼륨·새 UUID DB, media는 새 루트, API/프런트/worker/인증 에뮬레이터는 충돌 없는 별도 프로세스·포트·namespace를 사용한다. 같은 Docker 엔진/OS/하드웨어를 공유한다는 한계는 남는다. 실행 담당이 기존 서버를 종료하거나 전역 설정을 바꾸지 않고 기존 실행 안내를 따라 기동·초기 DB 이행·검사·핵심 구매/판매/운영 시연을 재현한다. 필요한 안내 보완과 수동 준비를 전부 기록한다. 미리 성공 결과/DB를 복제한 환경은 재현 근거가 아니다.

## 역할별 연결 시연과 데이터

1. **구매·판매 연결:** 승인된 두 판매자, 회원 구매자와 별도 비회원 구매 세션을 새 namespace에서 준비한다. 상품/옵션·재고1개·품절·숨김·공개행사·회원쿠폰을 실제 소유 API로 생성한다. 회원 두매대 주문과 비회원 주문을 모의 결제하고 판매자별 발송/분할/완료, 구매자 새 조회 세션에서 같은 주문 ID·금액·상태를 확인한다. 판매자는 일반 구매 자격을 유지한다.
2. **후속 처리·운영 연결:** 원 주문에 취소/반품 또는 교환 및 예외환불의 승인된 실제 생산자를 연결한다. 당주 정상 시연은 원 수량·배송비·예약·환불시도 및 조회 가능한 정산 상태까지 대조한다. 모의지급·다음 주 이월은 아래 격리 시간 검증 근거와 연결하며 즉시 지급을 약속하지 않는다. 후기/비밀문의/신고→권한 있는 담당 처리→숨김/복원→공개 조회·알림·대시보드 결과를 확인한다. 하나의 거대한 테스트에 모든 경계조건을 넣지 않고 정상 연결과 격리 DB 실패/경합 검사를 같은 추적행에서 묶는다.
3. **사이트 운영·복구:** CONTENT 게시/중단·배너 파일 접근과 SYSTEM 안내/배송두항목 변경·안전 작업조회를 정상 시연한다. 알림/집계 재처리는 격리 환경에서 실제 terminal FAILED 작업을 생산한 별도 복구 검증에서 수행한다. 새 견적 정책과 기존 주문 불변을 대조한다. 일반 작업 초기화·과거 성공행 수정·실제 지급은 수행하지 않는다.

`SettlementService`의 period_end 검사는 마감 전 명령에409를 반환한다. 새 DB에 만든 당주 거래로 바로 모의지급·차주 이월을 시연할 수 없다. 정상 시연은 실제 시각의 미마감 상태/거부를 유지한다. 주차 마감·지급·이월은 `SettlementIT`의 실제 구매/확정 생산자와 주입된 검사용 `SettlementClock` cutoff 방식, `SupportIT`의 원 지급→다음 주 환불/상계 assertion을 격리 DB에서 재사용한다. 운영체제 시계·운영 Clock·원거래 SQL 시각을 바꾸어 정상 시연처럼 만들지 않는다. 기존 격리 fixture의 시각 설정은 그 검사의 방법과 한계를 그대로 기록한다.

`NotificationRetries`는 `j.status='FAILED'`, `DashboardRuns`는 해당 작업 종류와 `FAILED`를 확인한다. 정상 READY/RUNNING/SUCCEEDED를 강제로 재시도 가능한 상태라고 표시하지 않는다. 실패 복구는 `QuestionsIT#publicAndPrivateQuestionBodiesAndAnswersRespectCurrentReaders`의 실제 알림 실패 생산·재처리, `DashboardIT#concurrentSystemCommandsCoalesceAndAFailedRunKeepsTheLastSuccess`의 실제 실패 작업/새 작업 영수증을 사용한다. 새 시연에 실패를 넣어야 한다면 후속 승인된 격리 환경의 실패 주입을 명시하고 원 실패·재시도 ID·최신 성공·중복0·원행 불변을 함께 검증한다.

시연용 계정·주문은 새 DB/media namespace에만 생성한다. 기존 서버·개발 DB·검증 DB·미디어·실패 증거를 초기화하거나 재사용해 덮어쓰지 않는다. 운영 권한 bootstrap은 기존 승인 경로를 사용한다. UI/API로 생산해야 하는 주문·결제·환불·정산 결과를 직접 SQL fixture로 만들어 실제 시연이라고 하지 않는다. 경계시각·장애주입을 위한 테스트 fixture는 별도 격리 DB에서 표시하고 실제 시연과 구분한다. 비밀번호·토큰·실제 개인정보는 문서/커밋/보고서에 넣지 않는다.

desktop/mobile 기본 프로젝트와 기존 브라우저 타이밍을 유지한다. 긴 문구·375/768/1440폭·키보드·로딩/오류/재시도·권한상실 상태는 실제 assertion에 연결한다. 캡처는 보조 근거이며 자동검사를 대신하지 않는다. 사용자 직접 시연·실기기 확인은 실제 수행 여부를 별도로 기록한다.

## 실패 복구·실행 영향·보존 계획

UNKNOWN 환불은 같은 시도의 조회/대사만 재개하며 예약을 유지한다. 확정 FAILED의 새 시도는 기존 소유 업무 명령으로만 생성하고 옛 결과 재전달이 최신 성공을 덮지 않아야 한다. 알림/집계는 해당 업무 재처리를 사용하며 원 실패·성공 snapshot/영수증은 불변이다. 응답 유실·중복·권한 회수·트랜잭션 rollback은 실제 원행 비교로 검증한다. 서버/worker 장애주입은 새 격리 인스턴스에만 수행한다.

현재 설계 변경은 문서뿐이므로 링크/번호/범위·제품 불변 정적 확인으로 충분하다. 향후 추적표 보완 과정에서 제품 결함을 발견하면 증거·계약·필요 수정 범위를 기록하고 현재 승인 범위를 넘는 구현은 자동 시작하지 않는다. 검사 추가는 기존 등록·필수 목록·제공/소비 영향표와 함께 검토한다. 공통 fixture/인증/금융/작업실행기/스키마/하네스 동작 변경이면 무선택 전체 조건을 적용한다.

E의 full1 failed, recovery28 selected-passed, dto-fixed 및 review-fixed selected-passed와 [독립 최종 판단](../../.local-tools/p11-e-independent-final-bc4a3538c9994cfabd785e66ac511313/review.md)을 그대로 보존한다. E의 유효 8묶음·브라우저176 재사용과 후속 범위 결합은 E 개별 수용 근거다. D 전체 통과도 이후 E 변경 전체에 자동 소급하지 않는다.

향후 실행마다 새 증거 경로·새 DB·새 media를 사용하고 소스946 기준 이후 추가/삭제/변경 목록과 SHA를 기록한다. 기존 자원 보존의 실제 범위는 하네스 문서를 따른다. 과거 모든 DB 행을 전수 대조했다고 주장하지 않는다. E에서 관측한 원 db-test 런타임 shm1GiB/생성설정64MiB 차이와 미확정 setup 실패 원인을 기록한 채 준비 상태를 확인한다. 기존 컨테이너 재시작·설정 변경은 이 설계의 실행 권한이 아니다.

## 설계 검토·인계 기록

2026-11-14 기존 Astra가 계획§14, 요구사항18F/16AC, E 최종 수용·제한과 운영 절차를 대조해 이 초안을 작성했다. 제품·검사·DB·하네스 실행·커밋·푸시·배포는 수행하지 않았다. F18개/AC16개 행의 중복·누락 없이 번호를 확인했고 상대 링크 대상 누락0을 정적으로 확인했다. Sol은 기존 구현/검사로 각 행을 연결할 수 있는지, 새 시연/AC16 환경의 부족분과 정확한 등록 ID를 검토한다. 부모가 결과를 통합해 설계 수용·남은 판단을 연결한다. 실제 Toss 외부차단은 로컬 검증 준비를 막는 조건이 아니지만 전체 인증의 미해결 제한이다. **설계 수용도 P12-A 실행 승인이나 P11 전체 마감이 아니다.**

부모·[Sol의 초안 검토 원문](../../.local-tools/p12-a-sol-feasibility-0e8f20f96fbc4842a8d0461a565fd793/review.md)을 반영해 대표 실제 검사/브라우저 앵커, AC16 같은 호스트 준비와 다른 환경 미검증의 구분, 당주 모의지급 불가와 격리 검사용 Clock 근거, terminal FAILED가 필요한 업무별 복구를 보완했다. F16에는 회원·판매자·매대·카테고리 관리와 seller-store 소비 범위를 명시했다. 설계 작성자의 판단은 **설계 검토·수용 진입 가능, 새 제품 정책 미결정 없음**이다. AC16 실제 외부 환경 확보·실행은 미해결 검증 조건이며 정책 변경이나 확보된 환경으로 간주하지 않는다. 정확한 전체 추적표·실행 원보고서는 향후 승인된 P12-A의 결과물이다. 현재 실행 진입은 승인·P11 로컬 통합 마감 조건 미충족으로 유지한다.
