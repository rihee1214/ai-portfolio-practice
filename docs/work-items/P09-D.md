# P09-D 반품 신청·승인·반려·회수·검수·환불

상태: **계획 문서 독립 검토 반영 / 구현·검증·구현 독립 검토 미착수**, 2026-10-30.
목표: 반품 절차와 금전/판매 가능 재고 복구를 분리해 추적한다.
요구사항: F12, AC09·10의 반품 부분. [공통 계약](P09.md)과 C 개발·독립 전체 통과가 선행이다.

## 상세 계약과 변경 위치

소비: A 배송완료 원단위/시각, B 신청 보류/확정 경합, C 환불/회수비/전체완료 계약. 생산: ReturnReceipt·검수 결과·반품 완료 사실과 E에서 재사용할 회수/검수 절차.

- 배송완료7일 미만·미확정·미점유 대상만 신청한다. 같은 항목의 다른 수량은 구분하되 취소/반품/교환 중인 동일 수량은 중복 신청할 수 없다.
- REQUESTED→APPROVED 또는 REJECTED, 승인 뒤 회수→검수→환불 처리→COMPLETED. 회수/검수 사실 없이 완료 금지. 반려는 이유/actor/시각을 보존하고 점유 해제 후 B 자동확정을 재평가한다.
- 구매자는 본인 신청, 판매자는 자기 하위주문 승인/반려/회수/검수, 운영자는 거래지원 권한·사유가 있는 지원 명령만 허용한다. 비회원은 현재 별도 조회 세션으로 소유권/CSRF를 확인한다.
- 수량별 반환·판매가능·불량·분실을 구분한다. 판매 가능 수량만 causeId별 StockMovement1회; 환불 성공만으로 재입고하지 않는다. 재입고 성공/환불 UNKNOWN 등 부분 진행도 각각 이력으로 남겨 재개한다.
- 변심 회수비3,000원·판매자 책임0원과 C의 확정된 공제/추가비용 정책을 사용한다. 현재 가격·무료배송 조건 재계산 금지. 하위주문 전체 금전+필수 반품 완료 후에만 쿠폰 복구한다.

후속 기간/회수비는 H03의 저장 정책 버전을 사용한다. 원단위/배송묶음과 반품 회수·검수 결과는 C의 전체완료 조정에 전달한다. 재고입고는 검수 판매가능 수량의 효과이고 쿠폰복구는 전체 처리의 효과이므로 서로 다른 시점/원인으로 검증한다. 전체 반품 시 원 배송비 반환 여부, 분할 신청의 회수비 공제 횟수·추가비용 미정산 상태의 완료 조건은 C1의 확정표를 따라야 한다. 정책 공백을 D에서 임의 선택하지 않는다.

예정 변경: C의 `claim/api/Claims.java`, `claim/infrastructure/JdbcClaims.java`, `claim/web/ClaimController.java`; 신규 `claim/domain/ReturnRules.java`, `claim/infrastructure/JdbcReturnReceipts.java` 및 migration (`backend/src/main/java/com/example/marketplace/` 기준). C 환불/inventory 공개 API를 사용하며 구현 직접 참조는 금지. 최소 신청 화면은 G의 전체 UI로 이어진다.

## 독립 검토와 E 인계

검토자는 환불액과 재입고량을 하나의 성공 플래그로 묶지 않았는지, 전체 반품 완료의 서버 근거, 분실/불량 처리와 반려 후 확정 경합을 확인한다. 수량·금액·재고·쿠폰·이력 각각의 assertion과 새 독립 하네스가 필요하다.

E에 원품 회수/검수·판매가능 입고 원인ID, 미완료/추가비용 상태와 공통 환불 전환 포트를 전달한다. 현재 실제 변경·검증·독립 결과·사용자 확인은 없다. 실행 시 동결 소스/증거 경로/실패 이력을 덧붙이며 과거 결과를 소급하지 않는다.
