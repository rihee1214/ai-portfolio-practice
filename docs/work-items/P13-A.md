# P13-A 반품 환불 worker 중단 재현

## 범위와 판정

구매자가 판매자 검수 뒤 견적에 동의한 반품 한 건에서 환불 worker가 처리 준비를 저장한 직후 종료되면, 재시작 뒤에도 자동으로 환불을 끝내지 못하고 검토가 필요한 상태에 머무는 현상을 확인한다. 반품 동의와 금액 예약은 이미 저장된다. 이때 실제로 빠져나간 금액이 없더라도 새 환불을 자동 제출하거나 주문 단위의 보류를 해제하지 않는다. 결과 대기와 운영 확인이 필요한 시간이 이 시나리오의 업무 영향이다.

[구현 계획 §15](../implementation-plan.md#15-p13-문제-재현과-기준-측정), [MSA 전환 설계 §3](../msa-evolution.md#3-재현과-측정), [통합 검증 하네스](../verification-harness.md)를 따른다. 이번 업무의 전달물은 한 가지 장애의 재현 절차와 원증거다. P13-B가 맡는 기준 측정, P13-C/D의 대안·분리 결정과 AC19의 비교 판정은 이후 범위다.

진입 HEAD는 `7b9147120f9a0d241936bb98bda6f0cd2443f191`이다. [선행 커밋 감사](../../.local-tools/perf2-final-98b4d2e9a31c4f8c9e180b825d761f2e/commit-record.md)와 [수용된 무선택 전체](../../.local-tools/perf2-final2-6643f2c1c5bd4114a638cad9523c3dcb/result.json)를 연결한다. 제품·공통 검증 하네스의 실행 소스를 고치지 않고 등록된 `process-recovery`의 테스트를 사용한다. 이 작업의 결과는 미커밋 작업 기록이다.

P13-A 로컬 재현을 수용했다. 동일 업무 조건의 두 실행은 모두 같은 환불 보류 상태를 재현했다. 새 선택 실행은 `selected-passed`, 보존 `passed`, 종료 `0`이다. 선행 무선택 전체의 같은 검사 1회와 신규 선택 1회를 사용했다. 동일 소스의 독립 필수 보완 1라운드 2건을 해결했고 잔여 0건이다.

| 장애 주입 | 첫 자식의 준비 트랜잭션이 커밋된 뒤 모의 제공자 호출 직전 `PREPARED` 표식을 기다린다. `PROCESSING`과 제공자 효과가 없는 상태를 확인하고 이 소유 자식 JVM만 강제 종료한다. 실제 저장된 lease 끝 이후로 고정한 clock으로 새 자식을 시작한다. 다음 조회 시각도 저장된 슬롯 기준의 고정 clock을 사용한다. |
| 관측 범위 | 재시작이 같은 작업에 두 번째 lease를 발급하는지, 같은 환불 시도의 자동 조회·결과·반품 작업이 실제 handler를 거치는지, 금액과 주문 단위 보류가 유지되는지 확인한다. 자식 JVM 시작 인자는 클래스패스와 probe 인자이며 힙·GC 옵션을 별도 지정하지 않았다. 실제 JVM 힙·GC·스레드, 호스트 메모리·부하, DB 풀 사용량·잠금, 처리량·지연 분포·오류율은 미측정이다. |

1. [기존 실제 업무 fixture](../../backend/src/test/java/com/example/marketplace/dbtest/PostgresContractFixture.java#L639)로 검수 후 상태 `AWAITING_CONSENT`와 revision `3`을 확인한다. [재현 검사](../../backend/src/test/java/com/example/marketplace/dbtest/ProcessRecoveryIT.java#L85)는 구매자 권한으로 견적 ID·fingerprint를 확인해 동의한다. 동의 receipt의 `refundAttemptId`가 작업의 `cause_key`에 연결된다.
2. [RefundWorkerProbe](../../backend/src/test/java/com/example/marketplace/dbtest/RefundWorkerProbe.java#L27)가 그 작업을 선점한다. `first-effect`와 DB의 `PROCESSING`을 확인하고 첫 프로세스를 종료한다. 저장된 기존 lease의 종료 시점보다 1,000 ns 뒤를 주입한 두 번째 JVM이 같은 작업을 인수한다. 첫 번째와 다른 PID·owner와 같은 작업 ID가 원증거에 남는다.
3. [저장된 조회 슬롯과 결과 소비](../../backend/src/test/java/com/example/marketplace/dbtest/PostgresContractFixture.java#L1009)를 통해 `REFUND_QUERY_DUE.v1` → `REFUND_RESULT_RECORDED.v1` → `RETURN_FINANCE_RESUME.v1`를 처리한다. `SUCCEEDED`는 worker 작업 실행 결과이고 환불 상태는 `UNKNOWN`이다. 반품 `REVIEW_REQUIRED`, 단위 보류 `ACTIVE`, 수수료 평가 `BOUND`, 예약 환불액과 회수비 증가분의 견적 일치, 동일 반품의 환불 시도 정확히 1건을 각각 검증한다.

검사에서 시각을 앞당겨 lease와 저장된 조회 슬롯을 소비한다. 강제 종료·독립 JVM 재시작은 실제이며, 제공자와 거래는 로컬 합성 조건이다. 실제 장애에서 몇 초 뒤에 고객 상태가 바뀌는지는 이 clock으로 판단할 수 없다. 이번 결과에서 비교할 조건은 같은 장애 경계에서 중복 제출 없이 불확실한 업무 결과와 보류가 유지되는가다.

## 실패 이력과 학습 확인

새 하네스 선택 실행과 원증거 대조·새 DB 확인은 각 1회 성공했고 개발 업무 assertion 실패는 0회다. 진입 진단에서 기본 5.1의 `pwsh` PATH 미등록, Git 소유자 불일치, Docker 파이프 거부, 기본이 아닌 `5433` 포트 연결 실패를 관측했다. 지정 7.6.9 파일 직접 호출, 호출 프로세스의 Git 작업폴더 설정, 승인된 Docker 실행과 확인된 인스턴스 `5785`로 전환했다. 5.1 기본 인코딩의 등록 JSON 읽기와 보조 PowerShell 인수 인용에도 오류가 있었고, UTF-8 또는 지정 exe의 고정 파일 실행으로 대체했다. 해당 진입 진단의 개별 수행 시간은 미측정이다.

`SUCCEEDED` 작업과 `UNKNOWN` 환불이 동시에 성립하는 지점은 [환불 worker의 처리 순서](../../backend/src/main/java/com/example/marketplace/payment/infrastructure/JdbcRefunds.java#L83)와 [반품 결과 소비](../../backend/src/test/java/com/example/marketplace/dbtest/ProcessRecoveryIT.java#L87)에서 확인할 수 있다. 별도 운영 장애 관측, 실제 PG·송금, 사용자의 직접 학습 확인은 미확인이다.

## 독립 검토와 인계

별도 Astra 독립 검토에서 필수 보완 1라운드 2건을 요청했다. 새 DB의 `quoteRefund`, `attemptAmount`, `refundReserved`가 각각 7,000원임을 대조해 환불 금액의 의미를 바로잡았다. 각 실행의 claim marker에서 같은 job의 `attempts=1`과 `attempts=2`, 다른 owner를 대조하고 최초 1회와 재인수 1회로 표현했다. 보완 범위는 문서이며 원 실행 결과와 실행 입력은 그대로다. 독립 검토는 로컬 P13-A를 수용했고 필수 잔여는 0건이다.
