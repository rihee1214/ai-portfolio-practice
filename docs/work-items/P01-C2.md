# P01-C2 Spring JDBC·Flyway PostgreSQL 연동

2026-10-23 / 상태: 구현·검증 완료, 후속 검토 대기

## 계약과 실행 순서

설계 v4·ADR-001·P01-C2의 JDBC·Flyway·초기 SQL 경로·최초 이행/재실행/이력 검증만 수행한다. 실행 계획 스킬을 적용한다. 기존 8080 PID68748, 5174 PID63940 및 db-dev(6a9f494624c9)/db-test(68d17431a4b1)는 중단·재시작·재생성하지 않는다. 실제 상태를 시작과 종료에 확인한다.

새 연결은 db 프로필에서만 활성화한다. 프로필 없는 기존 health 실행과 local 프로필은 DB 없이 유지한다. DB URL·사용자·암호는 명시적 환경값으로만 전달한다. Flyway가 스키마 초기화의 유일한 주체이며 SQL init은 never, clean은 disabled, baseline 자동 적용은 false다.

최소 V1은 Flyway 소유 스키마에 설명을 붙인다. 미정인 회원/상품 테이블이나 버전 관리용 별도 테이블을 임의로 만들지 않는다. 이력·체크섬은 flyway_schema_history가 담당한다. 동일 DB 재실행은 이력을 늘리지 않아야 하고, 변경된 기존 migration·잘못된 암호·실패 SQL은 시작을 거부해야 한다.

기존 marketplace_dev/test에는 DDL을 적용하지 않는다. 테스트 클러스터에 충돌 없는 c2_verify_* 전용 DB를 생성해 검사하고 삭제하지 않는다. 해당 DB와 스키마·실행 포트·잔여 데이터를 기록한다. C3 트랜잭션/업무 API, Flyway clean/repair, DB drop/reset은 수행하지 않는다.

버전은 기존 Boot 4.1.1 BOM의 Flyway12.4.0·PostgreSQL JDBC42.7.13을 따른다. 공식 웹 문서의 현재 Boot 버전은4.1.2이므로 실제 조합은 로컬4.1.1 BOM과 dependency tree로 확인한다. 공식 근거: [Boot 초기화](https://docs.spring.io/spring-boot/how-to/data-initialization.html), [관리 의존성](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html), [Flyway PostgreSQL 모듈](https://documentation.red-gate.com/flyway/reference/database-driver-reference/postgresql-database).

- [React 타입·린트·빌드](evidence/P01-C2-frontend-static.txt) 통과, [기존 Node 회귀](evidence/P01-C2-frontend-tests.txt) 68개 통과. React 기능 변경은 없고 UI 브라우저 재검사는 하지 않았다.
- [최종 대상](evidence/P01-C2-target.txt): c2_verify_1792755700154 DB, marketplace 스키마, marketplace_test 소유. localhost15433을 사용했다. 최초 디버깅용 c2_verify_1792755390505 및 c2_verify_1792755614835도 보존했다. 세 DB는 V1 이력/스키마 설명만 남겼고 drop/clean/reset은 실행하지 않았다. 실패 V2의 임시 테이블은 PostgreSQL의 migration 트랜잭션 실패로 생성되지 않았다.
- 임시 앱은 2971/12924/12952/12980/13325/2226/2270/14448/14705 포트를 썼으며 각각 종료했다. [실행 출력](evidence/P01-C2-run-output.txt)에 자체 PID와 종료를 기록했다. 기존 8080·5174를 재시작·대체하지 않았다.
- [기존 DB 시작 해시](evidence/P01-C2-original-db-before.json)와 [종료 해시](evidence/P01-C2-original-db-after.json)가 일치한다. pg_dump의 무작위 restrict/unrestrict 토큰만 제외해 스키마·데이터 텍스트 SHA256을 비교했으며 실제 덤프/데이터는 증거에 저장하지 않았다. [기존 프로세스](evidence/P01-C2-preserved-processes.json)의 PID/시작시각 및 [컨테이너](evidence/P01-C2-preserved-containers.txt)의 ID·running/healthy도 유지했다.

## 실패와 수정 이력

1. 제한 환경의 Maven DNS 실패는 승인 실행에서 해소했다. 기존 실행 JAR 잠금으로 clean이 실패했으므로 해당 서버를 종료하지 않고 marketplace.build.directory 옵션을 추가해 .local-tools/c2-build로 출력했다. 원래 target JAR는 교체하지 않았다.
2. DB 설정 누락은 시작 실패했지만 검사에서 기대한 DB_URL 문자열 대신 Boot의 url 형식 오류가 나왔다. [첫 검사](evidence/P01-C2-first-results.txt)를 보존하고 실제 오류 기준으로 검사 조건을 수정했다.
3. 처음 시도한 다중 문서 properties 구성에서 db 프로필에 공통 health 제한이 적용되지 않아 groups가 응답에 노출됐다. 빈 줄 조정만으로 해결되지 않았다. 이 방식은 제거하고 기본 파일의 자동 구성 제외를 application-db.properties에서 빈 값으로 해제하는 단순한 방식으로 바꿨다. [초기 health 실패](evidence/P01-C2-health-first-results.txt), [두 번째 실패](evidence/P01-C2-health-second-results.txt), 최종 21개 통과를 구분한다. 기존 V1 이행 자체는 성공했으므로 그 DB를 초기화하지 않고 새 전용 DB로 최종 최초 이행을 검증했다.

## 설명·인수인계

[실행 안내와 개념](../jdbc-flyway.md)에 기술 역할, 파일→DataSource→Flyway→health 흐름, 별도 빌드/실행 명령, 작은 SELECT 실습을 정리했다. Oracle 경험과 비교하면 JDBC는 연결·실행 API이고 Flyway는 순서 있는 배포 SQL 및 이력 관리다. Spring JDBC 자동 구성까지 준비했으며 업무 Repository·서비스 SQL·트랜잭션(C3)은 구현하지 않았다.

검토 및 반영세션의 후속 검토는 아직 수행되지 않았다. 사용자 직접 실습·새 PC/타 OS·운영 이행/백업 복원·C3 기능은 미검증이다. 기존 개발/테스트 본 DB에 V1을 적용하지 않았다는 점도 유지한다.


[최종 Flyway 이력](evidence/P01-C2-history.txt)을 추가로 조회했다. 스키마 생성 이력과 성공한 V1이 있으며 V2 행은 없다. 최종 검증용 9개 포트에는 리스너가 없고 기존 8080/5174 포트 소유 PID는 그대로다.

마지막 읽기 전용 [기존 HTTP 검사](evidence/P01-C2-existing-http.json)에서 8080 API와 5174 프록시는 모두 UP이었다. [비밀값 검사](evidence/P01-C2-secret-scan.json)는 추적 후보 파일에 실제 로컬 암호 일치 0건과 .env 제외를 확인했다. 코드 흐름·의존성·migration·예제·안내·증거만 로컬 Git 이력으로 남긴다. 후속 검토 결과는 아직 없다.
