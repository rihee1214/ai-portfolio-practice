# P03-C 판매 정지·복구·폐점

2026-10-24 / 기준 2a3bd21 / P03-C 계획 범위 구현·검증·독립 검토 완료. 사용자 승인에 따른 최종 로컬 커밋 기록.

## 범위 결정

실행 계획 스킬(executing-plans)에 따라 작은 계약 검사→구현→검증 순서로 진행한다.

현재 판매자당 한 매대 정책에서 판매 제한을 매대 운영 상태 OPEN/SUSPENDED/CLOSED로 표현한다. 이번 조치는 이미 생성된 매대를 대상으로 한다. 매대가 없는 승인 판매자의 사전 정지는 이번 화면의 대상이 아니다.

- ADMIN+ACCOUNTS가 OPEN→SUSPENDED 판매 정지, SUSPENDED→OPEN 복구. 자기 매대에 대한 운영 조치는 금지한다.
- 소유 판매자는 OPEN 또는 SUSPENDED→CLOSED 폐점. 폐점은 복구/재개설하지 않는다. 기존 매대·slug·판매자 역할을 보존해 새 매대로 제한을 우회하지 못한다.
- 정지·폐점은 visible=false로 만들고 복구 후에도 비공개를 유지한다. 판매자가 내용을 확인하고 명시적으로 공개해야 다시 노출된다.
- 조치마다 읽은 version과 사유1~300자 필수. 상태·공개 여부·버전·처리자·대상·전후 상태·시각·사유 이력은 같은 거래로 저장한다. 회원→매대 잠금 순서를 유지한다.
- 일반 회원 정지/탈퇴와 다르며 역할/로그인 세션은 폐기하지 않는다. 현재 ACTIVE SELLER일 때 정지/폐점 상태에서도 본인 매대 조회, 기존 거래 대응 공간 접근, 구매자 profile 기능을 유지한다. 회원 자체가 정지/탈퇴하면 기존 계정 정책이 우선한다.
- OPEN 매대만 편집 가능. 신규 판매 가능은 OPEN+visible, 상품 관리 공간은 OPEN에 한정한다. 주문·정산 공간은 정지/폐점에서도 접근할 수 있지만 실제 거래 구현은 후속 단계다. 이번에 주문/상품 API를 가짜로 구현하지 않는다. 미래 거래 모듈이 호출할 seller.api의 기능별 정책 계약을 제공하고 별도로 검증한다.

## 작은 작업

1. 정지/복구/폐점 HTTP 계약의 실패 확인과 V10·서비스·감사 이력 구현.
2. 권한·소유권·전이·경쟁·중간 이력 저장 실패 롤백·기능 정책을 새 격리 DB에서 확인.
3. 운영 매대 목록/조치와 판매자 상태·폐점·상품/기존 거래 공간 제한 화면 연결, 단위/실제 브라우저 검증.
4. 기존 검토 및 반영세션 독립 검토와 보존/제한 기록. P04 및 다음 단계 금지.

## 구현 계약

V10은 기존 매대를 OPEN으로 보존하고 상태 컬럼과 store_operation_event를 추가한다. DB CHECK로 SUSPENDED/CLOSED의 공개를 금지한다. 삭제 없이 상태만 바꾸며 소유자/slug 고유 제약은 유지한다.

| 경로 | 권한·결과 |
| --- | --- |
| GET /api/admin/accounts/stores?page=0 | ACTIVE ADMIN+ACCOUNTS, 20개와 hasMore, page 0~10000 |
| POST /api/admin/accounts/stores/{id}/suspend 또는 restore | ACTIVE ADMIN+ACCOUNTS, 자기 매대 금지, version·reason 필수 |
| POST /api/seller/stores/{id}/close | ACTIVE SELLER 본인만, version·reason 필수 |
| GET /api/seller/stores/{id}/history | 본인 매대 최근 이력 최대20개 |
| GET /api/admin/accounts/stores/{id}/history | ACTIVE ADMIN+ACCOUNTS, 최근 이력 최대20개 |
| GET /api/seller/capabilities | 현재 회원과 매대 상태의 기능별 허용 여부 |

조치 성공은200 관리 DTO, 입력 오류400, 권한403, 없는/타인 소유 매대404, 이전 버전·잘못된 상태 전이409다. 쓰기에는 기존 CSRF 검증을 적용한다. 오류는 공통 code/message/requestId 계약을 사용한다. 기존 health 응답은 변경하지 않는다.

| 기능 | OPEN 비공개 | OPEN 공개 | SUSPENDED | CLOSED |
| --- | --- | --- | --- | --- |
| 본인 매대·이력 조회 | 허용 | 허용 | 허용 | 허용 |
| 매대 편집·상품 관리 공간 | 허용 | 허용 | 차단 | 차단 |
| 신규 판매 정책 | 차단 | 허용 | 차단 | 차단 |
| 기존 거래 대응 공간·정책 | 허용 | 허용 | 허용 | 허용 |
| 구매자 프로필·로그인 | 유지 | 유지 | 유지 | 유지 |

모든 칸은 ACTIVE SELLER 기준이다. 매대 미생성은 세 판매 기능 모두 불허한다. 상품/주문/정산 업무 자체는 아직 미구현이므로 공간 접근과 정책 계약 검증을 실제 주문 성공으로 해석하지 않는다.

seller.api.Stores.requireCapability는 호출자의 활성 트랜잭션을 요구한다. identity.api를 통한 회원 잠금 후 매대를 잠그고 기능을 검사하므로, 후속 업무 모듈은 동일 트랜잭션 안에서 이 검사와 실제 쓰기를 수행해야 한다. 단순 capabilities 조회는 화면 안내용이며 미래 쓰기의 권한 검사를 대체하지 않는다. 아직 없는 거래 API에 검사를 적용했다고 주장하지 않는다.

React /admin/stores는 목록·조치 사유·정지/복구·이력을 표시한다. /seller/store는 운영 상태와 폐점 확인을 표시하고 제한 상태에서는 편집 폼을 숨긴다. 폐점은 복구 불가 확인 체크가 필수다. 상품 공간은 정책 거부를 표시하고 기존 거래 공간은 준비 중임을 표시한다. 조치 쓰기는 CSRF와 읽은 version을 전송하며 실패 시 자동 재전송하지 않는다. 인증 변경 후 도착한 늦은 응답은 버린다.

## 학습·운영 제한

핵심 흐름은 조치 사유 입력→CSRF→POST(version)→회원 잠금→매대 잠금→전이 검사→상태/비공개/버전/이력 동시 저장→화면 갱신이다. 롤백 검사는 이력 INSERT만 실패하도록 새 격리 DB에 일시 제약을 넣고 이전 상태·공개·버전과 이력 건수를 비교한다.

현재 운영 목록은 검색/필터 없이 페이지 단위이며 이력은 최신20개만 표시한다. 판매자 사전 정지, 폐점 재개업, 미처리 주문에 따른 폐점 조건, 실제 상품·주문·환불·정산은 후속 설계/구현 대상이다. 계정 자체가 정지/탈퇴된 판매자는 조치를 진행할 수 없으며 이번에 그 계정 정책을 변경하지 않는다. 외부 사업자 검증·상용 부하·실제 모바일 기기 검증은 하지 않는다. P04는 진행하지 않는다.

## 실패·검토 반영

1. 최초 HTTP 계약은 정지 API 미구현으로200 대신404가 발생했다(`p03-c-red`). 구현 후 `p03-c-core`에서 기본130·DB56 통과했다.
2. 화면 파일의 상수 export가 React Fast Refresh 린트 규칙을 위반해 상태 상수를 스토어 모듈로 옮겼다. 이후 타입·린트·단위81·빌드 모두 통과했다.
3. 독립 정적 검토 R1은 운영 권한/자기 조치·정지→폐점·편집/정지 경합의 검증 공백이었다. 추가 DB 검사로 보완했고 `p03-c-boundaries`에서58개가 통과했다. 제품 결함 재현으로 과장하지 않는다.
4. 브라우저 캡처가 상단 내비게이션만 보여 운영 상태를 확인하기 어려워 최종 독립 실행에서는 매대 카드/대상 운영 카드를 캡처하도록 좁혔다.

재현: `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p03-c-새로운이름 -Offline -RunBrowser`. 매번 새 격리 DB를 만들고 종료 후에도 유지한다. 기존 실행 서버에는 V10을 적용하거나 재시작하지 않았다. 따라서 기존 서버의 화면은 최신 구현과 다를 수 있다.

P04 또는 다음 단계와 원격 push는 진행하지 않았다.
