# P01-E2 업무 API 공통 JSON 오류

2026-10-23 / 상태: 구현·자동 검증·독립 검토 완료

## 범위와 완료 기준

기준 커밋 cc98717. `/api` 및 `/api/**`에서 Servlet ERROR 디스패치에 도달하는 오류를 `{code, message, requestId}`로 통일한다. 오류 body는 항상 JSON이며 Accept:text/html도 동일하다. HTTP 상태·Allow 등 의미 있는 헤더와 E1 요청 ID를 보존한다. 요청 ID는 body와 X-Request-ID가 같아야 한다.

404/405/잘못된 입력400/미지원 미디어415/예상외500을 실제 HTTP로 검증한다. 설계에 있는401/403/409/429는 해당 상태가 sendError로 전달되는 경우의 표현만 준비하고 인증·인가·재고·제한 기능을 구현한 것으로 간주하지 않는다. 406도 고정 안내를 사용한다. 알 수 없는4xx는 REQUEST_FAILED,5xx는 INTERNAL_ERROR로 외부 원문을 숨긴다.

`fieldErrors`는 선택 필드다. 아직 업무 DTO·검증 규칙이 없으므로 이번에는 생략한다. 성공 응답, controller가 직접 반환한 ResponseEntity 오류, 이미 커밋된 응답, 필터 이전 HTTP 파싱/프록시 오류는 이 단계의 정규화 범위가 아니다. 향후 업무 예외 handler도 같은 계약을 사용할 수 있지만 이번에는 범용 예외 계층을 만들지 않는다.

`/actuator/**`, `/error` 직접 접근, `/apiary` 등 비업무 경로는 기존 처리를 유지한다. health200/503의 status-only body와405의 Allow를 보존한다. 공통 오류에 원래 URL·쿼리·예외/SQL 메시지·stack trace·거절 입력값은 포함하지 않는다.

## 구현 계획

1. 실제 HTTP 계약 검사와 기존 /api404 기대값을 먼저 갱신하고 미구현 실패 확인.
2. E1보다 뒤에서 ERROR 디스패치만 처리하는 작은 필터로 JSON을 작성. 상태별 고정 코드·한국어 안내 사용.
3. 실제 오류 처리, 경계 경로, JSON 협상, HEAD, 요청 ID, 정보 노출 방지와 기존 health 회귀 검사.
4. 소유 RANDOM_PORT 서버와 별도 빌드 경로만 사용. DB 프로필·DB 쓰기/생성/초기화 및 기존 서버 재시작 금지.
5. 결과·실패·제한을 기록하고 검토 및 반영세션에서 독립 검토. 다음 단계·React 변경·원격 push 금지.

ControllerAdvice만 적용하면 컨트롤러가 없는404와 컨테이너 오류를 일관되게 다루기 어렵고, 전역 ErrorController 교체는 health를 포함한 비업무 경로에 영향을 줄 수 있다. 현재 단계에서는 원래 요청 URI를 기준으로 좁게 적용하는 ERROR 필터를 선택한다. 직접 오류 body를 반환하는 미래 업무 controller까지 자동 변환하는 설계는 아니다.

## 구현과 상태별 표현

ApiErrorConfiguration은 E1 필터보다 뒤에서 ERROR에만 ApiErrorFilter를 등록한다. 필터는 `RequestDispatcher.ERROR_REQUEST_URI`에서 원래 경로를 가져와 context path를 제외한 정확한 `/api` 경계를 검사한다. 최초 요청·성공 응답에 개입하지 않는다. 응답을 reset하지 않고 상태와 기존 헤더를 유지하며 Content-Type을 application/json, Cache-Control을 no-store로 설정한다. HEAD는 body를 쓰지 않는다.

ApiErrorResponse record는 공개 가능한 고정 문구만 갖는다. Jackson3의 기존 JsonMapper로 직렬화하며 의존성을 추가하지 않았다. requestId는 E1 요청 속성에서 가져온다. 새 오류 ID를 따로 만들지 않는다.

| 상태 | code | 의미 |
| --- | --- | --- |
| 400 | INVALID_REQUEST | 입력·본문 확인 |
| 401 | AUTHENTICATION_REQUIRED | 로그인 필요 |
| 403 | FORBIDDEN | 권한 없음 |
| 404 | NOT_FOUND | 대상 없음·비공개를 같은 표현으로 사용할 기반 |
| 405 | METHOD_NOT_ALLOWED | 요청 방식 미지원, Allow 유지 |
| 406 | NOT_ACCEPTABLE | 요청한 응답 형식 미지원 |
| 409 | CONFLICT | 현재 상태에서 처리 불가 |
| 415 | UNSUPPORTED_MEDIA_TYPE | 요청 미디어 형식 미지원 |
| 429 | RATE_LIMITED | 재시도 안내, 기존 Retry-After 유지 |
| 기타4xx | REQUEST_FAILED | 일반 요청 실패 |
| 5xx | INTERNAL_ERROR | 내부 원인을 노출하지 않는 일반 처리 실패 |

401/403/409/429 응답 표현 시험은 test 전용 controller의 sendError를 사용한다. 실제 인증·권한·충돌 판단·요청 제한 구현/검증이 아니다. 같은 상태의 업무별 세부 code와 fieldErrors는 실제 업무 규칙을 정의할 때 확장한다. HTML/XML Accept에도 오류 JSON을 보내는 것은 업무 API 오류 계약을 우선하는 명시적 선택이다. 비업무 경로의 콘텐츠 협상은 변경하지 않는다.

## 결과와 실패 이력

- [RED](evidence/P01-E2-red.txt): 실제 HTTP22개 중18개 실패,4개 통과,오류/skip0. 기본 오류 body/HTML 응답이 새 계약과 달라 실패했다. 환경·컴파일 실패가 아니다.
- 첫 구현 후 기존44개 + 신규22개 =66개 통과. 성공 응답 보존·실제406·대소문자 경계와 Retry-After 단언을 보완했다.
- [최종 verify](evidence/P01-E2-verify.txt), [집계](evidence/P01-E2-summary.json): **69개 통과**, 실패·오류·skip0. Checkstyle·컴파일·패키징도 통과했다.
- 신규 HTTP25개는 JSON/HTML/XML/wildcard Accept, /api와 /api/,404/405/400/415/406,동기/비동기500,고정 상태 표현,비업무 경계,성공 응답,HEAD를 포함한다. 모든 API 오류에서 body3개 필드·header/body ID 일치·고정 code·내부 문자열 미노출을 확인한다.
- 기존 ErrorHttpTest의 /api404 기대값과 E1의404 body 기대값만 새 계약으로 갱신했다. health200/503 status-only, health405 Allow, 비업무 기본 오류와 E1 정리는 기존 검사를 유지했다. 이를 예전 /api404 body까지 그대로 유지했다고 표현하지 않는다.
- 테스트 전용 probe는 src/test에만 있으며 [패키지 검사](evidence/P01-E2-package.txt)에서 배포 JAR에 포함되지 않음을 확인했다.
- 의도한 private-e2 예외·입력값은 테스트 로그에만 포함되는 가상 문자열이다. 응답 body에 노출되지 않는지 검사했다. 기존 Mockito 동적 agent 경고는 검사 실패가 아니다. 로그는 행 끝 공백과 마지막 빈 줄만 정리했다.

[시작 포트](evidence/P01-E2-ports-before.json)와 [종료 보존](evidence/P01-E2-preservation.json)을 확인했다. 기존8080/4174/5174 앱 리스너는 시작부터 없었고 실행/종료하지 않았다. DB 컨테이너 ID·healthy와15432/15433 PID57168을 유지했다. dev/test 정규화 덤프 해시는 E1 종료 기록과 동일하다. 읽기 전용 pg_dump에서 무작위 restrict/unrestrict 토큰만 제외했으며 원문을 저장하지 않았다. DB 생성·쓰기·초기화·재시작은 없다.

현재 실행 차단 항목은 없다. DB 통합 프로필·프런트·브라우저는 재실행하지 않았다. React 오류 표시·거래/인증/권한·fieldErrors·업무 예외 handler·커스텀 context path의 실제 배포·필터 이전의 비정상 HTTP·이미 커밋된 오류는 미검증 또는 범위 밖이다. 공통 오류는 현재 Servlet ERROR 경로의 계약이며 모든 미래 controller의 임의 오류 body를 자동 변환하지 않는다. 예외 원문을 응답에 숨기는 것이 서버 로그의 개인정보 정제 완료를 뜻하지 않는다.

## 코드 흐름·실행·직접 실습

`/api` 오류 → 컨테이너 ERROR 디스패치 → E1이 같은 ID와 MDC 재설정 → E2가 원래 API 경로/상태 확인 → 공개 고정 문구+ID 직렬화 → E1 finally 정리 순서다. 필터는 오류 원인을 판단하는 업무 서비스가 아니라 이미 결정된 오류의 공개 표현을 담당한다.

프로젝트 루트 PowerShell에서 기존 로컬 도구를 사용한다. 별도 출력 경로이며 db-it 프로필을 사용하지 않는다.

```powershell
$previousJava = $env:JAVA_HOME
$previousMaven = $env:MAVEN_USER_HOME
try {
  $env:JAVA_HOME = Join-Path $PWD '.local-tools/jdk-21.0.12.1+1'
  $env:MAVEN_USER_HOME = Join-Path $PWD '.local-tools/m2'
  ./backend/mvnw.cmd -f backend/pom.xml "-Dmarketplace.build.directory=$PWD/.local-tools/e2-build" verify
  if ($LASTEXITCODE -ne 0) { throw 'Verification failed' }
} finally {
  $env:JAVA_HOME = $previousJava
  $env:MAVEN_USER_HOME = $previousMaven
}
```

작은 실습: ApiErrorHttpTest의 missingApiAlwaysUsesJson에서 요청 Accept를 바꿔도 code·requestId가 유지되는지 확인한다. 이어 기대 code만 일부러 다르게 바꿔 실패를 확인하고 원복한다. 제품 코드나 DB를 바꿀 필요가 없다. 자동 검증 통과와 사용자의 직접 이해·실습은 별개이며 직접 실습은 미확인이다.

공식 근거: [Jakarta Servlet 오류 처리 규약](https://jakarta.ee/specifications/servlet/6.1/jakarta-servlet-spec-6.1.html), [RequestDispatcher 원래 URI·상태 속성](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/requestdispatcher). 현재 프로젝트 Boot4.1.1에서 실제 ERROR 디스패치로 검증했다.

## 독립 검토 및 완료 기록

구현 커밋 `35e0fd4`에 대한 [지정 세션 검토](P01-E2-review.md)를 완료했다. [독립 검증 요약](evidence/P01-E2-review-summary.json)과 실제 Surefire 보고서를 대조해69개 통과·실패/오류/skip0을 확인했다. 필수 코드 수정 결함은 없으며 검토 문서·요약·완료 상태를 최종 로컬 문서 커밋에 포함한다.

검토 의견: API ERROR 처리 시 이 필터가 응답을 끝내므로 뒤에 등록된 ERROR 필터와 기본 오류 컨트롤러는 실행되지 않는다. 현재 E1은 앞에 있어 영향을 받지 않는다. 향후 보안 헤더·관측·감사 필터 추가 시 실행 순서를 재검토해야 한다. 모든 헤더 조합·HEAD Content-Type/Cache-Control·커스텀 context path를 실제 시험한 것은 아니며, fieldErrors·업무 예외 handler·React/DB 거래는 이번 범위가 아니다. 이 주의점을 이유로 다음 단계 기능을 앞당기지 않았다.

독립 검토에서도 기존 DB 해시·컨테이너 정상 상태와 앱 서버 미실행 상태 보존을 확인했다. 사용자 직접 실습은 미확인이다. 다음 단계·프런트 단순화·원격 push는 진행하지 않았다.
