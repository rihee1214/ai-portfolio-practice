## R1 — 회원 행 잠금 대기 중 복구 토큰 만료

정적 검토 당시 `PasswordRecoveryService.reset`은 `clock.instant()`를 먼저 계산해 `store.consume`에 전달했다. `JdbcPasswordRecoveryStore.consume`은 회원 행 `FOR UPDATE`를 획득한 뒤 이미 전달받은 시각으로 `expires_at > :now`를 판단했다.

다른 트랜잭션이 회원 행을 잡고 있을 때 만료 직전 reset이 진입하고 만료 이후 잠금이 풀리면, 실제 소비 시점에는 만료된 토큰이 이전 시각을 기준으로 허용될 수 있다. 일반적인 만료 경계 테스트만으로 이 대기 구간은 검증되지 않는다.

개발세션이 시각 값 대신 `Supplier<Instant>`를 전달하고 회원 행 잠금 획득 뒤 `get()`으로 시각을 읽도록 수정했다. `recoveryRechecksExpiryAfterWaitingForMemberLock`은 별도 연결의 회원 행 잠금과 `pg_stat_activity.wait_event_type='Lock'`을 확인한 다음 가변 Clock을 1799초에서 1800초 경계로 이동시켜 거부를 검사한다. 수정 후 독립 실행에서 INVALID_RESET_TOKEN, 토큰 미소비, authVersion 미변경, 기존 비밀번호 유지가 통과했다. **R1 해결 확인.**

수정 전 코드를 실행해 RED를 확인한 기록은 없다. 정적 결함 발견과 수정 후 실제 DB 잠금 경계 검사 통과를 구분하며 RED→GREEN을 실행했다고 표현하지 않는다. 실제 30분 대기 대신 가변 Clock을 사용했다.

## 그 밖의 정적 확인

- 복구 발급/소비가 같은 회원 행을 먼저 잠그고, 회원당 토큰 1행을 교체하는 구조로 최신 요청을 구분한다. 이메일 확인 토큰 저장소와 복구 토큰 저장소·메일함을 분리했다.
- 토큰 소비·자격 해시 변경·authVersion 증가·JDBC 세션 삭제가 한 트랜잭션 안에 있다. 원문 토큰은 DB에 저장하지 않는다. 실제 롤백·경쟁 결과는 실행 검증 대상이다.
- 계정 ID는 HTTP 세션에서 가져오고 주소 SQL에 소유자 조건을 사용한다. 회원 행 잠금이 첫 배송지 생성·20개 상한·기본 변경을 직렬화하고, 부분 유일 인덱스가 복수 기본 주소를 막는다. 주소 0개이면 기본 0개, 주소가 있으면 기본 정확히 1개를 유지하는 서비스 흐름이다.
- AccountStore는 인증 상태 변화 시 개인 데이터를 비우고 요청을 취소한다. 세대 번호로 늦은 응답을 무시하고, 변경 요청 전에 CSRF를 가져오며 실패한 변경 요청을 자동 재전송하지 않는다. 화면 간 store 분리는 라우트 key를 사용한다.
- 기존 implementation-plan의 P02 요약에 남은 “A2 이후 미착수” 상태는 이미 완료한 A3와 모순되므로 최종 문서 정리 때 갱신하도록 전달했다.

## 한계와 미검증

독립 브라우저는 Vite 개발 서버의 Chromium PC/모바일 환경이다. 새 기능 전체의 production 미리보기·실제 TLS, 외부 이메일 전달, 수동 디버거 메일 확인 절차, 분산 제한·고부하·모든 경쟁 순서·응답 유실 복구는 검증하지 않았다. 기본주소·복구 경쟁은 제한된 동시 요청 검사이며 운영 부하 보증이 아니다. 메모리 메일함은 재시작 시 사라지고 실제 전화 소유 확인이나 주소 검색·배송 검증을 제공하지 않는다.

사용자 직접 실습·이해 확인은 아직 받지 않았다. 자동 검사 통과와 사용자 확인을 구분한다. 기존 P01 브라우저 16개·Node68·빌드는 개발세션의 별도 실행 결과이며 이 독립 실행의 수치로 합산하지 않는다.
