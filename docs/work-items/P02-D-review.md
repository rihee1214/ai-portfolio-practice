## 정적 확인

- 운영 정지·복구는 서버 URL 경계 외에 서비스에서도 ACCOUNTS 권한을 확인한다. 대상 회원 행을 잠근 뒤 상태와 ADMIN 여부를 검사하며, 잠금 대기 후 처리자의 권한을 다시 검사한다. 이미 시작한 요청을 소급 취소하거나 모든 권한 변경과 직렬화하는 보장으로 확대하지 않는다.
- 탈퇴 대상은 요청의 회원 ID가 아닌 인증 주체에서 얻는다. ACTIVE·비운영자 상태, 현재 비밀번호와 WITHDRAW 확인값을 요구한다. 화면에도 비밀번호와 복구 불가 확인 체크를 둔다.
- 상태·authVersion·전체 세션·확인/복구 토큰·감사 기록은 같은 트랜잭션이다. 탈퇴의 이메일 대체·프로필 비우기·주소·자격·역할·권한 삭제도 해당 트랜잭션 안에 있다. UUID 행은 남겨 외부 참조를 유지한다.
- 프로필/주소 쓰기와 비밀번호 복구도 회원 행부터 잠그고 ACTIVE를 확인한다. 상태 변경 뒤 도착한 요청은 CurrentMemberFilter에서 상태/authVersion을 재확인한다. 모든 동시 실행 순서를 검증한 것은 아니다.
- 성공 응답은 no-store, 변경 API는 기존 CSRF 경계를 사용한다. AuthStore는 시작 즉시 개인 상태를 숨기고 요청 세대가 바뀌면 늦은 성공을 무시한다. POST 자동 재시도는 하지 않는다. 탈퇴 성공 시 다른 탭에 비밀값 없는 변경 알림을 보낸다.

## 보완 요청

### R1 — 원 이메일 재가입과 과거 참조 분리 검사

계획에는 탈퇴 후 같은 이메일로 새 가입이 가능하되 새 UUID를 사용하고 과거 거래를 연결하지 않는다고 명시했다. 최초 검사에서는 이메일 변경과 기존 참조 보존만 확인했다. 실제 재가입·이메일 확인 후 새 UUID가 다른지와 기존 fixture가 여전히 옛 UUID만 참조하는지 검사를 요청했다. 이는 제품 결함 확정이 아니라 명시된 계약의 검증 공백이다.

### R2 — 개인정보 정리 후반 실패의 롤백 검사

최초 감사 제약 실패 검사는 transition 내부에서 실패한다. 이메일 대체와 주소·자격·역할 삭제보다 먼저 실패하므로 해당 정리 작업이 부분 실행된 뒤 복원되는지는 증명하지 않는다. 새 격리 DB에서 정리 후반부 실패를 유발하고 이메일·프로필·주소·자격·역할·상태/authVersion·세션·토큰·감사가 모두 복원되는지 보완을 요청했다. 현재 코드에서는 동일 트랜잭션이며, 부분 커밋 결함을 재현한 것은 아니다.

추가로 ADMIN 본인의 탈퇴 거부는 ADMIN 정지 거부와 다른 진입점이므로 별도 검사를 요청했다. 탈퇴 비밀번호 반복 제한은 개발세션이 보완 중이며 최종 코드·결과를 받은 뒤 확인한다.

## 최신 보완 결과

위 요청은 최초 정적 검토 당시의 검증 공백이며 최신 독립 실행에서 해결을 확인했다.

- **R1 해결:** 원 이메일로 activeMember를 다시 호출해 가입·확인하고 새 UUID가 다르며 기존 거래 fixture의 member_id는 옛 UUID인 것을 검사했다.
- **R2 해결:** 격리 DB의 자격 참조 FK로 credential 삭제에서 실패시켰다. 이는 상태·세션·토큰·감사·이메일·프로필·주소 변경 후 실패한다. 원 이메일·이름·전화 복원, 주소·자격·역할·확인/복구 토큰 행 유지, ACTIVE·authVersion 0·감사 0 및 기존 세션 me 200 검사가 통과했다. 모든 필드의 바이트 단위 스냅샷 비교를 한 것은 아니다.
- ADMIN 본인 탈퇴 409를 별도 HTTP로 확인했다. 동시 정지는 한 요청 성공·한 요청 거부 및 감사 1건을 확인했다.
- 탈퇴 반복 제한은 실제 연결 IP와 인증 주체 조합별 1분 5회이며 단일 프로세스 메모리 정책이다. 기본 검사에서 6번째 429를 확인했다. 분산 환경·모든 경로 변형과 부하 검증으로 확대하지 않는다.
