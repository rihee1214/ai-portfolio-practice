## 공통 고정 정책

- 기존 Java·Spring Boot·Spring JDBC·PostgreSQL·React·TypeScript를 사용한다. 혜택은 설계의 `promotion` 모듈에 두고 타 모듈 내부 저장소/테이블 쓰기를 금지한다. 공개 API에 JDBC/트랜잭션 객체를 노출하지 않는다.
- 회원/비회원에 공개 행사를 동일 적용한다. 쿠폰은 회원 본인 소유, 매대 범위·판매자 부담이며 판매자별 하위 주문당 1개다. 판매자 회원도 구매자로 자신의 쿠폰을 사용한다.
- 상품 정가 → 가장 큰 상품 행사 1개(동률 ID순) → 쿠폰 → 매대별 배송비 → 배송 행사 순서다. 배송비는 **행사 후·쿠폰 전 50,000원 이상 0원, 미만 3,000원**이다.
- 금액은 Java long/DB BIGINT, checked 곱셈·합산, 음수/초과 할인 금지. float/double 사용 금지. 시간은 Instant/timestamptz, UTC 저장·Asia/Seoul 표시, 시작 포함·종료 제외.
- 쿠폰 배분 기준은 대상 항목의 행사 후 금액 비율, 나머지는 안정적인 항목 ID 순이다. 수량별 잔액도 순서를 보존한다. 항목→매대→부모 합계가 같아야 한다.
- 결제 전 해제는 재사용 가능하되 만료를 연장하지 않는다. 결제 후 해당 하위 주문 전체 취소/반품 완료 때만 1회 복구하며 부분 환불은 복구하지 않는다. 만료 쿠폰은 복구 기록이 있어도 재사용할 수 없다.
- 주문 생성 때 최신 재검증·변경 시409/새 견적, 0원 결제 이력·PG 미호출, 실제 주문 스냅샷 보존은 P08에서 완성한다. P07은 입력/출력 계약과 fixture로 검증한다.

## 공통 검증·보존 절차

각 문서의 테스트 이름·신규 파일·API는 **예정**이다. 구현 시 실제 이름·assertion·기대/실제·증거 경로를 대응시킨다. 아직 존재하지 않는 검사를 통과로 표시하지 않는다.

1. AGENTS.md, README, [개발 흐름](../development-workflow.md), [검증 하네스](../verification-harness.md), 단계 문서와 이전 결과를 읽고 Git 상태/현재 입력 해시를 기록한다.
2. 순수 규칙 실패 검사를 먼저 작성하고 실행한다. 예: backend에서 `./mvnw.cmd -o -Dtest=PromotionRulesTest test`. 프런트는 frontend에서 `npm run test:unit -- tests/unit/PromotionStore.test.tsx`. 각 단계의 실제 파일명으로 대체한다. 실패 로그를 보존하고 최소 구현 후 같은 검사 통과를 확인한다.
3. 데이터·트랜잭션·브라우저 검사는 루트 `./verify.ps1 -Offline -EvidenceDirectory .local-tools/p07-a-dev-<새고유값>`처럼 단계/실행별 새 경로를 사용한다. B/C/D는 접두어를 바꾼다. 루트 하네스가 전화 에뮬레이터·새 PostgreSQL·새 미디어를 준비한다. 기존 DB에 migration/fixture를 실행하지 않는다.
4. JUnit/ArchUnit/PostgreSQL/프런트/PC·모바일 브라우저를 필수 목록에 **추가**한다. `verification/required-tests.json`, `required-frontend.json`, `required-browser.json`, `verify.ps1`의 scope를 실제 범위로 갱신한다. 목록 축소·테스트 삭제·timeout 확대만으로 실패를 감추지 않는다.
5. 개발 전체 통과 후 소스 동결. 지정 검토세션은 별도의 `.local-tools/p07-a-review-<새고유값>`에서 같은 루트 명령을 실행한다. 개발/검토 하네스를 동시에 실행하지 않는다. 검토 문서는 실제 검토 시 `P07-A-review.md` 등으로 생성한다.
6. 종료0 + result.status/preservation=passed + 필수 누락/실패/skip0 + 입력 해시 일치가 모두 필요하다. 각 제약의 assertion도 별도 확인한다. 의존성/캐시 미준비는 차단과 원인으로 기록한다.
7. before/after로 기존 서버·개발/데모 DB·과거 검증 DB 목록·미디어를 보존하고 모든 과거 실패 manifest 및 새 실패 해시를 대조한다. 실패 원본/새 DB/미디어는 삭제하지 않는다. 기존 실패 원인 미확정을 후속 성공으로 소급 해결하지 않는다.
8. 완료 기록: HEAD+inputs 해시, 명령·시간·경로·새 DB/미디어, 제약별 실제 결과, 검토 지적/해결/잔여 차단, 실패 manifest, 제한, 사용자 직접 확인 여부. `docs/work-items/evidence/`에 필요한 사본을 남긴다. 원본 로그 공백은 보존한다.
