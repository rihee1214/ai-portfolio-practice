### 개발 집중 검사 이력 — 진행 중

| L: 로컬 전체 복구 | 명시 `local-full` + `local-test` 전화 emulator, loopback TLS/API·격리 emulator, 새 L-source DB/media와 별도 새 L-restore DB/media·project·포트 | D-B/D03/D05/D06의 비회원 생산자·정상 조회·복원 후 새 조회 로그인·과거 자격 거부. source 준비→전체 writer 정지/checkpoint→원 대조→restore 자격 폐기→restore API/worker 순차 기동. source/restore가 같은 파일 root나 writer를 공유하지 않음 |

L용 후속 실행 설정은 기존 허용 모드를 명시적으로 선택하는 검증 설정이며 public-demo 시작 가드의 예외가 아니다. P에 필요한 사전 비회원 자료가 있더라도 조회 성공 근거로 사용하지 않는다. 복원/호환 검사 manifest에는 경로·모드·provider·source/restore identity를 남기고 실행 간 환경변수 누출을 검사한다. 각 경로의 신규 DB·media 수를 필수 등록의 expectedDatabaseCount/보존 목록에 반영한다.

릴리스 manifest는 release ID, 소스 HEAD와 미커밋 입력 SHA, JAR/image digest, dist 파일별 SHA, NGINX 설정 SHA, migration 파일/version/checksum 목록, 비밀값을 제외한 설정 이름·모드·origin·DB/media identity, 지원 구/신 조합을 포함한다. 비밀값은 manifest·CLI·로그·브라우저에 넣지 않는다. 같은 릴리스 API/worker는 동일 image/JAR다. 이미지·의존성 캐시 부족은 미실행으로 남기며 암묵적 다운로드/외부 조달을 하지 않는다.

운영 명령은 후속에 `infra/p12-d/` 아래 로컬 실행 스크립트로 제공한다(아직 없음). 입력은 동작 `Prepare/Checkpoint/Restore/Activate/Rollback/Inspect`, 릴리스 manifest 경로, 새 run UUID/증거 경로, 명시 project/DB/container/port/media 경로와 기대 기존 release ID다. `Restore`는 새 DB·빈 새 media 경로와 checkpoint manifest를 추가 요구한다. 원본/기존 검사 DB·기존 media·기존 증거 경로 입력, 심볼릭 링크·경로 이탈, 식별 불일치, 암묵적 기본 대상은 거부한다. `Inspect`는 읽기 전용이며 사용자 웹 권한으로 이 명령을 실행할 API는 없다.

오케스트레이터는 동일 project에 실행 잠금을 두고 상태를 `PREPARED → QUIESCED → CHECKPOINTED → MIGRATED → READY → ACTIVE`로 기록한다. 실패 시 실제 완료 경계와 실패 phase를 기록하고 다음 동작은 manifest/실제 대상 대조 후에만 진행한다. 같은 명령 ID·같은 입력은 완료 산출물 hash를 확인해 결과를 반환하며 다른 입력의 재사용은 거부한다. 미완료 dump·부분 복사 파일은 checkpoint로 승격하지 않고 보존한다. 성공 checkpoint에는 모든 파일 hash·DB 검증·쓰기 정지 증거가 있어야 한다. 완료 marker는 마지막에 원자적으로 게시한다. 종료 코드만으로 성공시키지 않는다.

## D02 실제 Flyway 이행과 교체 순서

현재 제품 migration 최신은 `V132__publication_window.sql`이다. 이 작업만을 위해 가짜 제품 V133이나 새 업무 테이블을 만들지 않는다. 기본 교체 쌍은 **R0=P12-C 수용 릴리스, R1=P12-D 구현 후보**이며 제품 스키마 변경 필요성이 없으면 둘 다 V132다. 같은 V132 재기동을 신규 migration 검증이라고 부르지 않는다.

역사적 이행의 별도 릴리스 **H129**는 P11-D 수용 commit `aee626bb8d69ba1b4191d5a4688cb6b39538839c`로 고정한다. 읽기 전용 Git tree 목록에서 최신 migration이 V129이고 V130~132가 없음을 확인했다. H129는 R0(P12-C/V132)·R1(P12-D 후보)와 다른 API/JAR·소스 manifest다. 후속 구현에서는 이 commit의 별도 산출물 경로와 migration checksum·실제 JAR SHA를 기록한다.

실제 이행 검사는 별도의 새 DB에서 **H129의 V129 스키마→기존 V130 배송 정책·V131 게시·V132 게시 기간**을 적용한다. H129 API의 실제 공개 명령으로 주문·결제·환불·정산·대시보드 자료를 만들고, 그 시대의 승인 fixture를 계정/시간 등 준비에 사용한 경우 producer·fixture의 출처/역할을 구분한다. H129 writer 정지→checkpoint→신 migration 독점 적용→R1 확인→신 writer 정지→**실제 H129 API를 이행된 V132 DB에서 기동하여 기존 읽기와 주문/상태 변경 계약을 실행**한다. 매 시점 API/media writer는 하나이며 DB 원장·효과/권한을 대조한다. H129가 제공하지 않는 신규 게시 기능은 이 조합의 검사 대상이 아니다. H129의 비회원 실행은 당시 로컬 DB 프로필·local-test emulator 설정을 사용하며 현재 public-demo 모드를 역사 산출물에 가장하지 않는다.

H129 산출물·캐시·실행 환경이 없거나 새 schema에서 실제 기동/소비를 지원하지 못하면 해당 필수 검사는 BLOCKED/실패이고 D02 완료를 차단한다. R0 API·현 API+V129 fixture·SQL 대조만으로 대체하거나 선택 skip으로 통과하지 않는다. 이행 전후 원 거래/원장/세션 데이터, 기본 정책3000/50000, 게시 기간 제약도 검사한다. 이미 적용한 migration 수정·Flyway clean/repair/임의 baseline 또는 검증 완화로 성공시키지 않는다.

별개인 R0→R1→R0 교체는 같은 V132여도 실제 보존 R0 산출물과 새 R1 산출물, 프로세스/container identity·release pointer·설정/dist/JAR hash의 교체를 관측한다. checkpoint 후 R1에서 실제로 추가한 거래가 R0 앱 복귀 뒤에도 남는지 검사한다. 같은 산출물 재시작을 버전 교체나 신규 migration으로 기록하지 않는다.

실행 순서는 새 경로에 산출물 준비→기존 릴리스/대상 식별→새 요청 차단 및 API/worker 정지→checkpoint→독점 이행 실행→Flyway validate/version/checksum 확인→새 API 기동·readiness/업무 조회 확인→동일 버전 worker 기동→새 정적 index/프록시 활성화→개방이다. 이행을 API 시작이 수행하는 현재 계약을 사용할 경우 그 API만 내부망에서 먼저 시작하고 worker와 공개 트래픽은 열지 않는다. 별도 migration 전용 역할을 도입하려면 같은 migration 설정을 쓰며 실제 동작 검증을 추가한다. 앱 프로세스의 기동과 migration 완료를 혼동하지 않는다.

실패 migration·checksum 불일치·신버전 시작 실패에는 worker/트래픽을 닫아 둔다. 확장 migration은 구 API가 신 schema에서 동작하는 경우에만 앱 복귀 가능하다. destructive SQL·컬럼 삭제·세션 직렬화 변경은 이번 범위에서 예상하지 않으며 필요 발견 시 Astra 설계 판단과 중요 정책 변경 승인으로 돌린다. 구 필드 정리는 이번에 하지 않는다.

## D04 일관된 DB·미디어 checkpoint

온라인 파일 snapshot 구현을 추가하는 대신 **통제된 쓰기 정지 checkpoint**를 채택한다. 운영자는 maintenance 응답으로 새 API 요청을 차단하고 진행 요청 종료·API/worker 프로세스 종료를 확인한다. 파일 정리 scheduler를 포함한 모든 쓰기 주체가 멈췄는지 PID/container·DB 연결·transaction 상태로 확인한다. 종료 확인 실패는 checkpoint 실패이며 열린 거래가 있는 채 dump·복사를 진행하지 않는다. 원래 서버/DB를 종료하는 검증은 금지하고 새 검사 소유 스택만 조작한다.

동결 후 호환 버전 `pg_dump` custom format(전체 앱 schema·Flyway history·JDBC session·작업/원장 포함)을 새 파일에 기록하고 media를 새 경로에 복제한다. `pg_dump` exit·dump 목록·크기·SHA와 파일 목록/path/size/SHA를 저장한다. `.database` marker의 UUID는 `marketplace.media_namespace.namespace`와 일치해야 한다. DB 물리 이름/하네스 실행 UUID는 새 값이지만 복원된 업무 media namespace는 원 checkpoint 값을 보존한다. `.lock`의 프로세스 잠금은 복제하지 않고 복원 시 새 파일 잠금으로 획득한다. 원본 marker/namespace를 임의로 바꿔 불일치를 숨기지 않는다.

checkpoint 전후 DB와 media inventory가 같아야 하며 참조 파일의 누락/변조·path traversal·symlink는 실패다. 정상화된 이미지뿐 아니라 공개/비공개·운영 숨김·첨부 권한 metadata와 bytes를 함께 보존한다. 미참조 파일은 별도로 분류해 그대로 보존하고 복구 성공을 위해 원본을 청소하지 않는다. 증거에는 개인정보/비밀값 원문 대신 필요한 ID·금액·hash를 기록한다. dump 자체는 비공개 로컬 자료이며 공개 배포 자산에 넣지 않는다.

이 방식의 복구 지점은 쓰기 정지 시점이다. 정지 후 쓰기를 재개한 뒤 발생한 거래는 과거 dump에 없다. 따라서 이번 로컬 rehearsal은 checkpoint 이후 원본 거래를 되돌리는 자동 운영 cutover를 제공하지 않는다. 라이브 데이터 손실 허용·RPO/RTO 보장은 별도 정책 승인 없이는 정하지 않는다.

## D05 별도 복원·격리·인증 경계

원본과 다른 새 DB 이름/하네스 UUID·새 media·새 포트/Compose project를 사용한다. 기존 DB가 존재하면 덮어쓰기·`--clean` 없이 거부한다. `pg_restore --exit-on-error`에 해당하는 엄격 복원으로 table/data/constraint·Flyway checksum을 확인하고 먼저 **쓰기 없는 원본 대조**를 한다. 성공/실패 target 모두 보존한다. 다른 checkpoint의 DB와 media를 섞으면 marker/hash/참조 검사가 실패하고 API를 시작하지 않는다.

복원 스택은 loopback·별도 내부망·모의 제공자만 사용하고 worker 자동 시작·외부 callback·실제 결제/송금·메일 발송을 차단한다. 원본과 복원본이 같은 외부 provider 업무를 중복 실행할 수 있게 열지 않는다. 실제 Toss의 외부 성공/내부 과거 상태 복구는 이번 성공 주장에 포함하지 않는다. 미래 공개 복구에는 외부 승인/환불 ledger와 대사 및 단일 활성 writer 정책이 별도로 필요하다.

snapshot의 세션/토큰을 외부에 재노출하지 않기 위해 원본 대조 후, 새 복원본을 최초 개방하기 전에 **복원본 한정 인증 자격 폐기 트랜잭션**을 수행한다. Spring Session와 속성은 FK 순서대로 제거하고, guest access session은 revoked 처리, 미소비 email/password reset token은 consumed 처리, 미소비 guest checkout은 REVOKED, guest recovery attempt의 사용 가능한 grant는 REJECTED·grant 폐기로 무효화한다. 사용 완료 주문의 checkout/인증 이력과 주문 소유자·계정 상태/권한·비밀번호 해시는 보존한다. 정확한 대상은 현재 schema와 기존 상태 제약을 대조해 구현하며 조건 없는 업무 테이블 TRUNCATE/인증 version 일괄 재작성은 하지 않는다. 이 관리 작업은 새 복원 대상 identity 확인 뒤에만 가능하고 affected count/전후 허용 필드 diff를 기록한다. 지원할 수 없는 자격 유형이 발견되면 개방을 차단하고 설계를 보완한다.

이 절의 비회원 자격 폐기 후 정상 새 조회는 L에서 검증한다. P 복원본은 사전 자격 유무와 무관하게 guest 조회503/DB무효과를 유지하며, 정상 guest 조회를 위해 emulator를 주입하거나 공개 가드를 변경하지 않는다.

복원 전 쿠키·CSRF·조회 grant·메일/비밀번호 재설정 token의 재사용은 거부하고 각 초대 검토자는 새로 로그인한다. 단순 포트 변경으로 쿠키가 격리된다고 가정하지 않는다. 보호 요청의 현재 계정 상태/권한 검사는 계속 유지한다. 비회원 새 조회 로그인은 기존 주문 소유 관계를 보존하고 다른 주문을 숨긴다. 백업 이후 정지/탈퇴/비밀번호 변경 자체를 과거 DB로 되돌려 원 서비스에 공개하는 것은 허용하지 않는다. 해당 변경이 존재하는 원본의 대체 cutover는 이번 기능 밖이다.

## D06 원 거래·금액 대사

대사는 동일 row 수나 총액 하나만으로 끝내지 않는다. 정지 checkpoint의 정렬된 business ID별 canonical 기록과 복원 직후 기록을 대조한다. 금액은 원단위 정수·정확 일치이며 허용 오차0이다. 인증 폐기 같은 허용 변경은 원 대조 뒤 별도 diff로 분리하고 원 거래 원장은 수정하지 않는다.

| 대사 대상 | 독립 기대값·불변식 |
|---|---|
| 주문·항목·판매자 하위 주문 | 각 항목 수량·단가·할인·배송 정책 snapshot 및 부모/하위 합계, 정확히 하나의 회원/비회원 소유, 원 주문번호 유지. 현재 상품/정책으로 재계산하지 않음 |
| 결제·환불·반품비 | 성공 결제·성공 환불을 각각 성공 상태/시각 기준으로 대조. 성공 환불 합≤성공 승인, UNKNOWN/실패는 성공 환불로 합산하지 않음. 반품/배송 비용 원장·예약/잔량·제공자 요청키/수신 이력 보존 |
| 재고·쿠폰·교환 | 판매/교환 예약·사용·해제·복구 수량과 원인키 보존, 복원·재처리 뒤 한 번만 효과. 활성 예약과 소비된 예약을 구분 |
| 정산 | 원 판매항목 귀속·순금액·수수료·hold·배치·모의 지급·후속 조정·음수 이월을 항목별 대조. 기존5% 원단위 배분·주간 KST 정책 유지. 원 지급 불변, 동일 환불의 조정1회, 모의 지급 총액·잔량 일치 |
| 알림·대시보드 | 원 이벤트/중복키·읽음 상태, 집계 generation/실패 기록 보존. 새 worker 갱신 후 성공 기간별 결제/환불과 현재 잔량 일치, 중간 세대 혼합 없음 |

준비 시나리오는 실제 회원/비회원 주문, 두 판매자, 정상 결제, 부분 환불, 반품비 차감, 확정 후 예외 환불/정산 조정·음수 이월, 실패/UNKNOWN 복구 대기, 공개/비공개 파일을 포함한다. 기존 P09/P11의 승인 금액 fixture와 API 생산자를 재사용하며 무관한 SQL 한 줄로 최종 상태만 만든 자료를 실제 업무 증거로 세지 않는다. 기대값은 UI/API가 반환한 합계를 다시 더하기만 하지 않고 준비 명령과 독립 원단위 계산·원 ledger를 연결한다.

복원 후 회원 주문 상세·결제/환불 이력, 비회원 새 조회 로그인, 판매자 자기 정산, 해당 권한 운영자 batch/실패 작업 화면에서 같은 business ID·상태·금액을 확인하고 DB 원장과 대조한다. 타 회원/타 매대/권한 없는 운영자는 거부되어야 한다. 새 읽기 전용 대사 결과 파일은 운영자 도구 결과이며 제품 내부 SQL을 공개 API로 노출하지 않는다.

## D07 실제 worker 재개와 멱등성

기존 `WorkerEngine`/`JdbcJobs`의 READY/RUNNING/SUCCEEDED/FAILED, owner token·30초 lease·10초 heartbeat, 최대5회·backoff·due claim 사실·transaction fencing을 유지한다. 새 복구를 위해 lease/시각/attempt를 임의 초기화하지 않는다. API 종료 후 worker가 웹 요청 없이 진행하는 경로와 worker 강제 중단 후 다른 실행권 인계를 모두 검사한다. 기존 작업의 실패 대기/업무별 안전 재처리 API를 소비하며 DB UPDATE로 SUCCEEDED를 만드는 운영 동작은 없다.

실제 주문/환불/정산/알림 명령→durable job/outbox/원장→worker→조회/UI의 생산·소비를 묶는다. 중단 지점은 (a) 업무 효과 전 claim 뒤, (b) 업무 효과 commit 뒤 job 완료 전이다. 재개한 worker가 새 token을 얻고 이전 token의 complete/fail/heartbeat·업무 쓰기는 거부되는지 확인한다. 같은 업무 효과는1회이고 전달/시도 횟수 증가와 효과 횟수를 구별한다. 최대5회 만료·terminal 실패는 자동 성공 처리하지 않고 실패 화면·이유·허용 재처리·감사 이력으로 연결한다.

30초 lease 경과는 기존 유한 준비 phase에서 실제 저장 lease_until·현재 시각을 관측해 대기한다. 검증 대상 재개 명령·claim·업무 효과·최종 assertion은 같은 업무10초 기한으로 묶는다. 제품 lease를10초 아래로 줄이거나 검증 대상 처리를 준비로 빼지 않는다. 두 worker 경쟁은 독립 연결·프로세스로 관측하고 늦게 도착한 원 worker가 효과를 중복 만들지 못함을 assertion으로 확인한다. 외부 성공이 불명확한 환불은 기존 UNKNOWN 조회/운영 확인 정책을 유지하며 복원했다고 새 환불을 발급하지 않는다.

집중 개발에서는 등록 후 `-DbGroups 'release-upgrade,release-recovery,package-runtime,public-demo-runtime'`와 변경 소비 범위 선택을 사용할 수 있다. 이 ID는 계획값이며 현재 명령으로 실행할 수 있다는 뜻이 아니다. 실패 수정은 실패 검사와 수정 영향 범위부터 재검증한다. 최종 동일 소스·같은 조건의 유효 전체 근거를 독립 검토 때문에 무조건 반복하지 않는다. `selected-passed/certificationEligible=false`는 선택 통과로 표시하고 적합성을 독립 검토하되 이번 전체 필요 조건을 대체하지 않는다.

기존 업무별 **공유10초 deadline**, 유한 준비60초·기동30초·정리10초 및 더 짧은 기존 연결/요청 기한·부모 watchdog을 유지한다. 사용자 업무의 클릭·요청·폴링·재조회·assertion이 하나의 기한을 공유한다. dump/restore·이미지 준비 같은 infrastructure 동작은 시작/진행/종료가 관측되는 유한 phase로 관리하며 실패를 숨기려고 timeout을 늘리지 않는다. 시나리오/전체 총 제한을 새로 넣지 않는다. 각 업무 검증 명령을 준비로 분류해10초를 회피하지 않는다. 의존성 부족·등록 누락·skip·필수 assertion 누락·미해결 결함은 완료 차단이며 예상 음성 결과·의도 RED·실제 실패를 구별한다.
