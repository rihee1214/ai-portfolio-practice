작성일: 2026-10-26. 기준 커밋: `a4f8068ecab16508ca21a7942c3e873181ee64cc` (P06-D 로컬 마감).

## 목표와 근거

비회원이 기존 조회 자격을 확인하고 현재 구매 전화 인증을 마친 경우, 새 가상 주문 참조를 기존 GuestBuyer에 연결한다. 기존 조회 인증 없이 구매하거나 다른 번호로 구매하면 새 GuestBuyer로 분리한다. 이름·전화가 같다는 이유로 과거 주문을 합치거나 기존 조회 비밀번호를 덮어쓰지 않는다.

- [요구사항](../requirements.md) F02, §7 재구매/별도 주문/번호 변경, AC02·AC04·AC12.
- [구현 계획](../implementation-plan.md) §8 P06-E. P06의 마지막 세부 작업이며 다음 계획은 P07-A 공개 상품·배송 행사다.
- [설계](../shop-design.md) P06-C 내부 생성 계약 및 P06-D 변경/복구 계약.
- 선행 결과: [P06-D](P06-D.md), [독립 검토](P06-D-review.md). 커밋 전 새 격리 전체 검증 Java293·브라우저52·프런트143·Node72 통과. 이 수치는 P06-E 실행 결과가 아니다.
- 작업 순서·완료 판정은 [개발 흐름](../development-workflow.md)과 [검증 하네스](../verification-harness.md), 루트 AGENTS.md를 따른다.

## 착수 당시 구현과 범위

현재 `JdbcGuestAccess.prepare`는 인증된 구매 시도에 새 비밀번호 해시를 준비한다. `createBuyer`는 구매 인증을 소비하고 새 GuestBuyer를 생성하며, `registerOrder`는 주문 참조를 연결한다. 기존 묶음을 선택하는 재구매 계약은 없다. `JdbcGuestPurchases`는 구매 세션·현재 시도·번호·용도·만료·소비 상태를 검사한다. 조회 세션과 비밀번호 변경/복구는 P06-C/D에 구현돼 있다.

기존 Java·Spring JDBC·React 및 공개 identity/phone API를 유지한다. P06-E는 연결 대상 선택·권한 재검사·가상 주문 참조의 거래 계약과 화면까지 다룬다. 실제 주문·재고/쿠폰 예약·결제와 통합된 원자성은 P08-C에 남긴다. 제품 주문 생성 endpoint나 실제 주문 성공 화면을 미리 만들지 않는다.

## 사용자 흐름과 서버 계약

| 상황 | 사용자 흐름 | 서버 결과 |
| --- | --- | --- |
| 기존 묶음에 재구매 | 주문번호·등록 번호·기존 비밀번호로 조회 인증 → 기존 묶음 연결 선택 → 현재 구매 전화 인증 → 연결 준비 | 등록 번호와 구매 인증 번호가 같고 조회/구매 자격 모두 유효할 때만 기존 buyer 선택. 기존 비밀번호 유지 |
| 별도 구매 | 새 묶음 선택 → 현재 구매 전화 인증 → 새 조회 비밀번호 준비 | 같은 이름·번호여도 새 buyer 생성. 기존 묶음 검색·자동 연결 없음 |
| 다른 번호 사용 | 기존 묶음 연결 불가 안내 → 새 묶음 선택·인증·새 비밀번호 준비 | 이전 번호/비밀번호/복구 코드/주문 참조는 변경하지 않고 새 buyer 생성 |
| 세션 만료·로그아웃·복구로 폐기 | 재인증 안내 후 선택부터 다시 확인 | 연결 거부. 실패를 신규 묶음 생성으로 조용히 전환하지 않음 |
| 응답 유실·중복 제출 | 서버 준비 상태 재조회, 비밀 입력 초기화 | 중복 소비/묶음 생성/주문 연결 없음. 성공을 확인하지 못하면 주문 완료로 표시하지 않음 |

다음은 기존 설계를 실행 가능하게 만들기 위한 계획상의 선택이며 구현 전 계약 검사로 고정한다.

1. 연결 모드는 NEW/EXISTING을 명시한다. 조회 쿠키가 있어도 NEW를 고르면 연결하지 않는다. 기존 주문 여러 개를 병합하는 기능은 만들지 않는다.
2. 기존 buyer ID를 클라이언트 입력으로 신뢰하지 않는다. 서버가 조회 세션에서 대상을 결정하고 구매 세션·현재 attempt에 결합한다. 다른 브라우저/시도에 선택을 재사용할 수 없다.
3. EXISTING 선택과 소비 시점 모두 조회 세션의 만료·폐기·password version, 구매 인증의 번호·PURCHASE 용도·만료·소비 여부를 확인한다. 선택 후 전화번호/시도/모드를 바꾸면 이전 연결 준비를 무효화한다.
4. EXISTING에서는 새 비밀번호를 받거나 기존 이름/번호/password hash/version/recovery hash를 덮어쓰지 않는다. 새 주문의 구매자 스냅샷 설계는 P08에 남긴다. NEW만 C의 새 비밀번호·D의 최초 복구 코드 계약을 사용한다.
5. 기존 buyer 선택·구매 인증 소비·주문 참조 등록은 호출자의 한 거래 안에서 수행한다. 중간 실패 시 모두 rollback한다. 기존 buyer/session 잠금 순서와 구매 attempt 잠금을 함께 설계하고 변경/복구와의 역순 잠금을 피한다. 잠금을 얻은 뒤 시간·권한을 다시 검사한다.
6. 조회 세션으로 구매 인증을 대신하거나 구매/복구 전화 인증으로 조회 자격을 대신하지 않는다. RECOVERY 증명은 PURCHASE 소비에 사용할 수 없다.
7. 준비 상태 응답은 모드와 준비 여부 등 최소 정보만 제공한다. password/code/token/buyer 내부 식별자를 URL·로그·영구 저장소로 노출하지 않는다. CSRF/no-store/쿠키 기본 정책과 기존 시도 제한을 유지한다.

## 작은 작업 순서

각 단위는 거부/경계 검사 추가 → 의도한 실패 확인 → 최소 구현 → 해당 검사 통과 → 결과 기록 순서로 진행했다. 현재 결과는 체크 목록과 아래 실행 기록을 따른다.

- [x] E1. NEW/EXISTING 선택 규칙과 무효화 조건을 순수 규칙으로 분리하고 JUnit으로 번호 정규화 후 비교·명시적 선택·실패 시 자동 전환 금지를 검증한다.
- [x] E2. 서버의 연결 준비 상태를 구매 attempt에 결합한다. 현재 스키마 확인 후 필요할 때만 다음 번호의 Flyway migration을 추가한다. 기존 V22~V24 및 기존 DB는 수정하지 않는다. 전화 변경/새 시도/모드 전환 뒤 오래된 준비가 거부되는 PostgreSQL 검사를 먼저 둔다.
- [x] E3. 내부 거래 계약에서 NEW 생성 또는 EXISTING 재검사를 거쳐 주문 참조를 연결한다. 새 격리 DB의 fixture로 기존 자격 불변·한 번 소비·rollback·경합을 검증한다. 제품 주문 생성 endpoint는 추가하지 않는다.
- [x] E4. 기존 GuestPage/GuestStore에 선택·기존 조회 인증 진입·번호 불일치/만료 안내·서버 준비 상태 복원을 연결한다. EXISTING에서 새 비밀번호 입력을 숨기고 서버도 거부한다. Vitest와 PC/모바일 실제 SDK 브라우저 검사로 두 흐름을 검증한다.
- [x] E5. 필수 검사 목록에 신규 이름을 추가한다. 새 경로 전체 개발 검증 통과 후 소스를 동결하고 검토세션에서 별도 새 경로로 독립 전체 검증한다. 지적 사항은 수정과 새 실행 증거로 닫는다.
- [x] E6. 제약별 실제 assertion·실행 경로·소스 식별·보존 비교·실패 이력·미검증 범위를 기록하고 README/구현 계획을 갱신한다. P07-A는 다음 작업으로 안내만 한다.

다음 표는 착수 당시 검증 계획이다. 최종 실제 이름과 assertion은 아래 실제 검사 이름 연결 표, 실행 결과는 최종 검증 절을 따른다.

| ID | 검사 방식·예정 이름 | 필수 assertion |
| --- | --- | --- |
| E01 | JUnit `GuestLinkPolicyTest` / DB `guestRepurchaseRequiresBothCredentials` | 유효 조회 세션+현재 PURCHASE 인증+같은 번호일 때만 기존 buyer 연결. 하나라도 없으면 거부 |
| E02 | DB `guestNewPurchaseNeverMergesByPhone` | 동일 이름/번호·조회 쿠키 존재에도 NEW는 별도 buyer, 과거 주문 조회 범위 불변 |
| E03 | DB `guestRepurchaseCannotOverwriteCredentials` | 연결 전후 기존 이름/번호/hash/version/recovery hash 동일, 새 password/buyer ID 조작은 거부, 다른 번호는 기존 연결 불가 |

| E06 | DB `guestRepurchaseConsumptionIsAtomic` | 후반 참조 등록 실패 시 인증 소비 rollback, 재시도 가능. 같은 인증 동시 소비 한 승자, 다른 묶음으로 참조 이동 없음 |
| E07 | HTTP/ArchUnit 기존+신규 | CSRF403, 실패/성공 no-store, 비활성503, 타 묶음 비노출, 테스트 fixture 제품 미노출, 모듈 경계 유지 |
| E08 | Vitest·브라우저 `guest-repurchase.spec.ts` 예정 | PC/모바일 기존 연결/NEW/다른 번호·응답 유실/만료·두 탭 상태 충돌. 중복 차단, 늦은 응답 무시, 입력 비밀 삭제, 실제 주문 성공으로 오인하지 않는 안내 |

검토 중점은 번호만으로 연결되는 우회, 선택 후 자격 폐기, 비밀번호 준비와 EXISTING 선택의 경합, reset과 연결의 잠금 순서, 응답 유실 후 중복 소비다. E01/E04/E05/E06/E08에서 각각 실행 근거를 확보한다. 검사의 총개수만으로 충족을 판단하지 않는다.

## 실행·보존·완료 흐름

1. 구현 요청 시 최신 HEAD/AGENTS/작업 기록을 다시 확인한다. 기존 서버·DB·데모·과거 검증 DB·미디어·실패 기록은 그대로 둔다. P06-D 커밋 마감 때 DB 서비스 중단이 있었으므로 Docker/기존 컨테이너 준비 상태를 먼저 읽기 전용으로 확인한다.
2. root `./verify.ps1 -Offline -EvidenceDirectory .local-tools/p06-e-dev-<고유값>`를 사용한다. 존재하는 경로를 재사용하지 않는다. 하네스가 만드는 새 DB/미디어만 검사 대상으로 변경한다.
3. 필수 실패·skip·누락이 있으면 완료하지 않고 원인과 로그를 기록한다. 테스트 삭제·목록 축소·타임아웃 확대만으로 통과시키지 않는다.
4. 개발 통과 후 검토세션에서 `.local-tools/p06-e-review-<고유값>`로 독립 전체 실행한다. 두 하네스를 동시에 실행하지 않는다. `P06-E-review.md`는 실제 검토 시 작성하며 지금 통과 문서를 만들지 않는다.
5. 완료 기록에 실제 HEAD+inputs 해시, result/coverage, 새 DB/미디어, before/after, 과거 실패 해시 비교, 미검증 사항을 연결한다. 제품 주문·결제 원자성과 실제 SMS는 미검증 범위로 유지한다.

## 학습·직접 확인 안내

조회 세션은 과거 주문 묶음에 대한 자격이고, 구매 전화 인증은 현재 구매 시도에 대한 증명이다. 기존 묶음 연결은 둘 중 하나로 대신하지 않고 둘 다 검사한다. 화면의 선택 값도 권한이 아니므로 서버에서 모드·현재 시도·조회 세션을 다시 대조한다. React의 linkKnown은 서버 확인이 끝났는지를 나타내며 확인 실패를 새 묶음 선택으로 바꾸지 않는다.

흐름은 GuestPage 버튼 → GuestStore의 CSRF 포함 요청 → GuestAccessController → JdbcGuestAccess의 checkout/buyer/session 검사 → 참조 등록 거래 → mode/ready/revision 응답이다. revision은 다른 탭이나 느린 요청이 과거 선택으로 되돌리는 것을 막는다. 실패 시 트랜잭션 rollback은 새 buyer/인증 소비/참조 등록을 함께 되돌린다.
