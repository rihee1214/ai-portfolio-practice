# P01-B4 Actuator health 프록시와 React 연결 계획

작성일: 2026-10-21 / 최신 확인: 2026-10-23 (Asia/Seoul) / 상태: **R4 수정·개발 및 preview 재검증 완료, 사용자 직접 확인 미확인**

## 최신 R4 수정 결과

부분 본문 수신 후 upstream이 끊기면 downstream도 전송 실패로 종료하도록 `frontend/vite/apiProxy.ts`를 수정했다. 잘린 JSON을 정상 완료로 처리하지 않으며 기존 공통 fetch가 연결 오류로 분류한다. 실제 스트림 회귀 테스트를 추가해 전체 68개 통과, 타입·린트·빌드 통과를 확인했다. 개발·preview 양쪽에서 무응답·부분 본문 정지·강제 종료 후 오류 표시와 정상 재시도, 취소·새 요청 우선 처리·화면 이탈을 확인했다.

[최신 검증과 증거](P01-B4-review.md#2026-10-23-r4-수정-후-최신-검증)에 실제 시간과 검사 한계를 기록했다. 10초는 무활동 제한이며 총 처리 기한은 아니다. 이번 시작·종료 시 8080·5174 서버는 실행되어 있지 않았고 재시작하지 않았다. 임시 검증 서버만 사용·종료했다. P01-B5는 진행하지 않았다.

아래는 R4 발견 및 이전 개발의 이력이다. 아래의 미해결 표현과 검사 수는 당시 상태이며 최신 판정은 위 결과를 따른다.

## 지정 검토 세션의 반영 결과

[P01-B4 검토 기록](P01-B4-review.md)에 기존 문제 3건의 수정·재현과 추가 UI·timeout 검사 결과를 기록했다. 기존 Node 테스트 56개는 재실행해도 통과했지만, 부분 본문 수신 후 연결이 끊기거나 timeout이 발생하면 화면이 로딩에 남는 **R4 결함을 추가 발견했다.** UI 27건은 23건 통과·3건 실패·1건 시간 관찰이며, 실제 HTTP 8건은 2건 통과·4건 실패·2건 제한 관찰이다. B4 전체 통과로 표시하지 않는다. 제품 수정과 B5는 진행하지 않았다.

검토 수정 직후 개발세션의 [정상 UI 확인](evidence/P01-B4-post-review-browser.json)은 이전 이력이다. 이후 요청에 따라 실패·취소·재시도·화면 이탈과 timeout까지 [추가 UI 검사](evidence/P01-B4-followup-browser.json)를 실행했다. 무응답은 약 10초 후 연결 실패로 끝나지만, 본문 수신 중단은 15초 검사 한도에도 끝나지 않았다. 계속 데이터를 보내는 응답은 12초에 정상 완료했으므로 `proxyTimeout`을 전체 10초 처리 기한으로 해석하지 않는다. 기존 8080·5174 서버는 유지했다.

아래 개발 검증 결과는 검토 수정 전 이력이다. 현재 동작·검사 건수는 위 검토 기록을 함께 확인한다.

## 2026-10-23 구현 및 검증 결과

아래 기존 계획을 기준으로 구현했다. P01-B5·DB·인증·업무 API는 진행하지 않았다. 백엔드 소스와 기본 설정은 변경하지 않았다.

### 변경과 결정

- `frontend/vite/apiProxy.ts`: 정확한 `/actuator/health`(쿼리 허용)와 `/api`, `/api/**`만 8080으로 프록시한다. 다른 관리 경로는 SPA fallback 전에 JSON 404로 종료한다. 헤더 전 upstream 연결 오류는 정보 노출 없는 JSON 502다. `proxyTimeout`은 10초지만 **무활동 시간 기준이며 전체 처리 기한이 아니다. 본문 시작 후 종료 문제는 위 R4로 미해결이다.** 개발·로컬 preview 모두 같은 규칙이다. 공개 배포 서버 구성은 아니다.
- `frontend/src/api/http.ts`: Accept JSON, Content-Type·JSON 파싱, HTTP 오류·네트워크·취소를 구분한다. 데이터는 `unknown`으로 반환해 업무별 런타임 검증을 분리한다. `/api`를 강제로 붙이지 않는다. JSON을 받는 함수이므로 204·HTML 성공은 계약 오류로 처리하며, 파일·빈 응답 API가 생기면 별도 계약을 추가한다.
- `frontend/src/api/health.ts`: HTTP 200·UP만 정상. 503·DOWN/OUT_OF_SERVICE, 200·UNKNOWN 등을 비정상으로 처리한다. AbortController와 요청 순번으로 취소·화면 이탈·오래된 응답의 덮어쓰기를 막는다.
- `frontend/src/components/HealthPanel.tsx`: 홈에 한국어 상태·연결 확인·다시 시도·취소를 추가했다. 최초에는 버튼으로 조회하며 자동 조회/반복 호출은 하지 않는다. `role=status`로 상태 변화를 알린다.
- Node 기본 테스트 러너를 사용해 별도 테스트 프레임워크 설치를 피했다. 프록시 HTTP 타입 검사를 위해 개발 의존성 `@types/node 24.19.2`만 추가하고 잠금 파일을 갱신했다. 실제 런타임은 기존 Node 24.22.0이다.
- `frontend/verify-proxy.ps1`: 실행 중인 실제 Vite+Boot에 대한 응답 계약 검사. UP/DOWN 조건마다 11건을 확인한다.

### 실행·학습·제한

프로젝트 루트에서 기존 JDK의 `java.exe -jar backend/target/marketplace-api-0.0.1-SNAPSHOT.jar --server.address=127.0.0.1 --server.port=8080`과 `./frontend/npm.ps1 run dev '--' --port 5174 --strictPort`를 각각 실행한다. [개발 화면](http://127.0.0.1:5174/)의 연결 확인을 누른다. 포트가 사용 중이면 소유를 확인하며 다른 서버를 종료하지 않는다. 실행 세션이 종료되면 서버도 다시 실행해야 한다.

흐름은 버튼 → HealthPanel → createHealthCheck → requestJson → Vite 프록시 → Boot Actuator → HTTP/JSON 해석 → React 상태 갱신이다. Java의 예외 분류처럼 공통 통신 결과를 구분하지만, TypeScript 타입만으로 외부 JSON을 믿을 수 없어 health 계층이 실제 값을 확인한다. AbortController는 요청 취소 신호이며 요청 순번은 이미 도착 중인 옛 응답까지 방어한다.

작은 실습: HealthPanel의 `healthy` 안내 문구를 바꾸고 연결 확인을 눌러 보자. 서버의 UP 응답은 그대로이고 화면 문구만 바뀌어야 한다. 사용자 실습·직접 이해 확인은 미확인이다.

실제 휴대전화·스크린리더·다른 브라우저는 미검증이다. UI 검증은 도구로 수행했으며 React DOM 자동 E2E 테스트 스위트는 아직 없다. DB·주문·결제의 정상 동작을 보장하지 않는다. 개발 검토는 사용자 지정 **검토 및 반영세션**에서 진행하며 그 결과를 별도 기록한다.

## 기존 승인 계획 (구현 전 기준)

## 범위와 선행 조건

[P01-B1](P01-B1.md)의 `/actuator/health`와 B2·B3의 React 화면을 연결한다. G01·G10과 AC16의 실행 재현성 준비에 해당한다. B1의 Actuator 교체·HTTP 27건 검증은 완료됐지만 Vite 프록시·공통 fetch·화면 연결은 아직 구현하지 않았다. DB·인증은 이 작업의 선행 조건이 아니다.

## 요청 경로와 응답 계약

브라우저의 상대 경로 `/actuator/health` → Vite 개발 프록시 → `http://127.0.0.1:8080/actuator/health` 순서로 연결한다. 기존 `/api/status`는 삭제됐으며 새 경로로 우회시키거나 다시 만들지 않는다.

| 항목 | 구현 기준 |
| --- | --- |
| health 프록시 | `/actuator/health`의 정확한 경로만 Boot로 전달. `/actuator/**` 전체를 프록시하지 않음 |
| 업무 API 프록시 | 기존 계획대로 `/api`·`/api/**`를 Boot로 전달. 아직 업무 API는 미구현 |
| 관리 경로·SPA fallback | `/actuator` 및 허용하지 않은 하위 경로는 404 처리. `/api`와 관리 경로의 오류를 index.html로 바꾸지 않음 |
| 요청 헤더 | `Accept: application/json`. 공통 fetch가 모든 요청에 `/api`를 강제로 붙이지 않도록 경로를 받음 |
| 정상 | HTTP 200과 `status: UP`을 모두 확인한 경우 정상 연결 표시 |
| health 장애 | HTTP 503의 `DOWN`·`OUT_OF_SERVICE`를 서버가 보고한 비정상 상태로 표시. 200의 UNKNOWN 등도 정상으로 표시하지 않음 |
| 통신·계약 오류 | API 중단·프록시 오류·네트워크 실패, 잘못된 JSON/HTML 응답을 정상·업무 데이터로 취급하지 않음 |
| 화면 문구 | 제거된 message 필드를 참조하지 않고 프런트에서 한국어 안내를 구성 |

health의 JSON은 업무 API의 공통 오류 응답과 별개다. 요청 처리에서 HTTP 상태와 JSON Content-Type을 확인하고 오류 응답도 안전하게 해석한다. 개발 프록시는 같은 출처의 연결 확인을 위한 것이며 공개 배포의 관리 경로 노출 정책은 P12에서 별도로 정한다.

## 화면과 공통 요청 처리

현재 학습 화면에 서버 연결 확인 영역을 두고 요청 중·정상·서버 비정상·연결 실패·다시 시도를 구분한다. DB·주문·결제 전체가 정상이라고 표현하지 않는다. 응답 취소와 오래된 응답이 최신 표시를 덮지 않는 처리를 포함하고, 자동 반복 조회는 기본으로 추가하지 않는다.

공통 fetch는 성공·HTTP 오류·통신 오류·취소를 구분한다. health에만 맞춘 반환 형태를 모든 업무 API에 강제하지 않는다. 구체적인 함수·타입·오류 구조는 이 작업을 구현할 때 현재 코드와 맞춰 정한다.

## 검증과 완료 조건

1. 타입·린트·빌드를 확인하고 React·Boot를 함께 실행해 실제 브라우저에서 정상 health 응답을 표시한다.
2. Boot만 종료해 연결 실패 표시를 확인한 뒤 다시 시작해 재시도·회복을 확인한다.
3. B1과 같은 임시 디스크 여유 공간 기준으로 503·DOWN을 재현하고 정상 연결로 표시되지 않는지 확인한다. 이후 기본 설정으로 복구한다.
4. `/api/status`와 없는 업무 경로가 404로 유지되고, 다른 관리 경로가 프록시·SPA 화면으로 노출되지 않는지 확인한다.
5. health 응답이 status만 포함하는지, 한국어 문구·요청 중·취소·재시도와 기존 홈·역할별 화면 동작을 확인한다.

실제 프록시·API·브라우저 결과와 미실행 항목을 이 문서에 추가한 뒤 완료 처리한다. 이번 계획 수정으로 B4나 P01-B 전체를 완료 처리하지 않는다. 이후 B5의 설정·실행 안내를 정리하고 C1에서 Docker DB를 준비한다.
