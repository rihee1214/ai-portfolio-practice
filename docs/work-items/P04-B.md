# P04-B 옵션·SKU·가격·판매 상태

2026-10-24 / 기준 eaba02d / 구현·검증·독립 검토 완료. P04-C 이후 미진행.

## 범위와 계약

설계의 Product → SKU(options, price, active), 상품 내 옵션 조합 고유·SKU 코드 고유·원 단위 정수 가격 음수 금지와 작업 계획 P04-B를 구현한다. 이미지·재고·예약·장바구니·구매·검색 화면은 제외한다. 상품 ACTIVE와 SKU active는 재고/구매 가능 보장이 아니다.

- 상품 생성과 같은 거래에서 기본 SKU 1개를 만든다. 기존 상품은 신규 마이그레이션에서 기본 SKU를 보충한다. 초기 가격 0원·판매 비활성으로 두어 임의 판매를 시작하지 않는다. 기존 서버/DB에는 적용하지 않는다.
- SKU 코드는 서버가 UUID 기반으로 생성하고 변경하지 않는다. 옵션은 이름/값 쌍 최대 3개, 각 1~40자 단일 행, 이름 중복 금지, 앞뒤 공백 제거·NFC 정규화·이름순 정렬 후 비교한다. 배열 순서가 달라도 같은 조합은409이다. 대소문자는 구분한다.
- 기본 SKU는 빈 옵션 조합이며 상품마다 정확히 1개를 유지한다. 옵션 SKU는 조합과 코드를 생성 후 변경하거나 삭제하지 않는다. 잘못 만든 조합은 판매 중지 후 새 조합을 등록한다. 옵션 SKU가 하나라도 있으면 기본 SKU는 비활성이고 다시 활성화할 수 없다. 옵션 SKU 최초 생성 시 기본 SKU 비활성/버전 갱신도 같은 거래로 수행한다. 기록은 보존한다.
- 가격은 0~999,999,999원 정수, SKU 판매 여부는 boolean. 수정은 읽은 SKU version 필수. 생성 version0, 오래된 수정409. SKU 최대100개(기본 포함). 전체 조합 자동 생성 대신 실제 판매할 조합만 한 건씩 등록한다.
- 판매자 본인 상품만 읽기/쓰기, 타인404. 쓰기는 기존 MANAGE_CATALOG 권한과 회원→매대→상품 잠금 사용, 보관 상품 수정409. 매대/판매자 제한·CSRF·운영 숨김 필드 경계를 유지한다. SKU 수정은 상품 version을 바꾸지 않으며 SKU version으로 충돌을 제어한다.
- 판매자 GET/POST /api/seller/products/{id}/skus, PUT /{skuId}. GET은 20개 페이지. 공개 GET /api/products/{slug}/skus는 기존 상품 공개 조건과 SKU active를 같은 SQL 스냅샷에서 확인하고 비공개 상품404, 공개 상품에 활성 SKU가 없으면 빈 목록이다. 공개 상품 기본정보 API의 기존 의미는 유지한다.

1. 기본 SKU 자동 생성·기존 상품 보충 실패 검사 → 저장/조회 구현 → 새 DB 검증.
2. 옵션 중복·가격 경계·소유권·판매 상태·버전 충돌·동시성·롤백 검사 → 보완 → 새 DB 검증.
3. 판매자 상품 선택 후 SKU 목록·가격·옵션·활성 관리 화면, 타입/린트/단위/빌드와 PC·모바일 실제 DB 브라우저.
4. 기존 검토세션에서 독립 검토·새 DB 재검증, 결과/차단/보존 기록. 다음 단계 및 커밋/푸시 미진행.

매 DB 검증은 verify-db.ps1의 신규 evidence 경로와 새 무작위 DB를 사용하고 보존한다. 작업 전 스냅샷은 evidence/P04-B-before.json. 기존 검증 DB를 재사용·삭제하지 않는다. 사용자 직접 학습·수동 확인은 미확인이다.

## 구현과 현재 검증

- V15 catalog_sku 및 기존 상품 보충. 상품/기본 SKU 생성은 JdbcProducts의 동일 거래. Skus API·JdbcSkus 저장/조회·SkuController HTTP 엄격 타입 검사. 공개 필터는 기존 상품 projection과 lateral SKU 조회를 하나의 SQL로 결합한다.
- 옵션 조합은 정규화 후 불변이며 가격·active만 수정한다. 제품 잠금으로 SKU 생성/수정/100개 한계를 직렬화한다. 첫 옵션 등록 시 기본 SKU 비활성 변경도 같은 거래다.
- React 상품 선택 아래 SkuPanel, CatalogStore의 인증 변경 취소·CSRF·읽은 version·자동 재시도 없음 재사용. 기본/옵션 SKU 목록·가격·활성·페이지·재조회와 등록 전 제한 안내를 제공한다.
- p04-b-default-red에서 조회 예상200/실제404 확인. 최초 green 빌드는 JSON 패키지를 기존 프로젝트와 다르게 사용해 실패했고 tools.jackson으로 교정했다. p04-b-default-green2 기본130·DB69 통과.
- p04-b-rules-red에서 변경 API 예상200/실제404 확인. 저장 구현 뒤 p04-b-rules-green 기본130·DB70 통과.
- p04-b-ui-red에서 기본 SKU 관리 버튼 부재 실패. 화면 구현 후 타입/린트/단위87/빌드 통과. 제어문자 정규식은 린트에 걸려 동일 검증을 코드포인트 비교로 표현했다.
- p04-b-boundaries 기본130·DB73 통과. 새 DB 내부 별도 schema에서 V14 기존 상품→V15 보충·재실행, 생성 실패 rollback, 동시 수정·중복·100개 한계, 5페이지100건 중복 없음, 가격 문자열/boolean/null/소수·active 문자열·version소수400, 공개 조건을 검증했다. 기존 검증 DB를 업그레이드한 것이 아니다.

## 학습 흐름과 제한

React 폼의 값을 정수 가격/옵션 쌍으로 보내면 서버가 JSON 타입·권한·상태·버전을 확인한 뒤 상품 행 잠금 아래 SKU를 저장한다. DB UNIQUE는 동시에 같은 조합을 등록해도 최종 중복을 막는다. 상품 변경 버전과 SKU 변경 버전은 별개다.

직접 해 볼 예: 새 격리 환경에서 기본 SKU 가격을1200원으로 바꾸고 활성화한 뒤 색상=빨강 조합을2500원으로 등록한다. 기본 SKU가 중지되고 공개 SKU 조회에는 빨강만 남는지 확인한다. 자동 검증과 별개로 사용자의 직접 확인·이해 여부는 미확인이다.

현재 원화·상품당100 SKU·최대3 옵션·수동 조합 등록만 제공한다. 기본 SKU 복귀·조합 이름/값 수정·삭제는 없고 중지 후 신규 등록한다. 옵션 SKU 전체를 중지해도 기본 SKU 복귀는 불가하다. 가격0은 유효한 입력이며 활성 여부는 별도로 선택한다. 공개 SKU는 재고·구매 가능을 보장하지 않으며 이미지·재고·구매 UI와 상용 부하·실제 기기 검증은 범위 밖이다. 기존 실행 서버에는 새 마이그레이션/코드를 적용하지 않는다.

독립 사전 검토에서 엄격 JSON 타입·기존 데이터 보충·잠금 경합·문자 경계 증거를 요청했다. 실제 회원/상품 잠금 대기를 관측한 뒤 계정 정지/상품 보관 commit 시409 및 SKU 불변, 기본 활성과 첫 옵션 생성 경합·실패 rollback을 추가해 p04-b-acceptance 기본130·DB75·브라우저22 통과. 최종 실행에는 NFC 동등 조합,40/41 emoji·제어문자·빈조합·매대 정지·판매자 역할 회수와 공개 응답 바깥 정렬을 보완했다. 현재 독립 최종 실행은 대기 중이며 아직 완료로 판정하지 않는다.
