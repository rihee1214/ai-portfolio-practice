# P09-C 발송 전 취소·전체/부분 환불 계약

상태: **계획 문서 독립 검토 반영 / 구현·검증·구현 독립 검토 미착수**, 2026-10-30.
목표: 출고를 먼저 차단한 뒤 원 단위 금액으로 환불을 예약·완료하고 수량/금액 초과를 막는다.
요구사항: F09·F10·F12, AC07~10. [공통 계약](P09.md), A/B의 개발·독립 전체 통과가 선행이다.

## 상세 계약과 변경 위치

소비: 원 unit별 net/할인·배송비 스냅샷, A 출고가능 수량, B 수량 점유, P07 CouponReservations와 재고 공개 계약. 생산: claimId/refundAttemptId/causeId로 연결된 취소·환불 견적/금액예약/DEMO 완료, D/E/F 공통 환불 포트.

- claim은 취소 절차, payment는 환불 시도/한도, order는 원수량 상태를 소유한다. claim→payment 공개 API를 호출하되 payment→claim 역호출 순환을 만들지 않는 결과 전달/Outbox 조정안을 설계한다. 외부 호출은 DB 거래 밖, 결과 확정·업무 효과의 원자성/재개 경계는 Astra 착수 판단으로 고정한다.
- 명령 입력은 orderNumber·원항목/대상 단위 또는 수량·이유·key/version. full/confirmed/금액/판매자/actor는 신뢰하지 않는다. 회원/GuestAccessSession 본인 및 CSRF·잠금 후 현재 자격 검증. 운영 처리는 거래지원 권한과 사유가 필요하다.
- 취소 승인 시 대상 미발송 수량을 잠금 아래 출고 불가로 만들고 환불 요청을 저장한다. 발송과 취소 한쪽만 성공. 환불 불명확 상태에서 출고 차단을 임의 해제하지 않는다.
- 환불액은 원 단위 net, 미발송 하위주문 전체 취소 때 원 청구 배송비도1회 반환. 부모 결제별 `성공환불+진행중/UNKNOWN 예약액≤원 결제액`. FAILED 판정의 예약 해제와 UNKNOWN 유지 구분. 0원 환불은 외부 호출0이지만 같은 업무 완료 이력/복구 조건을 적용한다.
- 환불 성공·취소 완료·판매 가능 재고 복구·쿠폰 복구는 각각 causeId로1회. 원 예약 COMMITTED를 release로 되돌리지 말고 inventory 소유 후속 입고 계약을 사용한다. CouponReservations.restore는 해당 하위주문 전체 처리의 서버 증거로만 호출하고 만료/부분환불을 구분한다.
- C의 DEMO 환불 어댑터는 실제 제공자가 아니다. 기존 PaymentProvider.cancel(Request)는 늦은 승인 전체 보상용이므로 부분환불 호출로 재사용하지 않는다. 새 환불 요청에는 원 payment 식별자·refundAttemptId·claimId·amount·mode를 저장한다. 동일 요청키 다른 내용409, 재시도 새 환불 생성 금지.

C는 A에서 고정한 `(orderItemId,ordinal)`를 소비하며 잔여1원이 배분된 단위를 환불 시 다시 선택하지 않는다. 원 청구 배송비는 `shippingBase-shippingDiscount`다. 전체 미발송 취소와 일부 출고/무료배송/부분 배송할인 경우를 구분하고 남은 가격·무료배송 기준을 소급 변경하지 않는다. 부분취소 성공 수량의 재고는1회 복구하고, **부분취소의 쿠폰 복구만0**이다. 여러 부분 처리 뒤 하위주문 전체 완료 여부는 별도로 판정한다.

C1은 H03/H04/H06과 아래 미정 사항을 전이표로 결정한다: 확정 FAILED 이후 금액예약 해제와 출고차단/claim 보류 유지·해제의 각각의 조건, 같은 시도 재처리와 새 환불 허용 조건, 취소 철회/운영 처리 경로, 배송비 반환과 회수비 공제·추가비용의 전체완료 판정. UNKNOWN의 점유 유지와 혼동하지 않는다. 근거 없는 보류 해제로 출고·확정이 환불과 동시에 성공하지 않게 검사한다. 회수비가 공제된 전체 반품을 `환불합==원결제액`만으로 판정하지 말고 원단위 소진·허용 공제·필수 회수/검수와 금전 확정 근거를 사용한다. 구체 정책은 승인 없이 정하지 않는다.

추가 fixture: gross10,001×3, promotionDiscount1,000×3, couponDiscount `[1000,1000,999]`이면 net `[8001,8001,8002]`, 상품 net24,004원이다. shippingBase3,000/shippingDiscount1,000은 실제 배송비2,000·하위총액26,004원이며 ordinal2 환불8,002 후 미발송 잔여전체 취소18,002로 합26,004가 된다. 무료배송 원 청구0의 부분취소 후 기준 미달도 재청구0이다. C의 새 실제 생성 fixture가 이 배분을 만들 수 있는 입력을 고정하거나 실제 배분 결과와 같은 항등식을 대조한다. 숫자만 직접 주입한 단위 검사를 실제 주문 경로 증거로 표시하지 않는다.

예정 신규: `backend/src/main/java/com/example/marketplace/claim/{api/Claims.java,domain/ClaimRules.java,infrastructure/JdbcClaims.java,web/ClaimController.java}`, `payment/api/Refunds.java`, `payment/api/RefundProvider.java`, `payment/domain/RefundRules.java`, `payment/infrastructure/JdbcRefunds.java`, `payment/infrastructure/MockRefundProvider.java`, inventory 후속 입고 공개 계약·신규 migration. 기존 모듈 내부를 다른 모듈에서 직접 쓰지 않는다. 정확한 포트 타입/잠금 표는 C1에서 확정하고 D~F가 동일 정의를 사용한다.

## 독립 검토와 D 인계

검토자는 부모 결제 한도를 하위주문별로만 잠그는 오류, 환불 성공을 기록하기 전 쿠폰/재고 복구, 동일 원 단위 재선택, 보상취소와 고객환불 ID 혼용을 집중 확인한다. 총액뿐 아니라 원단위·배송비·원인ID별 assertion이 필요하다. 모의 검증만으로 실제 PG 완료를 선언하지 않는다.

D에 환불 견적/예약/완료 포트·추가 비용 상태·전체완료 판정과 보류 해제를 전달한다. 실제 파일·API 서명·소스/실행경로·실패/독립 결과는 구현 후 기록하며 현재 모두 미실행이다. 사용자 직접 확인도 미확인이다.
