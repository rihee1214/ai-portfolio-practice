# P02-A2 독립 검토

2026-10-24 / 검토 및 반영세션 / 기준 커밋 `81e718c` 이후 작업 트리 / 판정: 검토 범위 내 필수 수정 잔여 없음

## 범위와 결론

개발세션의 사용자 직접 승인(로그인·로그아웃, Spring Session JDBC, me·csrf API, 별도 세션 검토)을 확인했다. 설계와 작업 계획, 인증 코드·V4 SQL·HTTP 통합 검사 및 [작업 문서](P02-A2.md)를 대조했다. 제품 코드를 수정하지 않았으며 이 검토 문서만 작성했다. P02-A3와 push는 진행하지 않았다.

독립 실행에서 기본 124개와 실제 PostgreSQL 통합 28개가 실패·오류·skip 없이 통과했다. 컴파일·Checkstyle·ArchUnit·패키징을 포함한 verify가 종료 코드 0이었다. 이 결과는 현재 A2 계약에 대한 검증이며 전체 인증 시스템의 운영 준비 완료를 뜻하지 않는다.

## 확인한 계약

| 항목 | 확인 결과 |
|---|---|
| 로그인 실패 | 잘못된 비밀번호·존재하지 않는 회원·미확인 회원·잘못된 이메일은 401 JSON. 상세 자격/회원 존재 사유와 redirect를 반환하지 않음 |
| 인증 상태 | 익명 me 401, 로그인 후 me에 ID·현재 역할만 반환, no-store |
| 세션 고정·복구·폐기 | 로그인 시 쿠키 값 변경, JDBC 행/속성 저장, 다른 HTTP 클라이언트의 동일 쿠키 복구, 로그아웃 후 예전 쿠키 401 및 세션 행 제거 |
| 자격 보호 | 직렬화된 세션 속성에 비밀번호 원문·Argon2id 해시 접두사 없음. 캡처 로그의 테스트 비밀번호·검사 대상 토큰 부재 확인은 제한된 자동 검사의 결과 |
| CSRF | 익명 csrf 200, 누락/다른 세션 토큰 403, 로그인·로그아웃·만료 뒤 이전 토큰 거부, 새 토큰으로 재로그인 가능 |
| 계정·권한 | 현재 역할 추가/제거가 me에 반영됨. authVersion 증가 및 정지/탈퇴 상태에서 기존 세션 거부 |
| 만료 | DB의 세션 시각을 과거로 변경해 만료 처리와 이전 CSRF 거부 검증. 30분 실시간 대기는 실행하지 않음 |
| 기존 기능 | 기본 검사와 기존 DB 통합 검사를 함께 실행. 기존 health 노출 정책과 HTTP 계약 회귀 검사 포함 |
| 스키마·쿠키 | V4만 추가하여 표준 세션 테이블/인덱스 생성. HttpOnly/SameSite=Lax 및 local-http의 Secure=false는 HTTP 응답 검사. 기본 Secure=true는 코드 확인 |

요청 ID 필터 → Session 필터 → Security 필터 순서, 단일 명시 ProviderManager, 세션 직렬화 전 자격 삭제, 보호 API의 계정·역할 재조회를 코드에서 확인했다. `/api/**` 밖의 경로는 이 인증 체인의 보호 대상이 아니므로 이후 업무 API 추가 시 경로 계약을 유지해야 한다. 현재 상태 변경은 요청 시 해당 세션을 거부하는 방식이며 전체 세션 즉시 일괄 폐기 업무 기능은 아직 구현하지 않았다.

## 실패와 재검증의 구분

- 개발 `a2-third` 결과는 통합 28개 중 1개 실패였다. 잘못된 비밀번호가 401 대신 500을 반환한 실제 결함이며 의도된 정상 결과가 아니다. 개발세션이 자동 부모 인증 제공자로 넘어가는 경로를 제거했다. 독립 실행은 수정된 명시 ProviderManager 코드에서 해당 실패 시나리오를 포함해 통과했다.
- 독립 첫 실행 `.local-tools/p02-a2-review`는 테스트 서버의 loopback 연결이 `Permission denied: connect`로 막혔다. 환경 실패로 분류하고 해당 실행 세션을 중단했다(종료 코드 1). 통합 통과로 집계하지 않는다.
- 로컬 연결을 허용한 독립 재실행: `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p02-a2-review-verified -Offline`. 새 출력 디렉터리와 새 DB를 사용했으며 종료 코드 0, 기본 124 + 통합 28 통과다. 증거 원본은 해당 디렉터리의 `maven.txt`, `summary.json`, `target.txt`다.

독립 검증 DB `d2_it_efaec51fb856433695e68394d455969b`를 생성했고 삭제하지 않았다. 기존 DB에는 마이그레이션이나 테스트 변경을 적용하지 않았다.

## 남은 한계와 사용자 확인

- 다른 HTTP 클라이언트의 세션 복구를 서버 프로세스 재시작 후 복구로 확대하지 않는다. 재시작·배포 간 직렬화 호환성은 미검증이다.
- 실제 TLS/Secure 쿠키 전송, 브라우저 다중 탭·React 연동, 동시 세션 변경 경쟁, DB 장애·세션 저장 실패 및 응답 유실, 부하·반복 실패 제한은 이번 실행에서 검증하지 않았다.
- 현재 필터의 계정·역할 조회 이후 동시에 발생하는 상태 변경까지 원자적으로 차단한다고 주장하지 않는다. 후속 업무의 권한·소유권·상태 전이 검사는 별도로 필요하다.
- HTTP 가입·이메일 확인 어댑터, React 화면, 복구·회원 관리 API와 모든 세션 일괄 폐기는 완료 범위가 아니다.
- 작업 문서의 역할 추가/제거와 authVersion 실습은 학습 예시이며 사용자의 직접 실행·이해 확인은 아직 받지 않았다.

참조한 공식 규약: [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)의 세션 토큰 저장·요청 처리와 [Spring Session JDBC](https://docs.spring.io/spring-session/reference/configuration/jdbc.html)의 PostgreSQL 스키마. 실제 동작 판정은 위 로컬 코드·실행 결과를 근거로 했다.
