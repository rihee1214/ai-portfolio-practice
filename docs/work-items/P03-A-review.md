## 범위

개발세션의 사용자 직접 승인 `01a16d09-a1e9-7921-ae5c-8aec8d55ba92`와 [작업 계획](P03-A.md)을 확인했다. 모의 판매 신청·승인·반려·이력·운영 화면을 검토하며 매대 생성/편집·판매 정지·실제 사업자 확인은 이번 범위가 아니다. 제품·검사는 개발세션 소유, 이 세션의 수정은 이 문서로 한정한다.

## 정적 확인

- 인증 예외는 GET/POST `/api/seller/applications`에만 먼저 적용한다. 해당 요청도 인증이 필요하고 CSRF 예외는 추가하지 않는다. 나머지 seller 경로는 SELLER, 운영 심사는 ADMIN 및 ACCOUNTS 경계를 유지한다.
- 신청자·처리자는 HTTP principal에서 얻는다. 입력 모델에 대상 회원·상태·역할을 받지 않는다. 본인 목록 SQL은 applicant_id 조건을 사용한다. 운영 목록과 결정은 서비스에서도 ACCOUNTS를 확인한다.
- seller는 identity.api의 SellerMembership·AccessPolicy에 의존한다. 회원/역할 SQL은 identity의 JdbcSellerMembership에 있고 실제 트랜잭션이 없는 회원 잠금은 거부한다.
- 신청/심사는 회원 행을 먼저 잠그고 신청 행을 잠근다. 심사 대기 이후 권한도 다시 확인한다. 승인 시 BUYER를 지우지 않고 SELLER를 추가하며 상태·역할·이력을 같은 트랜잭션에 묶는다. 자기 심사와 비활성 회원, 이미 판매자인 회원, 중복/끝난 결정은 거부한다.
- V8의 부분 유일 인덱스는 회원당 PENDING/APPROVED 최대 1개를 보조한다. 반려 후 새 신청은 새 행이며 기존 신청을 재처리하지 않는다. 실제 매대는 생성하지 않는다.
- React store는 인증 변화 시 이전 항목을 지우고 요청을 취소한다. 세대 번호로 늦은 응답을 무시하고 변경 전 CSRF를 얻는다. 목록·신청·결정 응답 형식을 검사하고 POST를 자동 재전송하지 않는다. 실제 작동은 후속 실행으로 확인한다.

## R1 — 신청 상태와 이력의 조회 시점 불일치

최초 JdbcSellerApplications.application은 events를 먼저 SELECT하고 신청 본문을 별도 SELECT한다. 두 조회 사이에 심사가 commit되면 APPROVED 본문과 PENDING 이벤트만 있는 응답이 만들어질 수 있다. 개발세션도 이미 보완 검토 중임을 알렸으며 이 세션에서 경로를 대조해 확인했다. 아직 실행 재현은 하지 않았다.

단순 READ_COMMITTED 트랜잭션은 문장별 snapshot 차이를 없애지 못한다. 단일 조회 또는 명시적인 일관 snapshot으로 상태·이력을 함께 읽고, 결정 중 조회에서도 반환 상태와 최종 이력이 일치하는지 검사하도록 전달했다. 목록 전체의 서로 다른 신청이 같은 시점이라는 보장과 개별 신청의 상태/이력 일치는 구분한다.

## R2 — 늦은 응답 검사 fixture의 분별력

최초 SellerApplications.test.tsx의 늦은 목록 응답은 events가 빈 배열이다. 제품 응답 검증은 events 길이 1~2를 요구하므로 해당 응답은 취소/세대 검사와 무관하게 거부될 수 있다. 유효한 PENDING 이벤트가 있는 응답으로 바꾸고 인증 재확인 또는 다른 회원 전환 이후 이전 신청이 노출되지 않는지 보완을 요청했다. 제품의 정보 노출 결함을 재현한 것이 아니라 테스트가 의도한 경계를 구분하지 못하는 검증 공백이다.

## 보완 확인

- **R1 해결 확인:** application()은 신청과 이벤트를 단일 LEFT JOIN SELECT로 읽는다. 개별 신청의 상태·이력은 동일 문장의 DB snapshot을 사용한다. 경쟁 심사 종료 후 상태와 마지막 이벤트 일치 검사도 통과했다. 구버전의 두 조회 사이에 commit을 강제로 끼워 넣은 RED는 실행하지 않았고, 최신 검사도 조회 중간시점의 강제 교차 실행을 재현한 것은 아니다. 정적 수정과 실제 회귀 증거를 구분한다.
- **R2 보완 확인:** 늦게 도착하는 응답에 정상 PENDING 이벤트를 포함하도록 고쳤다. 로그인 여부를 명시적으로 바꾼 뒤 401과 늦은 응답을 처리해 이전 신청 내용이 나타나지 않는 검사로 독립 통과했다. 다른 회원으로 직접 전환하는 모든 조합을 검증한 것은 아니다.
- **화면 전환 결함 수정 확인:** 개발 브라우저에서 기존12 통과·신규2 실패가 보고됐다. AccountPage 정리 시 auth.stop 후 신청 페이지가 인증을 재확인하지 않아 로딩 상태에 머문 문제였다. 비관리자 신청 페이지 mount에서 auth.invalidate를 실행하고 관리자 화면은 기존 WorkspaceAccess의 확인을 사용한다. 최신 독립 단위·PC/모바일 브라우저에서 실제 `/account` 링크 이동과 신청 입력이 통과했다. 기존 실패는 의도된 오류 검사가 아니다.
