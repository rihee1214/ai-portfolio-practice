# P03 전체 점검 R1 — 동일 회원 연속 흐름

2026-10-24 / 기준 1a9523a / R1 개발 검증·기존 검토 세션의 독립 검증 완료.

최종 상태: 사용자의 후속 승인에 따라 전체 점검·설계/계획 교정·R1 테스트·개발 및 독립 검증 증거·검토 문서를 로컬 커밋 `test: complete P03 audit and same-member seller journey`에 함께 기록한다. 아래 커밋 미진행 문구는 개발/검토 당시 이력이다. 최종화에서 제품이나 테스트를 추가 변경하지 않고 검증 증거·문서 링크·Git 범위·DB 보존을 재확인했다. R1 개발/독립 DB2개를 포함한 기존 모든 DB 목록과 컨테이너가 유지되며 개발/테스트 DB 해시도 동일하다. 푸시·P04·다음 단계는 진행하지 않았다.

## 요청과 범위

[전체 점검 R1](P03-completion-review.md)은 A/B/C 개별 검사가 서로 다른 회원 fixture에서 시작하여 승인 이후 매대 운영까지 같은 회원으로 연결된 증거가 없다는 검증 공백이다. 기존 개별 검사를 유지하고 `frontend/auth-e2e/seller-journey.spec.ts` 한 시나리오를 PC·모바일 프로젝트에 추가한다. 제품 기능을 새로 추가하는 단계가 아니다.

기존 미커밋 implementation-plan.md, shop-design.md, 전체 점검 문서와 증거3개는 검토 세션 소유로 보존한다. 개발 검증 당시 이 작업은 새 테스트·이 문서·R1 실행 증거를 담당했으며 P04·커밋·푸시를 진행하지 않았다. 이후 최종 로컬 커밋 승인은 아래 완료 기록에 구분한다.

## 검증 계약

1. 임의 이메일의 새 회원을 가입/모의 이메일 확인 API로 생성하고 화면에서 한 번 로그인한다. 처음 역할은 BUYER만인지 확인하고 회원 ID를 보관한다.
2. 유효한 CSRF와 매대 생성 입력을 보내 승인 전403을 확인한다. 화면에서 판매 신청을 제출한다.
3. 별도 운영자 문맥의 ADMIN+ACCOUNTS가 화면에서 승인한다. 운영자 fixture만 사전 준비하며 새 신청자의 SELLER는 SQL로 부여하지 않는다.
4. 신청자는 같은 browser context에서 재로그인 없이 me의 동일 ID, BUYER+SELLER, profile200을 확인한다. 화면 새로고침 후 판매자 자격 안내, 신청 applicantId/APPROVED 및 승인 처리자·사유 이력도 확인한다. 승인 전 거부된 매대 생성이 데이터로 남지 않았는지 본인 매대가 null임을 확인한다.
5. 같은 회원이 화면에서 매대를 생성·공개한다. 별도 비로그인 방문자 화면에 매대 이름이 보이는지 확인한다.
6. 운영자가 정지하면 공개 방문자는 찾을 수 없음, 판매자 편집 폼은 제거된다. 운영자 복구 후에도 비공개이며 공개 방문자에게 보이지 않는지 확인한다.
7. 판매자가 명시적으로 공개 체크 후 저장하면 방문자 화면에서 다시 보이는지 확인한다.
8. 같은 회원이 확인 체크와 사유로 폐점한다. 새로고침 후 CLOSED/비공개, 공개 방문자 비노출, 다른 slug를 사용해도 재개설409, 본인 매대 ID 불변을 확인한다.
9. 승인·정지·복구·폐점 후 동일 회원 ID와 BUYER/SELLER·profile200을 확인한다. 최종 이력3건은 close→restore→suspend 순서이고 각 처리자·전후 상태·사유를 검사한다.

신청/승인/매대 조치는 실제 화면·API·새 PostgreSQL DB를 사용한다. 가입/메일 확인은 준비 API를 사용하며 실제 메일 발송이나 실제 구매 성공을 의미하지 않는다. 역할·프로필 유지는 구매자 자격 유지의 증거이고 주문 기능은 후속 범위다.

## 실행과 재현

`./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p03-completion-r1 -Offline -RunBrowser`로 새 격리 DB와 테스트 전용 서버를 구성한다. 기존 서버를 재사용하거나 재시작하지 않는다. 반복 실행은 새로운 EvidenceDirectory를 사용한다. 검증 DB는 종료 후에도 유지한다.

## 개발 실행 결과

- 타입 검사·린트 종료0. [프런트 로그](evidence/P03-completion-r1-frontend.txt).
- 새 격리 DB 실행 종료0: Java 기본130·DB 통합58, 실패/오류/skip0. [집계](evidence/P03-completion-r1-summary.json), [DB 로그 발췌](evidence/P03-completion-r1-db.txt).
- 실제 브라우저20개 통과: 기존18 + 새 동일회원 흐름 desktop/mobile 각1. [브라우저 로그](evidence/P03-completion-r1-browser.txt). 새 흐름은 최초 실행부터 통과했고 제품 결함이나 검사 실패는 발생하지 않았다. 기존 개별 검사를 제거/축소하지 않았다.
- 새 DB `d2_it_6b6056ddfbd144d08a0ff7981a8d5ffc`를 보존했다. [식별](evidence/P03-completion-r1-target.txt). 자기 검증 서버 종료 후24176 리스너가 없는 것을 확인하고 독립 검토 세션에 인계했다.
- 제품·빌드 설정·Java·기존 테스트는 변경하지 않았다. 테스트 파일 추가만으로 닫는 검증 공백이므로 기존 Vitest/별도 health 브라우저를 이번에 다시 실행하지 않았다. Java 기본 검사에는 기존 health HTTP 계약 검사가 포함된다.

## 보존·잔여 범위

[작업 전](evidence/P03-completion-r1-before.json)과 [작업 후](evidence/P03-completion-r1-after.json)를 비교했다. 기존 개발/테스트 DB 정규화 pg_dump 해시 일치, 기존 DB 목록 누락 없음, 컨테이너 ID 및15432/15433 PID57168 유지를 확인했다. 과거 검증 DB도 삭제하지 않았으며 기존 모든 행을 개별 덤프 비교한 것은 아니다. [보존 결과](evidence/P03-completion-r1-preservation.txt).

8080/4174/5174 리스너는 보존 스냅샷 당시 관측되지 않았고 이 작업에서 시작하거나 중단하지 않았다. 기존 DB에 스키마를 적용하지 않았다. 다음 단계·커밋·푸시는 하지 않았다.

학습 포인트는 승인 후 별도 재로그인 없이 동일 회원의 me 권한이 갱신되고 그 권한으로 매대 쓰기가 연결되는지 추적하는 것이다. 코드에서 `buyerRetained()` 호출과 최초 `member.id` 비교를 따라가면 각 상태 변경 뒤의 회원 자격 유지를 확인할 수 있다. 사용자의 직접 실습·이해 완료는 별도로 확인해야 한다.

R1의 개발 검증 공백은 보완했다. 전체 P03 최종 판정과 독립 재실행 결과는 검토 세션 소유인 [전체 점검 기록](P03-completion-review.md)에서 관리한다. 상품·주문·실제 구매·상용 운영의 기존 제한은 그대로다.

## 독립 검토 완료

기존 검토 및 반영세션이 새 격리 DB에서 독립 실행한 결과 Java130·DB58·브라우저20(동일 회원2+기존18)이 통과했다. 동일 ID·기존 문맥·실제 승인·명시적 재공개·재개설409·조치 이력을 직접 검토하여 R1 해결과 P03 확정 계획 범위 완료를 기록했다. [독립 집계](evidence/P03-completion-r1-review-summary.json), [브라우저](evidence/P03-completion-r1-review-browser.txt), [DB 식별](evidence/P03-completion-r1-review-target.txt)을 확인했다. 독립 DB `d2_it_310224f7d3f643489a00dcde1cb70254`도 보존했다. 필수 잔여 검토 항목은 없으며 기존 후속 범위·운영 제한은 유지한다. 독립 검토 완료 반영 당시에는 문서 상태만 갱신했고 제품 코드·커밋·푸시·P04는 진행하지 않았다.
