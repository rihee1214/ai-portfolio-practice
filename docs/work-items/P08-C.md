# P08-C 주문 생성·인증 소비·통합 예약 — 구현 작업 계획

> **For agentic workers:** 구현 요청 시 `superpowers:executing-plans`로 작은 작업을 순서대로 수행한다. 개발 전체 통과 후 지정 검토세션에서 독립 검토한다. 이번 문서 작성은 구현/커밋 승인이 아니다.

**Goal:** 회원·비회원의 주문과 재고·쿠폰·인증 소비를 한 거래로 생성하고 응답 유실에도 같은 주문으로 수렴시킨다.

**Architecture:** order의 공개 애플리케이션 서비스가 외부 거래를 열고 guest/promotion/inventory 공개 API와 Outbox를 호출한다. 비밀번호 해시는 짧은 거래 전에 준비한다.

**Tech Stack:** Java/Spring Boot·Spring JDBC·PostgreSQL·JUnit/ArchUnit·React/TypeScript·Vitest/Playwright.

**Spec:** [설계](../shop-design.md) §4·7~11·13~16, [요구사항](../requirements.md) F05/F09/F10/F11·AC01~04/07/08/13, [구현 계획](../implementation-plan.md) §10, [P08 전체 계약](P08.md).

상태: 계획 작성 / 구현·검증 미착수. 선행: **A/B 완료**.

## Global Constraints

[P08 공통 정책·인계·검증](P08.md)을 모두 적용한다. 기존 서버·DB·검증DB·미디어·데모·실패 기록은 보존하고 새 격리 경로만 쓴다. 아래 파일/API/검사명은 예정이며 구현 존재/통과를 뜻하지 않는다. 새 정책 수치는 제안으로 구분하고 착수 계약에 채택 이유를 기록한다.

## Interfaces와 세부 계약

소비: A의 서버 소유 checkout/주문 모델, `Quotes.calculate`, 전체 `CouponReservations.Request` batch와 `Reservations.Request`, B의 거래형 Outbox. 생산: POST `/api/orders`의 orderNumber/상태/금액/기한 및 같은 세션·키의 결과 재조회 계약. 게스트는 서버 쿠키·현재 인증 attempt와 NEW/EXISTING 선택으로 식별하고 client memberId/guestBuyerId를 신뢰하지 않는다.

동일키·동일내용 retry는 현재 요청자의 접근을 확인한 후 최초 결과 반환; 동일키·다른내용409; 다른 구매 세션 접근 거부. 성공 재전송에서 소비된 인증이나 이미 예약된 쿠폰을 신규 신청처럼 재소비하지 않는다. hash에는 정규화된 SKU/수량/선택쿠폰·배송입력·견적내용·조회연결 revision 등 의미 입력을 반영하되 비밀 원문은 제외한다.

전체 잠금 표와 P07 batch 식별을 먼저 확정한다. 최신 견적 재계산과 계정/판매자/상품 변경의 실제 잠금 대기 후 재검사, 전체 재고/쿠폰 batch 예약, guest 인증 소비·참조 등록, 주문/Outbox가 같은 Spring 거래에 참여해야 한다. 성공 commit 뒤에만 주문 항목을 장바구니에 반영하며 새로 추가/수정한 항목을 무조건 전체 삭제하지 않는다. 거래 재시도는 외부에서 새 거래로 제한해 수행한다.

## C 착수 계약 — 2026-10-27 (실행 중)

통합 잠금 순서(모든 변경은 한 외부 REQUIRED 거래):
1. 브라우저 구매 세션+요청키 advisory 잠금. 기존 주문이면 현재 회원 일치/활성 또는 동일 서버 브라우저+불변 guest attempt 귀속을 먼저 검사하고 hash 일치 결과를 반환한다. 신규 인증/쿠폰을 재소비하지 않는다.
2. 비회원 checkout → attempt → 기존 buyer → access session. NEW/EXISTING 선택 revision과 현재 인증을 검사한다. 이미 준비된 비밀번호 hash만 사용하며 원문/해시는 주문 입력에 없다.
3. 구매자와 전체 판매자 identity_user를 UUID 문자열 정렬 FOR UPDATE → 전체 판매자 순 매대 FOR UPDATE → category 정렬 → product 정렬 → SKU 정렬. 해당 모듈 public API가 수행한다. 이 순서는 seller/catalog/inventory 수동변경의 identity→store→category/product→balance와 같다. 매대 잠금은 promotion 생성/변경도 차단한다. 대기 완료 후 현재 공개 projection과 권한을 다시 읽는다. identity/store FK 전에 전부 획득한다.
4. 현재 quote 재계산 후 fingerprint 불일치면409·새 quote. guest consume/create → order_checkout_attempt의 guest_attempt FK → purchase_order의 identity/guest FK → seller_order의 store FK → item/unit/contact. FK 대상은 이미 소유한 잠금이다.
5. 전체 checkout P07 coupon batch 한 번 → 이미 소유한 accounts/stores → coupon 정렬 → coupon reservation/event. V30은 batch 회원 FK를 이미 제거했다. 새 C checkout은 이 거래에서 처음 공개되므로 다른 거래가 같은 미완성 batch를 선점할 수 없다. 같은키 retry는 1에서 직렬화된다.
6. inventory 전체 request/order-item advisory 키 실제 정수순 → balance SKU순 → reservation/event. 쿠폰의 내부 재견적보다 먼저 재고를 예약하지 않는다(정확히 남은 수량 구매 회귀).
7. guest order reference·order reservation IDs·order audit → Outbox job/event. 기한은 서버 now+15분과 선택 쿠폰 종료 최소, microsecond 정규화. D 핸들러는 구현하지 않는다.

## C 실제 구현·집중 검증 — 2026-10-27

위 착수 잠금 표의 identity 단계는 검증 후 `FOR NO KEY UPDATE`로 확정했다. PK를 변경하는 API가 없으므로 계정 상태/권한 변경의 UPDATE·FOR UPDATE와 충돌하면서, category/account 관리자 감사 행의 actor FK KEY SHARE는 허용한다. 이 예외는 `SellerMembership.lockActiveBuyer`에만 적용했다. cart/wishlist/address의 강한 잠금은 주문 거래 안에 호출하지 않으며 장바구니 반영은 커밋 뒤 별도 거래다. `purchaseAccountLockAllowsAuditForeignKeysButExcludesMutations`는 직접 FK 호환성과 두 종류 변경 잠금 배제를 검사하며, `orderAdministratorAuditLocksDoNotCycle`은 관리자이자 구매자/판매자인 actor의 실제 category 및 account 감사 경합을 검사한다.

잠금 순서에는 HTTP 현재 세션 확인도 포함한다. 신규는 전체 identity/store/category/product/SKU 획득 뒤, 기존 성공 재시도는 현재 구매자 잠금 뒤 `PurchaseSessions.lockCurrent`를 호출한다. 서버가 읽은 sessionId·memberId·이전 authVersion만 전달하며, spring_session SHARE를 커밋까지 유지하고 principal_name/expiry/auth_version을 다시 검사한다. 계정→세션 순서는 비밀번호 초기화의 계정→세션 삭제와 같다. framework 세션 타입은 공개 API에 없다. 내부 trusted create와 HTTP createForSession은 분리했으며 HTTP가 trusted 경로를 선택할 입력은 없다.

프런트는 명시적 확인 checkbox 때 견적의 SKU/수량과 일치하는 현재 cart revision만 복사한다. 승인 이후 변경·삭제 후 같은 수량 재추가·다른 항목 추가는 보존한다. 승인 이전 동일 수량 재추가를 사용자가 새로 승인했다면 새 revision을 주문 후 반영해도 된다. 승인 전에 이미 수량이 달라진 항목은 반영 목록에서 제외한다. 빈 목록은 요청 없는 성공 no-op이다. 응답 유실 시 입력/키/반영 snapshot을 유지하고, 409는 새 견적+명시적 확인+새키, 401은 자동 재전송 금지다.
