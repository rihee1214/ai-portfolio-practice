# P01-E3 React 공통 오류·요청 ID 표시

2026-10-23 / 상태: 구현·자동 검증 완료, 지정 세션 독립 검토 대기

직접 사용자 최신 요청은 P01-E3 진행이다. 이전 E2 완료 인계의 다음 작업 금지와 구분한다. E3 다음 단계는 진행하지 않는다.

범위: E2 공통 오류를 해석하는 작은 함수와 React 안내 컴포넌트, 개발 모드 전용 /dev/api-errors 확인 화면. 버튼을 눌렀을 때만 없는 /api/error-preview를 GET하여 실제 E2 404를 표시한다. 일반 메뉴와 production 빌드에는 이 경로를 제공하지 않는다. 업무 기능이나 API endpoint를 추가하지 않는다.

알려진 code/status와 message 구조를 확인하되 서버 임의 문구 대신 고정 한국어 안내를 표시한다. E1 UUID v4 형식의 requestId만 텍스트로 표시한다. 잘못된 응답·네트워크·취소·재시도·늦은 응답·화면 해제를 검사하며 기존 health와 requestJson 계약은 유지한다. fieldErrors·업무 폼·인증·전역 toast·자동 재시도는 제외한다.

DOM 모의 검사와 실제 Chromium→React→Java404 연결을 구분해 검증한다. 기존 서버·DB는 유지하고 소유 임시 서버만 사용한다. 검토 및 반영세션 독립 검토 후 결과·차단 항목·완료 상태를 기록한다.

## 구현과 선택

- apiErrorView는 기존 requestJson의 결과를 받는 표시 전용 함수다. HTTP code/status 조합은 E2의400/401/403/404/405/406/409/415/429 및 기타4xx/5xx를 따른다. message는 비어 있지 않은300자 이하 문자열인지 확인하고 실제 출력은 로컬 고정 문구를 사용한다. 서버 문자열은 innerHTML이나 일반 텍스트로도 출력하지 않는다.
- body가 유효하지만 ID가 없거나 UUID v4가 아니면 오류 안내만 표시한다. 알려지지 않은 code·상태 불일치·잘못된 body는 일반 안내만 표시한다. 네트워크 실패는 연결 안내, 성공/취소는 오류 없음이다. header ID를 추출하거나 body/header 일치까지 검증하는 adapter는 아니며 실제 Java 연결 검사에서 E2 body/header 일치를 확인했다. 향후 서버 code가 바뀌면 이 계약도 갱신해야 한다.
- ApiErrorNotice는 role=alert와 요청 ID 텍스트만 담당한다. error/code 자체나 fieldErrors·예외·쿼리를 출력하지 않는다. ID는 줄바꿈 가능한 CSS를 적용한다. 실제 스크린리더 음성 출력이나 모든 접근성 기준을 검증한 것은 아니다.
- ApiErrorPreview는 개발 모드 전용이며 수동 GET만 사용한다. 재시도할 때 이전 오류/ID를 즉시 지우고 로딩을 표시한다. AbortController와 요청 순번으로 이전 응답을 무시한다. 취소·unmount도 순번을 무효화한다. 전역 요청 hook·toast·인증 상태·자동 재시도는 추가하지 않았다.
- 일반 메뉴에는 개발 경로를 연결하지 않는다. import.meta.env.DEV로 라우트를 제한하며 실제 production build에서 해당 경로가 NotFound로 가는 것을 검증했다. 배포 JS에서 error-preview/확인 화면 문구가 검색되지 않는 것도 확인했다. DEV 제한은 권한 제어 기능으로 간주하지 않는다.
- health/requestJson/Java 소스는 변경하지 않았다. 아직 업무 화면에 API가 없으므로 재사용 컴포넌트와 확인 화면으로 검증했다. 업무별 실제 폼 연결과 오류 표시 완료를 주장하지 않는다.

DOM에서는 HTML·깨진 JSON·네트워크 실패, 오류 code/상태/형식·ID 유효성, 서버 임의 메시지 미출력, 재시도/로딩/취소/화면 해제/성공을 검사했다. 응답 시점은 deferred Promise로 제어하며 임의 sleep을 쓰지 않는다. 화면 해제 후 검사 결과는 abort와 화면 미표시를 뜻하며 해제된 React 인스턴스 내부 콜백 호출 횟수를 직접 계측한 것은 아니다.

실제 브라우저는 mock 없이 Java404를 요청하여 E2 code와 body/header ID, 화면의 동일 ID와 재시도 시 새 ID를 확인했다. 키보드 Enter 재시도, 가로 넘침 없음, production 경로 미제공도 확인했다. [데스크톱](evidence/P01-E3-chromium-desktop.png)·[모바일](evidence/P01-E3-chromium-mobile.png) 캡처를 저장했고 모바일 안내/ID 줄바꿈을 확인했다. 모바일은 Chromium 에뮬레이션이며 실기기·Firefox/WebKit·시각 회귀 전체 검사가 아니다. 연결 장애/늦은 응답은 DOM 모의 검사이고 실제 서버 중단은 이번에 재현하지 않았다.

## 보존·실패·미검증

[시작 포트](evidence/P01-E3-ports-before.json), [종료](evidence/P01-E3-preservation.json): 기존8080/4174/5174 앱은 시작부터 리스너가 없었다. 임의 실행/종료하지 않았으며 테스트 소유18080/24174/24175도 종료 후 남지 않았다. DB dev/test 정규화 덤프 해시는 E2 기록과 동일하며 컨테이너 ID·healthy·DB 리스너 PID57168을 유지했다. 읽기 전용 덤프의 restrict/unrestrict 무작위 토큰만 제외했고 원문은 저장하지 않았다. DB 생성·쓰기·초기화·컨테이너 재시작은 없다.

최초 자동 승인 검토가 이전 E2의 다음 단계 금지를 근거로 E3 문서 생성을 거부했다. 최신 직접 사용자 E3 요청을 명시해 재검토 승인을 받은 뒤 진행했다. 현재 차단 항목은 없다. 처음 production JS 문자열 검색에서 PowerShell wildcard 경로 해석 오류가 있었고 디렉터리와 rg glob을 분리하여 정상 검색했다. 테스트 기대 문구 초안의 오타는 구현 시 한국어 계약으로 바로잡았으며 기능 결함 수정으로 계산하지 않는다. 출력의 NO_COLOR/FORCE_COLOR·Mockito 경고는 검사 실패가 아니다. 로그는 행 끝 공백과 마지막 빈 줄만 정리했다.

fieldErrors·업무 폼·인증·권한·자동 재시도·복사 버튼·실제 거래·서버 로그 검색 기능은 미구현이다. 요청 ID를 화면에 표시하는 것이 상담/로그 조회 기능 구현을 뜻하지 않는다. 사용자 직접 실습·이해는 미확인이다. 다음 단계·프런트 단순화·push는 진행하지 않았다.

## 실행과 작은 실습

루트에서 `./frontend/npm.ps1 run test:unit`, `run typecheck`, `run lint`, `run build`, `test`를 실행한다. 실제 E2E는 최신 Java JAR와 production dist를 먼저 준비해야 한다. 아래는 PowerShell 예시다.

```powershell
$previousJava = $env:JAVA_HOME
$previousMaven = $env:MAVEN_USER_HOME
try {
  $env:JAVA_HOME = Join-Path $PWD '.local-tools/jdk-21.0.12.1+1'
  $env:MAVEN_USER_HOME = Join-Path $PWD '.local-tools/m2'
  ./backend/mvnw.cmd -f backend/pom.xml "-Dmarketplace.build.directory=$PWD/.local-tools/d4-build" verify
  if ($LASTEXITCODE -ne 0) { throw 'Java build failed' }
} finally {
  $env:JAVA_HOME = $previousJava
  $env:MAVEN_USER_HOME = $previousMaven
}
./frontend/npm.ps1 run build
./frontend/npm.ps1 run test:e2e
```

Playwright는 기존 D4 설정을 재사용하며 production preview24175를 추가했다. 세 서버 모두 reuseExistingServer:false, Vite는 strictPort다. 포트 충돌 시 기존 서버를 종료하지 않는다. JAR/dist가 최신인지 자동 판단하지 않으므로 재빌드 안내를 따른다. 브라우저 준비 방법은 D4 문서와 같고 새 라이브러리는 추가하지 않았다.

코드 흐름: 버튼 → requestJson → apiErrorView의 계약 확인/문구 선택 → React 상태 → ApiErrorNotice. 작은 실습으로 ApiErrorView.test.tsx의 정상 ID를 잘못된 문자열로 바꾸면 ID가 생략되는지 확인하고 원복한다. 실제 화면은 개발 서버를 별도로 준비한 뒤 `/dev/api-errors`에서 확인할 수 있다. 이 작업은 기존 사용자 미리보기 서버를 새로 켜지 않는다.
