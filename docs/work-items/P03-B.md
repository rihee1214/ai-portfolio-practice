# P03-B 매대 기본 관리

2026-10-24 / 기준 0500242 / 구현·검증·독립 검토 완료. 최종 로컬 커밋 기록 포함.

## 확정 범위

승인된 ACTIVE SELLER가 본인 매대 한 개를 생성·수정한다. 공개/비공개는 폐점 상태와 다르며 비공개도 매대 수에 포함한다. 삭제·폐점·판매 정지는 P03-C까지 구현하지 않는다.

매대 이름 1~80자, 소개 1~1000자, 공개용 주소 1~200자, 공지 0~1000자, 대표 이미지 메타데이터(선택 assetKey 1~100 영문·숫자·하이픈/밑줄, 대체 텍스트 1~120자), 공개 여부를 관리한다. 주소는 공개 정보임을 화면에서 안내하고 테스트용 가상 정보를 사용한다. 이미지 파일/URL 수집·외부 이미지 로딩은 하지 않으며 업로드는 P04-C에 연결한다. 키만 등록한 것을 이미지 업로드 완료로 표시하지 않는다.

slug는 소문자 영문·숫자와 내부 하이픈, 3~63자, 전체 고유이며 생성 후 변경하지 않는다. 소유자는 인증 principal에서 정하고 입력으로 변경하지 못한다. 생성 시 비공개를 기본 선택한다. 수정은 읽은 version을 보내 이전 화면에서 덮어쓰는 경우 409로 거부한다.

API: GET/POST /api/seller/stores, PUT /api/seller/stores/{id}, 공개 GET /api/stores/{slug}. 관리 화면 /seller/store, 공개 화면 /stores/:slug. 본인 미생성 조회는 {store:null}; 공개 조회는 공개이며 ACTIVE SELLER인 경우만 허용하고 나머지는 404다. 관리 DTO와 공개 DTO를 구분하여 공개 응답에서 소유자 UUID와 version을 제외한다. 기존 health·인증 계약은 유지한다.

## 작업 순서

1. 실패하는 HTTP 계약 검사 → V9·서비스·소유권·고유 제약 구현.
2. 중복/경쟁·이전 version·비공개·비활성 회원·CSRF·권한을 새 격리 DB에서 검사.
3. React 관리/공개 화면과 오류·늦은 응답 처리, 실제 PC·모바일 브라우저 검사.
4. 검토 및 반영세션 독립 검토, 보존 비교와 결과 기록. P03-C는 진행하지 않는다.

## 구현 계약과 코드 흐름

V9 seller_store에 소유자·slug 고유 제약을 둔다. 비공개로 바꾸어도 두 번째 매대를 만들 수 없다. 버전은 생성0, 수정마다1 증가한다. 문자열 길이는 Unicode 코드 포인트 기준이고 앞뒤 공백을 제거한다. 제어 문자/잘못된 surrogate는 거부하며 현재 소개·공지 입력은 단일 줄이다.

| API | 성공 | 거부 |
| --- | --- | --- |
| GET /api/seller/stores | 200 {store:null 또는 관리 DTO} | 로그인·ACTIVE SELLER 필요 |
| POST /api/seller/stores | 201 관리 DTO, version0 | CSRF, 중복 소유자/slug409, 잘못된 입력400 |
| PUT /api/seller/stores/{id} | 200 관리 DTO, version 증가 | CSRF, 타인/없는 매대404, 오래된 version/slug 변경409 |
| GET /api/stores/{slug} | 200 공개 DTO | 없는/비공개/비활성 판매자 매대404 |

공개 GET 한 경로만 permitAll이다. 나머지 판매자 API의 SELLER 경계와 기존 health 계약은 유지한다. 응답은 no-store, 업무 오류는 기존 code/message/requestId다. 공개 DTO에는 관리 ID·version·회원 UUID가 없다. 주소·소개·공지는 의도된 공개 필드다.

쓰기 순서는 identity.api.SellerMembership을 통한 회원 잠금→본인 매대 잠금→버전 확인→저장이다. seller가 회원 SQL을 직접 소유하지 않는다. 공개 조회는 AccessPolicy로 현재 ACTIVE SELLER 여부를 확인한다. 조회와 판매자 상태 변경 전체를 하나의 직렬화 거래로 잠그지는 않으므로, 공개 요청과 동시에 정지/비공개가 일어나는 모든 순서를 보장하는 의미는 아니다. 후속 거래 실행 시의 자격 검사와 이 공개 조회는 별개다.

React StoreEditorStore는 인증 변화 시 매대 상태를 비우고 요청을 취소한다. 저장 전 CSRF를 얻고 읽은 version을 전송한다. 409나 통신 실패에 POST/PUT을 자동 재전송하지 않으며 다시 불러오도록 안내한다. 공개 화면은 slug나 재시도 번호가 바뀌면 이전 내용을 숨기고 이전 응답을 무시한다. 문자열은 React 텍스트로 출력하고 이미지 키로 네트워크 요청을 하지 않는다.

- 최종 빌드의 기존 health·헤더·라우팅 브라우저18개도 통과했다. [회귀 로그](evidence/P03-B-health-browser.txt), [프런트 결과 요약](evidence/P03-B-frontend.txt).

- [공개 모바일 화면](evidence/P03-B-public-mobile.png), [관리 모바일 화면](evidence/P03-B-editor-mobile.png)을 보존한다. 캡처는 화면 전체 높이의 모든 필드를 보장하지 않는다.

## 재현·학습·제한

새 이름으로 `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p03-b-새로운이름 -Offline -RunBrowser`를 실행한다. 기존 DB를 업데이트하지 않으며 생성된 검증 DB도 유지한다. 기본 도구와 보호 규칙은 [로컬 실행](../local-development.md)을 따른다.

학습 포인트는 폼 입력→StoreEditorStore→CSRF→PUT(version)→회원/매대 잠금→SQL→DTO→폼 재표시다. 작은 실습은 한 매대를 두 화면에서 불러온 뒤 각각 다른 공지를 저장하고 두 번째 저장의409를 확인하는 것이다. 자동 동시성 검사는 통과했지만 사용자의 직접 실습/이해 완료로 간주하지 않는다.

이미지 파일 업로드·실제 이미지 표시/소유 검증·상품 목록·매대 검색·운영자 매대 조치·폐점·판매 정지·삭제는 구현하지 않았다. 정지/탈퇴한 소유자의 매대 데이터는 유지하되 공개 조회를 거부한다. 외부 주소 검증이나 실사업자 확인도 하지 않는다. 상용 부하·전체 운영 환경·실제 모바일 기기는 미검증이다. 입력정보는 가상 정보만 사용한다. 기존 서버/DB는 보존하며 현재 화면을 제공하는 기존 서버에 새 스키마를 적용하거나 재시작하지 않았다. P03-C는 진행하지 않는다.
