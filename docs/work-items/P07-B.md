# P07-B 회원 쿠폰 생성·발급·보유 — 구현 작업 계획

> **For agentic workers:** 구현 요청 시 `superpowers:executing-plans`를 사용해 아래 작업을 순서대로 수행한다. 단계 전체 개발 통과 후 지정 검토세션에서 독립 검토한다. 이 문서 작성만으로 구현·다음 단계·커밋을 시작하지 않는다.

**Goal:** 판매자 쿠폰 템플릿과 회원 본인의 발급·보유·조건 확인을 제공하고 비회원·타인 접근을 차단한다.

**Architecture:** 설계의 promotion 모듈이 혜택 데이터와 계산을 소유한다. 기존 identity/seller/catalog 공개 API로 권한과 판매 정보를 확인하고, React는 서버 결과와 입력 상태를 표시한다. 거래 경계·정수 계산·현재 권한 검사를 서버에서 보장한다.

**Tech Stack:** 기존 Java·Spring Boot·Spring JDBC·PostgreSQL·Flyway·JUnit·ArchUnit, React·TypeScript·Vitest·Playwright. 새 프레임워크를 도입하지 않는다.

**Spec:** [요구사항](../requirements.md), [설계](../shop-design.md), [구현 계획](../implementation-plan.md), [P07 공통 계약/검증 절차](P07.md). F08·F02·F03, AC03·AC04·AC05·AC07(발급 한도), AC13(발급 조건 보존).

## 입력·출력·실패 계약

계획 계약은 `Coupons.saveTemplate(UUID actor, UUID id, TemplateInput input): Template`, `claim(UUID member, UUID templateId): Issued`, `owned(UUID member, int page): Page`, `eligible(UUID member, UUID couponId, UUID storeId, long afterPromotionSubtotal, Instant at): Eligibility`다. Page/DTO는 Coupons.api의 값 타입으로 정의한다. eligibility는 확인만 하고 예약하지 않는다. owner는 로그인 세션에서 유도하며 JSON ownerId는 받지 않는다.

템플릿은 매대·정액/정률·할인 상한·최소금액·발급 기간·사용 기간·총한도·version·상태를 가진다. 발급 시 조건과 만료를 복사한다. 발급 중단/템플릿 변경은 기존 발급 쿠폰 조건을 덮어쓰지 않는다. 같은 회원/템플릿 UNIQUE와 한도 조건부 UPDATE를 같은 거래에 둔다. 동일 회원의 재요청은 같은 발급 결과를 반환하고 카운터를 늘리지 않는다. 한도를 이미 발급한 수보다 낮출 수 없다.

예정 HTTP는 판매자 `/api/seller/coupons`, 회원 `/api/account/coupons`, POST `/api/account/coupons/claim`이며 화면 `/seller/coupons`, `/account/coupons`다. 공개 행사와 달리 비회원의 발급/보유/조건 API를 서버에서 거부한다. 회원 ID나 쿠폰 ID 변조도 차단한다. 판매자 역할 회원의 구매 기능은 유지한다.

## 실행 전 계약 점검 — A 독립 검증 대기 중

B 구현은 A의 독립 전체 통과 후 시작한다. 기존 seller/identity 공개 API를 대조한 구현 결정은 다음과 같다.

- Ruling: 발급자는 세션 회원이다. 템플릿의 매대 소유자 ID는 읽기 projection으로 확인하고 회원/판매자 ID를 UUID 문자열 순으로 잠근 뒤 매대, 템플릿을 잠근다. 판매자도 구매자이므로 두 계정을 역순으로 잠가 교차 발급 시 교착하지 않도록 한다. 타 모듈 테이블에는 쓰지 않는다.
- Ruling: 동일 회원/템플릿의 이미 성공한 발급 재요청은 본인 활성 자격 확인 후 같은 스냅샷을 반환한다. 템플릿 중지·발급기간 종료는 새 발급만 막는다. 기존 쿠폰 사용 가능 여부는 별도의 현재 판매 자격·사용 기간·최소금액·보유 상태 검사다.
- Ruling: 발급 당시 title/kind/value/cap/minimum/useStart/useEnd/templateVersion을 발급행에 복사한다. 이후 템플릿 관리와 발급 카운터는 이를 수정하지 않는다. 예약용 state/version은 D에서만 변화시킨다.
- HTTP 입력 금액과 한도는 A처럼 JS 안전 정수 범위로 제한한다. 내부 계산은 long을 사용하며 C의 견적 금액은 문자열 계약으로 별도 표시한다. totalLimit는 양수, 이미 발급한 수보다 작게 수정할 수 없다.
- 회원의 받을 수 있는 템플릿 목록을 위해 `/api/account/coupons/available` 읽기 API를 추가한다. 최대20개 페이지와 현재 발급 가능 필터를 사용한다. 보유 목록은 발급 당시 조건과 만료 상태를 표시하며 비회원·다른 회원 조회를 허용하지 않는다.
- 조건 확인 HTTP는 서버 계산 전 안내다. 임의 subtotal 입력에 대한 eligibility 응답은 예약/주문 권한이 아니며 C는 서버 가격으로 다시 계산한다. D는 서버 Quote와 현재 자격을 재검증한다.

위 결정은 기존 계획 제안의 구체화이며 사용자 확정 정책으로 소급하지 않는다. 구현/실행 결과는 아직 없다.

- API 대조 주의: SellerMembership.lockActiveBuyer는 비활성/BUYER 없음에 예외를 던지며 반환 boolean은 SELLER 보유 여부다. false를 구매 불가로 오해하지 않는다. 이미 발급된 쿠폰 재요청은 별도 본인 잠금 경로로 처리하고, 새 발급만 정렬된 구매자·판매자 잠금을 획득한다. 존재하지 않는 재요청 조회가 신규 발급의 잠금 순서를 바꾸지 않도록 구현한다.
