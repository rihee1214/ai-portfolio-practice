# P01-E1 요청 ID 생성·전달

2026-10-23 / 상태: 구현·자동 검증·독립 검토 완료

## 범위와 완료 계약

기준 커밋 `63fba6f`. P01-E의 첫 작업은 요청 ID 기반만 구현한다. 후속 공통 업무 JSON 오류·React 표시·설정 검증·Actuator 정책·ArchUnit은 제외한다. 기존 health body/HTTP 계약을 유지한다. 테스트 우선 개발과 완료 전 검증 스킬을 적용한다.

| 항목 | E1 계약 |
| --- | --- |
| 생성 | 애플리케이션 필터에 도달한 요청마다 서버 UUID v4 한 개 생성 |
| 외부 입력 | X-Request-ID는 유효한 UUID·잘못된 값·중복 헤더여도 읽거나 재사용하지 않음 |
| 응답 | X-Request-ID 헤더 한 개. health JSON을 감싸거나 기본 오류 JSON에 필드를 추가하지 않음 |
| 요청 범위 | `com.example.marketplace.requestId` 요청 속성에 보관, ERROR/ASYNC 재디스패치에도 같은 ID |
| 로그 문맥 | 디스패치 실행 스레드의 MDC `requestId`에 설정, finally에서 원래 값 복원 또는 해당 키만 제거 |
| 최소 로그 연계 | 기본 로그 level 패턴에 `[requestId=...]` 표시. 요청 안에서 발생한 기존/후속 로그가 활용. 매 요청 access log나 별도 구조화 로그는 추가하지 않음 |
| 완료 증거 | 실제 HTTP200/404/405/500, 외부 ID 무시, ID 유일성, 요청 속성·MDC·로그 일치, 실제 ERROR/ASYNC 재진입, 정상/예외 정리 및 기존 회귀 검사 |

계획: 계약을 테스트로 작성 → 미구현 실패 확인 → platform/web 필터·등록과 최소 로그 패턴 구현 → DB 없는 전체 verify → 보존·제한·실습 기록 → 로컬 커밋으로 지정 검토세션에 인계한다.

## 구현과 선택 근거

`RequestIdFilter`는 요청 속성에 값이 없을 때만 생성하고 응답 헤더에 설정한다. 외부 요청 헤더를 읽지 않아 발신자가 로그 상관 ID를 정하거나 개인정보/임의 문자열을 주입하지 못하게 한다. 아직 신뢰할 프록시 계약이 없으므로 외부 ID 전달을 허용하는 설정을 추가하지 않았다. UUID는 인증·권한·중복방지 키가 아니다.

`RequestIdConfiguration`은 필터를 한 번만 등록한다. `/*` 기본 매핑과 높은 우선순위, REQUEST/ERROR/ASYNC, asyncSupported를 명시한다. 단일 최초 요청 필터링만으로 끝내지 않고 오류/비동기 디스패치에서 MDC를 다시 묶는다. 오류 응답 reset으로 헤더가 지워진 경우 재설정할 수 있다. ServletRequest 속성은 외부 HTTP 헤더와 별개인 서버 내부 상태다.

MDC는 스레드 기반이므로 요청마다 finally에서 정리한다. 다른 MDC 키를 지우지 않고 기존 requestId 값도 복원하여 중첩 실행의 바깥 문맥을 보호한다. 속성은 오류/비동기 재디스패치를 위해 요청 수명 동안 유지하며 전역 Map에 보관하지 않는다.

최소 로그 패턴은 `logging.pattern.level`에 설정했다. 테스트 전용 controller의 INFO 로그를 캡처하여 응답 헤더와 같은 ID가 출력되는지 확인한다. 테스트 probe controller·observer는 src/test에만 존재한다. 제품 업무 endpoint나 공통 오류 handler는 추가하지 않았다.

공식 근거: [Spring Boot FilterRegistrationBean](https://docs.spring.io/spring-boot/api/java/org/springframework/boot/web/servlet/FilterRegistrationBean.html), [SLF4J MDC](https://www.slf4j.org/apidocs/org/slf4j/MDC.html). 공식 최신 API 문서와 함께 실제 프로젝트 Boot4.1.1 컴파일·실행으로 호환성을 확인했으며 버전 업그레이드는 하지 않았다.

## 검증 결과

- [RED](evidence/P01-E1-red.txt): 기존 코드에서 실제 HTTP 검사5개가 모두 헤더0개로 실패했다. 컴파일/환경 오류를 기능 실패로 계산하지 않았다.
- 첫 구현 후43개 전체 통과. 이후 실제 ERROR/ASYNC 디스패치 관찰 필터와 async HTTP 검사를 추가했다.
- [최종 verify](evidence/P01-E1-verify.txt): 기존33개 + 새11개 = **44개**, 실패·오류·skip0, Checkstyle·컴파일·패키징 통과.
- 새 HTTP6개: 요청마다 다른 UUID/health body 유지, 외부 유효·잘못된·중복 ID 무시,404/405, 요청 속성/MDC/로그 동일, 실제 예외500 ERROR 디스패치, 실제 Callable ASYNC 디스패치. 테스트 observer가 해당 디스패치 내부의 속성/MDC를 직접 비교하여 초기 응답 헤더만 검사하는 한계를 보완한다.
- 새 필터5개: 같은 스레드의 연속 요청 분리 및 타 MDC 키 유지, 예외 시 바깥 문맥 복원, 예외 시 ID 제거, ERROR/ASYNC 재진입에서 동일 ID와 reset 후 헤더 재설정.
- [검사 집계](evidence/P01-E1-summary.json)와 [패키지 확인](evidence/P01-E1-package.txt)을 남겼다. 배포 JAR에 테스트 클래스/probe controller가 포함되지 않음을 확인했다. 로그는 행 끝 공백과 마지막 빈 줄만 정리했다.
- 기존 정상/장애 health·기본 오류 검사가 그대로 통과했다. 프런트 변경이 없으므로 브라우저/Node 검사를 반복하지 않았다. DB 통합 프로필도 실행하지 않았다.

의도적으로 발생시킨 `intentional-e1` 예외 stack trace와 기존 Mockito 동적 agent 경고는 시험 로그에 포함되지만 검사 실패와 구분한다. 응답 본문에는 해당 예외 메시지가 없음을 단언한다.

## 보존과 한계

[현재 포트](evidence/P01-E1-ports-before.json)와 [보존 확인](evidence/P01-E1-preservation.json):8080/4174/5174 기존 앱은 이번 확인 시에도 미실행이었다. 과거 PID를 가정하지 않았다. Docker 컨테이너 ID·healthy와15432/15433의 PID57168은 유지된다. 읽기 전용 DB 덤프 정규화 해시는 D4 종료 증거와 동일하다. DB 생성·쓰기·초기화·컨테이너 조작은 없다. 자동 검증은 RANDOM_PORT의 소유 테스트 서버만 사용했고 build 경로도 `.local-tools/e1-*`로 분리했다.

현재 실행 차단 항목은 없다. 다음 제한은 완료 범위에 포함해 기록한다.

- 필터 이전의 HTTP 파싱 거부나 프록시 자체 오류에는 애플리케이션 요청 ID를 보장하지 않는다. 임의 downstream 코드가 헤더를 덮거나 최종 응답을 reset하는 모든 상황을 강제 봉쇄하는 response wrapper는 만들지 않았다.
- ASYNC **디스패치**의 MDC를 검증했다. Callable 내부의 작업 스레드·@Async·스케줄러로 MDC를 자동 전파하지 않는다. 분산 tracing/traceparent와 외부 서비스 전파도 미구현이다.
- 컨테이너가 필터 바깥에서 남기는 로그는 ID가 없을 수 있다. 매 요청 access log·완료 로그·구조화 로그·로그 수집은 이 단계의 보장이 아니다. 스레드 간 동시 요청의 부하 시험은 하지 않았다.
- 헤더만 추가한다. 공통 업무 오류 body requestId, React 표시, CORS expose-header 정책, 관리 endpoint 정책은 후속 별도 작업이다.
- UUID의 충돌 가능성은 확률적이며 테스트로 전역 유일성을 증명한 것은 아니다. 사용자 직접 이해·실습은 미확인이다.

## 실행과 작은 실습

프로젝트 루트 PowerShell에서 기존 로컬 JDK/Maven을 사용한다. 아래 verify는 DB 프로필을 활성화하지 않는다.

```powershell
$previousJava = $env:JAVA_HOME
$previousMaven = $env:MAVEN_USER_HOME
try {
  $env:JAVA_HOME = Join-Path $PWD '.local-tools/jdk-21.0.12.1+1'
  $env:MAVEN_USER_HOME = Join-Path $PWD '.local-tools/m2'
  ./backend/mvnw.cmd -f backend/pom.xml "-Dmarketplace.build.directory=$PWD/.local-tools/e1-build" verify
  if ($LASTEXITCODE -ne 0) { throw 'Verification failed' }
} finally {
  $env:JAVA_HOME = $previousJava
  $env:MAVEN_USER_HOME = $previousMaven
}
```

코드 흐름은 HTTP 요청 → 필터의 ID 생성/속성 저장 → 헤더/MDC 설정 → controller/health → finally 정리다. 오류는 같은 요청의 ERROR 디스패치에서 동일 ID를 다시 묶는다. 작은 실습으로 RequestIdHttpTest의 외부 문자열 `untrusted`를 다른 문자열로 바꿔도 서버 ID가 새로 생성되는지 실행해 본다. 다음으로 테스트의 기대값만 외부 값과 같다고 바꿔 실패를 확인하고 원복한다. 운영 코드·DB 수정은 필요 없다.

[독립 검토](P01-E1-review.md)에서 44개 검사를 재실행하여 모두 통과했고 필수 수정 결함은 발견하지 않았다. 구현 커밋 `08800c0`에 대한 검토 문서·검증 요약·상태 변경을 최종 로컬 문서 커밋에 포함했다. 추가 코드 수정은 없으며 독립 실행 보고서와 요약의 44개 통과를 개발세션에서도 대조했다. 다음 E 작업·프런트 단순화·원격 push는 진행하지 않았다.
