## R1 — 이메일 확인 토큰의 잠금 대기 중 만료

**정적 결함 후보와 필수 경계검증 공백. 이번 점검에서 실제 재현 실행은 하지 않았다.**

`SignupService.verifyEmail` 84행은 `clock.instant()`를 먼저 읽고 `consumeAndActivate`에 Instant 값을 전달한다. `JdbcIdentityStore.consumeAndActivate` 31~46행은 토큰 UPDATE의 `expires_at > :now` 및 활성화 시각에 그 값을 사용한다. 토큰 행 잠금을 기다린 뒤 현재 시각을 새로 읽는 절차가 없다.

예상 경로는 다음과 같다. 미소비 토큰 행을 다른 트랜잭션이 잠근 상태에서 만료 직전 확인 요청이 들어오면 유효한 시각이 매개변수로 고정된다. 대기 중 만료가 지나고 잠금이 토큰 소비 없이 해제되면 고정된 과거 시각으로 소비·활성화될 수 있다. 만료된 토큰으로부터 회원을 보호한다는 A1 계약의 경계다. 공격 가능성이나 실제 피해를 재현한 것으로 표현하지 않는다.

`expiryBoundaryIsExclusiveAndExpiredTokenRemainsUnconsumed`는 잠금 대기 없이 1799초 허용/1800초 거부를 검사한다. `concurrentTokenConsumptionHasExactlyOneSuccess`는 첫 요청이 토큰을 소비한 경쟁만 검사한다. 둘 다 잠금만 보유했다가 만료 이후 풀어 주는 상황은 포함하지 않는다. B의 `recoveryRechecksExpiryAfterWaitingForMemberLock`은 복구 토큰 저장소에만 해당한다.

필요한 보완은 새 격리 DB에서 토큰 잠금을 실제로 잡고 대기 진입을 확인한 뒤 가변 Clock을 만료 경계로 옮기는 검사다. 거부·미소비·PENDING_EMAIL 유지 및 기존 정상/중복 소비 회귀를 확인해야 한다. 구현 수정이 필요하면 잠금 획득 후 시각을 판단하도록 하되 기존 상태 변경의 잠금 순서와 충돌도 고려한다. 현재 요청은 점검이므로 이 문서에서 수정하거나 새 DB를 생성하지 않았다.

이 항목은 뒤 단계 기능으로 미룰 사항과 구분한다. 기존 단계의 통과 기록은 유지하되 이번 전체 점검에서 새로 확인한 잔여로 남긴다. 기존 검사가 모두 통과했다는 이유만으로 R1을 해결로 표시하지 않는다.

## 최신 실행 증거와 해석

[D 최종 집계](evidence/P02-D-review-summary.json)는 Java 기본130·DB통합46, 실패/오류/skip 0이다. [브라우저](evidence/P02-D-review-browser.txt)는 PC6+모바일6 총12 통과이며 Java 수에 합산하지 않는다. [프런트 단위](evidence/P02-D-vitest.txt)는73 통과, [P01 회귀](evidence/P02-D-p01-browser.txt)는16 통과다. 130·46·12와 별도73은 직전 이 세션에서도 독립 실행했으며, P01 16·타입·린트·빌드는 개발세션 결과다. 이번 점검에서 재실행한 것으로 표현하지 않는다.

D 당시 429 검사 간섭은 Java/Playwright의 소스 IP 창 분리 후 통과했고, 독립 첫 실행의 로컬 연결 권한 오류도 허용된 환경에서 재실행해 해소됐다. 현재 미해결 실행 차단으로 다시 계산하지 않는다. Node 전송·프록시68 검사는 D에서 재실행하지 않았으며 최신 전체 테스트 합계에 끼워 넣지 않는다.

- F01의 실제 거래 보존은 D의 참조 fixture 근거까지다. 실주문·결제·정산 보존과 보관 기간은 거래 단계에서 검증한다. 쇼핑몰 전체 완료나 첫 구매 완료를 뜻하지 않는다.
- F07 중 이번 범위는 배송지 기반이다. 장바구니·찜·구매 단계의 배송지 선택은 후속이다. AC11의 판매자 정지와 운영 권한 관리 업무 전체, AC16의 다른 환경 실행·수동 시연까지 완료한 것은 아니다.
- 외부 이메일 발송, 재발송 UI, 재시작 후 메모리 메일 보존은 구현하지 않았다. 수동 디버거 메일 확인 절차는 문서에 있으나 직접 시연은 미검증이다. 이는 현재 로컬 테스트 메일함 선택의 한계이며 이번에 상용 메일을 추가해야 한다는 판정은 아니다.
- 실제 HTTPS·전체 production 인증 화면, 분산 요청 제한·운영 부하·모든 경쟁 순서·서버 재시작 시 세션 직렬화 호환성·사용자 직접 실습/이해 확인은 미검증이다.
- 운영자 계정 인계/권한 편집 UI, 판매 신청·승인·판매 정지, 통합 운영 조치 화면은 후속 범위다. P02의 최초 운영자 명령과 접근 검사만으로 해당 업무를 완료 처리하지 않는다.
