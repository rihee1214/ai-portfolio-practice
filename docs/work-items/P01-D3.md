# P01-D3 화면 입력·비동기 상태 검사

2026-10-23 / 상태: 구현·검증·독립 검토 완료

## 범위와 판단

기준 커밋 `9630fae`의 설계·작업 계획에 따라 Vitest와 React Testing Library를 추가한다. 실행 계획·검증 스킬을 적용하고 개발 검토는 사용자가 지정한 **검토 및 반영세션**에서 진행한다. 기존 기능의 회귀 검사가 목적이며 업무 기능·P01-D4 이후는 구현하지 않는다.

1. 기존 화면과 HTTP 상태 흐름을 확인하고 테스트 도구의 호환 조건을 조회한다.
2. 독립 Vitest 설정과 테스트 정리를 추가한다. `test:unit`은 한 번 실행하고 종료한다.
3. 실제 HomePage/HealthPanel과 실제 health/http 모듈을 렌더링한다. fetch 경계만 모의 처리하여 입력·로딩·오류·늦은 응답을 검증한다.
4. 늦은 응답 보호를 임시 제거하는 통제 실험 후 원복하여 검사 탐지력을 확인한다.
5. 타입·린트·빌드·기존 Node 검사와 DB 보존을 확인하고 지정 세션에 검토를 요청한다.

판단: 사용자 입력은 이미 구현된 매대 이름과 연결 확인 버튼을 사용한다. 테스트용 구매/로그인 폼은 만들지 않는다. 브라우저 자동화와 실제 API·DB 연결 증거는 D3 DOM 검사와 구분한다.

공식 참고: [Vitest 시작](https://vitest.dev/guide/), [Testing Library 설정](https://testing-library.com/docs/react-testing-library/setup/).

독립 `vitest.config.ts`는 실제 API 프록시 플러그인을 로딩하지 않는다. 테스트 파일을 `tests/unit/**/*.test.tsx`로 제한하여 기존 `node:test`와 섞이지 않는다. 각 테스트 후 DOM 정리, global mock 복원, spy 복원을 수행한다. 기본 fetch는 실제 네트워크 대신 차단 모의 함수이며 개별 테스트가 응답을 명시한다. HomePage 검사는 fetch 호출 0건도 단언한다. 테스트 코드와 설정은 TypeScript 검사에 포함한다.

## 사용자 관점 검사 14개

- 매대 이름 입력·미리보기·초기화, 공백 안내·30자 제한, 다시 마운트할 때 초기화: 3개.
- 초기 상태·요청 없음·키보드 시작·로딩·정상 응답·취소 버튼 활성 상태: 1개.
- 503 DOWN·500·잘못된 스키마·HTML·깨진 JSON 안내와 성공 재시도: 5개.
- 통신 실패 후 재시도: 1개.
- 재요청 이후 이전 응답이 최신 요청 로딩 중/성공 후 도착하는 두 순서: 2개.
- 취소 후 늦은 성공 응답 무시·재시도: 1개.
- 화면 해제 시 AbortSignal 중단 및 이전 응답과 새 화면 분리: 1개.

HealthPanel은 StrictMode로 마운트한다. 응답은 임의 sleep 대신 deferred Promise로 제어한다. 모의 fetch가 AbortSignal을 무시하도록 해도 실제 HTTP/health 보호가 화면에 적용되는지 검사한다. 새 화면 재마운트 검사는 실제 브라우저 새로고침이나 라우팅 검사를 대체하지 않는다.

화면 해제 검사는 요청 중단과 새 화면의 표시 상태를 검증한다. 해제된 컴포넌트 내부의 콜백 호출 횟수 자체는 이 DOM 검사로 증명하지 않는다. 별도의 기존 `tests/health.test.mjs`가 dispose 이후 publish 호출 수가 증가하지 않는지 검증하며, 이번 Node 68개 실행에 포함된다.

## 코드 흐름과 직접 실습

매대 이름은 입력 이벤트 → HomePage의 React 상태 → 미리보기 문구 순서로 반영한다. 연결 확인은 버튼 → createHealthCheck → requestJson → fetch → 응답 분류 → React 상태 → 안내 문구 순서다. D3는 마지막 fetch만 모의 처리하므로 Java API나 SQL을 통과하지 않는다. `act`는 모의 응답을 처리한 React 화면 갱신을 기다리고, deferred Promise는 원하는 순서에 응답을 도착시키는 도구다.

작은 실습: HomePage.test.tsx의 입력 예시 ‘우리 매대’를 다른 이름으로 바꾸고 기대 문구도 맞춘 뒤 `test:unit`을 실행해 본다. 다음으로 기대 문구만 일부러 다르게 적어 실패 메시지를 확인하고 원복한다. 제품 코드나 DB는 수정할 필요가 없다. 자동 검사 통과와 사용자의 직접 실습·이해 여부는 별개이며 직접 실습은 아직 미확인이다.

기존 코드는 첫 실행부터 14개를 통과했다. 새 제품 결함을 수정한 RED→GREEN으로 주장하지 않는다. [통제 실험](evidence/P01-D3-mutation.txt)에서 health의 요청 순번 조건만 임시 제거했을 때 늦은 응답 검사 2개가 실패(12개 통과)했다. finally로 원문을 복원했고 제품 소스 최종 차이는 없다.

## 실행과 증거

프로젝트 루트 PowerShell에서 실행한다. 전역 Node 설정을 바꾸지 않는 기존 래퍼를 사용한다.

```powershell
./frontend/npm.ps1 run test:unit
./frontend/npm.ps1 test
./frontend/npm.ps1 run typecheck
./frontend/npm.ps1 run lint
./frontend/npm.ps1 run build
```

- [화면 검사](evidence/P01-D3-unit.txt): 14개 통과, 실패·skip 0.
- [기존 Node 검사](evidence/P01-D3-node.txt): 68개 통과, 실패·취소·skip 0. 실제 로컬 프록시 검사를 포함하며 Spring/DB 연동 검사와는 다르다.
- [타입](evidence/P01-D3-typecheck.txt), [린트](evidence/P01-D3-lint.txt), [빌드](evidence/P01-D3-build.txt): 모두 종료 코드 0으로 통과.
- [DB 보존](evidence/P01-D3-preservation.json): 기존 개발/테스트 DB의 정규화 덤프 SHA256은 D2 최종 기록과 동일하다. 무작위 restrict/unrestrict 토큰만 제외하고 원문은 저장하지 않았다. 기존 컨테이너 ID와 healthy 상태를 확인했다. D3는 DB 생성·쓰기·초기화·재시작을 하지 않았다.

기록 텍스트는 행 끝 공백과 마지막 빈 줄만 정리한다. 실제 서버·모바일 화면·브라우저·스크린리더 발화·사용자 직접 실습은 이번 단계에서 미검증이다. 설치·검사 실행 차단 항목은 없다. D4 이후에는 착수하지 않는다.
