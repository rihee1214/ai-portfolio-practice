# P08-A 주문 모델·상태·스냅샷 — 구현 작업 계획

> **For agentic workers:** 구현 요청 시 `superpowers:executing-plans`로 작은 작업을 순서대로 수행한다. 개발 전체 통과 후 지정 검토세션에서 독립 검토한다. 이번 문서 작성은 구현/커밋 승인이 아니다.

**Goal:** 부모/하위/항목과 구매자·수령인 스냅샷의 불변 조건을 저장 모델과 API 계약으로 확정한다.

**Architecture:** order 모듈이 주문 데이터와 상태를 소유한다. 순수 상태/금액 검증과 JDBC 저장을 분리하고 외부 예약·결제 실행은 아직 연결하지 않는다.

**Tech Stack:** Java/Spring Boot·Spring JDBC·PostgreSQL·JUnit/ArchUnit·React/TypeScript·Vitest/Playwright.

**Spec:** [설계](../shop-design.md) §4·7~11·13~16, [요구사항](../requirements.md) F05/F09/F10/F11·AC01~04/07/08/13, [구현 계획](../implementation-plan.md) §10, [P08 전체 계약](P08.md).

상태: 계획 작성 / 구현·검증 미착수. 선행: **P07 로컬 마감**.

## Global Constraints

[P08 공통 정책·인계·검증](P08.md)을 모두 적용한다. 기존 서버·DB·검증DB·미디어·데모·실패 기록은 보존하고 새 격리 경로만 쓴다. 아래 파일/API/검사명은 예정이며 구현 존재/통과를 뜻하지 않는다. 새 정책 수치는 제안으로 구분하고 착수 계약에 채택 이유를 기록한다.

## 범위와 제외

예약 실행·실제 주문 생성 API·결제 승인·배송/클레임은 제외한다. A 테스트용 저장 fixture를 실제 구매 완료로 표시하지 않는다.

## Interfaces와 세부 계약

소비: `Quotes.Quote`의 policyVersion·혜택 버전·상품/옵션·단위별 배분. 생산: 소유자/모드/상태를 분리한 OrderSnapshot 및 후속 API 입력·출력·오류 표. 예정 HTTP는 C의 POST `/api/orders`(구매 세션+Idempotency-Key, SKU/수량/쿠폰 선택·견적 지문·수령 정보), F의 GET `/api/orders/{orderNumber}`. 회원/GuestBuyer ID·서버 금액·DEMO/SANDBOX는 클라이언트 확정 입력으로 받지 않는다. 잘못된 입력400, 인증401, 접근거부403/타인 식별자404, 다른내용 동일키/견적변경409를 구분한다.

기존 `guest_checkout`와 신규 주문 CheckoutSession의 식별자·수명·1:1 연결을 먼저 문서화한다. 같은 브라우저의 두 주문 시도와 P07의 checkout당 한 coupon batch가 충돌하지 않도록 주문 시도 식별자를 고정한다. 게스트 인증 세션을 그대로 여러 coupon batch의 checkoutId로 재사용하지 않는다. 구매 세션 자체를 주문 소유권으로 취급하지 않는다. 현재 guest 연결 API/권한 추출은 C가 수행한다.

Order 상태 PENDING_PAYMENT/PAID/CLOSED/CANCELED/EXPIRED, 결제/배송 상태는 별도다. A는 허용 전이 표와 DB 불변 조건만 만들고 실제 결제/종료 업무는 D/P09가 구동한다. 수량별 할인과 배송 할인은 서로 분리하고 부모/매대/항목 합계가 일치한다. 주문번호는 예측 불가능한 값·unique와 충돌 재발급 경로를 가진다.

### 독립 사전 검토에 따른 구체화

- R-A01: 위 계획의 guest_checkout와 주문 CheckoutSession의 1:1 표현을 정정한다. 실제 guest_checkout 행은 재시작 때 재사용되므로 브라우저 구매 세션→여러 주문 시도 관계다. 성공 게스트 주문 시도는 소비한 `guest_attempt.id`를 불변으로 보관한다. 해당 인증 attempt는 최대 한 주문에 연결한다. guest_checkout.current_attempt 변경은 이미 저장된 주문 연결을 바꾸지 않는다. 동일키 재조회는 저장된 시도/요청hash/현재 소유권으로 판정하고 성공 인증을 재소비하지 않는다(C 검증). A04는 별도 시도 및 연결 보존을 검사한다.
- R-A02: A02에 `units.size == quantity`, 0기반 연속 ordinal, 주문 전체 SKU 중복 금지, 단위 할인 비음수와 gross−상품할인−쿠폰할인=net을 추가한다. 잘못된 스냅샷을 저장하기 전에 거부하여 관련 행0을 확인한다.
- R-A03: A01/A04에 DEMO/SANDBOX allowlist·null/알수없는모드 DB 거부·두 모드 저장/재조회·이후 설정과 무관한 저장값 보존을 연결한다. 클라이언트 모드 변조는 C의 HTTP 권한 검사다.

### 구현과 실제 검사 연결 (전체·독립 검증 진행 중)

V31은 주문 시도/부모/매대별 하위 주문/항목/단위/연락처6개 테이블을 추가한다. 주문 소유자 XOR·키/번호/매대/SKU/단위순번 unique·행 금액과 기한 CHECK를 DB가 검사한다. 여러 행의 합계/단위 개수/연속 순번은 저장 전 OrderRules가 검사한다. `JdbcOrders`는 REQUIRED 거래에 참여하여 모두 저장하며 요청 키 충돌을 DB로 직렬화한다. 원천 catalog/혜택을 다시 읽어 과거 값을 덮지 않는다.

계획의 별도 domain `OrderSnapshot.java` 대신 공개 DTO `Orders.Snapshot`을 사용한다. API→domain 의존과 중복 모델을 피하고 immutable Quote·Contact·SellerOrder/Item을 제공한다. `Orders.save/find`는 신뢰된 내부 포트다. 구매 자격/현재 견적/예약 통합·HTTP 소유권은 C/F의 책임으로 이번 저장 fixture를 실제 구매 완료로 표시하지 않는다. 번호는 무작위 UUID 기반이며 충돌 시 같은 거래에서 최대5개 후보, 소진 시 전체 rollback한다.
