### full1 후 수정·집중 근거

[guest 분석](../../.local-tools/p12-c-guest-failure-analysis-20261115.md)은 관측된 CSRF_TOKEN 중복 INSERT와 초기 세션 응답 순서 경합 가설을 구분한다. fresh context의 빈 장바구니를 원인으로 확정했던 추정은 철회했다. 서버 세션 저장/인증 정책을 변경하지 않고 GuestStore.load의 정상200/초기409 판정과 GuestPage의 초기 조회→동일 세션 CSRF 확인→입력 준비 순서를 명시했다. 실패·지연·화면 이탈에서는 준비 상태를 열지 않는다. 기존 브라우저의 동시 POST 두 건200 및 업무 deadline은 유지하며 첫 업무 안에서 실제 enabled 준비 조건을 기다린다. 새9개 준비 assertion을 포함한 관련24단위와 타입·린트가 통과했고 실제 브라우저 재검증은 대기다.

R1은 실제 NGINX에서 위조 Prefix가 상류에 남는 의도 RED를 확보한 뒤 Prefix/Ssl 제거와 실제 JAR·브라우저의 위조 헤더 조건을 보완했다. R2는 기존 deadline-core를 변경 없이 재사용해 공유 절대기한·자식 명령/요청 abort·부모 phase 감시·소유 자원 회수와 원실패/정리 오류 기록을 연결했다. [.local-tools/p12-c-r2-focused2-20261115](../../.local-tools/p12-c-r2-focused2-20261115/result.json)는 짧은 합성기한 회귀4건과 실제 NGINX8업무 통과다. focused1의 종료 중 ClientRequest 잔존 검출 실패1회는 close 완료 대기를 보완해 해결했으며 원실패를 보존한다. 합성 timeout/자식 실패의 예상 발생을 개발 실패로 합산하지 않는다. 이 집중 통과는 후속 통합 전체·독립 재검토를 대신하지 않는다.

### focused5 결과·잔여 준비 보완

[focused5](../../.local-tools/p12-c-focused5-46d1101d7c99427a9b1697afce348e90/result.json)는 browser-api/package-runtime 선택으로708.135초 후 `failed`, 보존 `passed`다. 공통 Java263 및 기존 브라우저178건은 실패/skip 없이 통과했고, 이전 guest desktop/mobile 동시 POST200 회귀를 확인했다. 패키지는 구형 번들용 두 번째 프록시 준비 중 Docker의 `all predefined address pools have been fully subnetted`로 실패해 이번 패키지 브라우저10건은 미실행이다. [원 준비 오류](../../.local-tools/p12-c-focused5-46d1101d7c99427a9b1697afce348e90/db/groups/package-runtime/legacy-proxy-start.txt)를 보존한다. 기존 네트워크/DB를 삭제하거나 전역 daemon 설정을 바꾸지 않고 새 검사 소유 네트워크의 충돌 없는 주소 할당을 보완한다.

[수정 독립 재검토](../../.local-tools/p12-c-implementation-review-20261115/review-fix.md)는1001입력 일치와 R1/guest 단위·정적/NGINX 근거의 적합성을 확인했지만 같은 R2의 child exit 이후 stdio close 이전 실패 로그 복구 경합을 잔여 필수로 남겼다. 기존 정리10초 안에서 close를 확인하고 잘못된 phase 숫자/형식의 감시 우회도 차단한다. 이는 최초 R1/R2 두 결함 중 R2의 잔여 보완이며 새 사용자 업무를 추가하는 것이 아니다. 필수 보완을 요청한 독립 검토는 최초 검토와 이 수정 재검토를 구분해 기록하고 최종 수용으로 표현하지 않는다.

R2 잔여와 네트워크 준비 보완의 [최종 집중 결과](../../.local-tools/p12-c-r2-ipam-final1-20261115/result.json)는 통과다. 기존4개에 malformed progress 거부를 더한 음성5개, 주소 선택 수학5 assertion, 실제 NGINX8업무를 확인했다. 부모는 child close 후 출력 복구·stdio 오류를 수집하고 phase kind/정수 시각/ID를 검증한다. `ProxyNetwork.ps1`은 Docker subnet/호스트 IPv4 경로를 읽고 default 경로를 제외해 충돌 없는 새 RFC1918 /28을 명시하며, 누락 inventory는 거부하고 생성 경합은3회 한정한다. 기존 네트워크 삭제와 daemon 변경은 없다. 초기 Docker 전체 목록과 개별 실행의 IPv4 subnet inventory는 시점·집계 범위가 다르므로 같은 개수로 단정하지 않는다. 최종 집중 실행의 network-inventory-1.json은 기존34개와 새 /28 하나를 구분해 기록한다. 주소 선택 검사 작성 중 PowerShell 배열 modulus 괄호 누락으로 실패한 개발 검사1회는 수정 후 통과했고 원본을 보존한다. 실제 패키지는 새 focused6에서 재검증 중이며 최종 전체는 아직 남아 있다.

| Java | `backend/pom.xml`: Java21, Boot4.1.1, executable JAR | 같은 소스에서 한 번 만든 JAR/hash를 API·worker에 사용. 새 프레임워크·모듈 분리 없음 |
| DB | `application-db.properties`: 필수 DB 환경값, pool5, Flyway validate/clean 금지; `DatabaseSettingsConfiguration`은 누락값을 비밀 없이 거부 | 전용 demo DB/user/schema·volume, 기존 dev/test와 분리. 이행 단일 실행과 앱 시작 순서는 P12-D에 전달 |
| worker | `application-worker.properties`: web type none·enabled=true; 기본은 enabled=false; `WorkerConfiguration`은 db+enabled 조건 | API=`db`, worker=`db,worker`가 기본 역할. 같은 JAR/DB, worker는 HTTP 포트 없음. 필요한 제공자 설정은 양쪽 동일. 역할별 전체 bean 기동은 패키지 검사 필요 |
| 파일 | `MediaConfiguration`: `MEDIA_ROOT`와 DB `media_namespace` 사용 | API·worker에 같은 지속 media root/namespace. 정적 서버에서 직접 노출하지 않음. 이미지/비공개 첨부는 기존 API 권한을 거침 |
| 세션 | `AuthConfiguration`: JDBC session, SESSION HttpOnly/Secure 기본 true/SameSite=Lax/path `/`; local-http만 secure=false | HTTPS 단일 origin에서 쿠키/CSRF 유지. 공개에 local-http 금지; 이를 강제하는 종합 공개 시작 가드는 아직 없음 |
| 전화 | `LocalPhonePolicy`: disabled 또는 local-test+127.0.0.1, prod/production에서 local-test 거부 | 이 제한은 실제 존재. 프록시 뒤 loopback이라고 공개 안전한 것은 아님. 기존 로컬 전화 검증을 인터넷에 그대로 연결하지 않음 |
| 메일·결제 | `IdentityLocalConfiguration`은 db & local-mailbox에서 활성화. payment/refund dispatcher는 DEMO/SANDBOX. Toss는 test_sk 키와 공식 HTTPS endpoint 제약 | **종합 demo/production 시작 가드·실제 메일 제공자는 미구현**. prod라는 이름만 붙여 안전하다고 하지 않음. 실제 판매 모드 준비 아님 |
| 운영 | 기본 health status만, 상세/컴포넌트/discovery/probes 비노출. `compose.yaml`은 dev/test PostgreSQL18.6만 | 배포 compose/Dockerfile/proxy는 없음. 현 compose를 공개용으로 재사용하지 않음. worker 상태·readiness·복구 runbook은 후속 구현/검증 필요 |

위 버전은 저장소의 현재 고정값이며 최신 버전 추천이 아니다. 컨테이너는 JAR/정적 산출물·설정을 동일하게 전달하기 위한 포장이다. OS 직접 JAR 실행도 가능하지만 API/worker 환경·권한·재시작 정책을 별도로 관리해야 한다. 로컬 검증은 기존 Compose DB 정책을 유지한 별도 project/volume을 사용하고 공개 후보도 단일 서버의 분리 컨테이너 구성을 우선 비교한다. DB·media까지 같은 서버에 있으면 단일 장애점이라는 비용/복구 한계를 명시한다.

## 사용자 명령과 생산·소비 경계

```text
브라우저 HTTPS /, 화면 경로 → 정적 dist (새로고침 SPA)
브라우저 HTTPS /api/... → 경로 검증·역방향 프록시 → Java API
  → 현재 세션/CSRF/권한 → 기존 도메인 명령 → PostgreSQL 업무행+outbox
  → 같은 버전 worker의 DB 실행권 → 후속 업무행/알림/집계
  → 브라우저 API 재조회 → 상태·금액·오류 표시
이미지/첨부 요청 → /api/... 권한·공개성 검사 → namespace의 지속 media
```

최소 연결은 가상 계정이 상품을 탐색하고 회원 주문/DEMO 결제 후 주문·배송/알림을 다시 보는 흐름이다. `frontend/src`의 기존 API 호출과 주문 생산자→payment→fulfillment→notification/reporting 소비를 그대로 사용한다. 새로운 공개 역할전환 UI나 공용 관리자 계정을 만들지 않는다. 운영 정책/게시 변경의 실명령은 [P12-B](P12-B.md)의 SitePages→ShippingPolicyController/JdbcShippingPolicies 또는 SiteController→revision/receipt→견적/공개 게시 소비를 재사용하며 지정 운영 접근에서만 시연한다.

인프라는 업무 성공을 대신 만들지 않는다. 타인 주문/첨부403 또는404, 비인증401, CSRF403, stale version/fingerprint409, 동일 요청키 재생과 다른 본문409는 API 책임이다. 금액·정책 snapshot·재고·쿠폰·환불·정산 이력은 기존 DB 잠금/transaction/unique 제약을 유지한다. 응답을 잃은 쓰기 요청을 프록시가 자동 재전송하지 않으며 클라이언트는 기존 같은 요청키로 결과를 조회/재확인한다. worker 중복·중단은 기존 lease/시도/재처리 계약으로 복구하고 UNKNOWN 결제/환불을 성공 또는 실패로 임의 변경하지 않는다.

## 같은 origin 프록시 계약

정적 제공/프록시 후보는 NGINX다. `try_files`와 `location`으로 정적/SPA/API를 분리할 수 있고 전달 헤더·오류 처리·요청 크기를 명시할 수 있다. [공식 core 지시어](https://nginx.org/en/docs/http/ngx_http_core_module.html), [공식 proxy 지시어](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)를 2026-11-15 확인했다. 이는 도입 설계이며 아직 검증한 설정 파일은 아니다. 아래 계약을 실제 HTTP assertion으로 만족하는 설정을 후속 작성한다.

| 경계 | 필수 결과 |
|---|---|
| SPA와 정적 | `/`·등록 화면 직접 진입/새로고침은 index.html. 해시 asset은 정확 파일만 제공하고 없는 asset404; asset 요청을 index200으로 바꾸지 않음. POST/PUT 같은 비조회 화면 요청도 SPA200으로 바꾸지 않음 |
| API namespace | 정확 `/api`와 `/api/` 하위만 원 URI/query/method/body로 전달, prefix 제거 금지. `/apix`는 API가 아님. API404/401/403/409/5xx의 status·JSON·content-type을 유지하고 SPA fallback/error interception 금지 |
| 경로 정규화 | 현 `vite/apiProxy.ts`의 encoded slash, dot segment, 역슬래시, 중복 slash, 대소문자 API/actuator 별칭, 제어문자·잘못된 percent 입력 거부 계약을 배포 프록시에서도 원요청 기준 검증. 정규화 후 관리 경로 우회가 생기지 않음 |
| 장애·응답 유실 | 연결 실패/기한 초과는 502/504와 API용 JSON/no-store, 성공200으로 변환 금지. 이미 전송한 잘린 body는 연결 실패로 전달. 자동 비멱등 재시도 금지. 기존 프런트 오류/같은 키 복구 소비 검사 |
| 헤더·쿠키 | Set-Cookie 복수값·CSRF 요청 헤더·Content-Type·Cache-Control·요청 ID 전달. SESSION 및 비회원 자격 쿠키의 Secure/HttpOnly/SameSite/Path를 유지; 별도 domain rewrite 없음. 인증 응답/오류·개인 API의 공유 cache 금지 |
| 신뢰 경계 | 공개는 HTTPS와 승인 host만. API/DB/worker·에뮬레이터 관리 포트 외부 비공개. 외부 Forwarded/X-Forwarded-* 입력은 제거 후 프록시가 관측한 값으로 설정; API는 허용 프록시 경로만 수신. 전역 forwarded 신뢰로 클라이언트 값을 받아들이지 않음 |
| 관리/health | 승인된 접근 경계 안에서 **exact `/actuator/health`를 허용**해 기존 HomePage→HealthPanel→`frontend/src/api/health.ts` 소비를 유지한다. 200 UP,503 DOWN/OUT_OF_SERVICE의 status-only JSON·no-store를 보존한다. 그 외 `/actuator/**` 및 별칭·상세/env/metrics는404, wildcard 공개 금지 |
| cache·배포 호환 | index.html은 no-cache 재검증, 해시 asset은 immutable 장기 cache 후보. 이전 asset은 호환/되돌리기 기간 보존. 공개 API도 기본 proxy cache 없음; 이미지 캐시가 비공개/비공개 전환 권한을 우회하지 않음 |
| 업로드 | Java의 파일5MB/request6MB와 맞는 proxy body 제한·유한 읽기 기한·임시파일 용량/권한. 한도 초과413은 API 오류로 표시하며 SPA 변환 금지. MIME/이미지 정규화·현재 권한·귀속 검사 유지, 업로드 원파일/volume의 alias 공개 금지 |

프록시 숫자 timeout은 하네스 업무 기한과 별개 운영 설정이며 느린 쓰기의 중복 재전송으로 해결하지 않는다. API 프록시 timeout을 설정할 때 기존10초 개발 경계와 제공자 제한을 대조하고 실제 오류/종료 검사를 남긴다. query·Cookie·Authorization·메일토큰·PG 비밀·개인 입력을 access log에 그대로 기록하지 않는다. 요청ID/오류코드/소요시간과 비식별 업무 ID 중심으로 추적한다.

## 패키지·DB·파일·역할 수명

후속 패키지는 commit/미커밋 input manifest, dist/JAR/image digest, JDK·빌드 lock·DB/image 버전, 공개 설정 예제, 비밀 변수 이름, 역할별 시작/종료·health 기준을 묶는다. secret은 이미지·VITE_*·Git·로그에 넣지 않는다. 예제는 비밀값 없이 작성하고 API·worker가 같은 artifact임을 SHA로 검증한다. worker JVM과 API JVM은 별도 자원 한도/종료 시간을 가지며 웹 요청이 없어도 작업이 진행되어야 한다.

기존 dev/test와 별도 DB/user·새 media·volume·동적 loopback port를 사용한다. `db` profile의 자동 Flyway는 양쪽에 적용되므로 배포 시 명시 migrator/단일 API 선행 중 하나를 P12-D에서 구현하고 성공 후 worker를 시작한다. 이미지의 migration과 실제 schema version을 기록한다. 별도 migration 실행을 채택한다면 app에서 끄는 설정/권한과 Flyway validation을 검증해야 하며 현재 이미 분리돼 있다고 하지 않는다. 세션 테이블 등 `marketplace` schema 참조를 임의 DB_SCHEMA 치환으로 해결했다고 가정하지 않는다.

API·worker가 공유하는 media root와 DB namespace를 복구 단위에 포함한다. 파일은 정적 dist와 분리하고 비루트 UID 권한·읽기/쓰기 필요 경로만 mount한다. 실패 업로드·rollback 뒤 기존 파일은 보존한다. 백업은 DB만 있으면 충분하지 않으며 파일 inventory/hash·namespace·소스 버전도 필요하다. 동일 시점의 DB/media 일관성 확보, 별도 DB/media 복원, 주문/금액/파일 대사·worker 복구·앱 되돌리기의 **실제 실행은 P12-D**다. destructive volume 삭제나 과거 검증 DB 재사용을 복구 실습으로 쓰지 않는다.

health UP 하나는 업무 정상/worker 진행/복구 성공이 아니다. API 내부 readiness는 DB 연결·migration 일치·필요 저장 경로 준비를, worker는 실제 작업 상태/실행권 지연을 관측하는 별도 계약이 필요하다. 프로세스 liveness에 외부 PG 실패를 직접 묶어 무한 재시작하지 않는다. 공개 상세 진단 대신 내부 로그와 작업 관리의 현재 권한을 사용한다.

## demo·운영 경계와 미정 정책

현재 설계 §16의 “운영에서 테스트 인증·결제 설정 거부”는 요구 계약이며 구현 완료 사실이 아니다. 다음 **배포 모드 계약 이름과 허용 행렬은 설계에서 확정**한다. 이 이름의 profile/설정 키는 아직 구현되지 않았다. 기존 `db`/`worker`는 실행 역할이고 아래 모드는 보안·제공자 정책이므로 구별한다. 종합 가드는 API·worker 모두 DB 연결/Flyway 및 제공자 생성 전에 유효 설정을 검사하며 금지 조합은 비밀값 없이 시작 거부한다. 기존 전화 가드를 완화하지 않는다.

| 모드 | 연결·인증 발급·계정 | 결제·역할·시작 정책 |
|---|---|---|
| `local-full` | 새 격리 합성 DB/media, loopback 전용. local-http의 secure=false는 이 모드의 명시 HTTP 검사에서만 허용; HTTPS 검사는 Secure=true. local-mailbox와 local-test/emulator는 이 모드에서만 허용하며 관리 인터페이스 외부 비공개 | DEMO 허용. SANDBOX는 별도 명시 제공자 검사에서 test키/공식주소를 사용하고 외부 준비 부족은 BLOCKED; Offline stub는 검사 소스만 주입. live키/실판매/실송금 금지. API poll=false·worker non-web 유지 |
| `public-demo` | 초대 검토자 접근 제한+개별 기존 로그인, HTTPS·Secure=true, 승인 host와 내부 API 수신만. local-http/local-mailbox/local-test/emulator 설정 금지. 신규 가입/메일검증·전화발급·비회원 구매/복구·메일복구는 미지원으로 차단/안내 | 합성 데이터의 **DEMO 결제·모의 정산만 허용**. SANDBOX/실제 Toss·test_sk/live키 설정과 경로는 금지. API/worker는 같은 artifact·DEMO 정책. 모드·접근제한 누락, 위험 설정 혼합 시 시작 거부 |
| `production` | 현재 실제 인증/메일/실결제 제공자와 종합 운영 검증이 준비되지 않음 | 현재 산출물에서는 **항상 시작 거부**. local/mock/DEMO/SANDBOX/test키는 운영 허용이 아니며 live키를 넣어도 우회 불가. 실제 판매 지원은 별도 승인·설계·검증 범위 |

public-demo의 테스트 모드는 provider 네트워크 없는 DEMO를 뜻하며 SANDBOX test키 허용과 다르다. `local-full`의 허용 test키까지 일괄 금지하지 않는다. public-demo에서 미지원 명령은 서버가 `503`과 안정된 `DEMO_FEATURE_UNAVAILABLE` 오류로 거부하고 UI는 해당 입력/제출을 비활성화해 이유를 표시한다. `/api/auth/signup`, verify-email, password request/reset, guest 구매 인증·전화 교환/복구 및 SANDBOX 준비/확인·Toss webhook을 명시 제한 대상으로 검사한다. 경로별 정확 목록은 기존 controller 전체 매핑을 등록해 누락을 거부한다. 인증/CSRF에서 먼저401/403으로 거부될 수 있으나 유효 세션·CSRF를 갖춰도 제한 명령은503·DB 변경0·provider 호출0이어야 한다. HTTP 본문/query의 mode를 SANDBOX로 조작해 현 payment/refund dispatcher가 Toss를 선택하려는 경로도 같은 차단 assertion으로 검사하며 시작 환경변수 검사만으로 대체하지 않는다. 기존 회원 로그인/로그아웃·CSRF·회원 DEMO 구매와 권한별 조회는 허용한다. 단순 UI 숨김이나 proxy 차단만으로 서버 계약을 대신하지 않는다.

계정 준비는 공개하기 **전**, 새 합성 DB의 loopback `local-full`에서 기존 가입→로컬 확인 흐름으로 검토자별 가상 이메일·개별 비밀번호의 ACTIVE BUYER를 만든다. 실제 사람의 이메일 소유나 본인확인을 검증했다고 표시하지 않는다. 원 운영/개발 DB 복사·실제 고객 정보·공용 비밀번호는 사용하지 않는다. 관리자 필요 시 지정 운영자 한 명만 [P02-C](P02-C.md)의 기존 `InitialAdminCommand`/`InitialAdmin.initialize`를 사용한다. 명시 DB 이름·대상 UUID·INITIAL_ADMIN 확인, ACTIVE/email-verified/BUYER 조건, 최초1회, auth_version 갱신·세션 폐기·감사를 유지한다. 검토자에게 SYSTEM을 일괄 주지 않고 기존 권한 관리 명령으로 필요한 역할만 부여한다. 테스트 fixture SQL 승격이나 새 공개 bootstrap endpoint를 추가하지 않는다.

준비 후 local-full 프로세스/메일함/emulator를 종료하고 일회 토큰과 준비 세션을 폐기한 뒤 public-demo 가드·금지 endpoint·권한 음성 검사를 통과해야 접근을 연다. 이 모드 전환은 새 환경의 명시 준비 절차이며 실행 중 public-demo에서 local 발급 기능을 켜지 않는다. 검토자 추가/복구가 필요하면 비공개 준비 절차로 돌아가고 공개 self-service 발급을 임의 도입하지 않는다. 현재는 이 절차를 실행하거나 자격정보를 만들지 않았다.

사용자는 **“권고안: 초대 검토자 제한·개별 로그인”**을 명시 승인했다. 미지원 전화/메일 발급과 실제 Toss는 차단/안내하고 공용 관리자·역할전환·익명 모의 인증은 도입하지 않는다. 이는 공개 접근 **설계 선택**이며 실제 공개/구매 실행 승인이 아니다. 아래 대안 중 첫 행을 채택했고 나머지는 범위 밖이다.

| 대안 | 영향·권고 |
|---|---|
| 로컬 격리 전체 시연 + 초대 검토자 제한·개별 로그인 | **사용자 승인안**. 위 준비/가드·발급 제한을 적용하고 기존 회원 DEMO 흐름을 시연. 모의 인증/관리 UI를 익명 인터넷에 노출하지 않음 |

## 호스팅·비용 비교 — 공급자와 예산 미지정

사용자는 **“지정 없음: 로컬 검증 후 공개 후보 비교”**를 선택했다. 로컬 격리 구성 우선과 공개 후보 비교 순서는 확정이며 공급자/예산은 후속 조달 결정이다. 이 답변은 이번 문서 범위를 제품 실행·구매·공개 승인으로 확대하지 않는다. 비교는 2026-11-15 공식 가격 기준 USD 표준 Linux VM 예시이며 세금·환율·지역별 제공량·초과분·할인 차이를 포함한 견적이 아니다.

기존 JUnit·ArchUnit과 등록38 DB 묶음, 프런트/브라우저 검사를 삭제·축소하지 않는다. 새 package/proxy 계약은 제공자와 소비 identity/guest/media/payment/job/browser 경계를 영향표에 등록한다. 한 파일의 문구/static 계약만 바뀌면 해당 선택 검증이 가능하나, 인증·공통 금융·worker·schema·공통 fixture·하네스 동작 변경 또는 영향 불명확/미등록은 **새 증거 경로 무선택 `./verify.ps1 -Offline`**가 필요하다. 이번은 문서만이므로 자동 제품 검사 미실행이 적절하다.

후속 실행 명령 예시는 `./verify.ps1 -Offline -EvidenceDirectory '<새 경로>'`다. 이는 지금 실행 요청이 아니다. 집중 개발은 실제 등록된 영향 계약으로 선택하며 `selection.json`의 선택/제외·이유를 남긴다. `selected-passed/certificationEligible=false`는 적절한 선택 작업 완료의 근거가 될 수 있지만 전체 인증은 아니다. 기존965입력 증거는 현재 업무 동작의 기준선이며 **새 프록시/컨테이너/시작가드/환경/배포를 검증하지 않는다**. 배포 전 통합 소스의 유효한 무선택 근거를 확보한다. 개발·독립이 같은 검사를 이유 없이 두 번 실행하지 않는다.

새 DB·새 media·새 증거를 사용하고 실제 명령/입력 SHA/결과/원 XML·브라우저 보고서를 연결한다. 업무 준비는 명시60초, 업무와 retry/poll은 공유10초, 정리10초 및 유한 child watchdog의 현 정책을 유지한다. 390초 전체/30초 시나리오 총제한을 복원하거나 실패를 timeout 확대로 감추지 않는다. 부정 기동 검사는 기대 실패와 하네스 실패를 구분하고 실패 원본·원인·수정 영향·재검증을 보존한다.

후속 구현 승인 시 최소 실제 정적서버→API→DB 연결부터 역할/쿠키·프록시 오류·파일·worker를 완성하고, 영향에 맞는 개발 검증→같은 소스 독립 적합성 검토·필요 검증→필수 수정·영향 재검증→인계 순서로 진행한다. 업무 결과를 하나의 실행 패키지 단위로 관리하며 proxy directive/DTO/container마다 별도 승인 게이트를 만들지 않는다. 미정 공개정책에 의존하지 않는 로컬 패키징을 먼저 수행할 수 있으나 **이번 설계 승인만으로 후속 구현/검증을 시작하지 않는다**.

실제 Toss F07/G08 BLOCKED, AC16 다른 개발 환경, 실제 송금·실기기·배포·사용자 직접 확인은 미검증을 유지한다. 새 공개 구성의 가드·패키지·브라우저 assertion도 미실행이다. 외부 제한을 로컬 설계 결함과 구분하되 공개/전체 완료로 생략하지 않는다. 설계의 최종 독립 판정·문서 SHA·정적 확인은 아래 기록에 추가하며 과거 원결과를 소급 변경하지 않는다.
