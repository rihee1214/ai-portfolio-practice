## 목표와 업무 범위

판매자는 자기 매대의 거래·처리할 일·정산 상태를, 운영자는 현재 업무 권한에 맞는 전체 운영 상태를 확인하고 기존 상세 업무로 이동한다. 각 숫자는 **정의·기간·대상·최종 성공 집계 시각**과 함께 설명할 수 있어야 한다. 누락/실패를 0으로 표현하지 않고 같은 기준 데이터와 대사 가능한 결과를 제공한다.

설계 §12가 이미 요구한 범위는 판매자의 매출·주문·상품·재고·클레임·정산, 운영자의 전체 주문·결제 실패/미확정·배송 지연·신고/문의·판매자 신청·정산 차이다. 이 범주를 제거하지 않고 구체적인 카드 정의와 권한을 결정한다. 첫 연결은 자기 매대의 거래 금액/건수와 갱신 시각→기존 주문 상세로 잡고, 나머지 범주를 같은 전체 완료표에서 완성한다.

제외: 새 금융 정책·수수료·지급 계산, 환불/클레임 상태 변경, 사용자 행동 추적·매출 예측·순위/판매자 비교, CSV 내보내기·개인정보 원문 복제, 외부 분석 서비스, 외부 알림, P11-E의 사이트 설정 관리. 과거 결제·배송·환불 작업을 재실행해서 지표를 채우지 않는다.

금액은 서버 정수/정확한 합산으로 처리하고 API는 십진 문자열로 반환한다. 클라이언트 Number 변환·재계산으로 원 단위 합계를 만들지 않는다. 합산 overflow·음수·0원·배송비 환불 누적1회·수수료 원 배분 501/500원 같은 사례를 포함한다. 원인이 다른 집계는 계산식으로 억지로 같게 만들지 않고 정의 차이를 표시한다. 모든 변경 명령/지급은 기존 상세 화면으로만 이동한다.

## UI → API → DB 제안

1. 판매자 화면: 기간 선택, 자기 매대 명칭, 지표 정의 도움말, 거래/처리 잔량/정산 카드와 표, 기준 시각·집계 완료 시각·지연/실패 표시. 모바일은 표의 정보와 이동 기능을 보존한다. 타 매대 선택 입력은 제공하지 않는다.
2. 운영 화면: 현재 허용 카드만 제공한다. 권한 회수 후 화면 캐시·금액·원인 ID·필터·진행 요청을 폐기한다. 일부 권한 부재와 집계 실패를 구분한다. 지연 수치는 정상 0원/0건과 다르게 표현한다.
3. 제안 GET `/api/seller/dashboard?from=&to=` 및 업무 권한별 운영 GET 경로. 운영 경로는 기존 `AccessArea.forAdminPath`와 서버 정책을 함께 설계해 ADMIN 포괄 허용을 피한다. 응답은 범위·기간·정의버전·세대ID·sourceAsOf·completedAt·status·허용 metric 값으로 제한한다. `sourceAsOf`는 실제 스냅샷 기준이며 '이 시간 이전 모든 미래 발견 사건까지 완전함'을 뜻하지 않는다.
4. 첫 집계 전에는 미준비 응답, 마지막 성공본이 있고 새 집계가 실패하면 이전 값+이전 시각+지연/실패 상태를 제공한다. 성공 시각을 실패 시각으로 덮지 않는다. 빈 기간의 정상 0과 미준비/null을 명시적으로 구별한다. 잘못된 날짜/범위는 400, 자격 상실은 401/403, 타 매대/불가 상세는 기존 404 계약을 따른다. GET은 no-store다.
5. reporting 소유의 집계 실행/세대/지표 테이블을 제안한다. 다른 모듈 DB 직접 접근 대신 소유 모듈의 공개 projection이 같은 트랜잭션의 일관된 snapshot에서 값을 읽는다. 원 주문·결제·환불·원장·알림 테이블을 지표 갱신으로 쓰지 않는다. 새 마이그레이션 번호는 실제 구현 시작 시 충돌 없이 정한다.
6. SYSTEM 재집계 명령(경로·DTO 미확정)은 범위·요청키·사유를 검증하고 감사와 전용 outbox를 원자적으로 남긴다. 판매자 GET/페이지 새로고침이 모든 매대 집계를 실행하지 않는다. 현재 권한을 잠금 전후 확인하고 불가 요청은 작업 0건이다.

## 동시성·멱등·복구 기술 제안

### 5분 세대와 임의 기간 조회의 연결

초기 구현은 **전체 이력의 서울 일자별 bucket + 같은 시점의 현재 잔량**을 한 세대로 생성한다. 요청 기간마다 job을 만들지 않는다. 각 세대는 같은 REPEATABLE READ snapshot에서 원천별 사실을 읽어 `generationId/definitionVersion/storeId/서울일자/metricId` 단위의 기간 가산 지표와, 날짜 범위에 종속되지 않는 현재 업무 잔량을 함께 저장한다. 운영 주문 distinct는 판매자 주문 수의 합으로 만들지 않고 order 소유 포트가 별도로 계산한다. 기간 내 distinct처럼 일별 합이 성립하지 않는 지표는 최초 계약에서 사건 귀속일의 유일 키를 정하거나 해당 소유 포트의 전용 집계를 설계해야 하며, 잘못된 단순 합산을 허용하지 않는다.

`from/to` GET은 공개된 generationId 하나를 고정해 해당 날짜 bucket을 합산하고 **동일 세대**의 현재 잔량을 반환한다. 현재 잔량 카드에는 '선택 기간과 무관한 기준시점 잔량'을 표시한다. 읽기 도중 새 세대가 공개돼도 기존 세대 참조를 유지한다. 집계가 성공한 범위의 bucket 부재만 정상 0이며, 원천 실패/미완료 범위는 0으로 반환하지 않는다. 늦게 확인된 과거 사건은 다음 세대의 해당 과거 일자 bucket에 반영하고 이전 세대는 수정하지 않는다. 기간 변경은 기존 세대 조회만 실행한다. 모든 원천·bucket·잔량의 생성이 성공한 경우에만 세대를 공개한다.

전체 이력을 매번 읽는 초기 방식은 정확성을 우선한 기술안이며 실측 전 성능 보장은 없다. 실행이 5분을 넘으면 같은 범위 실행을 중첩 누적하지 않고 진행 중 실행을 유지하며 지연을 노출한다. 366일은 한 조회 범위의 길이이고 이력 삭제/최근 366일만 집계하는 제한이 아니다. 미래의 증분 최적화는 같은 스냅샷·늦은 사실·원천 정정 계약을 보존하는 근거가 있을 때 검토한다. 금액이 다른 세대로 섞이지 않는 동시 GET/공개, 과거기간 조회가 job 0건인 조건, 일별 합의 유일성도 DashboardIT 필수 assertion에 포함한다.

### 구현 시 추가할 공개 포트와 책임 (아직 없는 파일의 제안)

| 제안 경로·소유자 | 책임과 반환 제한 |
| --- | --- |
| `order/api/DashboardOrders.java` | 원 주문/판매자 주문의 유일 건수, 결제 귀속의 매대별 상품/배송비 배분, 정책 이전 거래 포함. 연락처 없는 일자별 projection |

| `fulfillment/api/DashboardShipments.java` | 기본 배송 예외·교환 배송·진행 잔량과 실제 사건 시각. 배송 지연 의미는 승인된 P4 적용 |

| `reporting/api/Dashboards.java` 및 reporting 내부 실행/저장/웹 어댑터 | 정의버전·세대·범위·현재 권한 검사, 같은 트랜잭션에서 공개 포트 조합, bucket/잔량의 원자적 공개·GET. 타 소유자 테이블 직접 조회 금지 |

모든 projection 포트는 호출자가 시작한 동일 읽기 트랜잭션에 참여한다. 독립 연결·REQUIRES_NEW·비동기 읽기로 snapshot을 분리하지 않는다. 구현자는 기존 공개 DTO 재사용 적합성을 먼저 확인하고 불필요한 포트를 합칠 수 있지만 소유 책임과 snapshot 계약을 유지한다. 위 이름은 등록 완료 사실이 아니며 구현 결과에 맞춰 이 표를 갱신한다.

- 초기 권고 B 방식은 같은 정의버전·집계 범위의 새 세대를 만들고 완료된 세대만 원자적으로 공개한다. 계산 중 일부 카드만 새 값으로 바꾸지 않는다. 배치 시작/완료 시각과 원 데이터 snapshot을 구분한다.
- 단일 PostgreSQL의 소유 모듈 공개 projection을 동일 REPEATABLE READ snapshot으로 실행하는 방안을 검토한다. 단순 `max(id)`나 발생시각 cutoff만으로 늦게 commit한 행 누락을 해결했다고 주장하지 않는다. 큰 데이터 분할 시에도 한 snapshot/완료 세대 의미를 유지해야 하며, 더 큰 규모의 CDC·증분 설계는 현재 범위에 추가하지 않는다.
- 실행 식별자·범위·정의버전별 공개 순서를 단조롭게 보장한다. 늦게 끝난 옛 작업/실효된 lease가 최신 세대를 덮지 못하게 하고, 같은 키 재시도는 같은 실행을 반환한다. 시스템 원시각만으로 우선순위를 정하지 않는다.
- 원천 상태가 바뀌면 다음 새 snapshot에서 반영한다. 과거 성공본은 당시 기준을 유지한다. 재실행에서 금액을 다시 더하는 방식 대신 같은 범위를 재계산/교체해 중복 누적을 막는다. 금융 모의 지급·알림 생성·읽음·환불 예약은 불변이어야 한다.
- commit 후 ACK 전 중단, 작업 중 프로세스 종료, 임대 회수, 두 실행 경합, 원천 조회 오류를 실제 격리 DB/자식 프로세스로 검증한다. 실패 이력과 마지막 성공본을 보존하고 기존 Jobs 한도를 늘려 실패를 가리지 않는다.
- 회원→세션→매대/대상 잠금 순서를 기존 규칙과 맞춘다. 집계 worker는 사용자 세션을 가장하지 않는다. worker가 만든 값의 조회 권한은 현재 사용자의 별도 검사이며 과거 권한으로 캐시를 반환하지 않는다.

## 제공·소비 영향과 검증 범위

제안 제공 계약은 `reporting.dashboard`와 집계 실행/세대의 읽기 계약이다. 실제 구현 시 `verification/db-groups.json`에 소유 검사·직접 소비·제공 계약을 등록한다. 새 reporting 묶음 이름과 메서드는 아직 등록/실행되지 않았다.

| 변경/소비 | 필요한 영향 확인 |
| --- | --- |
| order/payment/claim/settlement 공개 집계 | 원 주문·환불·금액/예약·정산/이월 소비와 대사. 기존 사건의 새 쓰기나 이중 금융 효과가 없는지 확인 |
| fulfillment/catalog/inventory/seller | 일반/분할/교환 배송, 공개/숨김·재고/예약·매대 상태·판매자 신청 정의와 현재 권한 |
| operations/content/identity | 신고/문의/배정/조치·재개, 시간 미상·비밀정보 제외, 세부 권한·세션/담당 회수 |

## 검토 진입·완료 및 인계

1. **설계 판단:** D-P1/P2/P4 사용자 승인을 반영했다. P3/P5는 기술 초기안으로 적용하며 새 업무 충돌 근거가 있을 때만 재검토한다. 이 문서 초안 자체가 구현 지시를 대신하지 않는다.
2. **구현 진입:** C 실제 커밋·현재 작업트리·증거를 확인하고 범위 밖 변경을 구분한다. 정책은 승인됐으며 별도 구현 지시가 있어야 기존 Sol 담당이 시작한다. 내부 helper마다 새 인계/동결을 만들지 않는다.
3. **중간 검토:** 최소 UI/API/DB 연결과 권한·금액·세대/복구 위험이 실제 assertion에 도달한 뒤 필요한 경계만 기존 지정 검토세션에 요청한다. 준비 데이터 오류와 제품 결함을 구분한다.
4. **최종 검토:** 위 완료표·실제 영향표·필수 수집·같은 소스 SHA와 개발 근거가 준비된 후 기존 세션이 선택 적합성/재사용/필수 잔여를 판단한다. 미해결 필수 결함·assertion 누락·실패/skip·보존 누락이면 완료 불가다. 유효 전체 근거를 독립 세션에서 무조건 반복하지 않는다.
5. **인계:** 지표 사전 버전·권한/기간·공개 세대·소스/성공 시각·재처리/실패 의미와 원 금융 계약을 기록한다. E는 필요한 읽기 계약만 소비하며 D 인계가 E 구현/배포 승인이 아니다. 원 실패·소스/증거·차단을 유지한다.
