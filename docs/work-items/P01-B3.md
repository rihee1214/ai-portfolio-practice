# P01-B3 React Router·공통 레이아웃·역할별 화면 틀

작성일: 2026-10-21 (Asia/Seoul)  
최신 확인일: 2026-10-23 (Asia/Seoul)  
상태: **구현 완료·최신 내장 브라우저 재검증 통과 — P01-B3 범위 완료, P01-B4 미착수**

2026-10-21 Docker 방침을 검토했다. [ADR-002](../decisions/ADR-002-docker-postgresql.md)의 컨테이너 적용 대상은 PostgreSQL 서버이며, B3는 기존 호스트 Node·npm과 실행 명령을 유지한다. DB 준비는 P01-C1 이후이고 현재 화면 틀은 Docker·DB 실행 없이 동작하는 범위다. **검증 이력은 아래에 최신 순으로 구분한다. 이전 브라우저 성공을 최신 재검증 성공으로 계산하지 않는다.**

## 2026-10-23 내장 브라우저 연결 복구 및 최신 UI 검증

이 절이 현재 상태다. 아래 2026-10-22 차단 기록은 과거 진단 이력으로 보존한다. 업데이트 후 제어 도구에 실제 IAB가 나타났고 렌더링된 화면을 읽고 조작했다. 업데이트만이 해결 원인이라고 확정할 근거는 없다.

새로고침 시 로컬 서버의 `ERR_CONNECTION_REFUSED`도 별도로 관찰했다. 승인된 실행으로 기존 명령의 4174 미리보기를 다시 시작했다. 이전 오류 페이지의 data URL은 도구 정책으로 접근하지 못하여, 정상 HTTP 주소의 새 검증 탭에서 진행했다. 권한·방화벽 설정을 변경하지 않았다.

현재 B3를 막는 항목은 없다. 실제 휴대전화·다른 브라우저·스크린리더는 미검증이며 사용자 수정 실습 완료 여부도 미확인이다. 역할별 화면은 공개 미리보기로 실제 권한 검사가 아니다. 이번 작업은 앱 코드 변경 없이 문서·증거만 갱신했고 P01-B4는 시작하지 않았다. 결과 확인용 4174 서버와 홈 탭은 유지한다. 실행 세션 종료 후 접속이 거부되면 기존 preview 명령으로 서버를 다시 실행해야 한다.

## 2026-10-22 추가 연결 진단과 복구 절차

브라우저 탭이 보이지만 제어되지 않는 문제를 추가 조사했다.

| 확인 대상 | 이번 관찰 | 해석 |
| --- | --- | --- |
| 로컬 Codex 설정의 Browser 플러그인 | `browser@openai-bundled.enabled = true` | 이 설정 파일에서는 활성화되어 있음. 실행 중인 앱의 최종 적용 상태까지 증명하지는 않음 |
| 기존 미리보기 서버 | 승인된 실행의 `GET http://127.0.0.1:4174/`가 200·text/html | 현재 서버 중단이 원인은 아님 |
| 제어 도구의 목록 | 빈 `Codex MCP Apps`만 존재, `iab` 없음 | 탭 내부 DOM이나 사이트 접근에 앞서 내장 브라우저 연결이 도구에 제공되지 않는 상태 |
| Browser 플러그인 파일 | 버전 `26.1016.51333`의 매니페스트·연결 문제 안내 존재 | 플러그인 파일의 존재를 확인. 실행 중인 데스크톱 앱 버전이나 정상 연결을 의미하지 않음 |
| 앱의 사이트별 권한 | 사용자가 해당 설정을 확인하기 어렵다고 답변 | `Block` 여부와 실행 중 앱의 활성화 상태는 미확인. 설정이 없거나 차단되었다고 단정하지 않음 |

확인한 로컬 설정은 읽기만 했으며 다른 설정 값·인증 정보는 출력하지 않았다. 원인은 **앱과 제어 도구 사이의 브라우저 연결 제공 단계**로 좁혀졌지만, 내부 원인이나 특정 설정 오류가 확정된 것은 아니다. 로컬 설정이 활성화되어 있다는 이유로 실제 사이트 권한도 허용되었다고 가정하지 않는다.

사용자 확인·복구 순서:

먼저 질문의 답변 입력란이 아닌 **일반 메시지 입력창에서 `@Browser`를 선택해 새 메시지**를 보낸다. 앞선 플러그인 지정은 질문 응답으로 전달되었고, 그것이 실행 중 도구의 브라우저 연결에 적용됐는지는 확인되지 않았다. 새 메시지에서 연결되면 앱 재시작은 필요 없다. 이것이 원인이라는 단정은 아니며 적은 변경으로 확인하는 절차다.

사용자가 설정 항목을 확인하기 어렵다고 답했으므로 아래 1번은 현재 건너뛴다. 일반 입력창에서 연결을 요청해도 같으면 2~3번의 앱 재시작을 시도한다. 설정 확인을 완료한 것으로 처리하지 않는다.

1. **Settings → Browser**에서 Browser 플러그인의 활성화 표시를 확인한다. **Agent permissions → Browse** 기본값과 `http://127.0.0.1:4174` 사이트 예외의 `Block` 여부를 확인한다. `Requires approval` 자체는 고장이 아니며 필요한 접근 시 승인을 받는 설정이다. 항목이 없으면 보이지 않는다고 기록한다. [공식 설정 안내](https://learn.chatgpt.com/docs/reference/settings)
2. 활성화와 접근 설정에 문제가 없어도 연결이 없으면, 다른 실행 중 작업이 끝나고 저장된 것을 확인한 뒤 **데스크톱 앱을 종료 메뉴로 완전히 종료하고 다시 실행**한다. 이 단계는 연결 세션을 재생성하기 위한 진단 시도이며, 이번 현상을 반드시 해결한다는 뜻은 아니다. 이전에 수행한 JavaScript 도구 세션 초기화와 앱 전체 재시작은 다르다. 공식 문제 해결 문서의 앱 재시작 안내는 일반적인 멈춤 복구 안내이므로 이 브라우저 문제에 대한 확정 해결책으로 해석하지 않는다. [공식 문제 해결 안내](https://learn.chatgpt.com/docs/reference/troubleshooting)
3. 같은 프로젝트·이 채팅을 다시 열고 `@Browser`를 선택한 새 메시지로 `http://127.0.0.1:4174/`의 P01-B3 검증 재개를 요청한다. 재시작으로 서버가 종료될 수 있으므로 먼저 HTTP 응답을 확인하고 필요할 때만 서버를 다시 시작한다.
4. 연결 성공 기준은 미리보기가 눈에 보이는 것에 더해, **도구 목록에서 내장 브라우저가 발견되고 해당 탭의 화면 상태를 읽는 것**이다. 이 조건을 확인한 뒤 아래 남은 P01-B3 검증만 수행한다.
5. 재시작 뒤에도 같으면 앱 버전, 위 설정 표시, 탭은 보이지만 도구에는 `iab`가 없다는 재현 정보를 모아 앱의 피드백 기능으로 전달할 수 있다. 이번에 피드백을 전송하거나 세션·로그를 외부로 업로드하지 않았다.

전체 사이트 허용·전체 CDP 접근·방화벽 해제·플러그인 재설치·캐시 삭제는 이번 진단에 필요하다는 근거가 없어 수행하지 않았다. 실제 화면 검증 상태는 여전히 미완료이며 앱 코드나 다음 단계는 변경하지 않았다.

## 2026-10-22 후속: 로컬 통신 복구·브라우저 연결 재시도

사용자가 남은 B3 검증을 요청한 뒤 이어서 수행했다. 앱 소스와 설정은 그대로 두고 실행 권한·HTTP·브라우저 연결을 나누어 조사했다. 이번 기록의 원본은 [HTTP 결과와 소스 해시](evidence/P01-B3-browser-retry-20261022.json)다. 아래의 최초 재검증 기록과 JSON은 당시 차단 이력으로 보존한다.

### 해결한 범위

- 이전에는 제한된 셸에서 소켓 권한 오류·접속 시간 초과가 발생했다. 이번에는 도구의 승인을 받은 **샌드박스 밖 실행**으로 기존 미리보기 서버를 `127.0.0.1:4174`에 실행하고 같은 방식으로 HTTP 접속하여 **200·text/html**을 확인했다. 승인된 실행에서 검증할 수 있게 된 것이며, 샌드박스 자체의 제한이나 시스템 방화벽을 바꾼 것은 아니다.
- 현재 소스를 다시 빌드했고 타입 검사·린트·빌드는 각각 종료 코드 0이었다. Vite 8.3.4가 99개 모듈을 빌드했다. 앱 소스·설정·의존성은 변경하지 않았다.
- 정상 16개 경로와 없는 경로 4개에 각각 일반 GET과 `Cache-Control: no-cache` GET을 보내 **총 40개 요청이 모두 200**으로 같은 최신 `dist/index.html`을 반환하는 것을 확인했다.
- HTML이 참조하는 JS·CSS 2개도 각각 200으로 반환되었고, 내려받은 바이트의 SHA-256이 현재 빌드 파일과 같았다. 경로 응답 40건과 정적 파일 2건의 검사 실패는 0건이다.

| 검사 대상 | 경로 | HTTP 결과 |
| --- | --- | --- |
| 홈 | `/` | 일반·반복 요청 모두 최신 HTML 반환 |
| 구매자 | `/account`, `/account/orders`, `/account/addresses`, `/account/wishlist`, `/account/coupons` | 5개 모두 동일 |
| 판매자 | `/seller`, `/seller/store`, `/seller/products`, `/seller/orders`, `/seller/settlements` | 5개 모두 동일 |
| 운영자 | `/admin`, `/admin/users`, `/admin/sellers`, `/admin/moderation`, `/admin/orders` | 5개 모두 동일 |
| 없는 경로 | `/missing-b3`, `/account/missing-b3`, `/seller/missing-b3`, `/admin/missing-b3` | 4개 모두 SPA HTML 반환 |

이는 **직접 주소와 반복 요청에 대한 Vite 미리보기의 SPA fallback 검사**다. JavaScript 실행·React 화면 선택·브라우저 새로고침·UI 404를 검증한 결과는 아니다. 없는 경로의 HTTP 200은 SPA HTML 반환이라는 의미이며, 요청한 화면의 존재나 정상 동작을 의미하지 않는다. 운영 배포의 웹 서버 설정도 이 검사로 검증되지 않는다.

### 남아 있는 브라우저 연결 문제

1. UI 도구에서 확인되는 브라우저는 탭이 없는 `Codex MCP Apps` 하나뿐이었다. 내장 브라우저 `iab`와 일반 브라우저는 목록에 없었다.
2. Codex 미리보기 열기 요청은 `queued`로 반환되었다. 사용자는 **이 채팅과 미리보기 탭이 보인다**고 확인했다. 이는 사용자 확인이며 AI가 화면을 읽은 결과가 아니다.
3. 도구 세션 초기화 후 목록을 다시 확인하고, 보이는 미리보기의 정확한 URL로 직접 연결을 시도했지만 `Browser is not available: iab`가 반환되었다.
4. 사용자가 `@브라우저` 플러그인을 지정해 재개를 요청한 후에도 목록은 같았다. 설치된 Browser 플러그인의 연결 문제 안내도 확인했으나 현재 제공된 API로 없는 연결을 생성하거나 복구하는 방법은 확인하지 못했다.

따라서 **로컬 서버 응답 문제는 승인된 실행 방식으로 해결되었고, 브라우저 제어 연결 누락은 미해결**이다. 탭이 실제로 없다고 단정하거나, 앱 코드의 결함으로 처리하지 않는다. 연결 누락의 내부 원인은 확인하지 못했다. 새 스크린샷·브라우저 조작 검증 성공은 0건이다.

공식 문서에는 내장 브라우저를 `@Browser`로 지정할 수 있고 `Settings > Browser > Agent permissions`에서 접근 설정을 확인할 수 있다고 안내되어 있다. 이번에는 명시적 지정을 이미 시도했으며 실제 설정 값은 확인하지 못했다. 설정이 차단되어 있다고 추정해 변경하거나, 이 검증을 위해 전체 CDP 접근을 켜지는 않았다. [공식 Browser 안내](https://learn.chatgpt.com/docs/browser?surface=app)

비회원 주문 조회 인증·상품 상세·로그인·장바구니 등 설계 문서의 나머지 주소는 아직 구현하지 않았다. `/account/orders`는 회원 공간이며 비회원은 이후 `/guest/orders/login` 등 별도 조회 흐름으로 연결한다. 비회원 쿠폰 불가·공개 이벤트 가능 정책도 그대로 유지한다.

상단 공간 메뉴는 하위 경로에서도 활성 표시를 유지한다. 역할별 ‘한눈에 보기’에는 `end`를 사용해 시작 주소일 때만 활성화한다. 경로가 바뀌면 페이지 제목을 갱신하고 본문으로 포커스·스크롤을 이동한다. 같은 주소를 다시 누를 때는 포커스를 강제로 옮기지 않는다. 이 단계에서는 뒤로 가기의 이전 스크롤 위치 복원은 구현하지 않았다.

없는 경로 화면의 ‘404’는 **화면 안내**다. Vite의 SPA fallback은 index.html을 HTTP 200으로 줄 수 있으므로 서버 HTTP 404 검증과 구분한다. 공개 배포 서버의 화면 fallback과 `/api` 오류 응답 보존은 B4·P12에서 검증한다.

## 필요한 개념과 코드 흐름

Java Controller가 요청 URL을 API 처리와 연결하듯, React Router는 브라우저 URL을 화면 컴포넌트와 연결한다. 단, 이번 경로 이동은 Java Controller를 호출하지 않는다.

| 개념 | 이 코드에서 하는 일 |
| --- | --- |
| BrowserRouter | 브라우저 주소·이동 이력과 React 화면을 연결한다. |
| Routes / Route | 현재 주소와 일치하는 화면·레이아웃을 선택한다. `index`는 부모 주소의 기본 화면이다. |
| Outlet | 일치한 자식 화면이 들어갈 자리다. 공통 외곽과 바뀌는 내용을 분리한다. |
| Link / NavLink | 전체 문서를 새로 받지 않고 경로를 이동한다. NavLink는 현재 메뉴에 aria-current를 붙인다. 같은 페이지의 본문·상품 위치 이동에는 기존 `<a href="#...">`를 쓴다. |
| props / TypeScript 타입 | Workspace·Feature 정의를 레이아웃과 페이지에 전달하고 개발 중 데이터 모양을 검사한다. 서버 권한 검사는 아니다. |
| useLocation / useEffect / useRef | 주소 변경을 관찰해 제목·포커스를 갱신한다. ref는 본문 DOM과 직전 주소를 보관한다. |

예를 들어 ‘판매자 → 상품 관리’를 누르면 다음 순서다.

```text
main.tsx → App.tsx의 BrowserRouter
  → NavLink가 /seller/products로 주소 변경
  → Routes가 SiteLayout → WorkspaceLayout → FeaturePage 선택
  → SiteLayout의 Outlet에 판매자 레이아웃 표시
  → WorkspaceLayout의 Outlet에 상품 관리 안내 표시
  → 활성 메뉴·탭 제목·본문 포커스 갱신
```

`navigation.ts`의 판매자 `path: '/seller'`와 기능 `path: 'products'`가 합쳐진 주소다. 레이아웃은 해당 공간 정보를 props로 받고, 카드와 메뉴는 같은 feature 목록을 사용한다.

기존 매대 입력은 HomePage로 옮겼다. 입력 → onChange → setShopName → HomePage 재렌더링 → 미리보기 갱신은 동일하다. 다른 경로로 떠나면 HomePage가 제거되므로 돌아올 때 초기 상태다. 영속 저장이나 여러 화면에서 공유하는 상태는 아직 없다. JSX 텍스트 보간으로 입력을 표시하며 HTML 삽입 API는 쓰지 않는다.

이번 흐름에는 HTTP 요청 → Java 서비스 → SQL이 없다. 이후 B1에서 상태 API를 Actuator로 교체했으므로 다음 [B4](P01-B4.md)는 `GET /actuator/health`를 실제로 연결한다. DB 흐름은 C 작업 이후 이어진다.

## 실행과 검증 결과

프로젝트 루트의 PowerShell 7에서 실행한다. 준비된 프로젝트 도구가 없다면 B2의 Node 준비 안내부터 따른다.

```powershell
.\frontend\npm.ps1 ci
.\frontend\npm.ps1 run typecheck
.\frontend\npm.ps1 run lint
.\frontend\npm.ps1 run build
.\frontend\npm.ps1 run dev '--' --port 5173 --strictPort
# 별도 터미널에서 배포용 정적 결과 확인
.\frontend\npm.ps1 run preview '--' --port 4174 --strictPort
```

`ci`는 재현용 명령이다. 이번 실행 사실은 아래 표를 기준으로 한다. 5173이 실행 중이면 같은 서버를 중복 실행하지 않는다. PowerShell 도우미에는 구분자를 `'--'` 문자열로 전달한다. B2 재검증에서 발견·수정된 실행 안내를 그대로 따른다. `--strictPort`는 포트 충돌 시 다른 포트로 조용히 이동하는 것을 막는다.

375px에서 문서 표시 폭 360px은 세로 스크롤바를 제외한 폭이며 scrollWidth도 360px이었다. 768px 판매자와 1440px 판매자는 각각 scrollWidth가 표시 폭과 같았다. 실제 휴대전화·다른 브라우저·스크린리더 검증은 하지 않았다.

검증 중 4173은 이미 다른 서버가 사용 중이라 새 미리보기 실행이 실패했다. 그 주소에서는 B2 화면이 관찰됐으므로 B3 검증 성공으로 계산하지 않았다. 기존 서버를 종료하지 않고 4174에서 이번 dist를 실행해 다시 확인했다. 임시 JSX 오타로 개발 서버의 갱신 오류가 한 번 발생했으며 즉시 수정한 뒤 최종 타입·린트·빌드와 화면을 확인했다.

브라우저 자동 조작 중 도구의 선택자 옵션과 호출 시간 제한 오류도 있었으며, 해당 중단을 앱 실패나 테스트 성공으로 계산하지 않았다. 지원되는 선택자로 작업을 나눠 실제 결과를 다시 확인했다.

증거: [판매자 데스크톱](evidence/P01-B3-seller-desktop.png), [구매자 모바일](evidence/P01-B3-account-mobile.png). 확인 후 브라우저의 임시 화면 폭 설정을 해제했다. 개발 서버 5173은 결과 확인용으로 유지하고, 이번 검증용 4174 서버는 종료하고 포트 반환을 확인했다.

## 직접 수정해 볼 작은 예시

1. `frontend/src/navigation.ts`에서 판매자 features 중 `path: 'products'` 항목의 `title: '상품 관리'`를 `title: '내 상품'`으로 바꾼다. **path는 유지한다.**
2. `/seller`에서 왼쪽 메뉴·카드 제목이 함께 바뀌는지 확인한다. 카드를 누른 `/seller/products`의 큰 제목·탭 제목도 ‘내 상품’이어야 한다.
3. 주소는 그대로인데 표시 이름만 바뀐 이유를 설명해 본다. `path`는 주소 식별자이고 `title`은 화면 문구다.
4. 타입·린트·빌드를 실행한 뒤 원래 제목으로 되돌린다. 이번 연습은 DB 변경이 없다.

추가 확인: 홈에서 매대 이름을 입력하고 판매자 화면을 갔다가 홈으로 돌아온다. 이름이 초기화되는 이유를 `HomePage`의 생성·제거와 `useState`의 보관 범위로 설명해 본다.

| 구분 | 현재 상태 |
| --- | --- |
| 자동 정적 검사 | 실행·통과 |
| AI의 브라우저 조작 검증 | 위 표 범위에서 실행·확인 |
| 사용자의 화면 직접 확인 | 미확인 |
