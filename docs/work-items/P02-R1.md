검토 및 반영세션의 사용자 직접 요청 `01a16ceb-594e-76d1-98f7-92657489ad88`을 읽어 개발세션의 재현·수정·회귀 검증 승인을 확인했다. 기존 서버와 모든 DB를 유지하고 새 격리 DB에서만 검사한다. P03·삭제·초기화·원격 push는 진행하지 않는다.

## 범위와 검증 계획

- 기존 코드는 서비스에서 읽은 시각을 저장소에 값으로 넘겨 잠금 대기 후에도 같은 값으로 만료를 판단한다.
- 토큰 행 및 회원 행 각각을 다른 연결에서 잠그고 `pg_stat_activity.wait_event_type='Lock'`를 확인한 뒤 가변 Clock을 만료 경계로 진행한다. 단순 sleep으로 대기 여부를 추측하지 않는다.
- 기존 코드의 실제 실패를 확인한 다음 회원→토큰 순서로 잠금을 획득하고 두 잠금 이후 시각으로 만료를 확인하도록 최소 수정한다. B 복구/D 상태 변경과 회원 우선 순서를 맞춘다.
- 정상 확인·만료·재사용·동시 소비·활성화 실패 롤백 및 기존 전체 Java/DB 검사를 실행한다. 지정 검토 세션에서 새 DB 독립 검증 후 전체 완료 문서에 결과를 반영한다.

## 변경 이유와 한계

`Instant`는 이미 읽은 시각 값이다. `Supplier<Instant>`는 필요한 순간에 시계를 읽을 수 있게 한다. 시간 판정은 두 관련 행의 잠금 이후에 한 번 수행하며, 그 시각을 소비·활성화 시각으로 일관되게 사용한다. 트랜잭션 commit 시각까지 유효해야 한다는 별도 정책을 도입한 것은 아니다. 정책 기준은 관련 회원·토큰 행을 확보한 뒤의 처리 시각이다.

회원 행을 먼저 잠그므로 토큰을 먼저 잠근 뒤 회원을 기다리는 역순을 없앴다. B 복구와 D 상태변경도 회원을 먼저 잠근다. 원문 토큰 노출, 재발송, 외부 메일, HTTP 계약이나 스키마 변경은 이번 범위가 아니다. 모든 동시성 조합·운영 부하 검증으로 확대하지 않는다.

학습 확인 예시: 테스트의 `current.set(issuedAt.plusSeconds(1800))`와 저장소의 `expires_at > :now`를 함께 읽고, 만료 시각과 같은 경우 왜 거부되는지 설명해 본다. `clock.instant()` 값 전달과 `clock::instant` 함수 전달에서 실제 시계를 읽는 시점이 어떻게 달라지는지도 비교한다. 사용자 직접 실습·이해 확인은 자동 테스트 통과와 별개로 아직 받지 않았다.
