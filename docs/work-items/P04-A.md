# P04-A 카테고리·상품 기본 관리

2026-10-24 / 기준 3c5acc0 / 구현·검증·독립 검토 완료. P04-B 이후는 진행하지 않는다.

## 범위와 결정

F04·F16, AC05 일부: 운영 카테고리 생성/수정/비활성화, 판매자 본인 상품 생성/조회/수정/판매 중지/보관, 공개 API 필터, React 관리 화면. SKU·가격·옵션·이미지·재고·구매·검색 화면은 후속 단계다. 샘플 20개와 옵션/품절 데이터는 P04 전체 기준이므로 이번에 가짜 SKU를 만들지 않는다.

기존 기술과 모듈 경계를 유지한다. catalog가 상품을 소유하고 seller.api의 거래 내 MANAGE_CATALOG 검사로 회원→매대→카테고리→상품 잠금 순서를 지킨다. 기존 검토 세션과 같은 저장소에서 codex/p04-a 브랜치를 사용한다. 기존 서버 재시작/기존 DB 마이그레이션/기존 검증 DB 재사용은 하지 않는다.

- 카테고리는 단일 계층, 고유 이름 1~80자, active와 version. ADMIN+CONTENT만 운영하며 비활성화로 삭제를 대체한다. 기존 상품 연결을 보존한다.
- 상품은 storeId/categoryId/고유 불변 slug/title(1~120)/description(0~4000)/state/version/isHiddenByAdmin. DRAFT·ACTIVE·STOPPED·ARCHIVED. 물리 삭제 대신 ARCHIVED로 보관하며 보관 후 수정/복구는 이번에 제공하지 않는다. ACTIVE는 공개 등록 상태이며 SKU·구매 가능을 보장하지 않는다.
- 생성은 DRAFT만, 수정은 읽은 version 필수. 타인 상품은404, 권한403, 버전/운영 상태 충돌409, 잘못된 입력400. 카테고리 비활성 중 ACTIVE 전환 금지. 판매자가 운영 숨김 플래그를 입력·해제할 수 없다.
- 공개 목록/상세는 ACTIVE, 운영 숨김 아님, 활성 카테고리, OPEN+visible 매대, ACTIVE SELLER 모두 충족해야 한다. 응답에 소유자/운영 플래그를 노출하지 않는다. 목록은20개, 안정된 id 순서와 page/hasMore를 사용한다.
- 모든 쓰기에 기존 CSRF 및 서비스 권한 검증. 카테고리/상품 낙관 버전으로 오래된 값 덮어쓰기를 차단한다.

## 작은 작업과 검증 기록

독립 사전 검토 반영: DRAFT→DRAFT/ACTIVE/STOPPED/ARCHIVED, ACTIVE→ACTIVE/STOPPED/ARCHIVED, STOPPED→STOPPED/ACTIVE/ARCHIVED를 허용한다. ARCHIVED는 종료 상태이며 ACTIVE/STOPPED→DRAFT는 거부한다. 비활성 카테고리에서는 ACTIVE 저장을 거부하고 중지/보관 및 비공개 상품 수정은 허용한다. 카테고리 재활성화는 기존 ACTIVE 상품을 다시 공개한다(카테고리 화면에 안내). 매대 복구는 기존 P03 규칙대로 별도 재공개가 필요하다.

카테고리 변경은 처리자/대상/전후 이름·활성/시각 이력을 같은 트랜잭션에 저장한다. 상품 쓰기는 회원→매대→카테고리→상품 순으로 잠그고 카테고리 활성 여부를 잠금 뒤 판정한다. 카테고리 변경은 카테고리만 잠가 역순 잠금을 만들지 않는다. 공개 필터는 단일 SQL의 읽기 projection으로 관련 상태를 같은 스냅샷에서 판정한다(다른 모듈 테이블 쓰기는 금지). 이후 분리 시 projection/API 교체가 필요한 결합임을 기록한다.

1. 카테고리 HTTP 실패 검사 → V11/카테고리 API 구현 → 새 격리 DB 검증.
2. 상품 HTTP·소유권·공개 필터·상태 검사 → 상품 구현 → 새 격리 DB 검증.
3. 관리 화면 → 단위/타입/린트/빌드/실제 브라우저 검증.
4. 기존 검토 및 반영세션의 독립 검토, 보완, 보존 확인과 결과 기록.

초기 작업 트리는 깨끗했다. 기존 DB 덤프 해시·DB 목록·컨테이너·리스너를 evidence/P04-A-before.json에 기록했다. 사용자 직접 학습/화면 확인은 미확인이다.

## 구현 파일과 API

- `catalog.api`는 Category/Product 계약, `catalog.infrastructure`는 JDBC 거래·검증·공개 projection, `catalog.web`은 HTTP와 공통 오류를 담당한다.
- V11 카테고리, V12 상품/인덱스, V13 카테고리 변경 이력. 이미 새 검증 DB에 적용된 V11을 고치지 않고 V13으로 이력을 추가했다.
- `/api/admin/content/categories` GET/POST, `/{id}` PUT. `/api/categories` GET은 활성 목록. `/api/seller/products` GET/POST, `/{id}` GET/PUT. `/api/products` 및 `/{slug}` GET은 공개 필터 적용. 목록 page 0~10000, 20개와 hasMore.
- React `/admin/catalog`, `/seller/products`에 목록·페이지·등록·수정·오류·재조회·보관 확인을 연결했다. 카테고리는 CONTENT 권한, 상품 화면은 기존 판매 기능 경계를 사용한다. 쓰기를 자동 재시도하지 않고 CSRF/읽은 version을 보낸다.
- 설명은 CRLF/CR을 LF로 정규화하고 LF와 탭을 허용한다. 이름/상품명은 단일 행이다. 그 밖의 제어문자와 잘못된 surrogate는 거부한다. 문자 길이는 화면과 서버 모두 code point 기준이다.

## 재현과 보완

1. 카테고리 미구현 POST가201 대신404인 실패 후 구현, `p04-a-category-green`에서 기본130·DB59 통과.
2. 상품 미구현 POST가201 대신404인 실패 후 구현. 감사 테이블 부재를 확인한 뒤 감사 저장·롤백 구현, `p04-a-core-green`에서 기본130·DB61 통과.
3. 상품 등록 폼 부재 단위검사 실패 후 화면 연결. 코드포인트 보완 이후 Vitest12파일85개와 타입/린트 통과.
4. 독립 검토 R1: 실제 카테고리 행 잠금 대기를 관측한 뒤 CONTENT 회수 후에도 변경되던 경로를 재현했다(`p04-a-r1-red`: denied 대신 changed). 잠금 획득 뒤 권한 재확인을 추가했다. 최초 재현 시 pg_stat_activity 통계 스냅샷 캐시 때문에 대기 관측 자체가 실패했으며, pg_stat_clear_snapshot을 호출하도록 검사만 교정했다.
5. 독립 검토 R2: 여러 줄 설명이400으로 거부되는 문제를 실제 서비스/DB 검사로 재현 후 설명 전용 정규화·허용 규칙을 적용했다. 단일 행 필드 제어문자 거부는 유지했다.
6. 화면 emoji80자가 HTML maxLength의 UTF-16 기준으로 잘리는 실패를 재현했다. 문자 단위 제출 검사로 교체했다.
7. 최초 전체 브라우저 실행은 신규 검사에서 seed 비밀번호를 잘못 사용했다. 테스트의 비밀번호와 별도 브라우저 문맥 baseURL을 교정했다. 이후 중첩 label에 select 옵션/저장된 textarea 내용이 포함되어 정확한 레이블 조회가 실패했다. 명시적 htmlFor/id로 수정하고 저장된 여러 줄 설명의 레이블 회귀를 추가했다. 모바일 폼과 준비 상태 안내도 실제 구현에 맞게 수정했다.
8. `p04-a-acceptance`에서 신규 PC/모바일 상품 흐름은 통과했으나 기존 모바일 판매자 여정의 조치 응답 실패가 반복됐다. 서버 로그에서 Hikari 연결5개 모두 사용 중·대기4개의 연결 고갈을 확인했다. LoginMembers의 RowMapper 내부 roles 조회와 JdbcStores.published의 ResultSetExtractor 내부 access 조회가 연결을 보유한 채 두 번째 연결을 얻는 구조를 발견했다. 단순 시간 초과 연장으로 숨기지 않고 새 DB에서 pool1로 재현하고 보완한다. P04-A 완료를 막는 기존 결함에 대한 최소 보완이며 P04-B 또는 성능 개선 단계로 확장하지 않는다.
9. 최초 제한된 실행은 로컬 loopback 연결이 막혔다. 승인된 실행 권한으로 재검증했고, 최초 실행의 프로세스 트리만 식별해 종료했다. 기존 서버는 종료하지 않았다.

## 학습과 직접 확인

React 입력 → CatalogStore의 CSRF/버전 포함 HTTP → 컨트롤러 → 권한·매대 기능·카테고리/상품 잠금 → SQL과 감사 이력 → 응답 검증 → 목록/폼 갱신 흐름이다. Java의 익숙한 메서드 호출과 달리 화면의 요청은 늦게 도착할 수 있어 generation과 AbortController로 인증 변경 후 결과를 폐기한다.

직접 해 볼 작은 예: 새 격리 검증 환경의 카테고리 이름과 상품 설명 두 번째 줄을 수정하고 다시 조회한다. 공개 등록 상품의 카테고리를 비활성화하면 공개 API가404가 되고 재활성화하면 다시 보이는지 확인한다. 자동 검증 결과와 별개로 사용자 직접 확인·이해 여부는 미확인이다.

## 제한

SKU/가격/옵션/이미지/재고/구매·공개 탐색 화면은 아직 없다. ACTIVE는 실제 구매 가능 표시가 아니다. 카테고리는 단일 계층이며 감사 이력의 운영 조회 화면은 이번에 제공하지 않는다. 보관 상품 복구·카테고리 물리 삭제는 제공하지 않는다. 기존 서버에는 마이그레이션을 적용하거나 재시작하지 않았으므로 기존 실행 화면은 이번 구현과 다를 수 있다. 실제 모바일 기기·상용 부하 검증은 하지 않는다. 공개 projection은 다른 모듈 테이블을 읽는 결합이 있으며 MSA 전환 시 별도 데이터 계약이 필요하다.

### 연결 고갈 보완

`p04-a-pool-red`의 새 DB에서 연결 풀1개·300ms 대기 조건으로 회원 조회와 공개 매대 조회 모두 연결 획득 오류를 재현했다. 회원/역할은 하나의 SQL에서 읽고, 공개 매대는 조회 연결을 반환한 뒤 identity API로 판매자 자격을 확인하도록 수정했다. 풀 크기나 시간 제한을 늘려 문제를 덮지 않았다. 기존 회원/공개 매대 규칙은 유지한다. 해당 두 검사와 기존 전체 회귀를 새 DB에서 다시 실행했다. 연결 보완 당시 기본130·DB66·브라우저22가 통과했다. 후속 R4/R5 결과는 아래 최신 집계를 따른다.

### 독립 최종 검토 R4

독립 세션에서 기본130·DB66·브라우저22·화면86을 확인한 뒤, 마지막 계약 대조에서 상품 저장이 회원 잠금을 기다리는 동안 계정이 정지될 때 AccountException이 공통409로 매핑되지 않는 경계를 발견했다. 지정 검토 세션도 필수 보완으로 판정했다. HTTP 요청의 실제 회원 행 잠금 대기를 관측한 뒤 정지를 commit하여500을 재현하고, 기존 StoreController와 같은409 오류 계약으로 최소 보완한다. 이전 성공 수치로 이 경계가 검증되었다고 표시하지 않는다.

R4는 실제500을 확인한 뒤 AccountException409 매핑을 추가했고, 최종 개발 실행에서 HTTP409/공통 CONFLICT/상품0건과 전체 회귀가 통과했다. 프런트 제품·검사는 R4에서 변경하지 않았다.


### 독립 최종 검토 R5 — 이력 순서

R4 독립 전체 실행은 기존 모바일 판매자 여정의 이력 순서에서 실패했다. 실제 정지→복구→폐점 후 저장 시각은 각각 13:05:09.166468, 13:05:09.386373, 13:05:08.974427 UTC였다. 시각이 역행한 구체 시스템 원인은 확인하지 않았다. occurred_at/랜덤 UUID 정렬로 인과 순서를 보장할 수 없는 결함이다. `p04-a-history-red`의 새 DB에서 마지막 조치 시각을 강제로 앞당겨 기대 close/restore/suspend 대신 restore/suspend/close를 재현했다.

V10은 수정하지 않고 V14에서 nullable 양수 store_version 및 매대별 non-null 유일 인덱스를 추가했다. 기존 매대 잠금 안에서 상태 변경 뒤 버전(current.version+1)을 감사 이력과 함께 저장한다. 조회는 버전 내림차순, NULL은 뒤로 보내고 기존 시각/ID 정렬을 적용한다. 일반 매대 편집도 버전을 올리므로 이력 버전은 연속번호가 아니다. 기존 NULL 이력은 보존하며 과거 인과 순서 복원을 보장하지 않는다. 시각 역행·동률과 미래 시각을 가진 NULL legacy 이력이 섞인 경우 모두 새 버전 이력이 먼저 나오고 legacy 조회가 유지되는 회귀를 추가했다. 운영 DB에 마이그레이션은 적용하지 않았다. 기존 상태·visible·버전·감사 원자성 검사를 함께 다시 실행한다.

R5 개발 최종 실행 p04-a-history-green은 기본130·DB68·브라우저22 전부 통과했다. 새 DB는 보존했으며 지정 검토 세션의 별도 신규 DB 독립 재검증을 요청했다.

## 기존 환경 보존 확인

[보존 비교](evidence/P04-A-preservation.txt)에서 기존 개발·테스트 DB의 정규화 덤프 SHA256, 이전 DB 목록, 컨테이너 ID와 기존 리스너 주소·포트·PID가 작업 전과 동일했다. 과거 검증 DB 전체 행 덤프 비교는 하지 않았으며, 매 실행 신규 DB를 지정하고 기존 DB를 삭제·재사용하지 않았다. 신규 검증 DB와 실패 실행 증거도 남겼다. 기존 서버 재시작·기존 DB 마이그레이션은 하지 않았다.


## 최종 판정

기존 검토 및 반영세션의 [독립 검토](P04-A-review.md)가 별도 신규 DB에서 기본130·DB68·브라우저22를 통과하고 R1~R5 해결을 확인했다. 프런트 단위86·타입·린트·빌드도 독립 검증 증거를 확보했다. [최종 독립 보존 비교](evidence/P04-A-review-history-preservation.json)에서 기존 DB 해시·목록·컨테이너·리스너 유지와 새 검증 DB 보존을 확인했다. 필수 잔여 또는 차단 항목은 없다. 위 제한과 사용자 직접 확인 미완료는 유지한다. P04-B 이후는 미착수이며 원격 푸시는 하지 않는다.
