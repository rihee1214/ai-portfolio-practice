## 확정 정책

- Java/Spring JDBC/PostgreSQL 모듈형 모놀리스와 React/TypeScript를 유지한다. 각 모듈은 자기 테이블만 변경하고 다른 모듈은 `api` 계약으로 호출한다. 플랫폼은 업무 모듈을 참조하지 않으며 순환 의존은 ArchUnit으로 거부한다.
- 주문 소유자는 회원 또는 GuestBuyer 정확히 하나. CheckoutSession 자체는 소유권이 아니다. 부모 주문1개·매대별 하위 주문1개·항목/수량별 스냅샷을 저장하고 구매자/수령인 정보를 분리한다.
- SKU1~20종·수량1~99, Java long/DB BIGINT checked 계산, HTTP 금액은 P07처럼 10진 문자열·프런트 BigInt. 상품 행사→쿠폰→배송비→배송 행사와 50,000원 기준을 그대로 쓴다. 원 단위 배분·혜택/정책 버전·상품/옵션 이름을 복사하며 나중의 수정/비공개로 바뀌지 않는다.
- 견적 fingerprint는 권한이 아니다. 서버가 현재 견적을 재계산하고 달라지면409+새 견적, 사용자 재확인 후 새 요청 키. 응답 유실은 같은 키/내용으로 재조회하고 임의의 새 키로 재생성하지 않는다. 비밀번호·인증코드·복구코드·세션 원문은 requestHash/로그에 넣지 않는다.
- 부모 주문 전체 금액을 한 번에 결제한다. DEMO/SANDBOX는 서버 설정이다. 브라우저 redirect/클라이언트 금액/미검증 webhook은 결제 성공 근거가 아니다. 0원은 PG 없이 검증된 동일 확정 경로와 이력을 사용한다.
- 예약 기본15분. 쿠폰 예약은 원만료를 넘지 않고 최대15분·마이크로초 정규화 제약을 가진다. 하나의 주문 기한을 서버에서 `min(현재+15분, 선택 쿠폰 종료들)`로 제안하고 A/C에서 저장·경계 계약으로 고정한다. PROCESSING/UNKNOWN은 시간 도래만으로 해제하지 않는다.
- 외부 API를 DB 거래 안에서 호출하지 않는다. 승인 전 시도 저장→외부 호출→짧은 결과 반영 거래. 결과·주문·전체 예약 확정/해제·Outbox는 같은 거래다. 프로세스 중단 뒤 DB에서 재개한다.
- 회원 정지/탈퇴·판매자 권한 변경·상품 비공개 이후에도 기존 주문 스냅샷은 보존한다. 신규 주문 자격과 기존 거래 조회/후속 처리 권한을 혼동하지 않는다. 개인정보는 no-store, 판매자에게 자기 하위 주문과 배송 필요 필드만 제공한다.

## 선행 인계 계약과 설계 공백

| 실제 선행 계약 | P08가 이어받을 책임 / 담당 |
| --- | --- |
| `promotion.api.Quotes.calculate(UUID,List<LineRequest>,List<CouponSelection>)`와 immutable Quote/Unit | A는 전체 스냅샷 보존, C는 서버 재계산·현재 자격 재검사. 현재 HTTP는 `/api/quotes`이며 설계의 경로 예시 때문에 중복 엔드포인트를 만들지 않는다. |
| `CouponReservations.reserve(List<Request>)` | C는 같은 checkout/member/full Quote의 전체 batch를 한 번 전달. 일부 예약 뒤 새 쿠폰 추가는409. batch→정규 UUID 계정→매대→쿠폰 순서를 뒤집지 않는다. |
| `CouponReservations.commit/release/expire(checkoutId,ids)` | D는 DB에 저장한 해당 주문의 전체 IDs를 사용. 일부 ID만 전달해 부분 결제 확정을 만들지 않는다. 호출자만 결제 사실과 불명확 결과를 조정한다. |
| `inventory.api.Reservations.reserve/commit/release/expire` | C/D는 전역 예약/주문항목 키→SKU 정규순→예약 ID순 내부 잠금을 존중하고 수량/주문/권한을 먼저 검증한다. 현재 P04-E 상태와 새 주문 상태를 매핑한다. |
| `guest.infrastructure.JdbcGuestAccess.attachOrder` (아직 공개 api 아님) | C에서 최소 `guest.api` 계약을 추출해 기존 구현이 수행하게 한다. order가 infrastructure나 guest 테이블을 직접 참조하지 않는다. 전화 인증 소비·NEW/EXISTING 연결·실제 주문 참조가 같은 거래인지 증명한다. F용 조회 권한 공개 계약도 필요하다. |
| 쿠폰 commit은 기한 후 거부, UNKNOWN은 해제 보류 | D는 UNKNOWN 동안 예약을 잡아두되 임의 연장/기한 후 commit을 하지 않는다. 늦은 성공은 안전하게 확정 가능한지 확인하고 불가능하면 보상 취소·운영 확인으로 수렴. 고객 성공을 먼저 표시하지 않는다. |
| `RefundCompletion(full,confirmed)` / Restoration.reusable | 실제 하위 주문 전체 취소/반품 완료 증명은 P09 책임. P08의 결제 전 실패는 release/expire이며 restore로 우회하지 않는다. reusable은 당시 결과이며 새 사용 권한이 아니다. |

C 착수 첫 작업은 통합 잠금 표다. guest checkout→buyer→session, coupon batch→accounts→stores→coupons, inventory keys→SKU→reservation과 주문·결제/worker 잠금을 나란히 기록한다. 기존 API를 단순히 정해진 순서로 호출하는 것만으로 안전하다고 가정하지 않는다. 두 판매자가 서로 구매·같은 구매자 다른 주문·계정 정지·재고 수동 변경·동일 checkout retry를 barrier로 재현한다. 충돌 시 공개 API의 잠금 준비/명령 분리 등 필요한 최소 보완과 선행 회귀를 C에 포함하고, 잠금 순서 증거가 없으면 C를 차단한다.

의존 방향 초안은 payment→order→guest/promotion/inventory, fulfillment→order, 업무 모듈→platform의 일반 Job/Outbox 포트다. order가 payment 구현을 역참조하지 않으며 주문 잠금/결제 상태 조정은 공개 주문 계약을 통해 동일 거래에서 처리한다. 읽기 화면은 별도 권한 있는 API들을 조합한다. B의 플랫폼 실행기는 업무별 핸들러의 구현 타입을 import하지 않는다. A/B에서 실제 ArchUnit 판정과 비교해 확정한다.

## 모든 단계에 적용하는 실행·독립 검토 기준

1. 해당 문서의 제약 ID·검사 메서드·정상/경계/거부/경합 assertion을 먼저 확정한다. 계획 이름 변경 시 새 이름과 이유를 문서/필수 목록에 함께 남긴다.
2. 새 검사 red의 원인을 기록한 뒤 최소 구현→집중 green. 단위는 JUnit, 모듈 경계는 기존 ModuleArchitectureTest/ModuleRulesTest, 거래는 새 PostgreSQL의 실제 독립 연결·거래로 검증한다. sleep만으로 경합을 추정하지 말고 latch/barrier·실제 잠금 관측·조절 Clock을 사용한다.
3. 프런트 변경은 Vitest 상태 검사와 실제 API·DB를 사용하는 PC/모바일 Playwright를 추가한다. 화면 없는 A/B도 기존 프런트/브라우저 회귀를 전체 실행한다. 새 필수 검사는 `verification/required-tests.json`, `required-browser.json`, `required-frontend.json`에 추가한다. 새 IT/worker 검사 파일이 수집되지 않으면 하네스 연결도 해당 단계 작업이다.
4. 개발 최종 명령: `./verify.ps1 -Offline -EvidenceDirectory .local-tools/p08-<stage>-dev-<새고유값>`. 성공 조건은 종료0, result.status/preservation=passed, 필수 누락·실패·skip0, 실행 전후 inputs 해시 일치다. 캐시/의존성 부재는 차단으로 기록한다.
5. 소스를 동결하고 구현자와 분리된 지정 검토세션에서 설계·diff·제약별 assertion을 검토한 뒤 `.local-tools/p08-<stage>-review-<새고유값>`에서 같은 루트 명령을 독립 실행한다. 개발/독립 하네스를 동시에 실행하지 않는다. 검토자는 실제 검토 시 `P08-<stage>-review.md`를 작성한다. 이번 계획에는 가짜 검토 결과를 만들지 않는다.
6. 지적마다 ID·심각도·재현 검사·수정·새 증거·잔여 차단을 기록한다. 기능 수정 뒤 개발/독립의 최종 소스 일치를 다시 확보한다. 검사 삭제·필수 목록 축소·타임아웃 확대만으로 실패를 숨기지 않는다.
7. 기존 서버·DB·검증 DB·미디어·데모를 보존한다. 하네스가 생성한 새 DB/미디어만 사용하며 실패 DB/로그도 삭제하지 않는다. before/after와 P06/P07 실패 manifest14158파일 및 후속 신규 manifest를 해시 대조한다. 과거 검증 DB 존재 비교와 전체 행 덤프 비교를 구분한다.
8. 완료 기록에 HEAD+dirty/inputs SHA, 명령·실행 시각·새 DB/미디어/에뮬레이터 경로, 제약별 기대/실제 결과, 필수 coverage, 검토 결과, 보존 비교, 실패 이력과 미검증을 남긴다. `evidence/P08-<stage>-dev-final-*`, `review-final-*`, `failure-manifest.json`으로 필요한 증거를 저장하되 비밀/개인정보를 노출하지 않는다. 원본은 격리 경로에 유지한다.

P08-E의 실제 제공자 검증은 Offline 로컬 하네스 통과와 별도 증거가 필요하다. 로컬 하네스에 모의 계약 검사를 포함하고, 외부 테스트 실행의 환경/모드/서버 검증·수신 결과를 별도 기록한다. 제공자 접근이 없으면 로컬 성공만 기록하고 E/G의 PG 항목을 미검증으로 둔다.

## 작성 시점 점검과 인계

이번에는 저장소의 설계·계획·공개 API·P07/P06 인계를 대조하고 문서 링크/단계 커버리지를 정적 점검했다. 전체 하네스와 독립 구현 검토는 실행하지 않았다. 모든 단계의 아래 실행 기록은 미실행이며 P08 구현 완료가 아니다. 다음 실제 착수 대상은 P08-A다. 분할 배송·클레임·부분 환불·구매 확정 전체 정책은 P09에 남긴다.
