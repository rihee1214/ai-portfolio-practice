# P01-C1 Docker Compose PostgreSQL 개발·테스트 환경

2026-10-23 / 상태: 완료 — 구성·검증·지정 세션 검토 반영

## 범위와 결정

설계 v4·ADR-002·P01-C1만 수행한다. Docker 접근 → Compose·계정·볼륨 구성 → 접속과 분리 → 중지/재시작/컨테이너 재생성 후 데이터 보존 → 지정 검토 및 반영 순서다. Spring JDBC·Flyway·업무 스키마는 C2 이후다.

Docker client/engine 28.0.1, Desktop 4.39.0, Compose 2.33.1, desktop-linux·linux/amd64를 확인했다. 제한 환경에서는 named pipe 접근 거부, 승인 실행에서는 정상이다. 시작 당시 실행 중 컨테이너는 없었지만 기존 볼륨들이 있으므로 기존 볼륨을 정리하거나 재사용하지 않는다.

컨테이너 2개를 선택했다. 자원이 조금 더 들지만 개발·테스트의 중지와 볼륨을 독립 검증할 수 있다. 프로젝트 이름은 moa-market-local이며 서비스 db-dev/db-test, 호스트 loopback 포트 15432/15433, DB 및 앱 계정 marketplace_dev/marketplace_test를 사용한다. 앱 계정은 DB 소유자이지만 superuser·CREATEDB·CREATEROLE 권한은 없다. 초기화용 postgres 암호도 각각 분리한다.

공식 postgres:18.6 태그를 사용하고 실제 digest를 실행 결과에 기록한다. PG18 볼륨 마운트는 /var/lib/postgresql이며 PGDATA는 이미지 기본값을 따른다. .env는 추적 제외하고 비밀값 없는 .env.example만 공유한다. 새 볼륨에서만 실행되는 초기화 스크립트는 DB/역할만 생성하며 업무 테이블은 만들지 않는다.

완료 조건은 인증 접속, 잘못된 암호/반대 환경 계정 거부, DB 식별, 독립 중지, restart 및 force-recreate 후 검증용 데이터 보존이다. host TCP 접근과 컨테이너 내부 psql을 구분하며 미검증 항목은 통과로 표시하지 않는다.

## 실행 결과

- [18건 검사](evidence/P01-C1-verification.json) 모두 통과. DB·역할·버전 180006·비관리자 권한, 잘못된 암호와 반대 환경 역할 거부, 양방향 독립 stop/start, restart 데이터 보존, 컨테이너 ID 변경과 볼륨 데이터 보존, 호스트 두 포트의 PostgreSQL 응답을 확인했다.
- 최초 검사에서 server_version 문자열의 Debian 접미사를 정확히 비교하지 못했다. 제품 문제가 아니라 검사 조건 문제로, server_version_num으로 변경했다. [최초 실패](evidence/P01-C1-verification-first.json)를 보존한다.
- 호스트 TCP 검사는 SSLRequest에 N 응답을 확인했다. 로컬 비TLS DB이며 인증 SQL은 컨테이너 내부 TCP로 검증했다. 호스트 JDBC·Boot 연동은 미검증이며 C2에서 수행한다.
- [이미지 digest](evidence/P01-C1-image.txt), [컨테이너 상태](evidence/P01-C1-containers.json), [볼륨](evidence/P01-C1-volumes.txt), [실제 데이터 경로](evidence/P01-C1-data-directory.txt)를 저장했다. 앱 계정의 data_directory 조회는 권한 거부되었고 관리자 소켓으로 경로만 조회했다.
- 프로젝트 전용 신규 컨테이너·볼륨만 조작했다. 기존 볼륨과 API/프런트 서버를 중지·대체하지 않았다. 임시 검증 테이블은 제거했고 개발·테스트 컨테이너는 healthy 상태로 남겼다. 볼륨 삭제는 수행하지 않았다.
- .env에 무작위 암호4개를 생성했으며 Git ignore 확인. Compose config --quiet 통과. 실제 암호는 출력·증거·커밋에 포함하지 않는다.

[실행 안내](../postgresql-local.md)에 명령·연결 주소·암호 변경 한계·볼륨 보존·사용자 실습을 정리했다. [검사 스크립트 원문](evidence/P01-C1-verifier.txt)은 저장소 루트에서 .local-tools/verify-c1.ps1로 실행한 기록이다. 재실행 시 해당 프로젝트 DB를 중지/재생성하므로 실행 중인 앱 작업과 조율해야 한다.

새 PC·다른 플랫폼·호스트 JDBC·사용자 직접 실습은 미검증이다. 지정 검토 세션에서 최종 검토 범위 통과와 C1-R1 해소를 확인했다. P01-C2는 진행하지 않는다.

## 검토 보완

반대 환경 역할 검사를 보완해 두 서비스에서 password authentication failed와 반대 역할 0건을 확인했다. [추가 인증 증거](evidence/P01-C1-cross-role.json)를 별도로 기록했고 재현 스크립트의 해당 조건도 강화했다. 18건 전체 lifecycle을 반복한 것은 아니다. [임시 표 정리](evidence/P01-C1-probe-cleanup.txt)는 두 DB 모두 0건이다. [빈 암호 예제 거부](evidence/P01-C1-empty-password.txt)도 확인했다. [실제 로컬 암호의 Git 후보 포함 검사](evidence/P01-C1-secret-scan.json)에서 일치 0건이며 .env 제외를 확인했다. 완전한 보안 감사로 해석하지 않는다.

최종 보완: healthcheck에 -h 127.0.0.1을 지정해 초기화 임시 소켓 대신 TCP 준비를 확인한다. [설정 반영 재실행](evidence/P01-C1-final-up.txt)에서 두 서비스 healthy, 실제 TCP 인증 SQL에서 각각 marketplace_dev/marketplace_dev와 marketplace_test/marketplace_test를 다시 확인했다. healthy 자체가 인증 검사를 대신하지 않는다는 한계는 유지한다.

## 최종 호스트 인증 보완

최초 호스트 handshake 한계를 해소하기 위해 임시 pgJDBC 42.7.13을 Maven Central에서 .local-tools/c1-client에 준비했다. backend/pom.xml·앱 코드·Spring 설정은 변경하지 않았다. [호스트 JDBC 검사](evidence/P01-C1-host-jdbc.txt) 4건 통과: 127.0.0.1의 15432/15433에서 각각 DB·사용자 식별, 잘못된 암호 SQLSTATE 28P01 거부. [검사 원문](evidence/P01-C1-host-jdbc-source.txt)은 로컬 .env를 읽되 암호를 출력하지 않는다. 위 호스트 인증 미검증 표현은 이 추가 검사 전 이력이다. Spring Boot JDBC/Flyway 통합은 여전히 C2 미착수다.

healthcheck 변경 후 [최종 컨테이너 TCP 인증](evidence/P01-C1-final-auth.json)도 별도 저장했다. 현재 두 DB는 running/healthy이며 보존 검증용 표는 제거했다.


최종 변경은 compose.yaml, .env.example, infra/postgres/init-app.sh, DB 실행 안내와 작업·검토·증거·진행 문서다. [검토 기록](P01-C1-review.md)을 반영했다. 로컬 Git 이력으로 보관하며 원격 push는 하지 않는다. C1 완료는 개발/테스트 DB 준비와 검증 범위이며 Spring Boot 연동·Flyway(C2) 완료를 의미하지 않는다.
