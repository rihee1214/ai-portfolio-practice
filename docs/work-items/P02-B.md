# P02-B 비밀번호 복구·프로필·배송지

2026-10-24 / 기준 ab61e81 / 상태: 구현·검증·독립 검토 완료

사용자가 이 개발 채팅에서 P02-B 구현·검증을 직접 승인했다. 기존 React·Spring Security·JDBC 구조를 유지하고 `writing-plans` 방식으로 아래 작은 작업을 순차 진행한다. 다음 단계·push는 하지 않는다. 기존 서버·DB를 유지하고 검증마다 새 UUID DB만 변경한다. 개발 검토는 검토 및 반영세션에서 수행한다.

## 범위와 결정

1. 비밀번호 재설정: POST /api/auth/password/request 및 /reset. 가입 이메일의 로컬 복구 메일함, 30분·일회성·최신 요청만 유효한 토큰. DB에는 SHA-256만 저장. 없는/미확인/정지 회원에도 동일202 응답. 새 비밀번호는 기존12~128 코드포인트/Argon2id 정책. 성공 시 authVersion 증가·기존 JDBC 세션 삭제, 자동 로그인 없음. 토큰 재사용·만료·동시 소비·다른 용도 토큰 거부. 요청/확인에 CSRF·반복 제한 유지. 외부메일·비회원복구는 제외.
2. 프로필: GET/PUT /api/account/profile. 표시 이름(1~80자)·연락처(선택)를 수정하고 이메일은 읽기 전용. 연락처 저장은 전화 본인확인을 뜻하지 않는다. 계정 자격·이메일 변경·탈퇴는 제외.
3. 배송지: GET/POST /api/account/addresses, PUT/DELETE /{id}. 이름표40자, 수령인80자, 전화7~25자, 국내 우편번호5자리, 주소200자/상세200자. 최대20개. 첫 주소는 자동 기본, 새 기본 지정 시 이전 기본 해제, 기본 삭제 시 오래된 남은 주소 승격. false만으로 유일 기본을 없애지는 않는다. 회원 행 잠금과 부분 유일 인덱스로 경쟁을 제어한다. 타인 주소는404, 본인 ID는 세션에서만 받는다.
4. React: /password/request, /password/reset, /account/profile, /account/addresses. 변경은 CSRF 선행, 자동 POST/PUT/DELETE 재전송 없음. 인증 실패·로그아웃·탭 복귀 때 개인 정보 숨김/재조회. 회원정보 전체 삭제를 프로필 CRUD에 억지로 포함하지 않으며 탈퇴는 P02-D다.

- [x] React 폼과 세션 오류 처리, 타입·린트·단위·실제 브라우저 검증.

필드·상한은 이번 작업의 테스트 가능한 기본 결정이다. 기존 요구사항의 거래·주문 시 주소 스냅샷은 후속 작업이며 여기서 구현하지 않는다. 실제 메일·주소검색 API·전화 인증·운영 분산 제한은 범위 밖이다.

## HTTP 계약

| 요청 | 본문 | 성공 응답 |
| --- | --- | --- |
| POST /api/auth/password/request | email | 202, status=PASSWORD_RESET_REQUESTED |
| POST /api/auth/password/reset | token, password | 200, status=PASSWORD_RESET |
| GET /api/account/profile | 없음 | 200, email/displayName/phone |
| PUT /api/account/profile | displayName, phone | 200, 변경된 프로필 |
| GET /api/account/addresses | 없음 | 200, addresses 배열 |
| POST /api/account/addresses | 아래 배송지 필드 | 201, 생성한 배송지 |
| PUT /api/account/addresses/{id} | 아래 배송지 필드 | 200, 변경한 배송지 |
| DELETE /api/account/addresses/{id} | 없음 | 200, status=ADDRESS_DELETED |

배송지 응답은 id/label/recipient/phone/postalCode/addressLine1/addressLine2/isDefault다. 쓰기 본문에는 id를 넣지 않으며 서버가 경로·세션으로 식별한다. 프로필의 최초 표시 이름은 빈 문자열이며 저장 때는 필수다. 선택 전화는 null, 선택 상세 주소는 빈 문자열로 정규화한다. 유효성 오류400, 로그인 필요401, CSRF403, 소유권 불일치404, 개수 제한409, 반복 제한429는 기존 업무 오류 JSON과 요청 ID를 사용한다. health 응답은 이 계약에 포함하지 않는다.

텍스트는 앞뒤 공백을 제거한 Unicode 코드포인트 수로 길이를 검사하고 제어 문자·잘못된 surrogate를 거부한다. 전화는 숫자를 최소7개 포함하고 허용 구분 문자 `+() .-`를 포함해 최대25자다. 저장이 전화 소유 확인을 의미하지 않는다. 주소가0개면 기본0개, 주소가1개 이상이면 기본은 정확히1개다.

## 진행 중 확인한 실패·수정

- 첫 전체 실행 `.local-tools/p02-b-first`에서 기본 Java129개 중 설정 검사2개 실패. DB 연결을 제외하는 설정 전용 검사에 새 계정 서비스의 JDBC 의존성이 없었다. 실제 DB 생성·브라우저 실행 이전 실패이며 결과를 통과로 세지 않는다. 테스트용 가짜 구성 요소로 설정 검사의 독립성을 보완한다.
- 지정 검토 세션의 R1: 복구 소비 시각을 회원 행 잠금 전에 고정하면 잠금 대기 중 만료된 토큰이 허용될 수 있다. 잠금 획득 이후 시각으로 검사하도록 수정하고 실제 DB 대기·만료 검증을 추가한다. 완료 판정은 수정 후 검증에 따른다.

## 개발 검증 결과

`.local-tools/p02-b-second`에서 기본 Java129개·실제 PostgreSQL 통합41개·인증/계정 브라우저8개(PC4·모바일4)가 모두 통과했다. 통합41개는 기존31개에 P02-B10개를 더한 수다. 브라우저는 통합 검사 안에서 별도로 실행되므로 Java 테스트 건수와 구분한다. Vitest61개·Node68개와 최신 JAR/dist의 기존 브라우저16개도 통과했고, 타입·린트·정적 빌드는 성공했다. [Java 집계](evidence/P02-B-summary.json), [브라우저 결과](evidence/P02-B-browser.txt), [Vitest](evidence/P02-B-vitest.txt), [기존 화면 회귀](evidence/P02-B-p01-browser.txt)를 보존했다.

- 복구: 최신 발급만 유효, 용도 분리, 만료 경계, 중복·동시 소비 거부, 발급/소비 경쟁, 기존 세션 삭제·authVersion 증가·이전 비밀번호 거부. 세션 삭제 뒤 의도적 실패를 넣어 토큰·암호·버전·세션까지 함께 롤백됨을 확인했다.
- R1: PostgreSQL `pg_stat_activity`에서 실제 회원 행 잠금 대기를 확인한 뒤 검사 시계를 만료 경계로 이동했다. 잠금 해제 후 소비 거부와 토큰 미소비·비밀번호/버전 불변이 통과했다. 제품 구현은 잠금을 획득한 후 `Supplier<Instant>`를 호출한다.

첫 설정 검사 실패는 제품 조건을 완화하지 않고 설정 전용 검사에 연결 시 즉시 실패하는 가짜 JDBC/트랜잭션 구성 요소를 주입해 해결했다. 중간 Mockito 시도는 이 환경에서 멈춰 해당 검사 실행만 종료했고, 최종 검사에는 Mockito를 새로 사용하지 않는다. 개발 브라우저 첫 성공 실행은 메일 발급 완료 전 테스트 메일함을 조회해 일시500 로그가 있었다. 최종 테스트는 화면의 접수 완료를 기다린 뒤 조회하도록 보완했으며 독립 재실행에서 확인한다.

## 실행과 남은 제한

준비된 로컬 JDK·Node·Maven 캐시·Chromium·Compose 환경에서 저장소 루트의 `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p02-b-새이름 -Offline -RunBrowser`로 재현한다. 매번 새 디렉터리를 사용하며 새 UUID DB만 생성한다. V5는 기존 마이그레이션을 수정하지 않고 추가했다. 이번에는 기존 개발·테스트 DB에 이행하지 않았다. 임시 API 임의 포트와 브라우저24176이 실행되며 점유된 기존 포트는 재사용하지 않는다.

프로필·주소는 db 프로필, 복구는 db+local-mailbox 프로필에서 동작한다. 로컬 HTTP에만 local-http를 추가하고 SESSION 기본 Secure 설정은 유지한다. 실제 외부 메일은 보내지 않는다. 테스트의 `/__test/mail`, `/__test/reset-mail`은 테스트 소스에만 존재하고 배포 JAR에는 없다. 수동 시연용 공개 메일 조회 API는 만들지 않았다. 수동 확인은 디버거에서 `LocalPasswordResetMailbox.messages()`의 수신자·최신 코드를 확인하는 방식이며 직접 실행해 검증하지 않았다. 메모리 메일함은 서버 재시작 시 사라진다.

운영 HTTPS·실제 이메일 전달·주소검색·전화 소유 인증·분산 반복 제한·대규모 부하·전체 인증 흐름의 production 미리보기는 미검증/범위 밖이다. 반복 제한은 기존 단일 프로세스 IP 창(인증 변경100회/분, 로그인 이메일+IP5회/분)을 복구 경로에도 적용하며 성공 요청도 포함한다. 다중 인스턴스·공유 IP 정책은 후속 운영 설계 대상이다. 진행 중인 요청이 세션 행을 다시 저장하는 모든 경쟁을 재현한 것은 아니며, 다음 보호 요청은 현재 authVersion 대조로 거부한다. P02-C 이후는 구현하지 않았다.

## 독립 검토·완료 판정

지정된 **검토 및 반영세션**에서 별도 `.local-tools/p02-b-review-final` 실행으로 Java129+DB41, 브라우저8개, 프런트 타입·린트·단위61개를 다시 통과했다. [독립 검토](P02-B-review.md)에서 R1 수정 후 잠금 대기·만료 경계 검증을 확인했다. 원래 코드로 R1 실패를 별도 실행한 증거는 없으며 정적 발견과 수정 후 회귀 통과를 구분한다. 테스트 메일 조회를 UI 완료 뒤로 옮긴 마지막 수정도 독립 실행에 포함됐다. [독립 집계](evidence/P02-B-review-summary.json)와 [브라우저](evidence/P02-B-review-browser.txt)를 보존했다. 제품 JAR에 테스트 메일 접근 클래스가 없음을 [패키지 검사](evidence/P02-B-package.txt)로 확인했다. 현재 진행을 막는 항목은 없다.

[작업 전](evidence/P02-B-before.json)과 [작업 후](evidence/P02-B-after.json)의 주 개발·테스트 DB 정규화 덤프 SHA-256이 모두 동일하다.

`6EC093D4CD1B10F9C5516130D120B045391789B6D3DBD462D54833ED96279BE7`

기존 DB 목록 삭제 없음, 기존 컨테이너 `6a9f494624c9`/`68d17431a4b1`과15432/15433 리스너PID57168 유지. 8080/4174/5174는 작업 전후 리스너가 없었고 시작·종료하지 않았다. 이번 새 DB `d2_it_e0d163f9bba34c048ef1b2306e8a316f`와 `d2_it_69571ced865046249351576ae1faa45f`도 삭제하지 않고 보존했다. 기존 과거 격리 DB의 전체 행을 해시 비교한 것은 아니다.

이 문서와 제품·검사·증거를 같은 로컬 커밋으로 기록한다. 원격 push와 다음 단계는 진행하지 않는다. 작업 기록의 실행 한계를 실제 기능 완료와 구분한 상태로 P02-B를 완료 처리한다.

## 학습 연결

React 폼은 입력을 JSON으로 보내고, Java는 로그인 세션에서 회원 ID를 가져와 SQL 조건에 넣는다. 브라우저가 보낸 회원 ID를 신뢰하지 않는 것이 소유권 검사의 핵심이다. TypeScript 타입은 개발 중 실수를 줄이고, Java 입력 검사와 SQL 제약은 실제 저장을 보호한다.

기본 주소를 바꾸는 작업은 기존 기본 해제와 새 기본 지정이 함께 성공해야 한다. 트랜잭션은 중간 실패 시 두 변경을 함께 되돌리고, 회원 행 잠금은 같은 회원의 동시 요청을 순서대로 처리한다. 비밀번호 복구도 토큰 소비·비밀번호 변경·세션 폐기를 한 트랜잭션으로 묶는다.

직접 확인할 작은 실습: 격리 검증 환경에서 주소 두 개를 만들고 기본 주소를 바꾼 뒤 새로고침한다. 기본 표시가 하나인지 확인하고 기본 주소를 삭제해 남은 주소가 기본이 되는지 확인한다. 자동 검증과 별개로 사용자 직접 실습·이해 확인은 아직 미확인이다.
