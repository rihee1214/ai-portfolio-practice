# P09-F 제공자 취소·환불·재조회·대사·운영 복구

상태: **계획 문서 독립 검토 반영 / 구현·검증·구현 독립 검토 미착수**, 2026-10-30.
목표: C~E의 환불을 제공자 결과와 대사해 응답 유실/내부 실패에도1회로 수렴시킨다.
요구사항: F10·F12, AC07·09·10. [공통 계약](P09.md)과 E 개발·독립 전체 통과가 선행이다.

## 상세 계약과 변경 위치

소비: C Refunds/RefundProvider 및 D/E 완료 조건, P08 PaymentProvider/Toss 어댑터·Job/Outbox·UNKNOWN/보상 계약. 생산: 제공자 취소/환불 결과·재조회·운영 대사 기록. C에서 정한 포트를 F에서 임의 변경하지 않으며 필요한 변경은 영향/승인·C~E 회귀를 남긴다.

- 요청은 저장된 payment/claim/refundAttempt 식별자·금액·mode를 사용한다. 외부 API는 DB 거래 밖에서 호출하고 요청 저장→외부→짧은 결과 거래로 처리한다. 승인 보상취소와 고객 부분환불 키·효과를 분리한다.
- 외부 성공/내부 실패와 응답 유실은 UNKNOWN으로 재조회한다. UNKNOWN 점유액은 해제하지 않으며 새 키로 환불을 반복하지 않는다. 재조회 금액/원결제/제공자 취소 식별자를 대조하고 초과·다른 결제·mode 불일치를 거부한다.
- worker 재시도 횟수/시간 한도·backoff·REVIEW_REQUIRED 운영 전환을 이 문서의 작은 작업 F1에서 고정한다. 한도 소진을 실패 확정/금액 해제 근거로 삼지 않는다. 운영자도 근거 없는 강제 성공 boolean·임의 금액 직접 수정 불가; 신규 환불 대사 권한표·사유·조회 근거·감사 필요. 이는 P08-F1 배송 단계와 다른 작업 번호다.
- 제공자 검증 방식은 실제 사용 API/결제수단의 공식 계약을 착수 시 확인한다. P08 카드 webhook 미검증 서명 fixture를 일반 제공자 계약으로 확대하지 않는다. webhook 검증/중복키와 서버 재조회를 함께 검사한다.
- 테스트 키/MID/공개 수신/네트워크가 없으면 실제 SANDBOX는 NOT RUN/BLOCKED. Offline의 stub 결과는 로컬 계약 증거다. 실제 과금/운영키를 사용하지 않는다.

권한은 [공통 운영 권한 인계](P09.md#운영-권한-인계)를 따른다. 기존 P08 승인/보상 대사의 `/api/admin/system/payments`와 `AccessArea.SYSTEM`을 보존한다. 신규 환불 대사를 SUPPORT로 둘지 SYSTEM으로 둘지는 F1에서 경로/메서드별로 판단하고 필요한 승인을 받는다. C의 클레임 지원 권한이 기존 결제 대사 권한을 자동 포함하지 않는다. 확정 FAILED 이후 금액예약/claim 보류/출고차단의 전이는 C10의 확정표를 구현하며, UNKNOWN과 같은 동작으로 뭉개거나 독자적으로 바꾸지 않는다.

예정 변경: `backend/src/main/java/com/example/marketplace/payment/infrastructure/TossRefundProvider.java`, `RefundJobs.java`, `RefundReconciliation.java`, `payment/web/RefundOperationsController.java`(신규), C JdbcRefunds와 기존 Toss 설정의 최소 확장. 정확한 파일은 현재 어댑터와 대조해 F1에 기록한다. 운영 UI는 G에 연결하되 권한 있는 대사 API는 F에서 검증한다.

## 독립 검토와 G 인계

검토자는 프로세스 종료 위치가 실제 commit/ack 경계인지, 제공자 성공 증거 없이 로컬 SUCCEEDED로 만든 검사인지, 누적 환불과 UNKNOWN 합계·중복 복구를 각각 검증했는지 확인한다. F07 미실행이면 F 전체 완료 금지. P08 E/G05 미검증도 별도로 유지한다.

G에 API 오류/확인중/운영확인 상태·최종 조회 DTO·원인별 이력과 실제/모의 구분을 전달한다. 현재 실행 경로·소스 SHA·실패·독립 결과는 없으며 구현 후 기록한다. 실제 사용자 확인도 미확인이다.
