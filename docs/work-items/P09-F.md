### F1 기존 검토세션 설계 판단 — 2026-11-03, 사용자 결정 전 제안

RETURN/EXCHANGE_REFUND의 ITEM과 원배송비는 각각의 typed origin·revision·attempt binding·resultVersion을 유지하고 기존 결과 소비자로 전달한다. E의 세 stage 복구는 저장된 결과 이후만 담당하므로 제공자 재조회 완료로 간주하지 않는다.

#### 자동 조회 5회·기한 — 사용자 승인된 운영 정책(2026-11-03)

사용자가 최초 제공자 전송 준비를 영속화한 시각을 기준으로 **+1분, +5분, +30분, +2시간, +12시간**에 최대5회의 자동 GET 조회 정책을 승인했다. 간격은 1분/4분/25분/90분/10시간이며, **24시간**은 장애로 일정이 밀려도 자동 처리를 끝내고 REVIEW_REQUIRED로 전환하는 절대 기한이다. 5회 소진 시에는 24시간을 기다리지 않고 운영 전환한다. 이는 HTTP timeout 확대가 아니다.

조회 슬롯·기준시각·deadline·nextDue·실제 호출 이력은 영속화한다. 실제 호출 전 슬롯을 원자적으로 소비하며 그 뒤 프로세스가 죽으면 해당 슬롯은 사용된 것으로 취급해 재시작으로 횟수가 초기화되지 않게 한다. job 전달 재시도는 새 조회 슬롯을 만들지 않는다. 재기동 시 지난 슬롯을 한꺼번에 외부 호출하지 않고 한 번 조회 후 다음 미래 일정으로 이동하며 24시간 경과 시 호출 없이 운영 전환한다. 따라서 5회는 상한이며 장애 시 실제 호출은 더 적을 수 있다. webhook 유래 자동 조회도 같은 상한·동시 실행 제약을 따른다. 운영 전환 후에는 감사되는 명시적 조회 요청을 허용하되 자동 횟수/기한을 초기화하지 않는다. 수동 요청의 중복·동시 실행도 합쳐 처리한다.

#### 원응답 유실과 취소 거래 귀속

공식 [Payment/cancels 계약](https://docs.tosspayments.com/reference)에 따르면 취소별 `transactionKey`가 있고 `cancelStatus=DONE`이 성공이다. 국내 일반결제 등에서는 `cancelRequestId`가 항상 null이므로 내부 refundAttempt의 제공자 echo로 취급할 수 없다. `lastTransactionKey`, 같은 금액, 잔액 감소, 시각 근접 또는 요청 전후 목록 차이만으로 특정 attempt의 성공을 확정하지 않는다.

1. 전송 전에 원결제/paymentKey·MID·mode·통화·정확 금액·불변 요청 fingerprint·고객환불 전용 멱등키를 저장한다. 응답에서 식별한 취소 거래도 원결제 및 요청 귀속을 검증하고 불변 receipt로 보존한 뒤 기존 결과 소비에 연결한다. 제공자 거래는 상점·mode·원결제 범위에서 한 attempt에만 배정되도록 DB에서 중복을 차단한다. 취소 응답이 전체 취소 배열을 반환하므로 마지막 원소를 무조건 선택하지 않는다.
2. 저장된 거래 매핑이 있는 경우 GET 결과에서 그 거래의 정확 금액·DONE·원결제를 대조하여 수렴한다. 응답은 받았지만 receipt 저장 전에 죽은 경우도 매핑 없는 응답 유실로 취급한다.
3. 매핑 없는 경우는 **UNKNOWN query-only**를 유지한다. 서버 생성 불변 `cancelReason` 표식과 전송 전 snapshot은 진단 근거로 저장할 수 있으나, 공식 API가 표식의 고유성·위변조 방지·요청 귀속을 보장하는 것은 아니다. 같은 표식 복사·동시 상점 수동 취소·과거 무표식 건을 배제할 근거가 없으면 자동 성공하지 않는다. 앱 내 원결제별 전송 직렬화도 외부 상점 취소를 막지 못한다.
4. 운영자는 서버 GET에서 확인한 정확한 취소 거래·미사용성·원결제/금액/mode에 더해 해당 claim/attempt에 배정할 외부 운영 기록 등 귀속 사유와 증거를 제출해야 한다. 금액 일치와 운영자 선택만으로 귀속을 증명하지 않는다. 근거가 없거나 상충하면 REVIEW_REQUIRED/UNKNOWN과 예약액을 유지한다. 동일 거래의 다른 ITEM/원배송비 배정도 거부한다.
5. 같은 키의 POST 재전송도 GET 조회와 다른 제공자 쓰기 동작이다. [멱등 요청 계약](https://docs.tosspayments.com/reference/using-api/authorization)의 적용 조건·보존 기간을 확인하더라도 이를 query 내부에 숨기지 않는다. 현재 제안은 POST replay를 도입하지 않는 안이다. 따라서 모든 응답 유실 건의 완전 자동 수렴을 약속할 수 없다. 이를 요구하면 별도 사용자 정책 결정과 제공자 계약 검증이 필요하다. GET에 거래가 없다는 이유만으로 FAILED/예약 해제를 하지 않는다. 늦은 기존 worker 전송 가능성도 고려한다.

#### webhook·업무 묶음·검증 영향

2026-11-03 확인한 [공식 webhook 계약](https://docs.tosspayments.com/reference/using-api/webhook-events)은 원문 payload와 transmission-time의 HMAC-SHA256 및 복수 `v1:` 서명 검증을 정의한다. transmission-id는 발송마다 바뀌므로 업무 중복키로 쓰지 않는다. PAYMENT_STATUS_CHANGED에는 eventId가 없을 수 있고 CANCEL_STATUS_CHANGED는 중국·동남아 비동기 결제 전용이어서 국내 카드 취소 통지를 보장하지 않는다. 서명 통과는 특정 환불 attempt 귀속 증명이 아니다. 지원 이벤트는 동일 원결제의 서버 GET을 깨우는 신호로만 사용하고, 중복 알림의 조회 병합 및 최종 거래 매핑/결과 효과의 DB 멱등성을 별도로 검증한다. 기존 P08 fixture 통과를 실제 수신 증거로 소급 해석하지 않는다.

F2는 저장된 요청→DEMO/SANDBOX 어댑터→검증된 receipt→기존 ITEM/원배송비 결과 소비→확인중/운영확인/완료 최소 상태 표시를 한 업무 묶음으로 연결한다. F3는 위 5회 정책·응답 유실·운영 대사·lease/프로세스 중단·webhook 중복을 연결한다. 내부 메서드별 인계 게이트는 만들지 않는다. 새 IT는 기존 `PostgresJdbcIT` 이름을 그대로 추가하지 않고 현행 소유 묶음·필수 목록·소비 영향표에 등록한다. refund/payment 및 RETURN·EXCHANGE_REFUND 소비, process recovery/job, 권한, 실제 상태 UI가 검증 영향이다. 공유 금융·스키마·복구 변경이므로 최종 무선택 Offline 전체 근거가 필요하고 독립 검토의 전체 자동 반복은 요구하지 않는다. 이번 F1 문서 판단은 실행 PASS가 아니며 F07 실제 SANDBOX 차단을 유지한다.

**사용자 결정 현황(2026-11-03):** (1) 신규 환불대사 SYSTEM 제한·기존 claim SUPPORT 유지 확정. (2) 최초 전송 준비 기준 자동 GET +1분/+5분/+30분/+2시간/+12시간 최대5회, 5회 소진 또는24시간 경과 시 금액예약을 유지하고 운영확인 전환하는 정책 확정. (3) 사용자가 “UNKNOWN은 조회만, 귀속 불명확하면 금액 예약을 유지하고 운영 확인”을 명시승인했다. 같은 키 POST replay도 도입하지 않는다. 특히 (3)은 완전 자동 수렴의 한계를 수용하는 결정이며, 같은 키 POST replay 허용은 별도 대안으로만 다룬다. 승인 전 미정 동작을 구현하지 않는다.

소비: C Refunds/RefundProvider 및 D/E 완료 조건, P08 PaymentProvider/Toss 어댑터·Job/Outbox·UNKNOWN/보상 계약. 생산: 제공자 취소/환불 결과·재조회·운영 대사 기록. C에서 정한 포트를 F에서 임의 변경하지 않으며 필요한 변경은 영향/승인·C~E 회귀를 남긴다.

- 요청은 저장된 payment/claim/refundAttempt 식별자·금액·mode를 사용한다. 외부 API는 DB 거래 밖에서 호출하고 요청 저장→외부→짧은 결과 거래로 처리한다. 승인 보상취소와 고객 부분환불 키·효과를 분리한다.
- 외부 성공/내부 실패와 응답 유실은 UNKNOWN으로 재조회한다. UNKNOWN 점유액은 해제하지 않으며 새 키로 환불을 반복하지 않는다. 재조회 금액/원결제/제공자 취소 식별자를 대조하고 초과·다른 결제·mode 불일치를 거부한다.
- worker 재시도 횟수/시간 한도·backoff·REVIEW_REQUIRED 운영 전환을 이 문서의 선행 판단 F1에서 고정한다. 한도 소진을 실패 확정/금액 해제 근거로 삼지 않는다. 운영자도 근거 없는 강제 성공 boolean·임의 금액 직접 수정 불가; 신규 환불 대사 권한표·사유·조회 근거·감사 필요. 이는 P08-F1 배송 단계와 다른 작업 번호다.
