# P03-A 판매 신청·심사

2026-10-24 / 기준 e5734a5 / 상태: 구현·개발 검증·독립 검토 완료.

## 범위·결정

- ACTIVE BUYER가 모의 매대 이름(1~80자)·판매 계획(1~500자)으로 신청한다. 실제 사업자번호·증빙·은행 정보는 수집하지 않으며 화면에 모의 심사임을 표시한다.
- PENDING → APPROVED 또는 REJECTED만 허용. 결정 사유1~300자 필수, 결정한 신청은 수정/재처리 불가. 반려 후 새 신청 가능, PENDING/APPROVED는 회원당 최대1개. 이미 SELLER인 회원의 추가 신청도 거부한다.
- 본인은 자기 신청/이력만 조회. ADMIN+ACCOUNTS 운영자는 전체 목록과 승인·반려를 처리한다. 자기 신청 심사는 거부한다. 공개 입력으로 신청자/처리자/상태/역할을 정하지 않는다.
- 승인 시 BUYER 유지·SELLER 추가. 신청 상태·역할·제출/심사 이력은 한 트랜잭션. 기존 회원 행→신청 행 잠금 순서를 지키며 정지/탈퇴한 신청자의 결정은 거부한다. 역할 추가는 다음 보호 요청에서 반영하며 기존 세션을 강제 폐기하지 않는다.
- seller 모듈은 identity.api의 좁은 계약으로 회원 잠금/판매자 자격을 요청한다. identity SQL을 seller에 직접 작성하지 않는다. 스키마 V8에 신청·이력을 추가하며 매대 생성은 P03-B까지 하지 않는다.
- GET/POST `/api/seller/applications`는 승인 전 회원도 이용해야 하므로 해당 두 요청만 인증 회원에게 허용한다. 나머지 `/api/seller/**`의 SELLER 제한은 유지한다.
- 운영 API `/api/admin/accounts/seller-applications` 및 `/{id}/decision`; React 신청 `/account/seller-application`, 운영 `/admin/sellers`. 목록은 page0부터20개+다음페이지 유무, 최대page10000. 심사 사유·작성자·시각을 조회한다.
- 기존 서버·DB 유지, 매 실행 새 격리 DB. 다음 단계·원격 push 금지.

## 작은 작업과 검증

1. 신청/권한 HTTP 실패 확인 → 신청·상태·역할·감사 원자성 구현.
2. 중복/경쟁·잘못된 전이·자기 심사/권한/CSRF·정지/탈퇴 대상·중간 실패 롤백 검사.
3. 신청/운영 React 입력·목록·오류·늦은 응답/세션 변경 검사, 실제 DB 브라우저 시연.
4. 검토 및 반영세션 독립 검토·새 DB 검증, 보존 비교, 완료 기록.

## 결과·제한

### 구현과 API 계약

| 요청 | 정상 | 경계 |
| --- | --- | --- |
| GET /api/seller/applications?page=0 | 본인 신청 20개와 hasMore | 인증 필수, 다른 회원 ID를 받지 않음 |
| POST /api/seller/applications | 201, 신청과 최초 이력 | CSRF, ACTIVE BUYER, 중복·기존 SELLER 409 |
| GET /api/admin/accounts/seller-applications?page=0 | 전체 심사 목록 | ADMIN+ACCOUNTS |
| POST /api/admin/accounts/seller-applications/{id}/decision | 200, 결정과 이력 | CSRF, ADMIN+ACCOUNTS, 자기 심사 403, 잘못된 전이 409 |

신청 입력은 displayName/description, 결정 입력은 decision/reason이다. 길이는 Unicode 코드 포인트 기준이며 앞뒤 공백을 제거하고 제어 문자·잘못된 surrogate를 거부한다. 오류는 기존 공통 업무 API code/message/requestId 계약을 사용한다. health 계약은 변경하지 않았다. 조회·응답은 no-store다.

V8은 seller_application과 seller_application_event를 추가한다. 본문 상태와 이력은 단일 LEFT JOIN SELECT로 읽어 개별 신청의 같은 문장 snapshot을 보장한다. 목록 전체를 하나의 고정 snapshot으로 묶거나 페이지 이동 중 새 신청의 위치를 고정하는 계약은 아니다. 판매자 역할 추가는 기존 세션의 다음 요청에서 반영되고 BUYER는 유지된다.

React는 내 계정의 판매 신청·이력 링크와 운영자 판매자 심사 화면을 연결했다. 세션 변경 때 개인 목록을 비우고 이전 요청을 취소한다. 늦은 응답은 요청 세대 번호로 무시하며 변경 전에 CSRF를 얻는다. 오류는 공통 안내·요청 ID로 표시하고 승인/신청 POST를 자동 재전송하지 않는다. 통신 결과가 불명확하면 목록 새로고침으로 상태를 확인한다.

최신 개발 DB는 `d2_it_bbcdcb02e7724190938a661da2403455`다. 기존 Compose를 사용하며 모든 실행에서 새로운 DB를 생성했다. 검증 DB는 삭제하지 않았다.

새 DB 검사는 미인증/권한/CSRF, 위조 신청자 무시, 중복 신청, 잘못된 전이, 반려 후 재신청, 자기 심사 금지, 비활성 신청자, 페이지 경계, 두 신청/두 결정의 경쟁을 확인했다. 승인 이력 INSERT를 강제로 실패시켜 신청 상태·SELLER 역할·이력이 모두 롤백됨을 검사했다. 경쟁 결정 완료 후 반환 상태와 마지막 이벤트도 일치했다. R1의 두 SELECT 사이를 강제로 교차시키는 동시성 RED 실험을 수행한 것은 아니며, 단일 문장 snapshot 보장은 SQL 구조 검토와 함께 판단한다.

실제 브라우저에서 가입→로그인→내 계정 링크 이동→신청→새로고침→다른 운영자 문맥의 반려→재신청→승인→기존 구매자 자격/프로필 접근을 확인했다. PC·모바일에서 키보드 제출과 가로 넘침을 검사했다. [모바일 화면](evidence/P03-A-mobile.png)을 확인했다.

### 발견·수정 이력

- 최초 신청 HTTP 테스트는 기존 SELLER 제한으로 201 대신 403을 반환했다. 정확한 GET/POST 신청 경로만 승인 전 회원에게 열고 나머지 SELLER 경계는 유지했다.
- 중간 Java 컴파일의 AccessRejected 생성자 불일치, TypeScript nullable member 접근을 수정한 뒤 재검증했다.
- [검토 및 반영세션](P03-A-review.md)의 R1: 두 SELECT로 읽던 상태/이력을 단일 조회로 수정했다. R2: 늦은 응답 fixture의 빈 이벤트를 유효한 이벤트로 바꿔 응답 형식 거부와 세대 검사를 구분했다.
- 최초 브라우저는 기존 12개 통과·새 2개 실패. AccountPage를 나갈 때 세션을 초기화하지만 새 신청 페이지가 재확인하지 않아 로딩 상태에 남았다. 일반 신청 페이지 진입에서 인증 재확인을 추가했다. 운영 심사 화면은 WorkspaceAccess가 재확인을 담당해 반복 마운트를 피한다. 수정 후 14개 모두 통과했다.
- 세션 재확인 테스트는 호출 횟수에 기대던 로그인 fixture를 명시적 로그인 상태 전환으로 바꿨다. 오류 요청 ID fixture도 공통 계약의 UUID 형식으로 보정했다.
- JAR 점검의 넓은 TestMail 이름 검색은 기존 의도된 LocalTestMailbox도 잡았다. 테스트 전용 HTTP endpoint/fixture와 로컬 메일 구현을 구분해 검사했으며 LocalTestMailbox는 삭제하지 않았다.
- 최초 도구 자동 승인 검토가 이전 P02-R1 제한을 최신 요청으로 판단하여 P03-A 작업을 거절했다. 개발 채팅의 직접 사용자 승인 `01a16d09-a1e9-7921-ae5c-8aec8d55ba92`를 확인해 재시도했고 허용됐다. 현재 남은 차단이 아니다.

### 보존·재현·제한

[작업 전](evidence/P03-A-before.json)과 [작업 후](evidence/P03-A-after.json)의 기존 개발·테스트 DB 정규화 덤프 SHA256, 기존 DB 목록, 컨테이너 ID를 비교했다. [보존 결과](evidence/P03-A-preservation.txt) 기준 변경/삭제 없이 유지됐다. 기존 앱 서버는 시작·중지하지 않았으며 검증용 임시 서버만 사용했다.

재현: `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p03-a-새로운이름 -Offline -RunBrowser`. 매번 사용하지 않은 디렉터리를 지정한다. 프런트는 `./frontend/npm.ps1 run typecheck`, `run lint`, `run test:unit`, `run build`를 실행한다. 도구 준비와 DB 보호 조건은 [로컬 실행](../local-development.md)을 따른다.

실제 사업자 확인, 증빙·은행 정보 수집, 매대 CRUD, 상품 등록, 판매 정지, 운영자 권한 편집은 이번 범위 밖이다. 정지·탈퇴한 신청자는 심사할 수 없고 대기 신청의 자동 취소/정리 정책은 아직 없다. 탈퇴 후 모의 신청·심사 이력은 남는다. 검색·상태 필터·대규모 목록 성능, 운영 환경, 외부 메일, 실제 주문/결제는 검증하지 않았다. 승인은 판매자 자격만 부여하며 실제 매대를 생성하지 않는다. P03-B/C 및 원격 push는 진행하지 않았다.


## 최종 판정

검토 및 반영세션에서 새 격리 DB로 Java130·DB52·브라우저14, 별도 Vitest76을 독립 재검증했다. R1·R2 및 화면 전환 보완을 확인했고 검토 범위의 필수 잔여 지적은 없다. [독립 검토](P03-A-review.md), [독립 집계](evidence/P03-A-review-summary.json), [독립 브라우저](evidence/P03-A-review-browser.txt)를 근거로 P03-A 계획 범위 완료로 판정한다. 위의 범위 밖 기능과 운영 준비 제한은 유지한다. 로컬 커밋으로만 마무리하며 다음 단계는 진행하지 않는다.
