## 실제 명령과 생산자→소비자

### M1: 운영자가 새 배송 정책을 저장하고 구매자가 새 견적을 확인

1. SYSTEM 운영자는 `/admin/settings`에서 기본 배송비·무료배송 기준·사유를 입력한다. [SitePages.tsx](../../frontend/src/site/SitePages.tsx)의 `SettingsEditor` state가 문자열 입력을 숫자 필드로 구성하고 `useInquiryCommand`가 요청키·예상 version과 함께 `POST /api/admin/system/shipping-policy`로 전달한다. CONTENT 또는 ADMIN 역할명만으로 금전 설정 권한을 얻지 않는다.
2. [ShippingPolicyController](../../backend/src/main/java/com/example/marketplace/promotion/web/ShippingPolicyController.java)는 정확한 필드·정수 타입을 검사한다. [JdbcShippingPolicies](../../backend/src/main/java/com/example/marketplace/promotion/infrastructure/JdbcShippingPolicies.java)는 현재 회원/세션과 SYSTEM 권한을 잠금 후 확인하고 정책 head를 잠근 뒤 권한을 재확인한다. 새 `site_shipping_policy` revision INSERT와 `site_shipping_head` 변경은 같은 트랜잭션이다. 현재 구현 소유자는 **promotion**이며 P11-E 초안의 operations 소유 제안을 최종 구조로 오인하지 않는다.
3. `ShippingPolicies` 공개 포트→[JdbcQuotes](../../backend/src/main/java/com/example/marketplace/promotion/infrastructure/JdbcQuotes.java)·`QuoteCalculator`→견적 fingerprint/금액으로 소비한다. 일반 견적은 읽기 snapshot, [OrderCreationService](../../backend/src/main/java/com/example/marketplace/order/infrastructure/OrderCreationService.java)는 checkout 쓰기 거래 안에서 정책 head 공유 잠금과 재계산을 사용한다. 정책 변경과 주문 생성의 선후를 DB 잠금으로 정한다.
4. 구매자에게 달라진 견적·정책 버전을 보여 주고, 낡은 fingerprint 주문은409와 새 견적으로 재확인한다. 재확인 후 생성한 주문의 저장 명세를 payment→fulfillment→claim/refund→settlement가 소비한다. 기존 주문/환불/정산 원인은 재계산하지 않는다. 공개 `GET /api/site/shipping-policy`, 설정 이력 GET, 견적 화면이 같은 새값을 읽는다.

실제 DB 검사는 초기49,999원 상품의 배송비3,000원에서 새 정책4,567원·무료 기준51,000원으로 바꾸고 배송비4,567원·총액54,566원과 지문 변경을 확인한다. 이는 격리 검사 데이터이며 운영 정책의 권고값이 아니다. 최초 `P07-C-1` 지문 호환과 기존 거래 명세는 유지한다.

### M2: 게시·안내 입력의 잘못된 타입은 저장 전에 거부

1. CONTENT 운영자의 `/admin/publications` 공지·FAQ·배너 편집과 SYSTEM 운영자의 `/admin/settings` 사이트 안내가 생산자다. `PostEditor`/`SettingsEditor`의 state→`useInquiryCommand`→JSON 또는 multipart `command`의 전달을 설명한다. React/TypeScript 타입·HTML 숫자 입력은 임의 HTTP 요청을 막는 서버 검증을 대신하지 않는다.
2. `POST /api/admin/content/site-posts/{id}`의 JSON과 multipart command, `POST /api/admin/system/site-info`가 오류 경계다. 과거 DTO 변환은 소수·문자열 정수, 숫자 enum, 미허용 키를 받아들여 정상 명령으로 진행했다. [SiteController](../../backend/src/main/java/com/example/marketplace/operations/web/SiteController.java)의 `checkFields`, `version`, `text`, `publication`은 JsonNode 단계에서 허용 필드·정수·enum 문자열을 검사한다. JSON/multipart가 같은 publication 경계를 사용한다.
3. 유효 명령만 `SitePublications` 또는 `SiteAdministration`의 현재 권한·version·요청키 트랜잭션에 도달한다. `site_post`, `site_post_revision`, `media_site_image`, `site_info_revision`이 저장/감사·영수증을 보유한다. 오류는400이며 이 네 테이블의 **전체 행** 전후가 같아야 한다. 단순 status만으로 수정 성공을 판정하지 않는다.
4. 정상 명령은 게시 목록/이력과 공개 `/api/site/posts`, `/api/site/posts/{id}`, 이미지 경로 및 `/api/site/info`에서 소비된다. 잘못된 명령의 새 공개 revision·배너 귀속·안내 변경은 없어야 한다. 정상 문자열 개행·이미지 업로드·공개/중단·동일키 재생은 회귀로 유지한다.

### 전역 정책 브라우저의 데이터 수명과 불간섭 결정

기존 `browser-api`는 한 묶음 DB·seed를 실제178검사와 desktop/mobile이 공유한다. M1의 singleton `site_shipping_head` 변경은 상품·계정 namespace만으로 격리되지 않는다. 값을3,000/50,000으로 다시 저장해도 version은 증가하여 초기 `P07-C-1` 계약을 복구하지 못한다. 따라서 기존 공유 suite 앞/뒤에 정책 변경을 끼우거나 `finally`에서 정책행을 직접 reset하는 방안은 채택하지 않는다.

권고·설계 결정은 **정책 사례 전용 desktop/mobile 두 등록 묶음**이다. 각 묶음은 별도 단일 IT 클래스·새 Failsafe JVM·새 UUID DB·새 media·API/브라우저 프로세스·증거 경로를 소유하고 해당 프로젝트의 새 정책 시나리오만 실행한다. 기존 browser-api의178검사·desktop/mobile·seed·필수 목록은 그대로 유지한다. 두 새 묶음은 기본 무선택 실행에 추가하고 서로 순차 실행한다. 같은 API 프로세스의 DB를 교체하거나 공용 seed를 변경하지 않는다. 새 ID/클래스명은 구현에서 등록부와 대조해 정하되 이 수명 계약은 유지한다.

각 새 DB는 기존 migration으로 초기 정책 version1/3,000/50,000을 만든다. 합성 계정·SYSTEM 권한은 기존 승인 bootstrap을 사용하되 상품·원 주문/결제는 실제 업무 API로 생성하고, 정책 변경은 실제 React SYSTEM 명령으로 수행한다. 기대 업무 결과를 SQL fixture로 만들지 않는다. 변경 전 주문 ID/정책/금액, 변경 요청키/version, 새 견적/새 주문 ID를 읽기 전용 DB 관측과 연결한다. 시나리오 종료 후 새 정책/DB를 그대로 보존하며 초기 정책으로 되돌리지 않는다. mobile은 desktop 결과를 승계하지 않고 별도 새 DB에서 시작한다.

불간섭 assertion은 각 묶음 DB 식별·생성수·정책 최초값, 서로 다른 DB/API 귀속, 해당 DB의 주문/정책 ID만 소비함, 기존 browser-api에서 초기 정책과 원 seed 계약 유지, 전후 기존 DB/media 보존이다. 정책 사례의 유한 준비·10초 업무 deadline·자식 회수도 유지한다. 추가 묶음/프로젝트 실행 경로는 **하네스 실행 동작 변경**이므로 구현 후 최종 무선택 전체 근거가 필요하다. 이 확장은 검사 격리를 위한 것이며 제품 정책·MSA·실행 병렬화 변경이 아니다. 현재 설계만으로 구현을 시작하지 않는다.

`verification/db-groups.json`의 현재 `site-management` 영향 행은 site-management, browser-api, promotion, checkout, identity, media, job-contracts, questions, dashboard, refund, legacy, settlement다. 새 정책 브라우저 두 묶음은 아직 미등록이며 구현 시 제공/소비 행·필수 이름·기본 전체 경로에 추가한다. `-ChangedContracts 'site-management'`의 실제 `selection.json`과 소비 소스를 대조한다. M2만의 불변 제품/공유 fixture 아래 전용 브라우저 보완이면 browser-api 선택이 집중 피드백 후보지만, M1 새 실행 경로를 포함한 **P12-B 최종 검증은 무선택 전체**다. 전용 HTTP assertion 보강이면 site-management와 영향 있는 소비를 추가한다. 집중 실행의 제외 묶음은 불변 계약·유효 원근거를 이유로 명시하며 최종 전체를 선택 근거로 대체하지 않는다.

새 검사는 필수 브라우저/프런트/Java 목록과 DB 단일 소유·제공/소비 영향표에 등록한다. 기존 assertion 삭제·기대 목록 축소·skip 허용·timeout 확대 금지. 각 업무는 현 하네스의 준비 완료 뒤 **공유10초 deadline**을 사용하며 같은 명령의 retry/poll은 기한을 갱신하지 않는다. 이전390초 실패를 현 정책 통과로 소급하지 않는다.

후속 실행 예시는 `./verify.ps1 -Offline -ChangedContracts 'site-management' -EvidenceDirectory '<새 경로>'`이며 **현재 실행 명령이 아니다**. 인증·공통 금융·작업 실행기·공유 스키마·공통 fixture·하네스 실행 동작 변경, 영향표 불완전/불명확, 통합 마일스톤 마감·배포 전에는 선택 없이 `./verify.ps1 -Offline -EvidenceDirectory '<새 경로>'`가 필요하다. 해당 소스·조건에 유효한 기존 무선택 근거가 있으면 행사 이름이나 독립 검토 때문에 반복하지 않는다. 선택 통과는 certificationEligible=false이며 적절한 작업 범위 완료 근거가 될 수 있다. 실패 수정은 실패 검사·수정 영향만 재검증하고 새 위험이면 전체로 확대한다.

## 개발자 설명·직접 확인 안내

Java 경험을 출발점으로 `SettingsEditor`의 state는 화면 입력값, 이벤트는 새 state를 예약하고 렌더링을 다시 유도하는 흐름임을 설명한다. HTTP command는 Java 메서드 인자처럼 보이지만 신뢰 경계를 넘으므로 서버가 타입·권한·version을 다시 검사한다. 요청키는 네트워크 응답을 잃어도 같은 업무 결과를 찾기 위한 것이며 새 클릭마다 다른 키로 재시도하면 같은 의미가 아니다. SQL head 잠금은 변경 순서를, append-only revision과 주문 snapshot은 과거 거래 보존을 담당한다.

향후 격리 시연에서 개발자가 직접 해 볼 작은 변경은 **사이트 안내 문구 한 줄**이다. 설정 입력→state→POST의 siteName/supportGuide→SiteController→SiteAdministration revision→공개 안내 재조회 순서로 추적하고, 새 이력1건·공개 문구 일치·기존 주문 금액 동일을 예상 결과로 제시한다. 금액 정책 변경 실습은 현재 운영 환경에서 자동 수행하지 않는다. 오류 사례는 정수 expectedVersion에 문자열을 보내면400이고 이력 증가0임을 원 HTTP 검사와 연결해 설명한다. 실제 수행자·환경·명령/화면·결과가 있을 때만 직접 확인을 갱신한다. 사용자 미응답은 미확인이며 학습 확인을 별도 승인 시험으로 만들지 않는다.

## 미확정·외부 차단·착수 조건

새 업무 정책 결정은 필요하지 않다. 과거 수용 사례를 쓰는 현재 설계 권고는 불필요한 기능확장을 피하고 AC17의 실제 수행·회귀 이력을 활용한다. 만약 사용자가 “P12-B에서 새 정책 자체를 추가로 변경”하는 의미를 요구한다면, 현행 유지/기존 두 항목의 새 전향 변경 대안과 영향·승인 조건을 먼저 제시한다. 추가 금전·권한 정책을 임의 확정하지 않는다.

실행 착수 조건은 이 설계의 별도 독립 검토·필수 보완 해소와 **후속 구현/검증 승인**이다. 이전 로컬 커밋 승인은 이 실행 승인으로 확대하지 않는다. Sol High가 확정 설계의 구현을 맡고 설계 변경 판단·동일 소스 독립 검토는 Astra Medium이 맡되 기존 부모/세션 구조를 유지한다.

실제 Toss P09-F07/G08 BLOCKED, AC16 다른 개발 환경, 실제 송금·실기기·배포·사용자 직접 확인은 계속 미검증이다. 이 외부 차단은 로컬 사례 설계를 막지 않지만 전체 기능/인증/공개 완료의 근거로 생략할 수 없다. P12-B만의 필수 누락인 남은 브라우저 연결·최종 설명/동일 소스 대조와 외부 차단을 구별한다. 현재 하네스/제품 테스트 미실행, 독립 설계 검토 완료, AC17 미완료 상태로 인계한다.
