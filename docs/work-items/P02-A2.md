# P02-A2 로그인·로그아웃·JDBC 세션

2026-10-24 / 기준 81e718c / 상태: 구현·개발 검증·독립 검토 완료

## 승인 및 범위

이 개발 채팅의 사용자 직접 요청으로 A2 제한을 해제했다. Spring Security 로그인/로그아웃, Spring Session JDBC, me/csrf API만 구현한다. 기존 서버·DB 데이터는 유지하고 UUID 이름의 새 격리 DB에서만 마이그레이션·변경 검증한다. React 화면, HTTP 가입·이메일 확인 어댑터, P02-A3는 진행하지 않는다. 개발 검토는 별도 **검토 및 반영세션**에서 수행한다.

## API 계약

| 요청 | 입력·인증 | 결과 |
|---|---|---|
| GET /api/auth/csrf | 익명 허용, 세션 쿠키 | 200 `{headerName, token}`, no-store |
| POST /api/auth/login | application/x-www-form-urlencoded의 email/password, X-CSRF-TOKEN | 200 `{status: AUTHENTICATED}`, 실패401 공통 오류 JSON |
| GET /api/auth/me | 로그인 세션 | 200 `{id, roles}`, 익명·무효 세션401 |
| POST /api/auth/logout | 현재 세션의 X-CSRF-TOKEN | 200 `{status: LOGGED_OUT}`, 세션 폐기 |

- 오류는 기존 code/message/requestId 계약을 사용한다. 인증 실패의 회원 존재 여부·미확인·정지 등 상세 사유를 반환하지 않는다. CSRF 누락·잘못된 값은403이다. HTML 로그인 페이지나302 이동을 제공하지 않는다. 변경 요청의 CSRF 검사가 인증 검사보다 앞서므로 익명 POST도 토큰 없으면403이다.
- 최초 csrf 호출 → 받은 쿠키·토큰으로 로그인 → 로그인 성공 뒤 csrf 재발급 → me/변경 요청 순서다. 로그인·로그아웃·세션 만료 뒤 과거 토큰은 재사용하지 않는다. 실패한 변경 요청을 자동 재전송하지 않는다.
- 기본 HttpSessionCsrfTokenRepository와 XOR 요청 핸들러를 함께 사용한다. csrf API에서 받은 마스킹된 토큰을 그대로 헤더로 보낸다. 응답마다 문자열이 달라질 수 있으므로 문자열 차이만으로 폐기를 판단하지 않고 과거 토큰의403을 검사한다.

## 구성 및 책임

- Security config/web 모듈과 Session JDBC를 Boot BOM 버전으로 사용한다. starter의 자동 기본 로그인 구성을 추가하지 않고 db + servlet 웹 환경에서 명시적으로 활성화한다. DB 없는 P01 검사·health 기동은 유지된다.
- Session 필터(-110) → Security 필터(-100), 요청 ID 필터가 가장 앞이다. 인증 체인은 /api/**에 적용하며 csrf GET과 login POST 외 업무 API는 로그인 필요다. 기존 /actuator health는 이 체인 밖이며 기존 노출 정책·상태-only 응답·POST405를 유지한다. 이후 추가 업무 경로도 /api 아래에 둬야 한다.
- 로그인은 UsernamePasswordAuthenticationFilter와 DaoAuthenticationProvider를 사용한다. ProviderManager를 하나로 명시해 자동 부모 제공자와 비밀번호 인코더가 달라지는 실패를 방지한다. A1과 같은 Argon2id 파라미터/접두사를 사용하며 자격 증명은 세션 직렬화 전에 제거한다.
- SessionMember는 회원 ID·authVersion·자격을 보유한다. CurrentMemberFilter가 인증된 API 요청마다 현재 계정 상태·authVersion·자격을 JDBC로 재조회한다. 정지/탈퇴/버전 불일치면 현재 요청의 세션을 폐기하고401, 권한은 현재 값으로 교체한다. 상태/권한 변경 업무 API와 모든 세션의 즉시 일괄 삭제는 후속 작업이다.
- V4가 Spring Session의 PostgreSQL 표준 테이블/인덱스를 추가한다. V1/V2/V3를 수정하지 않는다. 테이블은 marketplace.spring_session 및 attributes이며 Flyway만 생성한다. JDBC 저장에는 Java 직렬화가 사용되므로 배포 간 principal 클래스 호환성과 DB 쓰기 접근 보호를 유지해야 한다.
- 세션은 비활성30분 만료다. SESSION 쿠키는 Path=/, HttpOnly, SameSite=Lax, Secure 기본true. 로컬 HTTP에서는 **local-http** 프로필만 추가해 Secure=false로 사용한다. 운영에서 이 개발 프로필을 활성화하지 않는다. 외부 CORS 허용·토큰 로컬스토리지 저장은 추가하지 않았다.

## 실행·검증 계획

1. 익명 me401/csrf200 검사를 먼저 추가하고 미구현404 실패를 확인한다.
2. 로그인/로그아웃·JDBC 스키마·필터·JSON API를 구현한다.
3. 기존 verify-db 보호 초기화기로 새 DB를 생성하여 기본 검사와 실제 HTTP 통합 검사를 실행한다. 현재 PostgresJdbcIT 프로필은 db,c3-fixture,local-mailbox,local-http다.
4. 별도 검토세션의 발견사항을 검토·수정하고 최신 코드의 검사 결과, 보존 증거, 제한을 기록한다. A3는 시작하지 않는다.

## 실패와 수정

- a2-red: 기본124 통과, 통합22 중 새 익명 me 검사만 expected401/actual404 실패. 이 검사가 기능 부재를 검출했다. 이후 추가한 상세 시나리오 전체를 RED-first로 구현했다고 확대하지 않는다.
- a2-first: Session 필터 등록의 제네릭 타입 추론 컴파일 오류. 타입을 명시했고 DB 생성 이전 실패였다.
- a2-second: 기본124 중 설정 검사2 실패. 비웹 설정 검증에도 인증 구성이 적용되어 JDBC 빈을 요구했다. servlet 웹 환경 조건을 추가했다. DB 생성 이전 실패였다.
- a2-third: 기본124 통과, 통합28 중 잘못된 비밀번호 검사1 실패(500). 명시 제공자 실패 후 자동 부모 제공자가 다른 encoder로 재인증하면서 발생했다. 부모 없는 ProviderManager로 수정했다.

## 학습 및 제한

로그인은 비밀번호 비교만이 아니라 CSRF 검사, 인증 상태 생성, 세션 ID 교체, DB 저장을 잇는 흐름이다. me는 화면이 현재 사용자를 알기 위한 조회이고, CSRF 토큰은 세션 쿠키를 자동 전송하는 브라우저의 변경 요청을 보호한다. 회원의 자격과 계정 상태는 다른 개념이다.

직접 확인할 작은 예: 자동 검사에서 로그인 후 SELLER 자격을 추가/제거하는 부분과 me 응답을 비교한다. authVersion을 증가시키면 같은 쿠키가401이 되는 이유를 CurrentMemberFilter에서 따라간다. 사용자가 직접 실습했다는 확인은 아직 받지 않았다.

이번 범위는 실제 HTTP+PostgreSQL 자동 검사다. 실제 HTTPS/TLS 환경, 브라우저 화면/다중 탭, 프로세스 재시작 후 복구, 동시 로그인·로그아웃 경쟁, 분산 배포, 부하·rate limit은 미검증이다. 다른 HttpClient가 같은 쿠키로 조회한 검사를 서버 재시작 검증으로 표현하지 않는다. 기존 marketplace_dev/test에는 V4를 적용하지 않는다.

## 공식 근거

[Spring Session JDBC](https://docs.spring.io/spring-session/reference/configuration/jdbc.html)의 PostgreSQL 테이블과 명시 활성화 구성, [Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)의 세션 저장소·토큰 처리 규약을 기준으로 했다. 실제 사용 버전과 최종 결과는 증거로 별도 기록한다.
