# P13-B 반품 환불 중단 시 Java 모놀리스 기준 측정

[구현 계획 §15](../implementation-plan.md#15-p13-문제-재현과-기준-측정)의 B는 [P13-A](P13-A.md)에서 재현한 장애의 시간·자원 사용과 업무 결과를 함께 기록하는 항목이다. 기준 HEAD는 `fcb528bb6fced81903842b3782e1fe81fcf031b3`이다. A의 작업 문서 SHA-256은 `831a700174e7cd4f0cdac1bd1b805b26c8b55ae0ab90d56a3f259a7086ed5cc6`이며 [독립 확인](../../.local-tools/p13-a-independent-89dcdd92c7514a26849e66ab8f0e33df/review.md)과 일치한다.

## 측정 전 정한 조건

별도 `gpt-6.2-astra` Medium 검토자가 원자료에서 시간과 업무 결과를 대조하고 집계 JSON·표의 바이트 일치를 재현해 로컬 기준 측정을 수용했다. 독립 검토의 필수 보완 요청과 잔여는 0건이다. 개발 중 워밍업 실행 실패 2회와 업무 검사 통과 후 발견한 관측 파일 형식 결함 1건은 아래에 별도로 기록했다.

최종 선택 검증은 워밍업 1회와 측정 3회를 통과했다. 실행 소스 SHA-256은 `1947e00789eb617739f05889e16731624732c2260239820433d9f49cd1594549`이며 실행 전후 일치와 기존 자원 보존을 확인했다. 실험 전용 테스트·관측기·실행기·집계기만 추가해 기존 공통 실행 및 제품 계약을 유지했다. 기존 42개 검증 묶음 등록과 process-recovery의 필수 검사 12개를 대조했다. 이번 실행은 실험 선택 검증이며 전체 하네스 인증은 종전 기록을 따른다. [실행 결과 및 회차 목록](../../.local-tools/p13-b-trialset-20261118-final/result.json) · [독립 검토 기록](../../.local-tools/p13-b-independent-617cd50ccf044f99a68c2d5ed026a2e0/review.md)

구매자 한 명이 검수를 마친 반품 한 건의 견적에 동의한다. 로컬 모의 환불 제출 직전 준비 트랜잭션을 커밋한 지점에서 첫 worker를 종료하고 두 번째 worker가 같은 작업을 인수한다. 측정마다 새 DB와 미디어를 사용하고 동의 직전 데이터 규모, 업무 입력, worker 실행 순서와 동시성을 대조한다.

워밍업 1회는 통계에서 제외하고 같은 조건에서 3회 측정한다. 세 번의 개별값과 중앙값·최솟값·최댓값으로 실행 간 차이를 확인한다. 각 자식은 새 JVM이므로 자식 프로세스의 기동 비용이 포함된다. 고정 clock으로 이동한 lease와 조회 슬롯은 실제 경과시간에서 제외한다.

구매자의 동의는 Java 업무 API 호출 경계에서, 장애와 재인수는 자식 프로세스 경계에서, 후속 처리는 원래 반품·환불 시도의 상태로 각각 관찰한다. 브라우저에서 견적에 동의하고 HTTP 202를 받는 경로의 적용 근거는 A의 검토 기록을 따른다. 의도한 종료, 기술 오류, 환불 결과 `UNKNOWN`은 따로 센다. 원결제 43,000원, 환불 시도와 예약 7,000원, 회수비 증가분 3,000원, 확정 환불 0원을 확인한다.

## 검증 범위

| 확인할 계약 | 관찰 경계 |
|---|---|
| 구매자의 견적 동의 → 환불 작업 | 동의 receipt의 환불 시도 ID로 제출 작업과 반품을 찾는다. 업무 호출의 경과시간은 프로세스 안에서 잰다. |
| 최초 선점 → 준비 커밋 → 중단 → 재인수 | 준비 완료 표식, 종료한 자식 PID, 저장 lease, 재시작 PID, 같은 job ID와 서로 다른 owner를 대조한다. |
| 조회 결과 → 반품 상태·금액·상품 보류 | 같은 시도의 조회와 후속 작업을 추적하고 최종 DB의 금액·상태·시도 수·제공자 효과 수를 검증한다. |
| 런타임과 DB 자원 | JVM별 GC 카운터와 스레드·메모리, 연결 풀 스냅샷, 해당 DB의 잠금·대기 관측을 회차별로 남긴다. 특정 시점의 표본에서 보이지 않은 대기는 실행 전체에 대해 판정할 수 없다. |

설계 판단은 `gpt-6.2-astra` Medium, 실험 구현은 `gpt-6.2-sol` High에 배정했다. 독립 검토는 구현에 참여하지 않은 별도 담당자가 맡는다. 실제 Toss·실송금·운영 부하의 측정은 기존 외부 미검증 범위에 남는다.

## 워밍업에서 확인한 입력 차이

첫 실행은 부모 테스트의 전화 인증 설정이 에뮬레이터를 요구해 업무 시작 전에 중단됐다. 이메일 계정만 쓰는 실험 클래스에서 전화 모드를 비활성화했다. [첫 실행 결과](../../.local-tools/p13-b-trialset-20261118T2338/result.json)

두 번째 워밍업에서는 실제 worker 복구 뒤 환불액 검사가 실패했다. 주문에는 회수비가 서로 다른 두 상품이 있다. UUID로 정렬된 첫 배송 단위를 선택하면 회수비 5,000원 상품이 들어올 수 있고, 이때 계산된 환불액도 5,000원이었다. 측정 조건인 회수비 3,000원 상품을 주문 당시 정책과 배송 단위로 식별하도록 실험의 준비 과정을 고쳤다. 이 실패는 다른 입력에 대한 관측으로 보존하며 통계에서 제외한다. [두 번째 실행 결과](../../.local-tools/p13-b-trialset-20261118-retry1/result.json)

입력을 고친 뒤 워밍업과 측정 3회가 모두 업무 검사를 통과했다. 다만 PostgreSQL이 JSON 집계 안에 물리적 개행을 넣어 잠금·대기 표본 한 건이 파일의 여러 줄에 걸쳤다. JSON 값을 한 줄로 직렬화하고 실제 개행을 거부하도록 관측 출력을 고쳤다. 이 수정 뒤 새 자원에서 워밍업과 측정 3회를 다시 실행한다. 앞선 네 회차의 수치는 최종 통계에 합산하지 않는다. [형식 수정 전 실행](../../.local-tools/p13-b-trialset-20261118-retry2/result.json)

## 재현 명령과 측정값의 해석

저장소 루트에서 지정 PowerShell과 준비된 오프라인 도구·전용 PostgreSQL 인스턴스를 사용한다. 실행기는 인증된 endpoint를 확인한 뒤 새 경로에 소스 manifest·보존 스냅샷·회차별 XML과 업무 관측 파일을 남긴다.

```powershell
$pwsh = 'C:/Users/rihee/.cache/codex-runtimes/codex-primary-runtime/dependencies/native/powershell/pwsh.exe'
& $pwsh -NoProfile -NonInteractive -File ./verification/Run-P13ReturnRefundExperiment.ps1 `
    -TestPostgresPort 5785 `
    -TestPostgresInstance f090f3a1-4f55-4a28-a29a-2949b8ad89be `
    -TestPostgresContainer p12-a-pg-f090f3a1-4f55-4a28-a29a-2949b8ad89be
```

부모 JVM은 Spring의 실제 견적·동의 메서드를 직접 호출한다. 단조 시계로 각 메서드의 반환까지 재고, 견적 시작부터 동의 receipt와 제출 작업을 찾을 때까지 10초를 공유한다. 첫 JVM 시작 요청부터 준비 표식 관측까지는 부팅·DB 검증·선점·준비 저장·관측이 포함된다. 종료 요청부터 프로세스 종료 확인까지는 인위적 종료 비용이다. 재기동 요청부터 두 번째 JVM 종료까지에는 기동·작업 재인수·처리·종료가 포함된다. 운영 장애 탐지기와 사용자 브라우저 왕복 시간은 이 구간 밖에 있다.

Hikari 연결 수와 대기 스레드 수는 체크포인트에서 읽은 순간값이다. 별도의 읽기 전용 연결이 약 100ms 간격으로 해당 DB 세션·잠금·대기 이벤트를 읽는다. DB 누적 트랜잭션 통계에는 관측기 쿼리도 들어간다. 컨테이너 CPU는 Maven 회차 전후에 읽은 전체 PostgreSQL 컨테이너의 누적 CPU 차이로, 같은 컨테이너를 쓰는 다른 작업의 영향도 포함한다. 각 JVM의 heap은 프로세스 전체 메모리와 측정 범위가 다르다.

## 최종 기준값

측정은 동시 업무 1건, 최초 worker 한 프로세스 종료 뒤 새 worker 한 프로세스를 시작하는 순서로 했다. 네 DB 모두 견적 직전 24,581,823바이트였고, migration 133건·인덱스 668개·업무 테이블 19개의 행 수가 일치했다. 측정값은 새 JVM의 기동 비용을 포함한다. 집계는 워밍업과 앞선 실패·진단 실행을 제외한다.

| 단조 시계로 잰 구간 | 1회 | 2회 | 3회 | 중앙값 |
|---|---:|---:|---:|---:|
| 견적과 동의 → 작업 등록 확인 (ms) | 381.611 | 366.779 | 370.586 | 370.586 |
| 첫 worker 실행 요청 → PREPARED 관측 (초) | 4.118 | 4.129 | 4.483 | 4.129 |
| 강제 종료 요청 → 종료 확인 (ms) | 0.954 | 0.975 | 0.986 | 0.975 |
| 재시작 요청 → 재인수 worker 정상 종료 (초) | 4.251 | 4.199 | 4.245 | 4.245 |
| 재시작 종료 → 후속 업무 결과 관측 (ms) | 154.132 | 161.860 | 151.920 | 154.132 |
| 동의 시작 → 후속 업무 결과 관측 (초) | 8.860 | 8.789 | 9.182 | 8.860 |

동의 시작부터 결과 관측까지 세 구간의 합으로 계산한 직렬 처리량은 초당 0.112건이다. n=3에서 nearest-rank p50은 중앙값, p95와 p99는 모두 최댓값이다. 동의 시작부터 결과 관측까지 p95·p99는 9.182초이며 운영 부하의 꼬리 지연을 추정할 표본은 부족하다.

최종 측정에서 기술 실패 0/3, 의도한 최초 worker 종료 3/3, 재시작 정상 종료 3/3이었다. 각 회차의 동의 receipt, 환불 시도·견적·반품 ID, 같은 job의 최초 선점과 재인수 기록을 조회 작업·환불 결과·반품 진행 작업까지 연결했다. 세 후속 작업은 각각 1회 성공했다. 3회 모두 원결제 43,000원, 견적·시도·예약 7,000원, 회수비 예약 3,000원, 환불 시도 1건, 제공자 제출·효과·확정 환불 0건이었다. 환불은 `UNKNOWN`, 반품은 `REVIEW_REQUIRED`, 상품 보류는 `ACTIVE`였다. [JUnit 및 업무 결과](../../.local-tools/p13-b-trialset-20261118-final/groups)

세 측정의 DB 표본은 86·87·91개다. 표본에서 미부여 잠금과 잠금 대기는 0건, 데드락 카운터 증가도 0이었다. 최대 부여 잠금은 261·294·294개였다. PostgreSQL 컨테이너 CPU는 3.842·3.760·3.771 CPU초였다. JVM별 최대 스레드 수는 부모 42, 최초 worker 12, 복구 worker 11이었다. 각 JVM의 두 체크포인트 사이 GC 횟수 증가는 0이었다. Hikari는 모든 체크포인트에서 사용 중 0·유휴 5·전체 5·대기 0이었다. 동시 요청 처리 용량, 프로세스 RSS, 브라우저 응답, 실제 lease 만료까지의 고객 대기, 운영 장애 감지 및 외부 결제 성능은 미측정이다.
