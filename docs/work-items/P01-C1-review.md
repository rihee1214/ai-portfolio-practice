# P01-C1 개발 검토

검토일: 2026-10-23 (Asia/Seoul)

현재 판정: **C1 검토 범위 통과·지적 반영·완료 기록 및 로컬 커밋 확인. C1-R1(P3)과 호스트 인증 검증 공백은 해소됐으며 Spring Boot 통합(C2)은 미착수다.**

## 범위와 근거

`compose.yaml`, `.env.example`, `infra/postgres/init-app.sh`, P01-C1 작업 문서, PostgreSQL 실행 안내와 P01-C1 증거 파일을 대조했다. 실제 `.env` 내용, 전체 Docker inspect/config 환경 출력은 읽거나 출력하지 않았다. `git check-ignore -v --no-index .env`로 제외 규칙을 확인했다. 이 검토의 변경은 본 문서 하나이며 Docker·DB·볼륨·서버·제품 설정·Git 상태를 변경하지 않았다. 개발세션의 실행 증거를 검토했으며 18개 검사를 여기서 재실행하지 않았다.

## C1-R1 · P3 · 반대 계정 거부 검사가 모든 명령 오류를 성공으로 계산함 — 보완 확인

대상: `evidence/P01-C1-verifier.txt`의 `rejects other environment role` 검사.

최초 검토 당시 `$LASTEXITCODE -ne 0`만 확인했다. 인증 거부뿐 아니라 네트워크 단절·컨테이너 exec 실패·psql 실행 오류도 같은 통과 판정이 될 수 있었다. 실제로 잘못 통과했다고 단정한 것은 아니다.

보완: 잘못된 암호 검사처럼 인증 실패 메시지 또는 구조화된 인증 오류를 확인한다. 별도로 반대 역할이 현재 클러스터에 존재하지 않는지도 정상 인증 세션에서 조회하면 분리 근거가 명확해진다. 현재 검사는 반대 역할 이름에 대상 환경 암호를 사용하므로 반대 환경의 전체 자격 증명을 교차 사용한 검사와도 구분한다. 비밀값 자체는 증거에 남기지 않는다.

후속 확인: 검사 스크립트가 종료 코드와 `password authentication failed`를 함께 확인하도록 바뀌었다. [반대 역할 검사 증거](evidence/P01-C1-cross-role.json)에서 두 환경 모두 인증 거부 및 반대 역할 0건을 확인했다. 이 근거로 P3 지적을 해소한다. lifecycle 전체를 반복 실행한 결과가 아니라 해당 조건만 추가 검사한 기록이며 기존 18건 결과와 합쳐 재실행했다고 표현하지 않는다.

## 추가 증거와 실행 안내 검토

- [임시 표식 정리 기록](evidence/P01-C1-probe-cleanup.txt)에 marketplace_dev/test 각각 0건이 기록됐다. 최초 18건 JSON에 정리 결과가 없던 한계를 별도 후속 증거로 보완했다. 이 검토세션에서 DB 조회를 직접 실행하지는 않았다.
- [빈 암호 검사](evidence/P01-C1-empty-password.txt)는 DEV_ADMIN_PASSWORD 값 누락으로 Compose 보간이 거부된 결과다. 빈 예제를 그대로 사용할 수 없다는 점을 확인한다. 네 암호 변수를 각각 비워 검사한 결과까지 입증하는 것은 아니다.
- 최신 [PostgreSQL 실행 안내](../postgresql-local.md)를 검토 범위에 포함해 재확인했다. 기존 .env 덮어쓰기 방지, 명령별 종료 코드 확인, 비밀값 출력 금지, 서비스별 중지와 볼륨 보존, 기존 볼륨의 암호 변경 한계를 설명한다. 호스트 handshake·컨테이너 TCP 인증 SQL·C2의 Boot JDBC 통합을 구분하며 추가 수정 사항은 발견하지 않았다.

### healthcheck TCP 지정 후속 검토

두 서비스의 healthcheck가 `pg_isready -h 127.0.0.1 -U "$${APP_USER}" -d "$${APP_DB}"`로 변경된 것을 확인했다. 기존 로컬 소켓 준비 확인을 컨테이너 내부 TCP 준비 확인으로 바꾸는 최소 변경이며 포트·역할·볼륨 범위를 확대하지 않는다. 최초 초기화용 소켓 서버의 응답을 최종 TCP 서버 준비로 오인하는 가능성을 줄인다.

[설정 반영 로그](evidence/P01-C1-final-up.txt)는 두 컨테이너의 재생성·시작·Healthy를 기록한다. 갱신된 [컨테이너 증거](evidence/P01-C1-containers.json)에서도 2026-10-23 20:24:13 생성, 두 서비스 running/healthy 및 기존 loopback 15432/15433 바인딩을 확인했다. 해당 로그는 개발세션 실행 증거이며 이 검토가 컨테이너를 조작한 것은 아니다.

최초 후속 검토에서는 변경 후 인증 증거를 기다렸으나, 이후 [최종 컨테이너 TCP 인증](evidence/P01-C1-final-auth.json)에서 두 서비스의 DB/역할 식별과 passed=true를 확인했다. 변경 후 인증 증거 대기는 해소됐다. 기존 18건 전체를 재실행한 결과로 계산하지 않는다.

### 최종 호스트 인증 SQL 검토

[호스트 JDBC 결과](evidence/P01-C1-host-jdbc.txt)와 [검사 소스](evidence/P01-C1-host-jdbc-source.txt)를 대조했다. 독립 Java 실행 도구는 `.env`에서 포트·암호를 읽고 호스트 127.0.0.1에 연결한다. 두 환경 각각 current_database/current_user를 기대값과 비교하고, 잘못된 암호는 SQLException의 SQLSTATE가 정확히 28P01일 때만 통과시킨다. 다른 연결 오류를 인증 거부로 계산하지 않으며 결과 출력에는 암호가 없다.

개발세션 기록의 15432/15433 게시 포트에 대해 정상 인증·DB/역할 식별 2건과 잘못된 암호 거부 2건, 총 **4건 통과 증거**를 확인했다. 이로써 이전의 호스트 handshake만 검증됐던 공백은 해소된다. 검토세션에서 Java 도구를 재실행하거나 `.env`를 직접 읽지는 않았다. 포트값은 실행 안내·컨테이너 바인딩 기록을 함께 근거로 삼으며, 결과 로그 자체는 환경명과 판정만 출력한다.

pgJDBC 42.7.13을 `.local-tools/c1-client`에 준비한 것은 개발세션 기록이며 해당 경로의 Git 제외 규칙을 확인했다. `git diff --name-only -- backend` 및 staged 동일 검사에는 변경 파일이 없었다. 독립 클라이언트 검사와 Spring Boot의 DataSource·트랜잭션·Flyway 통합은 구분한다. 최신 실행 안내 및 작업 문서의 최종 호스트 인증 보완 절도 이 구분과 일치한다. 작업 문서 앞부분의 호스트 미검증 문장은 최종 절에서 이전 이력으로 명시하고 있다.

## 확인한 구성과 증거

| 항목 | 판단 |
| --- | --- |
| 환경 분리 | db-dev/db-test가 별도 클러스터·DB·앱 역할·이름 있는 볼륨을 사용한다. 포트는 각각 loopback 15432/15433이다. 저장된 컨테이너 기록도 동일한 바인딩을 보인다. 네트워크까지 격리된 구성은 아니며 두 서비스는 기본 Compose 네트워크를 공유한다. |
| 권한 | 스크립트는 NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION을 명시한다. 기록에서 DB·현재 역할과 앞의 세 권한 false를 확인했다. 앱 역할은 자신의 DB 소유자이므로 그 DB의 DDL 권한까지 제한된 계정은 아니다. |
| SQL 인용 | 환경값을 psql 변수로 읽고 식별자는 `:"..."`, 암호는 `:'...'`로 인용한다. shell 문자열로 SQL 암호를 직접 이어 붙이지 않는다. ON_ERROR_STOP 및 shell 실패 종료가 있다. |
| 볼륨 | 서로 다른 dev-data/test-data를 `/var/lib/postgresql`에 마운트한다. PostgreSQL 18 계열의 권장 부모 경로와 맞는다. [공식 이미지 entrypoint](https://raw.githubusercontent.com/docker-library/postgres/master/docker-entrypoint.sh). 읽은 공식 소스는 현재 master이며 실행 digest 내부 소스와 동일하다고 증명한 것은 아니다. |
| 버전 | Compose는 postgres:18.6 태그를 사용한다. 증거에 linux/amd64 digest가 있으며 실제 SQL 버전 번호는 180006이다. 태그가 digest로 고정된 구성은 아니고 문서가 이를 구분한다. |
| 암호·제외 | 예제는 빈 값이며 Compose 필수값 검사가 적용된다. `.env` 제외 규칙 확인. 무작위 값 생성·네 값의 상이함은 개발 기록에 근거하며 비밀 파일을 직접 비교하지 않았다. Docker 환경값과 로컬 파일 접근의 한계가 문서에 명시돼 있다. |
| 데이터 보존 | 성공 기록 18건은 두 환경 식별/권한·잘못된 암호·반대 역할 각 3건, 독립 stop/start 4건, restart 2건, 재생성/데이터 보존 4건, 호스트 handshake 2건이다. 초기 버전 문자열 비교 실패는 별도 파일에 보존됐다. |
| 초기화·운영 안내 | 초기화는 새 볼륨에서만 적용되며 암호 파일 변경이 기존 DB 암호를 자동 변경하지 않는다고 설명한다. down -v와 일반 stop/restart를 구분한다. 기존 볼륨을 재사용·정리하지 않는 범위가 명확하다. |

## 미검증과 완료 조건

- **호스트 인증 SQL 검증 공백은 해소됐다.** 위 독립 JDBC 4건은 호스트 게시 포트 경로의 인증·DB 식별 증거다. Spring Boot 연결과 GUI DB 도구 접속까지 검증한 결과는 아니며 C2 구현은 수행하지 않았다.
- **healthy는 인증 성공이 아니다.** 최초 검토 당시 pg_isready는 로컬 소켓을 사용했고 이후 위 TCP 지정으로 보완됐다. 올바른 사용자·암호·DB 없이도 준비 상태를 얻을 수 있다는 한계는 그대로다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/18/app-pg-isready.html). TCP 준비 상태를 인증 SQL 성공이나 호스트 게시 포트 경로의 검증으로 확대하지 않는다.
- 검사 스크립트의 정리 실패는 여전히 경고만 남기며 기존 18건 JSON에는 정리 성공 여부가 없다. 이번 후속 정리 증거는 별도 파일로 확인했으며 검사 도구가 정리 실패를 자동 실패 판정한다는 뜻은 아니다.
- 원격/TLS 인증·백업 복원·버전 업그레이드·새 PC·다른 OS·Boot JDBC/Flyway·업무 스키마는 이 증거의 검증 범위가 아니다. 사용자의 직접 실습 완료도 미확인이다.
- 최초 검토 당시 실행 안내·상태는 갱신 중이었고 최종 커밋 확인이 남아 있었다. 현재 로컬 커밋 확인은 아래 최종 기록을 따른다. 기존 8080·5174 서버 상태나 다른 볼륨의 전후 동일성을 이 검토에서 직접 검사하지 않았다.

기존 B1~B5 변경이나 PostgreSQL 구성 이후 업무 기능을 이번 C1 성과로 계산하지 않는다. 검토만 수행했으며 P01-C2 및 다른 단계는 진행하지 않았다.


## 개발세션 최종 기록

검토 완료 후 작업 문서와 진행 상태를 P01-C1 완료로 정리했다. 위 진행 중·커밋 마무리 문장은 검토 당시 이력이다. 이 문서를 포함한 C1 변경을 로컬 Git에 기록하며 실제 SHA는 Git 로그를 따른다. 제품 범위는 Compose DB 준비이고 C2는 미착수다. 두 DB는 running/healthy 상태로 남겼으며 기존 다른 볼륨·API/프런트 서버를 중지·대체하지 않았다. 호스트 JDBC 4건과 최종 컨테이너 인증 증거는 작업 문서에서 확인할 수 있다. 이 추가 절은 개발세션의 완료 기록이며 검토세션이 새 검사를 실행했다는 의미는 아니다.
