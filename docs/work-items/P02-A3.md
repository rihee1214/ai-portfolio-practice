# P02-A3 React 회원 인증 연결

상태: 재승인 후 구현·개발 검증·독립 검토 완료 / 기준 968e08e / 2026-10-24

사용자가 기존 설계와 계획에 따른 A3 구현을 직접 승인했다. 승인된 React+Spring Security+JDBC 세션 구성을 유지한다. 작업은 아래 순서로 직접 실행하며 개발 검토는 검토 및 반영세션에 요청한다.

## 범위와 작은 결정

- /signup, /verify-email, /login, /account 화면. account는 현재 로그인 정보만 보여주며 프로필·주소 CRUD는 다음 단계다. 기존 판매자·운영자 화면은 기능 없는 미리보기로 유지한다.
- 가입/확인 POST JSON 어댑터를 A1 서비스에 연결한다. signup은201 및 확인 필요 상태, verify-email은200. 공개 입력에 자격을 받지 않는다. 중복409, 입력/토큰400, 저장 실패503, 기존 공통 오류 형태다.
- 가입 화면에 ASCII 이메일 정규화·비밀번호12~128 Unicode 코드포인트·실제 외부메일 미발송 정책을 안내한다. 이메일 확인은 토큰을 직접 붙여넣는 방식으로 URL·로그에 원문 토큰을 넣지 않는다. 로컬 메모리 메일함은 공개 API로 열지 않는다. 실제 브라우저 자동검사는 테스트 소스에만 존재하는 메일 어댑터로 토큰을 읽는다.
- React 인증 상태는 메모리에만 저장한다. 첫 진입/새로고침/탭 복귀 때 me 확인, 요청 취소와 순번으로 늦은 응답 무시. 로그인·로그아웃 뒤 CSRF 재발급. 변경 요청은 자동 재전송하지 않는다. 개인 화면은 확인 중·401·실패·로그아웃 즉시 숨기며 다른 탭에는 비밀값 없는 변경 알림만 전달한다.
- 반복 요청 보호는 단일 프로세스의 제한된 메모리 창으로 시작한다. 로그인 계정+IP 1분5회, 인증 변경 전체 IP 1분100회, 최대10000키로 제한하고429와 Retry-After를 반환한다. 성공도 시도 횟수에 포함한다. 프록시 헤더를 신뢰하지 않고 실제 연결 IP를 사용한다. 분산/운영 정책은 후속 한계다.
- 기존 서비스/DB는 유지. 기존 verify-db 초기화기가 새 UUID DB를 만든다. 브라우저 검증 서버도 임시 포트만 사용하고 기존 서버를 재사용하거나 종료하지 않는다.

## 실행 계획

- [x] 가입 HTTP/반복 제한 실패 검사 → 최소 API 어댑터·필터 → Java 기본/새 DB 통합 검사.
- [x] 인증 클라이언트·상태·폼 → 사용자 입력/로딩/오류/늦은 응답 검사 → 타입·린트·빌드. 폼 사용자 입력은 실제 브라우저, 비동기 상태 경계는 Vitest로 구분한다.
- [x] 테스트 전용 메일 접근과 Playwright를 실제 임시 Java 서버·새 DB에 연결. 가입/확인/로그인/새로고침/독립 문맥/로그아웃/CSRF/모바일·키보드 검증.
- [x] 검토세션 독립 검토·필요 수정, 보존 비교, 결과·실패·잔여 한계 기록. 다음 단계 금지.

기술 판단은 기존 설계를 따르며, 새 인증 라이브러리·JWT·로컬스토리지 세션을 도입하지 않는다. 화면 안내와 HTTP·DB 검증 결과를 구분하고 사용자가 직접 이해·확인한 것으로 자동 검사를 대신 표현하지 않는다.

## 중간 결과와 당시 차단 기록 (재승인 전 이력)

- a3-red: 신규 가입 HTTP 검사는401로 실패했다. 이후 익명 가입/확인 API를 연결하고 CSRF를 유지했다.
- a3-api: Java 기본126개·실제 DB 통합29개 통과.
- a3-browser: 기본126개 통과. 통합30개 중 브라우저 호출 검사1개 실패. PC/모바일 Playwright4개 중 입력·오류·반복 제한2개 통과, 가입·확인 후 로그인 화면 전환2개 실패.
- 자체 BroadcastChannel 알림 수신이 로그인 후 조회를 취소하는 원인을 발견해 source UUID로 자기 수신을 제외했다. /account 중복 라우트도 정리했다. **이후 실제 브라우저 재검증은 실행되지 않았다.**
- 프런트 타입·린트·Vitest51개 통과 기록이 있다. Node 프록시 검사는 sandbox EACCES 실패 후 허용 환경에서68개 통과했고 빌드도 성공했다. 이후 라우트 변경이 있어 최신 전체 검사 완료로 확대하지 않는다.
- 검토세션 R1은 신규 signup/verify-email의 CSRF 누락403·DB 무변경, 잘못된 입력400·중복409·토큰 재사용400 HTTP 검사를 추가하라는 내용이다. 이 보완 패치도 자동 검토가 거절했으므로 **아직 반영되지 않았다.**
- 수정 후 새 DB/브라우저 검증은 자동 승인 검토에서2회 거절됐다. 이전 A2 요청의 ‘A3 미진행’을 현재 유효 지시로 판단한 것이 사유다. 최신 A3 진행 사용자 메시지를 read_thread로 확인해 제시했지만 승인 근거로 인정되지 않았다. R1 검사 추가도 같은 사유로 거절됐다.
- 다른 실행 방법으로 우회하지 않았고 검토세션에도 독립 실행 보류를 요청했다. 기존 서버·DB를 변경하거나 검증 DB를 삭제하지 않았다. 최종 데이터 해시/서버 상태 비교는 아직 수행하지 않았다.
- 코드와 문서는 미커밋이며 A3 완료가 아니다. 사용자 명시적 재승인 후 R1 보완 → 새 DB/브라우저 재검증 → 최신 프런트/기존 화면 회귀 → 독립 검토 → 보존 확인·완료 기록 순서로 재개한다. 다음 단계는 진행하지 않았다.

## 로컬 메일함과 남은 한계

외부 이메일은 발송하지 않는다. 테스트 소스의 메일 조회 엔드포인트는 브라우저 자동검증에만 사용하며 배포용 공개 메일함 API는 없다. 수동 시연은 디버거에서 SignupController.signup의 register 호출 직후 SignupService의 mailbox(LocalTestMailbox).messages() 중 recipient와 일치하는 token()을 확인해 화면에 붙여넣는 방식이다. 이 수동 절차는 직접 검증하지 않았다. 재시작하면 메모리 메일이 사라지고 재발송 UI는 없다.

실제 TLS, 분산 반복 제한, 부하·동시 세션 경쟁, 사용자의 수동 이해·시연은 미검증이다. 재승인 후 자동 브라우저 결과는 아래 최신 기록을 따른다.

## 재승인 이후 최신 검증

검토세션의 사용자 직접 메시지 `01a16c82-84e1-7483-81d6-771813970ed0`에서 검사 보완·새 격리 DB·브라우저 재검증을 재승인했다. 개발세션이 원문을 읽어 확인했고 이후 동일한 안전한 실행이 허용됐다. 이전 차단은 해소됐으며 다음 단계·push 금지는 유지한다.

- R1: signup/verify-email CSRF 누락403과 회원·토큰 상태 무변경, 잘못된 입력400, 중복409, 토큰 재사용400 검사를 실제 HTTP로 추가했다. 정상 확인200 후에도 회원행은1개임을 확인한다.
- R2: source UUID로 같은 화면의 변경 알림을 무시한 최신 코드에서 정상 로그인·CSRF 재발급·me 조회·화면 전환, 새로고침, 다중 탭 로그아웃, 독립 문맥 재로그인·독립 세션 유지가 통과했다.
- `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/a3-resumed -Offline -RunBrowser`: 기본126개·PostgreSQL 통합31개 실패/오류/skip0, 인증 Playwright4개(PC2/모바일2) 통과. 브라우저 결과는 Java 검사 수에 더하지 않고 별도 집계한다.
- 프런트 타입 검사·린트, Vitest51개, Node68개, production 빌드 통과. Vitest에는 CSRF 선행·POST 재시도 금지·로그인 후 재발급/조회·로그아웃 시작 즉시 개인 상태 제거·늦은 me 무시·401/네트워크/잘못된 성공 응답 처리가 포함된다.
- 기존 P01 Playwright는 최신 a3-resumed JAR를 E2E_API_JAR로 지정하여 health·공통 오류·직접 URL/새로고침·키보드·모바일·문맥 분리16개 회귀 통과. 기존 고정 서버는 재사용하지 않았다.
- 모바일 계정 화면 캡처를 직접 확인했다. 가로 넘침 검사 통과, 계정 내용과 버튼·회원 메뉴가 표시된다. 실제 로그인 쿠키는 HttpOnly라 화면 코드가 읽지 않으며 localStorage/sessionStorage에 인증값을 저장하지 않는다.
- 배포 JAR 클래스 목록에서 SignupController/AttemptLimitFilter는 포함되고 PostgresJdbcIT/TestMailboxEndpoint는 포함되지 않음을 확인했다. 본래의 LocalTestMailbox는 개발용 어댑터로 남는다.

## 재현·학습 안내

프로젝트 JDK·Node·Maven 캐시·Playwright Chromium과 Compose 테스트 DB가 준비된 상태에서 저장소 루트의 위 RunBrowser 명령을 실행한다. 실행마다 새 EvidenceDirectory를 사용한다. 기존 보호 초기화기가 새 UUID DB를 생성하며 브라우저는 임시 Java 포트를 받아24176의 전용 Vite와 연결한다. 해당 포트가 이미 사용 중이면 재사용하지 않고 실패한다. 검증 후 새 DB를 삭제하지 않는다. 실패 결과·브라우저 캡처는 해당 증거 디렉터리에 보존된다.

직접 따라볼 코드 흐름: AuthForm 제출 → AuthStore의 csrf GET → 가입/로그인 POST → Java 서비스/인증 필터 → JDBC → 로그인 후 새 csrf와 me → AccountPage. 변경 요청은 통신 오류로 자동 재전송하지 않는다. 재현 예시는 다른 탭에서 로그아웃한 뒤 원래 탭의 회원 ID가 사라지는지 확인하는 것이다. 사용자 직접 실습·이해 확인은 아직 받지 않았다.

브라우저 인증 검사는 개발 서버에서 실행했고 production 빌드의 전체 인증 과정은 별도 검증하지 않았다. 실제 메일 전달·토큰 재발송·비밀번호 복구·주소 CRUD는 다음 범위이며 이번에 구현하지 않았다. 단일 프로세스 반복 제한은 재시작하면 초기화되고 여러 인스턴스에 공유되지 않는다.
