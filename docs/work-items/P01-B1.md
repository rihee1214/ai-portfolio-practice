# P01-B1 최소 Boot API 구현과 검증

작성일: 2026-10-21 (Asia/Seoul)  
작업 상태: **완료 — Actuator health로 교체·패키징·HTTP 27건 검증. 사용자 직접 확인은 미확인**

2026-10-21 상태 확인을 직접 만든 `/api/status`에서 Spring Boot Actuator의 `/actuator/health`로 교체했다. 아래 계약·실행 안내는 현재 구현이며, 최초 구현과 13시 재검증의 8건 결과는 당시 이력으로 보존한다. 최신 변경·검증 결과는 마지막 Actuator 교체 절을 따른다.

## 목적과 범위

[P01-A2](P01-A2.md)를 바탕으로 Java 애플리케이션을 빌드하고 실제 HTTP 요청에 JSON으로 응답하는 최소 단위를 만든다. G01·G07과 AC16의 실행 재현성 준비에 해당한다. 이 작업만으로 회원·상품·거래 기능이나 AC16 전체를 완료 처리하지 않는다.

최소 API와 공식 Wrapper를 구현하고 실행 JAR 및 실제 HTTP 응답을 검증했다. 아래 선행 조건 표는 착수 당시 이력이며 실제 해결 결과는 실행 결과·재검증 절에 기록했다. DB·React·인증·Git 초기화는 B1의 범위에 포함하지 않았다. 이후 React의 B2·B3도 완료됐으며 현재 다음 구현은 B4다.

2026-10-21 [ADR-002](../decisions/ADR-002-docker-postgresql.md)의 Docker 적용 대상은 PostgreSQL 서버로 정했다. 이 문서의 JDK·Maven Windows ZIP, `.local-tools` 경로, 호스트에서 Java API를 실행하는 방법은 유지한다. DB용 이미지 주소와 혼동하지 않도록 [P01-A2 10절](P01-A2.md#10-docker-방침-반영과-현재-준비-기준)에 다운로드·저장 기준을 정리했다. 현재 DataSource가 없어 health에 DB 연결 검사는 포함되지 않는다.

## API 계약

| 항목 | 설계 |
| --- | --- |
| 요청 | `GET /actuator/health`, 요청 본문 없음 |
| 성공 | HTTP 200, `{"status":"UP"}` |
| 장애 | `DOWN`·`OUT_OF_SERVICE`는 기본 HTTP 503. 이번 검증은 디스크 여유 공간 기준으로 `DOWN` 재현 |
| 응답 형식 | 기본 `application/vnd.spring-boot.actuator.v3+json`, `Accept: application/json`이면 `application/json`. 필드는 status 하나 |
| 의미 | 구성된 health 검사 결과. 현재 DB 미연결이며 주문·결제 등 전체 업무 성공의 증거는 아님 |
| 권한 | 공개 읽기 전용. 개인정보·환경 변수·서버 경로 노출 없음 |
| 데이터 변경 | 없음. 반복 호출해도 업무 상태를 변경하지 않음 |
| 제거·미공개 경로 | `/api/status`, `/actuator`, `/actuator/info`, `/actuator/env`, `/actuator/metrics`는 HTTP 404 |
| 지원하지 않는 메서드 | `POST /actuator/health`는 HTTP 405 |

기본 Actuator health를 이 단계로 앞당겼다. 상세 정보·컴포넌트·discovery 목록과 자동 liveness/readiness 그룹은 노출하지 않는다. 그룹 분리·접근 정책과 상세 관측은 P01-E·운영 단계에서 필요에 맞게 설계한다. 업무 API의 공통 오류 JSON은 P01-E에서 정의하며 health 응답을 그 구조로 감싸지 않는다. [Actuator 공식 계약](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html)

패키지는 `com.example.marketplace`, Maven artifactId는 `marketplace-api`, 앱 버전은 `0.0.1-SNAPSHOT`을 기본안으로 한다.

| 경로 | 책임 |
| --- | --- |

| `backend/mvnw`, `backend/mvnw.cmd`, `backend/.mvn/wrapper/` | 고정 Maven 실행 진입점. 공식 Wrapper 배포 형식에 필요한 파일만 포함 |
| `backend/src/main/java/com/example/marketplace/MarketplaceApplication.java` | Boot 시작점·컴포넌트 탐색의 기준 패키지 |

| `backend/verify-api.ps1` | 실제 JAR의 정상·장애·복구, 응답 형식·공개 범위·기존 경로 제거 검사 |

기존 StatusController·StatusResponse는 삭제했다. 상태 확인용 컨트롤러·DTO·서비스를 중복 작성하지 않고 Boot 4.1.1이 관리하는 Actuator를 사용한다. JDBC·Flyway·Security는 해당 후속 단계에서 추가한다.

## 요청과 코드 흐름

HTTP 클라이언트 → 내장 웹 서버·Spring MVC → Actuator health 엔드포인트 → 구성된 HealthIndicator 결과 집계 → 공개 범위에 따른 JSON·HTTP 상태 반환 순서다. 이번에는 SQL·React 상태 갱신 구간이 없다. 컨트롤러·DTO 학습은 이후 회원·상품 등 업무 API에서 이어간다.

Maven은 컴파일·패키징을 수행하고 Boot Maven 플러그인은 의존성을 포함한 실행 JAR를 만든다. Wrapper는 JDK를 설치해 주는 도구가 아니며 최초 Maven 배포본 접근이 필요하다. [실행 JAR](https://docs.spring.io/spring-boot/maven-plugin/packaging.html), [Wrapper](https://maven.apache.org/tools/wrapper/)

## 구현 절차와 검증 기준

1. 기존 문서 보존 여부와 도구·다운로드 상태를 확인한다. 실패한 조건은 실제 오류와 함께 기록한다.
2. 선택 JDK·Maven을 준비하고 버전·경로·무결성을 기록한다. 프로젝트 생성기로 기존 루트를 덮어쓰지 않는다.
3. backend의 시작점·공식 Wrapper를 유지하고 Actuator starter와 최소 health 공개 설정을 구성한다.
4. backend에서 `./mvnw.cmd -version`, `./mvnw.cmd verify`를 실행한다. 종료 코드와 컴파일·패키징 결과를 기록한다. 테스트가 0건이면 테스트 통과로 보고하지 않는다.
5. 생성한 `target/marketplace-api-0.0.1-SNAPSHOT.jar`를 `java -jar`로 실행한다. 로컬 확인에는 `--server.address=127.0.0.1 --server.port=8080`을 사용한다. 포트 충돌 시 기존 프로세스를 종료하지 말고 다른 포트를 기록해 사용한다.
6. 실제 HTTP로 정상 200·UP, 장애 503·DOWN과 JSON 형식·status 단일 필드를 확인한다. 제거한 경로·미공개 관리 경로 404와 POST 405도 검사한다.
7. 정상 → 임시 장애 조건 → 기본 설정 복구 순서로 기동·종료한다. 검사에서 시작한 프로세스만 종료하며 실행 환경·명령·예상/실제 결과를 남긴다.

이 작은 상태 API는 우선 실제 패키징·HTTP 확인으로 검증한다. 본격적인 JUnit·MockMvc 검사 체계는 P01-D1에서 추가한다. 테스트를 생략한 상태를 자동 테스트 통과라고 표현하지 않는다.

## 학습과 직접 수정 예시

현재 실습은 `verify-api.ps1`의 healthy·unhealthy·recovered 세 조건과 결과를 비교한다. 임시 실행 인수로 디스크 여유 공간 요구량을 매우 크게 설정하면 실제 디스크를 채우지 않고 DOWN을 재현할 수 있다. 다음 실행에서 해당 인수를 빼면 UP으로 돌아온다. status 값을 직접 고정하는 코드가 없고 검사 결과가 응답을 결정한다는 점을 설명해 본다. 한국어 화면 안내는 B4에서 프런트가 status를 해석해 표시한다.

자동 실행 결과와 사용자의 직접 이해·수정 결과는 각각 기록한다. 사용자 응답이 없으면 직접 확인은 미확인으로 둔다.

## 2026-10-21 P01-B1 재검증 이력 (Actuator 교체 전)

사용자의 P01-B1 요청으로 현재 파일을 다시 확인했다. 시작 시점에 이미 위 API·Wrapper·프로젝트 전용 도구와 P01-B2 프런트 코드가 있었다. 기존 최소 API가 계약에 맞으므로 앱 코드를 중복 생성하거나 변경하지 않고 처음부터 다시 빌드·실행했다. 프런트와 다음 단계 구현은 진행하지 않았다. P01-A·P01-A2·요구사항·MSA 문서는 보존했다.

| 기존 JDK ZIP 무결성 | 정확한 릴리스 이름의 Adoptium 메타데이터 SHA-256과 일치 | Windows x64 JDK 자산 확인. ZIP 재다운로드는 하지 않음 |

JDK의 `/v3/assets/version/21.0.12.1%2B1` 조회는 HTTP 404였다. [정확한 릴리스 이름 조회](https://api.adoptium.net/v3/assets/release_name/eclipse/jdk-21.0.12.1%2B1?architecture=x64&image_type=jdk&os=windows)로 전환해 `jdk-21.0.12.1+1`과 `OpenJDK21U-jdk_x64_windows_hotspot_21.0.12.1_1.zip`을 확인했다. 첫 조회의 404를 JDK 배포본 부재로 판단하지 않았다.

- JDK ZIP SHA-256: `f9d6e191ab098c0d416e7d588a24420a8621cd2f4720dab2459b8b7b2d2d8b4e`.
- Maven ZIP SHA-512: `ed41650d42485cfc243fad22158caf9cbb5dc408ce7a09ddb94dd42a019de929ca43065bfa450612cf12bf78b5cafa3884b96c090de326ff590448c933454af3`. [공식 체크섬](https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.16/apache-maven-3.9.16-bin.zip.sha512).

Java 21과 Maven 3.9.16은 [Boot 4.1.1의 공식 지원 범위](https://docs.spring.io/spring-boot/system-requirements.html)에 들어간다. 이번에는 지원 표 비교에 더해 실제 컴파일·실행도 검증했다. 환경 변수 지정은 실행 프로세스에만 적용했으며 영구 JAVA_HOME·PATH는 변경하지 않았다. 초기 루트 경로의 Wrapper 버전 조회에 `Access is denied.` 한 줄이 함께 출력됐으나 Maven 버전은 확인됐고, 아래 backend 빌드는 성공했다. 해당 한 줄의 원인은 별도로 확정하지 않았다.

| 로컬 통신이 허용된 실행의 동일 `verify-api.ps1` | 종료 코드 0. 포트 18081에서 기동·종료 2회, **HTTP 자동 검사 8건 성공** |

HTTP 검사는 회차마다 정상 GET 2건(200·JSON Content-Type·정확한 필드 2개·한국어 응답), 없는 경로 1건(404), POST 1건(405)을 확인한다. 재시작 후에도 같은 계약을 확인했다. 실행 JAR 안의 Boot 4.1.1·Spring Web/MVC 7.0.9·Tomcat 11.0.24·Jackson Databind 3.1.5도 확인했다.

실패 로그는 `backend/target/recheck-restricted.stdout.log`와 `recheck-restricted.stderr.log`, 성공 로그·결과는 기존 `smoke-1.stdout.log`·`smoke-2.stdout.log`·`smoke-results.json`에 남겼다. target은 다음 clean에 지워질 수 있으므로 위 표가 영구 기록이다.

재현은 앞 절의 JAVA_HOME·MAVEN_USER_HOME 설정 후 backend에서 다음 두 명령을 순서대로 실행한다. 첫 명령의 종료 코드가 0일 때 두 번째를 실행한다.

```powershell
.\mvnw.cmd -B -ntp '-Dmaven.repo.local=../.local-tools/m2/repository' clean verify
.\verify-api.ps1
```

기존 Maven 캐시를 재사용한 재빌드다. 캐시가 완전히 빈 다른 PC에서의 최초 설치는 이번에 검증하지 않았다. 제한된 실행 환경의 DNS·로컬 통신 제약은 남아 있으며, 여기서의 성공은 해당 접근이 허용된 실행 환경의 결과다. Docker·DB·인증·프런트 연동·배포·사용자 직접 수정 확인은 이번 범위에서 검증하지 않았다.

이번 변경은 P01-B1 기록과 관련 문서의 상태·재현 안내 보완이다. 최소 API 소스·빌드 설정·Wrapper·HTTP 검사 스크립트는 기존 구현을 유지했다. **P01-B1 재검증을 완료했으며 다음 단계는 진행하지 않는다.**

## 2026-10-21 Docker 방침에 따른 문서 점검

프로젝트 JDK·Maven 경로와 버전, Wrapper 배포 URL·체크섬 설정을 다시 확인했다. JDK·Maven을 Docker 이미지로 바꾸지 않고 기존 호스트 실행을 유지한다. JDBC 드라이버·Flyway도 P01-C2에서 Java의 Maven 의존성으로 추가할 항목이며 PostgreSQL 서버 이미지와 별개다. 이번에는 API 빌드·HTTP 검사를 재실행하지 않았고 기존 결과를 보존했다. 확인 범위와 Maven 버전 조회의 접근 거부 메시지는 P01-A2 10절을 따른다.

## 2026-10-21 Actuator health 교체와 검증

약 21:46~21:49 (Asia/Seoul)에 사용자의 교체 요청을 수행했다. 고정 UP 응답을 유지하는 대신 표준 health 검사·HTTP 상태를 사용한다. `spring-boot-starter-actuator`를 추가하고 상태 컨트롤러·응답 record를 제거했다. 실제 JAR에도 기존 클래스가 남지 않도록 clean 빌드했다.

`application.properties`는 health만 노출하고 details·components·discovery를 끈다. Boot 4.1.1의 자동 probes는 기본 활성화되어 응답에 groups가 포함됐으므로 초기 최소 계약에서는 `management.endpoint.health.probes.enabled=false`로 정했다. 배포 환경에서 liveness/readiness가 필요해지면 검사 대상·공개 범위를 별도로 정한다. [공식 설정 목록](https://docs.spring.io/spring-boot/appendix/application-properties/index.html)

| 검증 | 실제 결과 |
| --- | --- |
| 최초 제한된 환경의 clean verify | Actuator 의존성 다운로드 중 Maven Central DNS 오류로 실패 |
| 네트워크 허용 환경의 clean verify | BUILD SUCCESS, Java 소스 1개·설정 1개 포함 실행 JAR 생성 |
| probes 설정 보완 후 verify | 제한된 환경에서 기존 캐시로 BUILD SUCCESS, 최종 설정 재패키징 |
| 제한된 환경의 HTTP 검사 | Tomcat의 loopback connection·Permission denied로 기동 실패 |
| 로컬 통신 허용 환경의 최종 HTTP 검사 | 종료 코드 0, 3회 기동·종료, 27건 성공 |
| JUnit | 테스트 소스 없음, 0건 |

각 실행에서 기본 Accept와 `application/json`의 GET health 2건, `/api/status`·`/api/not-found`·`/actuator`·info·env·metrics의 GET 404 6건, POST health 405 1건을 검사했다. healthy·recovered에서는 200·UP, unhealthy에서는 503·DOWN을 확인했으며 모든 health 응답은 status 필드만 있었다. 원본 결과는 [HTTP 검사 기록](evidence/P01-B1-actuator-health-results.json)에 보관한다.

장애 조건은 검사 프로세스에만 `--management.health.diskspace.threshold=9223372036854775807B`를 전달했다. 실제 파일을 늘리거나 디스크를 채우지 않았다. PowerShell에서 Actuator의 vendor JSON이 바이트 배열로 반환되는 경우를 확인해 UTF-8로 해석한 뒤 JSON 계약을 검사하도록 스크립트를 보완했다. 초기 실패를 통과로 계산하지 않고 최종 설정·스크립트로 27건을 다시 검사했다.

DB·Docker·프런트 소스는 이번에 변경하지 않았다. DB 연결 검증은 C 단계에 남아 있으며 기존 B2·B3의 UI 검사를 이번에 재실행하지 않았다. 다음 작업은 [P01-B4 계획](P01-B4.md)의 health 프록시·화면 연동이고 구현은 미착수다.
