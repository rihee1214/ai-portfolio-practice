# P13-C 반품 환불 worker의 복구 비용 비교

[구현 계획 §15](../implementation-plan.md#15-p13-문제-재현과-기준-측정)와 [P13-B](P13-B.md)의 로컬 수용 기록을 따른다. 기준 커밋은 `82ebf9f50b610d2e306e750ef5abdcfe5a49af1e`다.

## 비교 결과

**판단 요약.** 동일 반품 업무의 재시작 요청부터 복구 worker 종료까지 중앙값이 4.245초에서 2.967초로 30.11% 줄었다. 이 장애에서 금융 정합성을 유지하면서 복구 구간을 줄이는 선택으로 짧게 실행하는 모놀리스 worker의 옵션을 우선 권고한다. 장시간 상주 worker는 상위 JIT 최적화를 포기할 수 있으므로 동일 설정을 채택할 근거가 부족하다.

## 측정 전에 정한 비교

P13-B에서 새 worker 실행 요청부터 준비 표식까지 중앙값은 4.129초, 재시작 요청부터 재인수 worker 종료까지는 4.245초였다. 같은 입력에서 DB 잠금 대기가 표본에 나타나지 않아 이번에는 인덱스나 캐시를 바꾸지 않고, **실험의 자식 worker 두 개에만** JVM 옵션 `-XX:TieredStopAtLevel=1`을 적용한다. 짧게 실행되는 JVM에서 상위 단계 JIT 컴파일 비용을 피하는 방법이다. 이 옵션이 실제 절감하는 시간은 실행해서 비교한다.

주 지표는 재시작 요청부터 worker 정상 종료까지의 중앙값이다. B보다 10% 이상 짧고 업무 불변식이 매번 성립하면 짧게 실행하는 worker에 유망한 후보로 평가한다. 동의부터 후속 결과까지의 시간, 구매자 명령 구간, 실행별 범위와 자원 관측을 함께 게시한다. 이 기준은 운영 성능 목표가 아니다.

워밍업 1회와 측정 3회를 각각 새 DB·미디어·JVM에서 직렬 실행한다. P13-B의 단조 시계 경계, 2개 주문 항목·배송 단위 4개·구매자 귀책 회수비 3,000원 입력, 동시 업무 1건, 최초 선점→준비 커밋→강제 종료→저장 lease 직후 재인수 순서를 고정한다. 견적 시작부터 동의 결과와 작업 등록 확인까지는 기존 10초를 공유한다. 고정 clock의 lease 이동은 실제 장애 감지 또는 고객 대기시간에 포함할 수 없다. 앞선 날짜의 B와 새 C는 비동시 측정이며 호스트 캐시·백그라운드 부하까지 동일하게 통제할 수 없다.

## 서비스 분리안의 기대와 비용

| 판단할 문제 | 모놀리스 내부의 worker 기동 변경 | 환불 실행을 독립 서비스로 분리하는 가정 |
|---|---|---|
| 제공자 제출 직전 worker가 종료됨 | 같은 DB에 저장한 작업·시도·예약으로 재인수한다. 기동 시간이 줄어도 제공자 처리 여부를 추가로 알 수는 없다. | 독립 프로세스를 재기동하거나 미리 준비한 복제본에 넘길 수 있다. 모놀리스 worker도 별도 프로세스이므로, 추가 복제본이나 다른 감지 주기를 분리 자체의 효과로 계산할 수 없다. |
| 중복 환불과 화면의 상태 | 기존 조회 작업과 반품 소비자가 같은 환불 시도를 따라간다. 확정 금액이 0원이면 예약과 보류를 유지한다. | 네트워크 타임아웃 뒤 무조건 재제출하면 이중 환불 위험이 있다. 안정된 시도 ID·제공자 멱등키, 재조회, 결과 이벤트 중복 제거 및 순서 검사가 필요하다. 제공자 근거가 없으면 검토 대기와 보류가 남는다. |
| 쓰기·배포 격리 | 같은 앱 버전과 DB의 기존 금융 계약을 재사용한다. 다른 역할과 함께 릴리스하는 비용은 남는다. | 별도 릴리스와 자원 상한이 구매 API의 배포·부하 영향을 줄일 가능성이 있다. 전용 저장소, 단일 쓰기 주체, Outbox와 소비 위치, 누락·중복 이벤트 재처리, 예약·원장·반품 대사, 서비스 인증·추적·백업·복구가 추가된다. |

분리 효과와 운영 비용은 [기존 MSA 계획](../msa-evolution.md)의 계약을 적용한 가정이다. 독립 서비스, 네트워크 왕복, 상시 복제본의 추가 자원, 장애 격리나 배포 주기는 이번에 실측하지 않는다. P13-D의 경계·소유권 결정과 P14 구현은 후속 범위다.

재인수 뒤 안전성의 기준은 [환불 처리](../../backend/src/main/java/com/example/marketplace/payment/infrastructure/JdbcRefunds.java)의 저장 상태와 소유 토큰이다. 이미 처리 중인 환불은 조회를 예약하고, 제공자 결과가 불명확하면 예약금을 유지한다. [반품 후속 처리](../../backend/src/main/java/com/example/marketplace/claim/infrastructure/ReturnFinancialWorker.java)는 이 결과를 소비한다. 두 역할의 데이터 저장소를 분리하면 예약금 7,000원과 반품 보류가 서로 다른 시점에 관측될 수 있다. 이 경우 환불 시도와 원 반품을 연결해 누락된 결과를 재전달하고, 확정 전에 보류를 해제하지 않는 계약까지 검증해야 한다.

## 실측 결과와 권고 근거

재기동 구간은 B 4.199~4.251초, C 2.953~3.187초였다. 세 업무 구간의 합으로 계산한 직렬 처리량은 초당 0.112건에서 0.154건으로 바뀌었다. 워밍업을 제외한 3회 규모로 상주 worker의 최대 처리량이나 운영 꼬리 지연을 추정할 수 없다. 구매자 응답은 부모 JVM에서 측정하며, 자식 옵션이 적용되기 전의 1.57% 차이를 옵션의 효과로 해석하지 않는다. 가장 큰 차이는 자식 실행 구간에 나타났다.

네 회차의 부모 JVM은 유효 단계 4, 두 자식은 각각 단계 1이었다. 같은 모의 결제 입력·DB 행 수·인덱스·이행 상태를 확인했고 네 DB 모두 견적 직전 크기는 B와 같은 24,581,823바이트였다. C 측정 3/3에서 최초 worker는 계획대로 종료됐고 다른 소유자가 같은 작업을 재인수했다. 조회·환불 결과·반품 재개 작업이 각각 1회 성공했다. 매번 원결제 43,000원, 환불 시도 1건, 견적·예약 7,000원, 회수비 예약 3,000원, 제공자 제출·효과·확정 환불 0을 단언했다. 환불은 `UNKNOWN`, 반품은 `REVIEW_REQUIRED`, 보류는 `ACTIVE`였다. 업무 결과를 더 일찍 관측했어도 환불이 확정되지는 않았다.

DB 표본 수는 C에서 66·64·65개였고, 미부여 잠금·잠금 대기·데드락 카운터 증가는 모두 0이었다. Hikari는 각 체크포인트에서 사용 중 0·유휴 5·대기 0이었다. 같은 PID의 두 체크포인트 사이에 자식 GC 횟수 증가는 없었다. 부모에서는 측정 2회차에 young GC가 1회 증가했다. 상주 시 CPU 비용, 장기 처리량, 외부 제공자 오류율 및 운영 장애 감지 시간은 미측정이다. 실제 Toss, 실송금 및 공개 배포는 종전 미검증 상태다.

실험 소스 manifest SHA-256은 `4f2cc91c19608bc434cd2d720760c8ad49dd0e09848674e2186d332eb8d88efa`다. B와 1,119개 엔트리를 대조해 실험 JUnit·JVM 관측기·전용 PowerShell 실행기 3개만 달라졌음을 확인했다. 최종 선택 실행은 워밍업 1회와 측정 3회 모두 통과했고 소스 일치·기존 자원 보존 검사도 통과했다.
