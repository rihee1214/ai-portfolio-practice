# P02-C 역할·운영 권한·최초 운영자

2026-10-24 / 기준 7568a3a / 상태: 구현·검증·독립 검토 완료

사용자가 P02-C를 직접 승인했다. 기존 공유 작업 폴더·로컬 커밋 흐름을 유지하고 지정 검토 및 반영세션에서 독립 검토한다. P02-D/P03 이후 기능과 기존 DB 이행은 하지 않는다.

## 범위와 결정

- BUYER/SELLER/ADMIN은 추가 역할이다. SELLER/ADMIN이 BUYER를 대체하지 않는다. 공개 가입은 BUYER만 저장하며 body의 역할·권한 값은 권한 부여에 사용하지 않는다.
- 운영 권한은 ACCOUNTS/CONTENT/SUPPORT/SETTLEMENTS/SYSTEM 5개로 분리한다. ADMIN 역할만으로 개별 업무에 접근하지 못한다. 서버는 현재 ACTIVE 계정·역할·개별 권한을 조회한다. 기존 세션의 권한 회수도 다음 요청에 반영한다.
- GET /api/seller/access, /api/admin/access, /api/admin/{accounts,content,support,settlements,system}/access는 현재 공간 접근 가능 여부를 확인하는 최소 읽기 API다. 실제 승인·정지·정산 업무는 구현하지 않는다. admin 미등록 영역은 기본 거부한다. 서비스용 권한 검사도 같은 정책을 사용한다.
- React 판매자/운영자 경로에 서버 접근 확인을 연결한다. 로그인 필요·권한 부족·통신 오류·확인 중에는 업무 내용을 표시하지 않는다. 기존 안내 화면의 업무 자체는 여전히 준비 상태다. 운영 화면 users/sellers→ACCOUNTS, moderation→CONTENT, orders→SUPPORT로 연결한다.
- 최초 운영자는 웹 API가 아닌 명시적 로컬 명령으로, 이미 이메일 확인된 ACTIVE 구매자에게 ADMIN과 5개 권한을 추가한다. 대상 UUID·실제 DB명 일치·INITIAL_ADMIN 확인값을 요구한다. 단일 초기화 행 잠금과 완료 표시로 동시/반복 실행을 거부한다. 기존 ADMIN이 있으면 거부한다. 역할·권한·감사 이력·authVersion 증가·세션 폐기는 같은 트랜잭션이다. 임의 새 암호·기본 관리자·공개 승격 API는 없다.
- 이 선택은 최소 권한 기반을 만들기 위한 이번 작업 결정이다. 운영자 추가/권한 편집 UI와 판매자 승인 절차는 후속 업무다. 로컬 명령 실행 권한과 DB 자격은 신뢰 경계이며 DB 직접 수정 자체를 앱이 통제하지는 않는다.

## 작은 작업 순서

- [x] C1 역할별 API 거부 검사 RED → 최소 서버 권한 경계.
- [x] C2 개별 운영 권한·최초 운영자 V6/로컬 초기화, 실패·경쟁·감사·롤백 검증.
- [x] C3 React 공간 접근 확인·취소·권한 안내, 단위/실제 브라우저 검증.
- [x] C4 지정 세션 독립 검토, 보존 비교·실패/제한 기록·로컬 커밋.

React의 숨김은 사용자 안내일 뿐 보안 경계가 아니다. Java 서버와 서비스의 권한 검사가 핵심이며, SQL은 현재 역할/권한과 대상 상태를 읽는다. 실제 거래 기능의 소유권·상태 전이는 각 후속 업무에서 이 검사에 추가한다.

## 계약·구현

`/api/admin/access`는 ADMIN이면 시작 공간에 들어갈 수 있다. 각 업무에는 ADMIN과 해당 권한이 모두 필요하며, 모르는 admin 영역은 기본 거부한다. 판매자는 SELLER 역할을 확인한다. 성공 JSON은 `{ "access": "CONTENT" }`처럼 확인한 영역명 하나이고 no-store다. 익명401·권한 부족403은 기존 업무 API 오류 JSON/요청 ID를 유지한다. health 계약은 그대로다.

HTTP는 `AuthConfiguration`의 경계 검사와 현재 회원 재조회 필터를 거친다. `AccessController`에서도 `AccessPolicy.require`를 호출하며, 후속 Java 업무 서비스는 이 API를 사용하고 대상 소유권·상태 전이를 추가해야 한다. 현재 `JdbcAccessPolicy`는 매번 DB의 ACTIVE·역할·개별 권한을 조회한다. 역할·권한의 세션 캐시를 허가 기준으로 삼지 않는다.

V6는 admin_permission(5개 권한), admin_bootstrap(단일 행), authorization_audit(초기 승격 감사)를 추가한다. 감사에는 대상·시각·부여 내용·LOCAL_BOOTSTRAP 출처를 남기며 실제 사람의 신원을 검증했다는 뜻은 아니다. 이번에 감사하는 제품 변경은 최초 승격뿐이다. 테스트 fixture의 직접 역할 변경이나 외부 DBA 변경을 자동 감사하는 범용 시스템은 아니다.

## 로컬 초기 설정 명령

이미 V6까지 이행되고 이메일 확인된 ACTIVE BUYER가 있는 명시적 대상 DB에서만 사용한다. 이번 작업은 기존 DB에서 이 명령을 실행하지 않았다. 정상 웹 서버는 초기 설정 코드를 자동 호출하지 않는다. 제품 JAR의 별도 진입점은 `com.example.marketplace.identity.infrastructure.InitialAdminCommand`다.

1. DB_URL·DB_USERNAME·DB_PASSWORD를 해당 실행 프로세스 환경에 준비한다. 비밀값을 문서·Git·로그에 기록하지 않는다.
2. BOOTSTRAP_USER_ID에 대상 회원 UUID, BOOTSTRAP_EXPECTED_DATABASE에 정확한 DB명, BOOTSTRAP_CONFIRM에 INITIAL_ADMIN을 지정한다.
3. 준비된 JDK로 아래 명령을 실행한다. JAR 위치는 실제 빌드 결과로 바꾼다.

```powershell
& ./.local-tools/jdk-21.0.12.1+1/bin/java.exe `
  '-Dloader.main=com.example.marketplace.identity.infrastructure.InitialAdminCommand' `
  -cp ./backend/target/marketplace-api-0.0.1-SNAPSHOT.jar `
  org.springframework.boot.loader.launch.PropertiesLauncher
```

명령은 외부 인수를 거부하고 환경의 명시적 확인값을 먼저 검사한다. web=NONE, Flyway=false, SQL init=never를 고정하므로 이 명령이 자동 스키마 이행을 실행하지 않는다. 접속 후 current_database를 대조하고 초기 설정 행을 잠근다. 성공은 INITIAL_ADMIN_COMPLETED와 종료0, 거부/실패는 고정 오류 문구와 종료1이다. 완료 후 해당 프로세스용 BOOTSTRAP_* 값은 정리한다. 기존 세션은 폐기되므로 다시 로그인한다. 완료 표시를 지우는 재설정 도구는 제공하지 않는다.

## 재현·학습·한계

기존 도구가 준비된 환경에서 `./backend/verify-db.ps1 -EvidenceDirectory .local-tools/p02-c-새이름 -Offline -RunBrowser`를 실행한다. 새 디렉터리·새 UUID DB만 사용하며 기존 서버와 DB는 유지한다. 브라우저 역할 계정은 테스트 소스가 새 DB에만 준비하는 fixture이며 일반 공개 승격 API는 없다.

직접 해 볼 작은 실습은 CONTENT만 가진 운영자로 콘텐츠 화면과 회원 관리 화면을 각각 여는 것이다. 전자는 준비 화면, 후자는403 안내가 나와야 한다. 역할이 운영자라는 사실과 모든 운영 업무를 할 수 있다는 사실이 다름을 확인한다. 사용자 직접 실습·이해 확인은 미확인이다.

판매 신청/승인·운영자 추가/권한 편집 UI·계정 정지/탈퇴·실제 조치·정산은 구현하지 않았다. 업무 화면은 권한을 확인한 준비 화면이며 실제 업무 데이터는 없다. 운영 권한 변경은 후속 업무가 감사와 함께 구현해야 한다. 이미 시작한 요청을 소급 취소하는 보장이나 운영 부하·모든 경쟁 순서·실제 HTTPS·새 기능 전체 production 브라우저 흐름은 검증하지 않았다. 초기 명령의 실행자 OS/DB 자격은 신뢰 경계다. 기존 DB 이행은 미실행이며 다음 단계는 진행하지 않는다.
