> **For agentic workers:** 구현 요청 시 `superpowers:executing-plans`로 작은 작업을 순서대로 수행한다. 개발 전체 통과 후 지정 검토세션에서 독립 검토한다. 이번 문서 작성은 구현/커밋 승인이 아니다.

## Interfaces와 세부 계약

판매자는 본인 주문의 준비·발송 버튼만 제공받는다. 발송 중 중복제출 방지와 동일 원인 키 재시도, version 충돌 재조회, 실패 시 입력 보존/첫 오류 포커스를 적용한다. 브라우저가 성공 응답 없이 낙관적으로 배송완료를 표시하지 않는다.

회원·비회원 상세에는 sellerOrder별 Shipment의 상태/항목/시각을 분리해 보여주며 실제 택배 추적이 아닌 모의 배송 진행이라고 표시한다. 서버 재조회로 새로고침·다른 기기 결과가 일치한다. 미결제/배송생성대기/오류/빈상태를 구별하고 로딩·세션만료·계정전환 시 이전 개인 내용을 숨긴다. 375/768/1440px·키보드 조작·aria 오류 연결은 기존 입력 흐름을 따른다. 개발용 시간진행/모의이벤트 조작은 공개 구매자 화면에 두지 않는다.

### 착수 계약과 실행 이력

F22/F203: `ShipmentStore.test.tsx`의 요청·개인정보·상태 전이 검사10개를 추가했다. `f2-unit-setup-red1.txt`의 import 실패는 환경/구성 실패이고 요구사항 RED가 아니다. 실행 가능한 무동작 골격에서 `f2-unit-red1.txt`는 실제 assertion8실패/2통과, 최소 구현 뒤 `f2-unit-green1.txt`10통과다. 경계2개는 초기 무동작에서도 통과하여 별도 mutation/실제 초기데이터 검사를 보강할 예정이며 이 결과만으로 최종 완료를 선언하지 않는다.

발송은 key/version/원항목을 첫 POST 전에 고정하고 유실 시 명시적 동일요청 재시도만 한다. F1 동일키 결과는 최초 SHIPPED/version1이므로 POST 응답으로 현재 상태를 덮지 않고 성공 후 GET을 수행한다. 409는 GET만 하며 확인 선택·오류를 보존한다. 401/403은 개인 결과를 폐기하고 자동 발송하지 않는다. CSRF preflight 실패는 latch를 해제해 명시적 재시도를 허용한다. StrictMode cleanup 후 auth 구독을 복구하고 최종 set 직전 generation/current auth를 검사한다.

실행 ledger: `.local-tools/p08-execution/task-f2-ledger.md`. 실제 DB 목록 RED 및 UI/브라우저·전체 검증은 진행 중이다. 실패 원본과 이전 실패 manifest28개54949파일을 보존한다.

검토 도중 실제 provider enum이 `MOCK_PROVIDER`임을 확인했다. 잘못된 `MOCK` 비교로 provider 이력이 시스템으로 표시되던 사례와 취소/만료 주문의 과거 PREPARING에 새 발송이 제안되던 사례를 검사에 추가해 `f2-review-red1`2실패12통과→`f2-review-green1`14통과로 보완했다. 발송 시작은 PAID만 허용하며 이전 배송 이력은 남긴다. 409 재조회 후 상태가 SHIPPED여도 확인 입력은 보존하고 새 발송은 비활성화한다.

현재 프런트 전체 `f2-unit-all1.txt`201/201과 typecheck3/lint3는 통과했다. focused1은 test fixture의 Timestamp import 누락 컴파일 실패로 요구사항 RED가 아니며 DB/브라우저 미실행이다. focused2는 새 DB에서 목록+fixture 비운영검사와 기존 실제 브라우저 host를 실행 중이며, 필수 전체검사 선택이 있으므로 종료가 정상이어도 최종 전체 통과 증거로 사용하지 않는다.
