# P09-A 운송장·분할 배송·모의 추적·배송 예외

상태: **P09-A 로컬·모의 범위 완료 / R-A01~03 해소 / 개발3·지정 검토세션 독립1 전체 통과**, 2026-10-30. 아래 NOT RUN·대기·보류 문구는 각 실행 당시 이력이며 최종 판정은 이 문서 끝과 독립 검토 기록을 따른다. B 이후는 미착수다.

## 실행 착수 — 2026-10-30

사용자가 P09-A 시작을 요청했다. 이번 승인 범위는 기존 실제 Toss 차단을 유지하는 로컬·모의 배송 확장 A이며 B 이후 구현은 포함하지 않는다. 독립 검토는 기존 **검토세션**(`01a189b0-2b5e-70d3-8276-214a42f6570d`)에서 수행한다. 커밋·배포·푸시는 하지 않는다. 기존 `codex/p05-d` 작업 폴더와 세션 구조를 유지하고, 미커밋 P09 계획 문서를 보존한다.

현재 A1 상세 계약을 해당 검토세션의 Astra Medium에 전달했다. 설계 판단 결과는 `P09-A-design-review.md`에 남기며, 승인 필요한 중요 정책이 남으면 관련 구현을 진행하지 않는다. 개발 자체 검증은 이 개발세션의 책임이며 최종 완료 판정은 검토세션의 독립 전체 결과 이후다. 아래 체크박스는 실제 증거가 생길 때만 갱신한다.
목표: P08 BASIC 배송과 이력을 보존하며 원 주문 수량을 여러 배송으로 나눈다.
요구사항: F09·F11, AC09 및 AC04·13 회귀. [P09 공통 계약](P09.md)을 전부 적용한다.

## 선행 입력과 범위

P08-F1/F2의 Shipments·JdbcShipments·MockShipmentJobs와 P08-G 인계를 읽는다. 구현 요청 및 P09의 P08 외부차단 진입 게이트가 필요하다. 현재 BASIC은 기본 생성 중복방지 목적이며 영구1:1이 아니다. 기존 PAYMENT_SETTLED handler·backfill을 중복 등록하거나 완료 job을 초기화하지 않는다. 실제 택배 연동·구매 확정·클레임은 이번 범위 밖이다.

## 상세 계약과 변경 위치

- 소비: `Shipments.seller/buyer/ship`, `FulfillmentOrders.lockPaid`, 원 sellerOrderId/orderItemId와 수량. 생산: 분할 배송의 항목별 수량·완료시각·version·이력과 B가 사용할 신뢰된 배송 완료 사실.
- 새 분할 명령은 요청 키·예상 version·원 항목/수량을 받는다. 판매자/출처/현재 상태/가격은 서버가 결정한다. A에서는 자기 매대의 PAID·미발송 수량을 배정/출고한다. B가 추가하는 보류 계약은 B에서 출고 경계에 연결하고 C에서 실제 취소 신청과 경합 검증한다. A에 가짜 always-unheld 포트를 넣거나 아직 없는 클레임 차단까지 통과했다고 하지 않는다. 같은 수량을 BASIC과 새 배송에 이중 배정하지 않는다.
- 같은 키/내용은 최초 결과, 다른 내용/오래된 version은409, 잘못된 형식은400, 타인/없는 자원은404. 현재 권한·CSRF·잠금 후 만료 재검사는 재시도에도 적용한다.
- 운송장 변경 전후와 이유·actor를 저장한다. 모의 이벤트는 출처/시각/키/sequence/applied를 유지하고 상태를 후퇴시키지 않는다. DELAYED/FAILED가 배송 완료로 취급되지 않아야 한다.
- 착수 설계 게이트: 운송장 형식/길이·수정 허용 구간, 예외 상태에서 정상 진행 복귀표, 분할 재배정 잠금/원 단위 식별 방식을 Astra 판단으로 고정한다. 중요 정책 변경은 승인 전 구현하지 않는다.

원단위 식별은 실제 `order_unit(item_id,ordinal)`를 따른다. 원 항목의 ordinal 선택 순서와 quantity 입력을 서버가 어떤 단위로 고정하는지 A1에서 정하고, 배송/보류/확정/환불이 같은 단위와 그 원 금액을 사용한다. C가 환불 때 단위를 새로 선택하지 않는다. 없는 ordinal·다른 항목/판매자의 단위를 배정하는 직접 INSERT도 거부하도록 FK/제약과 검사 계획을 고정한다.

기존 BASIC은 현재 전체 원수량을 가지고 `JdbcShipments.prepare` 재시도와 `ship`이 원수량 동등성을 검사한다. A1은 기존 생성 사실과 현재 분할 배정을 구분하는 이행·재실행 계약을 반드시 결정한다. 기존 발송/완료 배송과 이벤트를 재작성하지 않으며 신규 migration/재개 가능한 이행으로 단위 연결을 만든다. 분할 후 PAYMENT_SETTLED/prepare/backfill 재호출이 BASIC 전체수량을 복원하거나409 루프를 만들면 실패다.

현재 의존 방향은 fulfillment→order다. A1에서 배송 사실의 생산·전달·저장·소비와 잠금 경계를 B가 사용할 수 있게 설계한다. applied 완료 eventId·원단위·완료시각·배송 묶음을 신뢰된 내부 계약으로 전달하고, 기존 DELIVERED 배송의 최초 이행·유실/중복 재개를 포함한다. order에서 Shipments를 역조회하는 순환 의존이나 브라우저가 입력한 완료 boolean/시각을 허용하지 않는다. H01~03은 A 종료 인계의 필수 항목이다.

## 독립 검토와 B 인계

검토자는 BASIC 중복방지를 제거해 중복 배송을 허용하지 않았는지, 분할 후 합계뿐 아니라 같은 원수량이 중복 배정되지 않는지, 예외/중복 이벤트가 완료시각을 조작하지 않는지 확인한다. DB 제약·경합 assertion·P08 회귀와 동결 소스의 새 독립 전체 결과가 모두 필요하다. 누락 시 B 진입 보류.

B에 원 단위/배송 묶음별 완료시각, 배송 사실 읽기 공개 계약, 잠금 순서와 이력 ID를 전달한다. 실제 메서드·migration·변경 파일·소스 SHA·개발/독립 실행 경로·실패 이력은 아래 후속 기록을 따른다. 구현 실행 결과·독립 검토가 없다는 표기는 최초 계획 시점의 이력이며, 사용자 직접 확인은 계속 미확인이다.

## 구현 계약과 검증 변경 근거 — 2026-10-30

V37 `split_shipments_and_initial_delivery`를 추가했다. V31/V36과 기존 job/event/audit를 고치지 않는다. 현재 배정 `shipment_unit`의 원단위 PK/FK·shipment_item 복합 귀속 및 양쪽 deferred count trigger가 직접 INSERT/UPDATE 불일치를 거부한다. `shipment_preparation`은 최초 BASIC id/원단위 SHA256 digest를 저장한다. `shipment_command`는 종류/출처/키별 canonical hash와 최초 source/target/선택 ordinal 결과를 보존한다. 원 BASIC은 분할 후 잔여 ordinal을 유지하고 prepare는 하위주문 전체 배정과 불변 marker를 비교하여 쓰기0으로 재실행한다.

분할은 `/split`, 번호 등록·정정은 `/tracking`이고 기존 `/ship`의 입력 형식은 유지했다. 서버가 현재 단위 오름차순을 선택하며 HTTP에 ordinal/actor/source/시각/완료 입력은 없다. `Shipments.View`에 units/tracking/trackingHistory/exceptionStatus/progressEpoch/deliveredAt을 추가했다. 번호 미등록 출고는 기존 ship 이벤트에 SYSTEM 자동번호 이력을 연결하므로 순수 BASIC의 상태/version과 기본 이벤트 개수는 그대로다. 정정 이벤트·이력은 이전/이후/사유/출처/actor/시각을 별도 조회한다. UI는 부분 수량의 합집합·귀속·중복 원단위를 확인하며, 낙관적으로 POST 결과를 현재 배송으로 표시하지 않는다.

새 progress payload는 `v2|shipmentId|epoch|expectedStage|target|occurredAt`, epoch0 키는 기존 `progress:<id>:<target>`, 후속 세대 키는 `progress:v2:<id>:<epoch>:<target>`이다. 기존 3필드 v1 payload는 epoch0/단계로 해석하고 원 content/receipt는 유지한다. 운송장 변경으로 total version이 증가해도 물류 세대는 바뀌지 않는다.
