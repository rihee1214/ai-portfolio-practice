# ADR-002 Docker Compose로 개발용 PostgreSQL 구성

작성일: 2026-10-21 / 적용: 설계 v4, P01-C1 이후 / 상태: **방침 채택, 구성·실행·연결 검증 미착수**

## 1. 배경과 결정

사용자는 PostgreSQL 서버를 PC에 직접 설치하지 않고 Docker로 실행하기로 했다. [ADR-001](ADR-001-java-spring-react.md)의 PostgreSQL 선택을 유지하고, 개발·테스트용 DB의 실행 환경을 Docker 컨테이너로 정한다. Docker Compose로 이미지 버전·포트·볼륨 등 실행 설정을 관리한다.

React 개발 서버와 Spring Boot API는 기존처럼 각각 실행한다. DB를 사용하려면 Docker 엔진과 PostgreSQL 컨테이너가 실행 중이어야 한다. 이번 결정으로 프런트엔드나 API의 컨테이너화까지 범위를 넓히지는 않는다. 실제 구성은 [구현 계획](../implementation-plan.md)의 P01-C1에서 진행한다.

## 2. 선택 이유

- **로컬 환경 관리:** PostgreSQL 서버를 호스트 OS에 직접 설치하거나 Windows 서비스로 관리하는 부담을 줄이고, 프로젝트에 필요한 DB를 실행·중지하기 쉽게 한다.
- **환경 재현:** 이미지 버전과 실행 설정을 Compose 파일에 기록해 다른 개발 환경에서도 같은 DB 구성을 준비하기 쉽게 한다. 실제 이미지와 설정으로 재현되는지는 P01-C1에서 확인한다.
- **애플리케이션과 DB의 실행 분리:** DB를 별도 실행 단위로 관리하고 Spring Boot에서 네트워크로 연결한다. API와 DB의 시작·종료를 각각 다루며 연결 주소·포트·계정과 DB 중단 시 영향을 학습한다.
- **3계층 구조 학습:** 화면·애플리케이션·데이터의 책임을 구분하고, 애플리케이션과 DB 사이의 통신 경계를 개발 환경에서 경험한다.

| 계층 | 담당 | 역할·연결 |
| --- | --- | --- |
| 표현 계층 | 브라우저의 React | 화면과 사용자 입력, HTTP로 API 호출 |
| 애플리케이션 계층 | Spring Boot | 업무 규칙·권한·트랜잭션, JDBC로 DB 연결 |
| 데이터 계층 | Docker의 PostgreSQL | 데이터 저장·SQL·제약, 볼륨에 데이터 보관 |

계층별 책임 구분은 애플리케이션 설계에서 정하며 Docker는 DB의 실행 환경 분리를 돕는다. 개발 PC 한 대에서 실행하므로 세 대의 물리 서버나 독립 장애 영역을 구성한 것은 아니다. 브라우저는 DB에 직접 연결하지 않는다. DB 컨테이너 사용을 MSA 전환이나 성능 향상의 근거로 삼지 않으며, 업무 서비스 분리는 기존 P13~P14 계획을 따른다.

## 3. 구성 원칙

1. PostgreSQL 공식 이미지를 사용한다. 기존 목표 버전에 맞춘 구성 후보는 `docker.io/library/postgres:18.6`이며, 웹의 공식 태그 안내를 확인했다. 실제 pull·플랫폼·digest는 P01-C1에서 확인·기록한다. 다운로드 출처·호스트 도구 경로·컨테이너 데이터 경로의 구분은 [P01-A2 10절](../work-items/P01-A2.md#10-docker-방침-반영과-현재-준비-기준)을 따른다.
2. 개발용·테스트용 DB와 접속 계정을 분리하고 각각의 연결 설정을 명시한다. 컨테이너 개수와 포트 등 세부 구성은 P01-C1에서 정한다.
3. 데이터는 컨테이너의 임시 파일시스템 대신 명시한 볼륨에 보관한다. 볼륨을 유지한 컨테이너 재생성 후에도 개발 데이터가 남는지 검증한다. 볼륨 삭제는 데이터 삭제이며, 볼륨 사용 자체가 백업을 대신하지 않는다.
4. Compose 설정과 비밀값 없는 설정 예제는 버전 관리한다. 실제 비밀번호는 Git에서 제외한 로컬 설정으로 관리하고 브라우저의 `VITE_*` 설정에 넣지 않는다.
5. DB 스키마 변경은 기존 계획대로 P01-C2에서 Spring JDBC·Flyway와 연결한다. 테스트는 실제 PostgreSQL을 사용하며 개발 데이터를 초기화하지 않도록 구분한다.

## 4. 부담과 대안

Docker 엔진의 실행·접근 권한과 자원 사용, 포트·볼륨 관리를 추가로 다뤄야 한다. 같은 PC의 API와 DB는 호스트 장애의 영향을 함께 받으므로 운영 환경의 가용성·백업·배포 정책은 별도로 설계한다.

PC 직접 설치는 Docker 없이 DB를 실행할 수 있지만 사용자의 환경 관리 선호와 맞지 않아 채택하지 않는다. 별도 원격·관리형 DB는 현재 개발 환경 범위에 포함하지 않는다. Docker 접근이 안 되면 원인과 실행 가능 환경을 먼저 확인하며, PC 직접 설치로 자동 대체하지 않는다. 운영 DB의 배포 방식은 P12에서 정한다.

## 5. 현재 상태와 후속 검증

2026-10-21에는 구성 방향과 선택 이유만 문서에 반영했다. Compose 파일 작성·이미지 다운로드·컨테이너 생성·DB 연결은 수행하지 않았으며 P01-C1은 미착수다. 앞선 조사에서 Docker 클라이언트는 확인했지만 엔진 접근이 거부되어 컨테이너 상태를 확인하지 못했다. 이를 엔진 중지나 PostgreSQL 미설치의 증거로 단정하지 않는다.

P01-C1에서는 Docker 엔진 접근과 이미지 준비, 개발·테스트 DB 및 계정 식별·접속, 독립적인 DB 실행·중지·재시작, 볼륨을 유지한 컨테이너 재생성 후 데이터 보존을 검증한다. P01-C2~C3에서는 Spring Boot의 JDBC 연결·Flyway 이행·트랜잭션을 확인한다. DB 연결 실패 시 API 동작도 DB 연동 단계에서 확인하고 실행 결과를 기록한다.

후속 P01-A~B 문서 점검에서 [공식 이미지 안내](https://hub.docker.com/_/postgres)의 `18.6` 태그와 PostgreSQL 18의 데이터 볼륨 경로를 확인했다. 이 웹 확인은 로컬 이미지 존재·다운로드·DB 실행의 증거가 아니며 해당 검증은 여전히 미착수다.

[P01-A](../work-items/P01-A.md)·[P01-A2](../work-items/P01-A2.md)의 로컬 설치·원격 DB 대안은 조사 당시 이력으로 보존한다. 이후 개발용 DB 구성에는 이 결정의 Docker 방침을 적용한다.
