# AI와 함께 진행하는 개발 작업 흐름

## 필수: 하네스 선행 검토 (2026-11-03 정책 갱신)

모든 후속 구현·검토에는 [통합 자동 검증 하네스 규칙](verification-harness.md)을 적용한다. 구현·검토 전에 변경 계약·소비 계약·위험과 실행 가능한 assertion을 연결하고 아래 검증 범위를 결정한다. 선택 범위의 작업 완료와 전체 검증 PASS는 구분한다. 작업 제약의 필수 assertion 누락·선택 범위의 실패/skip·미해결 필수 결함·근거 누락은 완료를 차단한다. 화면 직접 확인과 코드 독해는 실행 동작의 자동 검사 근거를 대신하지 않는다. 과거 개발/독립 전체와 실패·완료 기록은 당시 증거로 유지하며 새 정책으로 소급 변경하지 않는다.

### 변경 영향과 위험에 따른 검증 범위

| 변경·마감 조건 | 필요한 확인과 완료 기준 |
| --- | --- |
| 범위가 명확한 도메인 변경 | 해당 도메인과 영향표에 등록된 소비 계약을 포함한 선택 검증. 모든 작업 제약의 assertion과 영향 범위가 충족되면 선택 범위로 작업 완료 가능 |
| 인증·공통 금융·작업 실행기·공유 스키마·공통 fixture·검증 하네스 등 넓은 실행 동작 변경 | 최종 소스의 무선택 `./verify.ps1 -Offline` 전체 근거 필수 |
| 영향 불명확, 영향표 누락·불완전, 신규/삭제/이름 변경의 소비 영향 불확실 | 전체로 확대. 등록 오류/누락은 수정하고 실패를 무시하지 않음 |
| 여러 변경을 통합하는 마일스톤 마감·배포 전 | 통합된 최종 소스의 무선택 전체 근거 필수. 같은 소스·조건의 유효한 전체 증거가 있으면 행사 이름만 바뀌었다고 재실행하지 않음 |
| 실행 동작에 영향 없는 문서·서식만의 변경 | 링크·형식·차이·실행 파일 불변 등 해당 변경에 필요한 정적 확인으로 마감 가능. 설정·실행 예제·생성 입력이 동작을 바꾸면 이 분류를 적용하지 않음 |
| 단순 로컬 커밋 | 그 자체로 전체 실행 조건이 아님. 실제 변경 영향에 맞는 유효한 증거를 연결. 커밋 권한은 별도 사용자 지시를 따름 |

개발자는 선택·제외한 계약과 이유, 영향표와 실제 소비 코드의 대응, 필요한 단위/ArchUnit/DB/프런트/브라우저 assertion을 기록한다. 독립 검토자는 **같은 소스**에서 변경 영향·선택 범위·assertion 적합성을 확인하고 필요한 범위를 검증한다. 전체 필요 조건이면 무선택 전체 근거가 있어야 하지만 개발·독립에서 이를 기계적으로 두 번 실행하지 않는다. 독립 검토는 유효한 실행 증거를 대조하고 추가 실행/재현이 필요한 범위와 이유를 기록한다. 구현자의 자체 확인을 독립 검토로 바꾸지 않는다. 문서·서식 작업에서 별도 독립 실행이 불필요하면 그 이유와 정적 검토 결과를 명시한다.

실패 수정 뒤에는 실패 검사와 수정 영향 범위를 재검증한다. 소스가 바뀌면 어떤 기존 증거가 무효인지 계약·파일·실행 조건으로 판정하고 영향 없는 증거는 출처를 연결해 재사용한다. 공통 동작/불명확 변경이면 전체 조건을 적용한다. 소스 변경·새 실패·새 위험 근거 없이 이미 통과한 검사를 관성적으로 반복하지 않는다. 재현 조사에는 가설·목적·조건을 남기고 원 실패를 보존한다.

현재 P01 종합 점검 결과는 [완료 점검 기록](work-items/P01-completion-audit.md)을 기준으로 한다. P01의 결과·제한은 해당 기록을 따른다. [P02 전체 점검](work-items/P02-completion-audit.md)의 R1 재현·수정·독립 검증을 완료했다. 계획 범위 완료와 운영 준비 제한을 구분하며 P03는 진행하지 않았다.

## 1. 새 작업 창에서 이어가는 방법

같은 프로젝트 폴더를 선택한 새 작업 창에서 시작한다. 목적과 설계 본문을 매번 복사하는 대신 README와 docs를 읽게 한다. 다른 폴더에서 시작하면 이 문서와 코드가 자동으로 공유된다고 가정하지 않는다.

새 창이 이전 대화를 모두 알고 있다고 가정하지 않는다. 먼저 실제 파일·현재 구현·선행 단계의 최종 개발/독립 검증·인계 기록을 확인하고, 문서와 코드가 다르면 차이를 기록한다. 승인된 범위와 남은 차단을 확인한 뒤 7절의 기존 작업 문서 안에 전체 완료표·업무 묶음·검토 조건을 정리한다. 선행 완료나 문서 정비 자체를 다음 단계 착수 승인으로 해석하지 않는다.

[P01-B1 최소 Boot API](work-items/P01-B1.md)의 구현·패키징·실제 HTTP 검증을 완료했다. [P01-B2](work-items/P01-B2.md)의 첫 React 화면과 [P01-B3](work-items/P01-B3.md)의 라우팅·역할별 화면 틀도 검증했다. [P01-B4](work-items/P01-B4.md)는 추가 UI·timeout 검사에서 발견한 부분 응답 종료 결함 R4를 수정하고 개발·preview에서 재검증했다. 이 문단은 B4까지의 이력이며 현재 P01 상태는 종합 점검 기록을 따른다. 사용자 직접 확인은 미확인이다. P01-A2는 조사 당시 이력으로 보존하고 이후 도구 준비·실행 결과는 B1~B4를 확인한다.

B1의 최신 상태 확인은 Actuator `/actuator/health`이며 기존 `/api/status`는 제거됐다. 기본 health 도입을 P01-E에서 앞당겨 정상·장애·복구 HTTP 27건을 검증했다. P01-B4는 health 경로만 개발 프록시로 전달하고 status 기반 한국어 안내·503·통신 실패·재시도를 구현했다. [B4 검토 기록](work-items/P01-B4-review.md)의 경로 차단·응답 분류 수정과 최종 검증·미검증 항목을 함께 읽는다.

사용자는 Java에 꽤 유창하고 레거시 Spring 경험이 있다. Spring Web은 보완이 필요하지만 다룰 수 있으며 Oracle 사용·간단한 SQL 작성 경험이 있다. JavaScript/TypeScript·React·Node 도구는 새로 학습하며 자료를 찾아가며 확인할 수 있다. Java 경험을 설명의 출발점으로 삼되 React나 Boot·웹·인증·고급 SQL까지 능숙하다고 가정하지 않는다.

사용자가 Java·Spring Boot 백엔드와 React 화면을 확정했다. 목적·목표·전체 기술 설계·구현 계획은 v4이며 현재 선택 근거는 새 ADR-001이다. 이전 기술 구성의 ADR은 제거했다. P01-A의 과거 환경 관찰은 날짜와 함께 보존하고 설치 목표·후속 지시는 현재 기술 구성으로 교체했다. F01~F18·AC01~AC20은 유지하고 React/API 학습 목표 G10을 추가했다.

## 2. 문서를 읽는 순서

1. README: 프로젝트 목적, 문서 위치, 현재 단계.
2. requirements: 사용자가 정한 요구와 제안 기본안, 기능 ID·완료 기준.
3. shop-design: 모듈·데이터·권한·상태·거래 처리.
4. [ADR-001 Java·Spring Boot + React 채택](decisions/ADR-001-java-spring-react.md)과 [ADR-002 Docker PostgreSQL 구성](decisions/ADR-002-docker-postgresql.md): 현재 기술의 역할·선택 이유·부담·대안·버전·검증 조건.
5. implementation-plan: 이번 단계·업무 묶음의 범위·선행 조건·검증.
6. msa-evolution: P13 이후 또는 초기 모듈 경계를 검토할 때.
7. 이전 작업 기록과 결정 기록: 실제 변경·검증·남은 제한.

사용자의 새 지시가 기존 문서와 다르면 바뀐 요구를 문서에 반영한다. 사소한 구현 선택은 기존 목표 안에서 판단하고 기록한다. 결제 정책·권한·개인정보 노출 범위처럼 의미가 큰 변경은 영향과 선택안을 구체화해 확인한다.

Java·Spring Boot·React는 사용자 확정 선택이고 TypeScript·Vite·JDBC 등 세부 구성은 ADR-001의 설계 결정이다. Node.js는 React 개발·빌드 도구의 실행 환경이며 업무 API는 Java가 맡는다. 후속 Java·React 환경 조사와 실제 실행 증거를 함께 읽는다. 새 도구를 도입하거나 교체할 때에는 역할·요구와의 연결·장단점·대안·검증 방법을 설명한다. 기존 선택안 안의 매 작업에 별도 기술 승인 절차를 추가하지 않는다.

개발·테스트용 PostgreSQL은 사용자 요청에 따라 Docker Compose로 구성하며 PC에 DB 서버를 직접 설치하지 않는다. ADR-002의 환경 재현·실행 분리·3계층 학습 목적과 같은 PC에서 실행한다는 한계를 함께 설명한다. Docker 접근 문제는 P01-C1에서 확인하고, 문서상 채택과 실제 구성·연결 검증 완료를 구분한다.

## 3. 한 작업의 반복 흐름

### 업무 결과와 의존 순서

작업은 메서드·DTO·accessor·테이블이 아니라 실제 assertion으로 확인할 수 있는 업무 결과 단위로 묶는다. 각 묶음은 끝낼 결과, 검증할 제약, 다음 묶음에 전달할 계약과 의존 순서를 명시한다. 독립적인 실패·완료 조건이 있는 책임은 무조건 합치지 않는다. 내부 구현 단계마다 별도 인계·소스 동결·독립 검토를 만들지 않는다.

기존 업무 실패 재현이 내부 의존 구현을 포괄하면 구성요소마다 별도의 RED 실행을 요구하지 않는다. 서로 다른 업무 제약의 assertion과 실패 증거는 유지한다. 소스 식별·동일성 확인은 검토 대상과 최종 검증을 증명하기 위한 것이며 매 내부 수정의 동결 게이트가 아니다.

| 순서 | 수행 내용 | 남기는 결과 |
| --- | --- | --- |
| 1 범위·계약 | 선행 인계·요구사항·전체 완료 조건·미정 정책 확인 | 업무 묶음과 의존 순서, 제약별 검사/기대 결과 |
| 2 최소 연결 | 필요한 최소 UI→API→DB→결과 표시를 조기에 연결 | 실제 정상 흐름의 집중 증거; 화면 없는 작업은 UI 해당 없음과 이유 |
| 3 필수 경계 완성 | 권한·금액·실패·복구·동시성·회귀와 나머지 UI 구현 | 전체 완료표의 남은 항목 및 관련 assertion |
| 4 최종 검증 | 영향·위험 및 제약 연결 확인 → 개발 검증 → 동일 소스 독립 범위 검토·필요 검증 | 선택/전체/정적 구분, 새 실행 시 새 DB·미디어·증거 경로, 재사용 증거와 근거 |
| 5 수정·인계 | 실패 검사·수정 영향 재검토·재검증 → 최종 인계 | 최종 소스와 범위에 유효한 개발/독립 근거, 실패 이력·한계·소비 계약 |

최소 정상 흐름이나 영향 계약을 빠뜨린 집중 검사만으로 완료를 선언하지 않는다. 선택 검증으로 완료하려면 해당 작업의 전체 완료표와 선택 범위가 충분해야 하며 전체 PASS라고 표현하지 않는다. 최종 검증 후 변경은 위 영향·위험 기준으로 재검증하고 새 근거 없이 통과 검사를 반복하지 않는다. 요청받지 않은 다음 단계로 진행하지 않는다.

2026-11-04 P09-G부터 후속 작업의 전체 검증 진입 전에는 기존 작업 문서에서 변경 계약·소비 영향의 assertion 연결, 새로 작성하거나 수정한 fixture의 실제 업무 assertion 도달, 변경한 정상 흐름과 관련 경계·실패 조건의 집중 근거, 테스트 준비 오류·필수 결함 잔여, 최종 필수 등록·수집·실행 옵션을 확인한다. 이는 기존 업무 묶음의 과정이며 별도 문서·승인·검토 게이트가 아니다. 유효한 기존 증거를 재사용하고 모든 기존 검사에 새 집중 실행을 요구하지 않는다. 준비 데이터·worker 시각·UI 위험 조건의 구체적 기준은 [하네스의 변경 범위 준비·집중 검증](verification-harness.md#변경-범위의-준비-조건과-ui-집중-검증)을 따른다.

| --- | --- | --- |
| 설계 판단 | 정책·모듈 소유권·트랜잭션·데이터 계약이 미정이거나 변경됨 | 기존 계약·선택안·영향·검증 계획; 중요한 변경은 기존 사용자 승인 적용. 구현 통과 판정이 아님 |
| 중간 독립 검토 | 계획한 업무 묶음이 연결됐거나 잘못되면 후속 재작업이 큰 경계를 구현함 | 대상 소스 식별·관련 집중 assertion/실행 증거·미완료 범위. 해당 경계 판단이며 단계 전체 통과가 아님 |
| 최종 독립 검토 | 작업 완료표의 구현·필수 제약 연결·변경 영향과 개발 검증이 갖춰짐 | 같은 소스의 선택 적합성·assertion·실행 증거·보존·인계를 대조하고 필요한 범위를 검증. 전체 필요 조건과 필수 차단 확인 |

검토 요청에는 새로 판단할 쟁점, 대상 소스, 관련 증거, 미완료 범위를 적는다. 임의 횟수 상한으로 필수 검토를 막지 않으며 새 쟁점 없는 내부 변경은 묶어서 요청한다. 확정 계약 안의 구현·컴파일·테스트 준비 오류는 구현 담당자가 처리한다. 새 근거 없이 확정 설계를 반복 질문하지 않는다. 지적 수정 후에는 해당 지적과 영향 범위를 재검토하며 위 전체 필요 조건에 해당하면 전체 근거를 확보한다. 담당·모델·기존 검토세션은 모델 라우팅 정책을 따른다.

### 실패 분류와 재실행

2026-11-17 D/E 후속 개선: 실패 원장은 실행별 새 증거 경로에 `command`, `sourceIdentity`, `environmentIdentity`, `expected`, `actual`, `causeStatus`(확정/가설/미확정), `cause`, `change`, `rerunPurpose`, `affectedContracts`를 연결한다. 동일 원인과 실행 횟수를 구분하며 이전 원장을 덮어쓰지 않는다. 준비 오류·도구/환경 오류·계획 RED·업무 assertion 실패·독립 검토 요청은 별도 집계한다. 변경 없는 재실행도 관측 보완·재현 조사·환경 변화의 목적과 조건을 명시하면 허용되며, 재통과가 원인 확정이나 해결을 대신하지 않는다.

장시간 실행의 상태 조회는 기존 진행 이벤트와 최상위 결과를 사용한다. 완료·실패·결정 필요·의미 있는 단계 변화만 묶어서 전달하고, 하위 `result.json`을 전부 재귀 집계해 최상위 묶음 완료로 오인하지 않는다. 같은 상태의 상세 목록·전체 로그를 반복 읽지 않는다. 현재 작업 문서 상단은 최신 소스/판정/증거/필수 잔여를 짧게 유지하며 원 이력은 아래에 보존한다. 도구가 노출하지 않는 모델 호출·비캐시 토큰·압축 횟수는 미측정으로 남기고, 비교 가능한 동일 정의 데이터 없이 절감률을 추정하지 않는다.

실행 전에 검증 목적과 예상 결과를 정하고, 실제 결과를 다음처럼 구분한다: 의도한 업무 RED, 제품 결함, 테스트 준비 오류, 환경 오류, 선택 범위 통과/실패, 전체 필수 검사 미충족. 현재 하네스의 정상 `selected-passed`는 제외 범위를 명시한 선택 통과이며 그 자체가 실패는 아니다. 과거 선택 실행의 root failed는 당시 결과로 보존한다. 선택 범위 통과를 전체 PASS로 바꾸지 않는다.

재실행은 원인 가설과 변경 사항에 연결한다. 비결정적 실패 조사는 변경 없이 재현할 목적·조건을 명시한다. 같은 원인 반복 실패는 기존 모델 라우팅 정책에 따라 분석·개입 필요성을 판단한다. 같은 종류의 결함은 현재 변경 범위의 동종 및 반대 방향 사례도 확인한다. 실행 횟수나 통과 개수로 진척·완료를 판단하지 않으며 실패 결과도 보존한다.

실패 뒤에는 실패 검사와 수정 영향 범위를 먼저 확인하고, 전체 재실행 여부는 위 영향·위험 기준으로 정한다. 기존 작업 기록에 실패 분류·원인 가설·변경과 실제 측정된 실패/재실행 소요시간 및 측정 범위를 함께 남긴다. 측정되지 않은 시간을 구현·검토·대기 시간으로 배분하지 않으며, 관측하지 못한 과거 실패 원인을 확정하지 않는다. 재진입 시 완료·미완료 상태부터 확인하고 완료 구현·유효 검증은 다시 시작하지 않는다. 진행 중인 검증은 임의 중단하거나 실행 중 소스를 변경하지 말고 결과를 보존한 뒤 안전한 작업 경계에서 예방 조치를 반영한다.

### 학습을 포함한 작업 방식

전체 기술을 먼저 공부하고 돌아오도록 요구하지 않는다. 이번 기능에 필요한 문법·개념·라이브러리만 실제 변경과 연결해 설명한다.

Java 문법을 처음부터 설명하기보다 익숙한 메서드·클래스·예외·SQL과 새 도구의 역할을 연결한다. Spring 기존 경험에서 그대로 활용할 부분과 Boot·웹 구성에서 새로 확인할 부분을 구분한다. React는 컴포넌트·props·state·이벤트·비동기 요청부터 필요한 순서로 설명하고 Java 객체와 동일하게 동작한다고 가정하지 않는다. TypeScript의 타입 검사는 서버 입력 검증을 대신하지 않는다는 점도 실제 사례로 연결한다. 사용자가 특정 기능을 이미 안다고 밝히면 중복 설명을 줄인다.

1. 도입 전에 무엇을 해결하려는 도구인지, 이번에 알아야 할 개념이 무엇인지 짧게 설명한다.
2. 변경 후 핵심 파일과 React 입력/상태 → HTTP → Java/SQL → 응답/화면의 흐름을 실제 코드 위치와 함께 안내한다. DB가 없는 단계에는 해당 부분을 제외한다.
3. 예를 들어 “상품명 표시를 바꾸고 결과 확인”처럼 사용자가 직접 해 볼 작은 수정 하나와 예상 결과를 제시한다.
4. 실행 오류가 나면 오류 메시지·관련 파일·검증 명령을 어떻게 연결해 확인하는지 설명한다.
5. 구현·자동 검증 결과와 사용자 학습·직접 확인 결과를 별도로 기록한다.

몇 개의 패키지가 함께 필요한 경우에도 모든 개념을 한 번에 이해한다고 가정하지 않는다. 작업이 크면 설명을 나누고 구현은 위 업무 결과 단위로 묶는다. 학습 설명의 분할을 내부 단계별 인계·독립 검토로 확대하지 않는다. 사용자 실습은 확인 방법으로 제안하며 별도 시험이나 매번의 승인 절차로 만들지 않는다. 응답이 없으면 사용자 직접 확인은 미확인으로 기록하고, 이미 요청받은 범위의 작업은 수행한다.

>
> 나는 Java는 꽤 유창하고 레거시 Spring과 Oracle 경험이 있어. Spring Web은 보완이 필요하고 간단한 SQL은 작성할 수 있어. React·JavaScript/TypeScript·프런트엔드 도구는 새로 배우고 있어. 기존 경험을 활용해 이번 기능에 필요한 개념과 React→API→Java/SQL→화면 흐름을 설명하고, 내가 직접 해 볼 작은 수정 하나와 예상 결과를 제시해줘. 자동 테스트 결과와 내가 직접 이해·확인한 결과를 구분해줘.
>
> 정상 흐름뿐 아니라 해당 기능의 경계값·권한 오류·실패 복구를 검증해줘. 변경에 맞춰 Java 검사와 React 타입·화면 검사를 실행하고, 브라우저 검사가 필요하면 실제 API와 연결해 확인해줘. 주문·재고·쿠폰·환불처럼 동시성이 중요한 부분은 실제 테스트 DB에서 확인해줘.
>
> 실행 목적·기대 결과를 먼저 정하고, 실패 종류·원인 가설·변경과 재실행을 연결해줘. 동종·반대 방향 사례도 확인하고 실행하지 못한 검증을 통과로 표시하지 마. 선택 범위 완료와 전체 PASS를 구분하고, 영향·위험/제약 확인→개발 검증→동일 소스 독립 범위 검토·필요 검증→실패/수정 영향 재검증→인계 순서로 마쳐줘. 전체 필요 조건은 유지하되 로컬 커밋이나 새 근거 없는 반복을 이유로 전체를 다시 실행하지 마.
>
> 끝나면 변경 내용, 실행 방법, 검증 결과, 남은 제한, 다음 작업을 기록하고 설계와 진행 상태를 갱신해줘. 다음 작업 구현은 시작하지 마.

`[작업 ID]`에는 `P01-B4` 또는 `P04-B`처럼 실제 ID를 넣는다. B4·B5 및 PostgreSQL Compose 구성은 완료했으며 현재 지정 작업 범위만 진행한다. 다운로드·도구 경로와 DB 이미지·볼륨의 구분은 [P01-A2 10절](work-items/P01-A2.md#10-docker-방침-반영과-현재-준비-기준)을 따른다. 단계 전체를 맡기려면 “요청한 단계의 업무 결과 묶음을 의존 순서대로 구현·검증하고 전체 완료 조건까지 진행”이라고 범위를 명시한다.

## 6. 오류 수정과 정책 변경 요청

오류 수정에는 재현 행동, 예상 결과, 실제 결과, 가능하면 오류 메시지를 전달한다.

> [재현 순서]에서 [예상 결과]가 나와야 하는데 [실제 결과]가 발생해. 먼저 재현하고 원인을 확인해줘. 관련 설계와 권한·상태 규칙을 확인한 뒤 수정하고, 같은 오류가 다시 발생하지 않는 검증과 주변 흐름의 회귀 검증을 수행해줘. 원인·변경·검증 결과를 기록해줘.

정책 변경은 변경 전후와 영향 범위를 연결한다.

> [정책]을 [변경 내용]으로 바꾸고 싶어. 먼저 기존 주문·회원·판매자·환불·정산에 미치는 영향을 확인해줘. 과거 거래에 소급 적용할지와 새 거래부터 적용할지를 구분해 설계를 갱신한 뒤 구현·검증해줘.

## 8. AI 개발과 포트폴리오의 증거

개발자는 기능 하나를 완료할 때 “어디서 권한을 확인하는지, 어떤 데이터가 바뀌는지, 실패하면 무엇을 복구하는지, 테스트가 무엇을 보장하는지”를 설명할 수 있어야 한다.

기록에는 요청문 원문 전체보다 문제·판단·변경·검증·한계를 남긴다. 성공 화면만 모으지 않고 권한 오류, 동시 주문, 응답 유실, 잘못된 운영 조치의 복원, 요구사항 변경 사례도 포함한다.

MSA 단계에서는 서비스 개수보다 분리 이유·계약·데이터 이행·실패 복구·전후 측정을 보여준다. 실제 실행 결과와 설계상의 예상 효과를 구분한다.

## 9. 완료 보고 기준

작업 완료 보고에는 업무 결과와 완료표, 최종 소스 식별(HEAD/변경 상태·입력 해시), 변경 계약, 선택·제외 범위와 이유, 실제 명령·증거 경로·결과와 재사용 근거, 동일 소스 독립 검토 결과, 지적 해결·미검증 범위·실패 이력, 후속 소비 계약을 적는다. 작업 제약의 필수 assertion 누락·선택 범위 실패/skip·미해결 필수 결함·근거 누락은 완료를 차단한다. 적절한 선택 범위로 작업 완료할 수 있으나 전체 PASS라고 쓰지 않는다. 실행 동작에 영향 없는 문서·서식은 필요한 정적 확인으로 완료하고 하네스 미실행을 명시한다. 다음 구현은 별도 요청 범위를 따른다.

전체 프로젝트는 세 구간으로 완료를 구분한다. P08 첫 구매 완료, P12 전체 기능·유지보수 검증 완료, P14 첫 MSA 전환 검증 완료다. 어느 한 구간을 마쳤다고 나머지까지 완료했다고 표현하지 않는다.



## 10. 프로젝트 절차와 Skills의 적용 규칙

2026-11-02 추가 정비. P09-E 이후와 P10 이후 모든 개발·검토에 적용한다. 기존 작업 계획은 Superpowers 도입 전에 작성되었으므로 스킬 양식과 다르다는 이유로 무효화하거나 처음부터 다시 작성하지 않는다. 이 절은 기존 3절의 운영 절차와 7절의 작업 기록 양식에 스킬을 대응시키는 기준이며 별도 실행 체계가 아니다.

### 우선순위·재사용·완료 조건

1. **우선순위:** 상위 시스템·개발자 지침과 실제 도구 제약을 준수한다. 그 범위에서 사용자의 명시적 요청과 프로젝트 규칙이 스킬의 기본 절차에 우선한다. 스킬의 MUST/HARD-GATE 문구만으로 새 실행 권한이 생기지 않는다.
2. **기존 문서 재사용:** 승인된 계획·설계·인계·실행 기록이 스킬의 목적/범위/계약/검증 정보를 충족하면 그대로 사용한다. 부족한 정보만 기존 작업 문서에 통합하며 같은 목적의 spec/plan/ledger를 병렬 생성하지 않는다. 승인된 운영 문서 정비를 이유로 별도 brainstorming 승인이나 계획을 추가하지 않는다.
3. **task와 step:** 프로젝트의 업무 결과 묶음을 스킬의 task에 대응한다. 메서드·DTO 작성, 테스트 실행, 파일 수정은 내부 step이며 그 자체로 별도 task·인계·동결·검토 게이트가 되지 않는다. 독립적인 실패·완료 조건과 서로 다른 업무 제약의 assertion은 유지한다. 이미 관측한 업무 RED가 내부 의존 구현을 포괄하면 구성요소마다 반복 RED를 만들지 않는다.
4. **검토의 동등성:** 프로젝트 검토와 스킬 검토의 대상 범위·목적·독립성·소스/실행 증거 조건이 모두 같으면 하나의 검토로 충족한다. 기존 검토 기록에 대응 범위와 부족분을 적고 부족분만 추가한다. 설계 판단, 중간 검토, 최종 검토는 목적이 달라 자동 통합하지 않는다. 구현자 자체 확인을 독립 검토로 바꾸지 않는다.
5. **담당 유지:** 지정 검토세션과 기존 부모·구현자 구조, [모델 라우팅](model-routing.md)을 유지한다. 스킬 진입만으로 새 구현자·검토자·오케스트레이터를 만들거나 가장 큰 모델로 자동 전환하지 않는다. 기존 담당에게 필요한 쟁점·대상 소스·증거를 전달한다.
6. **승인 재사용:** 사용자에게 승인받은 결정·실행 방식을 스킬 진입마다 재승인받지 않는다. 확정 계약 안의 구현 선택은 담당자가 처리하고 새로운 정책·중요한 설계 변경에만 기존 승인 기준을 적용한다. 스킬의 자율 판단 문구로 이 승인 기준을 우회하지 않는다.
7. **커밋 금지와 검토 자료:** 커밋 금지 요청이 있으면 commit 단계, 자동 stage/commit과 커밋을 전제로 하는 검토 스크립트를 그대로 실행하지 않는다. 기존 HEAD와 미커밋 diff, untracked 파일을 포함한 대상 파일 목록·해시/보존 사본, 실행 inputs를 묶어 검토 소스를 식별한다. HEAD끼리의 비교만으로 미커밋 변경을 검토했다고 하지 않는다. 검토 후 변경은 범위·해시로 추적하고 필요한 영향 재검토에 연결한다. 내부 step마다 동결 절차를 만들지는 않는다.
8. **증거 재사용의 한계:** 관련 소스·제약·실행 조건이 유효한 증거는 중간/최종 검토에서 재사용하고 변경 영향만 보완할 수 있다. 같은 소스의 독립 영향·선택 적합성 검토와 필요한 검증, 위 전체 필요 조건은 유지한다. 개발·독립에서 전체를 자동 반복하지 않으며 스킬 재진입·로컬 커밋도 재실행 사유가 아니다. 과거 통과를 현재 변경에 소급하지 않고 유효성을 기록한다. 문서 정비는 필요한 정적 확인과 실행 미수행 이유를 보고한다.
9. **실패·수정 라운드:** 스킬의 라운드 상한, parked/deferred/ruling 또는 자체 수정 통과를 미해결 필수 결함의 완료 근거로 사용하지 않는다. 반복 실패 때 원인·범위·담당 개입을 모델 라우팅 기준으로 재판단한다. 실패 검사와 수정 영향 범위를 재검증하며 넓거나 불명확한 변경이면 전체 기준을 적용한다. 새 소스 변경·실패·위험 근거 없이 통과 검사를 반복하지 않는다. 실패 분류와 원문 보존은 3절을 따른다.
10. **보존과 정리:** 스킬의 workspace/branch 정리나 TDD 재시작을 이유로 과거 실패 증거·DB·미디어·작업 기록·완료 구현을 삭제하지 않는다. 프로젝트 보존 조건과 사용자 승인 범위를 우선한다. 스킬 적용만으로 worktree·설정·전역 스킬을 변경하거나 커밋·푸시·배포를 시작하지 않는다.
11. **재진입과 컨텍스트 복원:** 기존 작업 문서의 완료/미완료·소스 식별·결정·지적 처리·차단·다음 의존을 먼저 읽는다. 스킬 자체 ledger나 커밋이 없다는 이유로 완료 작업을 다시 실행하지 않는다. 기존 진행 기록을 갱신하며 별도 실행 체계를 추가하지 않는다.

7절의 기존 작업 기록에서 필요한 경우 스킬명·확인한 버전/경로·재사용 문서/검토·부족분·조정한 기본 절차를 짧게 남긴다. 이를 위한 별도 문서·승인·검토 단계를 만들지 않는다.

### DB 계약 선택 실행

개발 중 피드백과 범위가 명확한 작업 완료에는 [하네스의 DB 계약 선택 실행](verification-harness.md#db-계약-묶음과-선택-실행-2026-11-03)을 따른다. 변경 도메인만 고르지 말고 `verification/db-groups.json`의 제공·소비 계약을 함께 확인한다. 공통 인증/실행기/금융/스키마/검사 도구 또는 신규·삭제·이름 변경의 영향이 불명확하면 전체로 확대한다. `-ChangedContracts`는 영향표 선택, `-DbGroups`는 이미 판단한 정확한 집중 범위다.

선택 실행은 전체 PASS가 아니지만, 변경 영향과 소비 계약을 충분히 포함하고 같은 소스의 독립 범위 검토·필요 검증을 충족하면 해당 작업 완료의 근거로 사용할 수 있다. 전체 필요 조건이면 선택 옵션을 생략한 실행 근거를 확보한다. `-ChangedContracts 'unknown'` 등으로 모든 묶음을 골라도 명시 선택 결과는 전체 인증이 아니므로 전체가 필요한 경우 처음부터 무선택 명령을 사용한다. 새 테스트는 묶음 소유권·필수 목록·영향표·작업 assertion을 함께 등록하고 미등록/빈 선택/누락/skip을 성공으로 처리하지 않는다. 상세 격리·경로·명령·등록 기준은 하네스 문서에만 관리한다.
