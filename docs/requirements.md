# 목적·목표와 서비스 요구사항

개정일: 2026-10-20 / 설계 v4 Java·Spring Boot + React / 요구사항 기준 문서; 현재 구현 상태는 단계별 작업 기록 참조

## 1. 프로젝트 목적

Java·Spring Boot 백엔드와 React 프런트엔드를 사용해 구매자·판매자·사이트 운영자가 함께 이용하는 마켓플레이스를 만든다. AI를 요구사항 정리·설계·구현·테스트·오류 수정에 활용하되, 개발자가 생성된 코드의 동작과 선택 이유를 이해하고 직접 변경·검증할 수 있는 수준을 목표로 한다.

익숙한 Java와 기존 Spring·Oracle 경험을 서버 개발의 출발점으로 삼고, React·TypeScript·브라우저 상태·API 연동은 작은 기능을 만들면서 학습한다. 회원·비회원의 테스트 구매, 판매자의 매대 운영, 운영자의 관리·비공개 조치까지 실제로 연결되는 서비스를 먼저 완성한다.

이후 부하·장애·변경 문제를 재현하고 모놀리스 내부 개선과 서비스 분리를 비교하면서 필요한 영역을 점진적으로 MSA로 전환한다. 이직용 포트폴리오에는 기능 화면과 함께 문제 정의·기술 판단·AI 제안 검토·테스트·수정·복구·전후 비교의 증거를 남긴다.

첫 구매 시제품 완성은 중간 목표다. P08에서 회원·비회원의 상품 선택 → 테스트 결제 → 결제 이력·판매자별 기본 배송 진행 조회까지 실제 화면·API·DB로 연결한다. 비회원은 다른 브라우저나 기기에서도 조회 인증 후 본인 결제·배송 진행을 확인할 수 있어야 한다. 기본 배송은 준비·발송·배송 중·배송 완료의 모의 진행을 뜻하며, 분할 배송과 거래 후속 처리는 P09에서 확장한다. 전체 기능 완성은 아래 F01~F18의 완료 기준을 충족하는 시점이며, MSA 전환은 그 이후 별도 목표다.

G10은 P01·P05의 화면/API 연습과 P12의 변경 사례에서 확인한다. 자동 테스트 통과와 개발자의 직접 이해·수정 여부는 따로 기록하며, 학습 확인을 매 작업의 별도 승인 절차로 만들지 않는다. 기존 F01~F18·AC01~AC20의 기능·정책·번호는 유지한다.

## 3. 사용자 요구와 설계 기본안의 구분

### 사용자가 정한 요구사항

- AI 개발 연습과 유지보수 경험을 포트폴리오로 만든다.
- 백엔드는 Java·Spring Boot, 화면은 React로 개발한다.
- 기존 Java 역량을 활용하면서 React 화면·API 연동을 배우고 AI가 만든 코드를 직접 이해·변경·검증한다.
- 쇼핑몰의 구매·판매·운영 기능을 구현한 후 문제 해결을 위해 MSA로 발전시킨다.
- 회원은 로그인해 상품을 선택하고 장바구니에 담아 테스트 주문을 완료한다.
- 사업자는 구매자 기능을 유지하면서 자기 매대의 상품과 이벤트를 등록·수정·삭제한다.
- 운영자는 대시보드와 사이트 관리 기능을 사용하고, 문제 상품·댓글은 플래그로 비공개 처리한다.
- 비회원 구매를 허용한다. 비회원은 쿠폰 사용이 불가하며 공개 이벤트는 적용 가능하다.
- 비회원은 이름·휴대전화 번호를 입력하고 인증을 완료한다.
- 인증은 완전 무료인 테스트 수단을 우선 검토하며, 없으면 모의 문자 인증을 사용한다.
- 비회원 주문 조회 비밀번호는 구매자가 직접 설정한다.
- 비회원도 자신의 결제 이력과 배송 진행을 조회한다.

### 이번 설계에서 제안하는 기본안

한국어·원화·국내 배송, 승인된 판매자당 매대 1개, 옵션별 재고, 판매자별 배송비, 회원의 구매 후기, 취소·반품·교환, 모의 정산을 기본으로 제안한다. 이 문서의 금액·기간·수량 제한은 테스트 가능한 정책을 만들기 위한 제품 설계값이며 법정 기준이나 실제 사업 운영 조건을 뜻하지 않는다.

“전체 기능”은 F01~F18로 범위를 명시한다. 네이버·쿠팡의 모든 사업·물류·광고 기능과 동일한 규모를 의미하지 않는다. 새 기능은 요구사항 ID와 완료 기준을 추가해 범위를 관리한다.

## 4. 사용자와 권한

| 사용자 | 허용 범위 | 주요 제한 |
| --- | --- | --- |
| 방문자 | 상품·매대·행사·공개 콘텐츠 조회, 장바구니 | 개인 주문과 관리 화면 접근 불가 |
| 비회원 구매자 | 구매 인증, 테스트 주문, 연결된 주문·결제·배송·클레임 조회와 신청 | 쿠폰·회원 찜·회원 리뷰 작성 불가 |
| 회원 구매자 | 회원 정보·배송지·찜·쿠폰·리뷰, 구매와 주문 후속 처리 | 자신의 데이터만 관리 |
| 판매자 | 회원 구매 기능 + 자신의 매대·상품·재고·행사·판매 주문·배송·문의·정산 | 다른 판매자의 데이터와 운영자 조치 변경 불가 |
| 사이트 운영자 | 회원·판매자·매대·콘텐츠·거래 문제 관리와 전체 운영 지표 | 개인정보와 거래 변경도 업무 권한 확인 및 조치 이력 필요 |

역할은 추가 권한으로 관리한다. 판매자 승인 때문에 구매자 자격을 잃지 않는다. 판매 정지와 회원 로그인 정지도 구분한다. 판매 정지 후에도 기존 주문의 배송·환불·문의 대응에 필요한 제한된 기능은 유지한다.

운영 권한은 계정·콘텐츠·거래지원·정산·시스템 관리로 구분할 수 있게 설계한다. 포트폴리오 초기에는 한 운영 계정이 모두 가질 수 있으나, API는 필요한 권한을 각각 확인한다.

## 6. 주요 이용 흐름

### 회원 구매

가입·로그인 → 상품·옵션 선택 → 장바구니 → 주소·이벤트·쿠폰 확인 → 주문 생성·재고 예약 → 테스트 결제 → 판매자별 배송 조회 → 구매 확정 또는 취소·반품·교환 → 후기.

### 비회원 구매

상품 선택 → 비회원 구매 → 구매자 이름·휴대전화 입력 → 인증 → 조회 비밀번호 직접 설정 → 배송 정보·이벤트 확인 → 테스트 결제 → 주문번호 확인 → 주문번호·휴대전화·비밀번호로 재접속 → 본인 주문·결제·배송·클레임 확인.

인증한 구매자 정보와 배송받는 사람의 이름·연락처·주소는 구분한다. 모의 인증은 전화 소유나 이름의 실명 일치를 증명하지 않는다.

### 판매자 운영

회원 가입 → 판매자 신청 → 운영자 승인 → 매대 생성 → 상품·옵션·재고·이미지 등록 → 이벤트 운영 → 판매 주문 확인 → 발송·문의·클레임 처리 → 매출·모의 정산 확인. 구매 메뉴에서는 일반 회원으로 구매한다.

### 사이트 운영

대시보드 이상 확인 또는 신고 접수 → 대상·거래·이력 확인 → 판매 중지·비공개·정지·거래지원 조치 → 사유와 처리자 기록 → 재검토·복원 → 결과 알림. 상품을 숨겨도 기존 구매자의 거래 내역과 후속 처리는 유지한다.

## 7. 비회원 인증과 주문 조회 정책

| 항목 | 설계 기준 |
| --- | --- |
| 무료 인증 테스트 | Firebase Authentication Emulator의 `demo-` 프로젝트 우선. 환경에 맞지 않으면 동일 계약의 자체 모의 문자 인증 |
| 실제 문자 | 초기에는 발송하지 않음. 실사용 인증 연동은 비용·제공 범위 확인 후 별도 결정 |
| 인증 정보 | 구매 세션·전화번호·용도·만료·사용 여부를 서버에 연결 |
| 인증 재시도 | 기본안: 인증번호 유효 3분, 재발송 60초 간격, 시도당 실패 5회. 전화번호·접속원별 추가 제한 |
| 조회 비밀번호 | 구매자가 직접 설정. 기본안 12~128자, 공백·붙여넣기 허용, 확인 입력 일치 검사 |
| 저장 | 검증된 느린 비밀번호 해시 사용. 원문·인증번호를 로그·URL·브라우저 영구 저장소에 보관하지 않음 |
| 조회 인증 | 주문번호 + 주문 묶음에 등록된 전화번호 + 조회 비밀번호 |
| 조회 범위 | 해당 GuestBuyer에 연결된 주문과 관련 결제·배송·클레임만 |
| 조회 세션 | 기본안 유휴 30분·최대 12시간. 로그아웃·비밀번호 재설정 시 서버에서 폐기 |
| 실패 안내 | 주문·전화번호 존재 여부를 구별하지 않는 공통 안내와 반복 시도 제한 |
| 재구매 | 기존 조회 인증 후 현재 구매의 전화 인증을 완료하면 같은 묶음에 연결. 기존 비밀번호 유지 |
| 별도 주문 | 기존 조회 인증 없이 구매하면 새 묶음 생성. 같은 이름·번호만으로 과거 주문 자동 병합 금지 |
| 번호 변경 | 기존 묶음 번호는 주문 제출로 변경 불가. 인증한 새 번호로 새 구매 묶음 생성 |

Firebase 에뮬레이터는 실제 클라우드 프로젝트 없이 로컬에서 인증 흐름을 시험할 수 있으며 실제 SMS를 보내지 않는다. 개발·테스트용 가상 이름과 번호를 사용하고 화면에 모의 인증을 표시한다. [Firebase 공식 안내](https://firebase.google.com/docs/emulator-suite/connect_auth)

비밀번호 복구 기본안은 첫 주문 완료 시 발급하는 충분히 무작위적인 복구 코드와 전화 재인증을 함께 사용하는 방식이다. 주문번호·복구 코드·재인증을 검증한 뒤 짧은 일회성 재설정 권한을 발급한다. 코드는 한 번 보여주고 서버에는 해시만 저장한다. 재설정 후 코드도 교체하고 기존 조회 세션을 폐기한다.

코드까지 잃은 경우 자동 복구하지 않고 지원 문의로 연결한다. 포트폴리오에서는 가상 데이터의 확인 절차만 시연하며, 실사용 복구의 신원 확인 근거는 운영 도입 전에 별도 설계한다. 전화 재인증 하나로 과거 전체 주문을 노출하지 않는다. 서로 다른 비회원 묶음 통합과 회원 전환 시 주문 연결도 별도 확장이다.

## 8. 상품·혜택·금액 기본 정책

| 항목 | 제안 기본안 |
| --- | --- |
| 판매 단위 | 옵션 조합별 SKU. 옵션 없는 상품도 기본 SKU 1개 보유 |
| 매대 | 승인 판매자당 활성 매대 1개. 향후 여러 매대로 확장 가능한 관계 |
| 판매 가능 | 판매자 승인·매대 공개·상품 판매 중·운영 비공개 아님·SKU 유효 조건 모두 충족 |
| 수량 | SKU당 주문 수량 1~99, 한 주문 최대 20개 SKU. 재고 범위 내 |
| 금액 | 원 단위 정수, 음수 금지. 계산과 검증은 서버가 수행 |
| 상품 행사 | 기간과 대상이 일치하는 행사 중 할인액이 가장 큰 1개. 동률은 행사 ID 순서 |
| 쿠폰 | 회원 소유 쿠폰만, 판매자별 하위 주문당 1개. 초기 쿠폰은 매대 범위·판매자 부담 |
| 공개 행사 | 회원·비회원에게 같은 상품·배송 이벤트 조건 적용 |
| 계산 순서 | 상품 정가 → 상품 행사 → 회원 쿠폰 → 판매자별 배송비 → 공개 배송 행사 |
| 배송비 | 행사 적용 후·쿠폰 적용 전 상품 합계 50,000원 이상 무료, 미만 3,000원 |
| 할인 제한 | 상품 할인은 해당 상품 금액, 쿠폰은 해당 상품 잔액, 배송 할인은 배송비를 초과하지 않음 |
| 배분 | 주문 시 할인액을 상품·수량에 배분해 보관. 반올림 잔액 처리 순서도 고정 |
| 행사 시간 | UTC 저장, 한국 시간 표시. 시작 포함·종료 제외 |
| 쿠폰 복구 | 결제 전 예약 해제 시 복구. 결제 후 해당 하위 주문 전체 취소·반품 완료 시 1회 복구하되 만료 쿠폰은 재사용 불가. 부분 환불은 복구하지 않음 |
| 가격 변경 | 주문 생성 전 최신 견적과 다르면 변경 내용을 보여주고 다시 확인 |

상품·행사가 나중에 수정·비공개되어도 이미 생성된 주문의 가격·할인·상품명·옵션명은 변하지 않는다. 판매자 부담 할인 외 플랫폼 부담 쿠폰과 적립금은 후속 확장으로 둔다.

## 9. 거래 후속 처리와 정산 기본 정책

- 결제 대기 재고 예약은 기본 15분이다. 결제 결과가 불명확하면 확인 절차 없이 재고를 풀지 않는다.
- 한 번의 장바구니 주문을 부모 주문 1개와 판매자별 하위 주문으로 나눈다. 초기에는 부모 주문 전체 금액을 한 번에 결제한다.
- 배송은 판매자별로 관리하고, 같은 판매자의 상품도 여러 배송 묶음으로 나눌 수 있다.
- 발송 전 취소는 대상 수량의 출고를 먼저 막는다. 발송과 취소가 동시에 성공하지 않도록 상태를 검증한다.
- 반품·교환 신청은 데모 기준 해당 수량의 배송 완료 시각부터 7일이 되기 전까지로 제안한다. 구매 확정 뒤 자동 신청은 종료하고 운영 문의로 처리한다.
- 구매 확정은 배송 완료된 수량에 대해 구매자가 직접 처리하거나 배송 완료 7일 후 자동 처리한다. 진행 중인 클레임 수량은 보류하며, 같은 시점의 신청과 확정은 상태 검증으로 한쪽만 반영한다.
- 부분 환불은 주문 당시 해당 수량에 배분된 실결제액을 사용한다. 남은 상품 가격과 무료 배송 기준을 소급 변경하지 않는다.
- 미발송 하위 주문 전체 취소는 청구한 배송비도 환불한다. 단순 변심 반품의 회수비는 판매자가 상품 등록·수정 시 설정하며 기본 3,000원이고 0원도 허용한다. 구매 전 표시하고 주문 당시 정책을 저장한다. 같은 원 배송 묶음의 반품 대상 상품 중 누적 최대 금액을 부과하며 후속 반품에는 차액만 추가한다. 서로 다른 원 배송 묶음은 합산하고 판매자 책임 단위는 제외한다. 공제액·추가 납부액은 환불 견적에 표시한다. 정책이 저장되지 않은 기존 주문은 새 견적에 비용을 밝히고 명시 동의를 받아 적용한다. 상세 계약은 [P09-C 설계 §11~12](work-items/P09-C-design-review.md)를 따른다(2026-10-31 사용자 결정 반영).
- 반품 재고는 회수·검수 후 판매 가능 수량만 복구한다. 환불 성공만으로 재고를 자동 복구하지 않는다.
- 발송 후 최초 배송비는 판매자 책임으로 전체 반품할 때만 실제 청구액을 환불하며, 변심 반품에는 환불하지 않는다. 회수비와 별도 계산하고 현재 가격·무료배송 조건으로 원 배송비를 재계산하지 않는다(2026-11-01 P09-D 사용자 결정).
- 일부 상품을 발송 전에 취소했다면 나머지 실제 발송 상품이 모두 실제 반품되고 판매자 책임으로 확인된 경우에도 최초 배송비를 한 번 환불한다. 신청·승인 또는 책임 주장만으로 환불하지 않으며 실제 회수·검수와 책임 확인 근거를 요구한다(같은 날 사용자 추가 결정).
- 교환은 동일 가격 SKU만 우선 지원한다. 새 재고 예약·검수·교환 출고를 기록하고 추가 배송비는 초기 데모에서 판매자 부담으로 둔다. 가격 차이가 있으면 반품·재주문으로 처리한다.
- 2026-11-02 P09-E 사용자 결정: 동일 가격은 원 주문의 할인 전 SKU 단가와 교환 승인 시 대상 SKU 단가를 비교한다. 원 실결제액·할인·쿠폰 배분은 변경하지 않는다. 교환 재고는 승인부터7일 예약하고 만료 전 사유를 남겨1회7일 연장한다. 만료는 예약만 해제하며 자동 환불·구매확정의 근거가 아니다.
- 교환품의 실제 배송 완료부터 새7일을 적용하고 확정 전 기간 내 추가 반품·교환을 허용한다. 실제 대체 SKU·배송 회차를 추적하며 원품을 중복 입고하지 않는다. 교환 후 변심반품의 회수비는 실제 배송 회차별 새 묶음으로 계산하고 같은 묶음 안에서는 기존 누적최대·후속 차액 규칙을 적용한다. 교환 출고 배송비의 판매자 부담과 별개다.
- 교환 매대 자격은 정상 영업을 기본으로 한다. 정지·폐점 매대는 판매자가 실제 검수로 제품 하자·판매자 책임을 확인한 경우 기존 거래의 예외 교환을 허용한다. 교환품은 같은 매대의 공개·활성·관리자 숨김이 아닌 SKU로 제한하며 현재 판매자 권한을 검사한다. 같은 SKU 교체도 허용하되 가격·자격·재고를 확인하고, 적합한 재고가 없으면 구매자 명시 동의를 받아 환불 전환한다. 현재 판단·구현·검증 상태는 [P09-E](work-items/P09-E.md)를 따른다.
- 정산은 구매 확정된 판매자별 거래를 기준으로 한다. 판매자 하위 주문의 상품 순매출에 5%를 적용해 원 미만을 한 번 버리고 원 수량에 배분한다. 배송비와 회수비는 수수료에서 제외한다. 부분 환불 시 해당 수량의 배분액을 되돌린다. 한국 시각 월요일 0시부터 다음 월요일 0시 직전까지 주간 모의 정산한다. 최초 정산 정책 적용 이후 생성된 주문부터 지급 대상이며 이전 주문은 거래 지표에 포함한다. [P11-A 사용자 결정](work-items/P11-A.md#승인된-정산-정책)
- 지연 실행한 지난주 배치도 해당 주의 마감 시점으로 판정한다. 같은 하위 주문의 다른 수량에 마감 정각 이후 접수된 반품은 지난주 확정액에 소급하지 않는다. 마감 직전부터 유지된 보류로 제외한 금액은 실제 해제 주에 한 번 지급한다. [마감 후 보류 결정](work-items/P11-A.md#주간-마감-이후-새로-접수된-보류)
- 정산 원장은 상품 순매출·배송 수입·환불·수수료·조정을 구분한다. 지급 완료 뒤 환불은 다음 정산 조정으로 기록하고 과거 지급 기록을 덮어쓰지 않는다.

2026-11-11 P11-B 승인 정책(구현·검증 상태는 [작업 기록](work-items/P11-B.md) 참조):

- 귀속이 명확한 보류는 관련 원 수량과 공통 배송비에만 적용한다. 무관한 구매확정 수량과 다른 매대 지급은 유지한다. 환불·회수비 예약 귀속이 불명확하면 해당 판매자 하위 주문 전체를 보류한다. 주간 마감·소급 금지·마지막 예약 해제 기준은 유지한다.
- 지급 후 성공 환불은 원 수수료 배분액을 반환하고 원인별 조정1회로 기록한다. 같은 매대의 후속 양수 정산에서 차감하고 부족분을 이월한다. 매출이 없어도 미회수 조정 잔액을 판매자·운영자에게 표시한다. 실제 지급액은0 이상이며 타 매대 상계·출금·추심은 하지 않는다.
- 구매확정 후 예외 환불은 기존 운영 문의를 바탕으로 판매자 책임 하자가 확인된 상품에 한정한다. 거래지원 운영자가 원 주문·수량·문의·회수/검수·하자 확인 근거·사유를 연결해 승인하고 별도 명시 실행한다. 일반 반품 신청을 재개하거나 구매확정을 되돌리지 않으며 문의 답변만으로 환불하지 않는다. 무회수·변심·자유 금액 보상 및 별도 자동 신청 기한은 없다. 원 주문·기존 승인 환불 정책으로 금액을 계산하고 기존 예약·UNKNOWN 조회/복구를 재사용한다. 최초 배송비는 위 기존 판매자 책임 전체 반품 조건을 유지한다.
- 새 정책은 시행 후 생성하거나 명시적으로 재작성하는 미지급 초안에 적용한다. 검토 완료 명세가 바뀌면 새 버전으로 재검토해야 한다. 지급 완료 배치·원장·검토 이력은 보존한다. 판매자는 자기 매대 정산·보류·조정·이월만 조회한다.

금액과 기간은 설정 버전과 함께 주문에 기록한다. 실제 결제·송금·택배 업무로 운영하기 전에는 제공자 계약과 운영 정책을 별도로 확정한다.

## 10. 콘텐츠·관리 정책

회원은 본인이 구매 확정한 주문 항목당 리뷰 1개를 작성한다. 기본 평점은 1~5점이다. 댓글은 회원이 작성하며 작성자는 수정·삭제할 수 있다. 비회원 리뷰는 초기 범위에서 제외한다.

작성자 삭제와 운영 비공개는 별도 값으로 관리한다. 공개 여부는 두 값과 상위 상품·매대 상태를 함께 확인한다. 운영자가 숨긴 콘텐츠를 작성자나 판매자가 수정했다고 다시 공개하지 않는다.

판매자는 자기 상품의 문의·후기에 답변할 수 있지만 부정적인 리뷰를 임의로 숨길 수 없다. 신고와 운영 판단을 거친다. 숨겨진 리뷰는 공개 평점 집계에서도 제외하고 복원하면 재집계한다.

판매자 정지와 운영자가 내리는 계정 정지는 신규 판매와 기존 거래 대응에 미치는 범위를 구분한다. 관리자 조치에는 사유·처리자·시간·대상·이전/이후 상태를 남긴다.

## 12. 문서 관계와 현재 상태

이 문서는 서비스 정책의 기준이다. 기술 구조는 [전체 기술 설계](shop-design.md), 구현 순서와 기능별 검증은 [구현 계획](implementation-plan.md), 서비스 분리는 [MSA 전환 설계](msa-evolution.md), 새 작업 창의 진행 방법은 [개발 작업 흐름](development-workflow.md)에 둔다.

이번 개정으로 전체 범위와 기본 정책을 정리했다. 제안 기본안은 각 소단계 착수 때 실제 화면·API·데이터 제약으로 구체화하며 변경 이유를 기록한다. 설계 최초 작성 시점에는 앱 구현·설치·DB 생성·배포 전이었다. 현재 P01 기반 구현·검증 상태는 [종합 점검](work-items/P01-completion-audit.md)을 따른다. 전체 서비스와 배포 완료를 뜻하지 않는다.

현재 기술 결정은 [ADR-001 Java·Spring Boot + React](decisions/ADR-001-java-spring-react.md)다. 설계 v4는 목적·목표와 화면 기술을 정리한 개정이며, 기존 구매·판매·운영 정책과 MSA 검증 목표를 축소하지 않는다.
