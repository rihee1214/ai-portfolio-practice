# Sol·Astra 모델 라우팅 정책

일반 개발·구현은 `gpt-6.2-sol` High가 담당한다. 그 밖의 작업에는 현재 메인 세션의 모델인 `gpt-6.2-astra`를 사용하며, 설계 분석·설계 변경 판단·독립 검증은 Medium으로 수행한다.

이 문서는 기존 운영 정책을 보완한다. [AGENTS.md](../AGENTS.md), [개발 작업 흐름](development-workflow.md), [통합 검증 하네스](verification-harness.md), 해당 작업 기록의 세션·담당자·승인·검증 규칙을 유지한다. 기존 작업 계획과 진행 상태를 변경하거나 새로운 실행 권한·오케스트레이터·Skill·에이전트 구성을 도입하지 않는다.

## 1. 모델별 기본 책임

### 1.1 Sol High — 구현 중심

Sol은 확정된 설계를 기준으로 구현 작업을 수행한다.

주요 책임은 다음과 같다.

- 기능 구현
- 도메인 로직 구현
- 애플리케이션 계층 구현
- 데이터 접근 계층 구현
- 외부 연동 구현
- 단위 및 통합 테스트 작성
- 일반적인 구현 오류 수정
- 기존 설계 범위 내 리팩터링
- 구현 결과 및 기술 문서 작성

Sol은 단순 반복 코드를 작성하는 역할로 제한하지 않는다.

설계가 확정되어 있다면 복잡한 기능도 Sol이 구현할 수 있다.

### 1.2 Astra Medium — 설계 및 검증 중심

Astra는 설계 판단과 결과 검증을 중심으로 작업한다.

주요 책임은 다음과 같다.

- 요구사항 및 설계 해석
- 설계 모순과 누락 분석
- 상세 설계 보완
- 복잡한 기술적 문제 분석
- 트랜잭션 및 동시성 정책 판단
- 도메인 경계 및 아키텍처 변경 영향 분석
- 설계 변경안 작성
- 구현 결과와 설계의 정합성 검증
- 복잡한 구현 오류의 원인 분석

Astra가 설계 판단을 수행하더라도 실제 구현은 가능한 한 Sol에 위임한다.

### 1.3 기존 실행 구조 유지

모델별 역할 정의는 기존 부모 및 서브 에이전트 구조를 변경하지 않는다.

기존 Astra 부모 및 Sol 구현 서브 에이전트 구성이 적용되어 있다면 이를 유지한다.

다른 구성이 적용되어 있어도 이번 작업에서 임의로 변경하지 않는다.

모델의 책임과 실제 에이전트 배치 구조를 구분한다.

## 2. Sol의 자율 판단 기준

Sol은 기존 설계 및 승인된 정책의 범위에서 다음 사항을 직접 판단할 수 있다.

- 내부 메서드와 클래스 구성
- 자료구조 및 알고리즘의 세부 구현 선택
- 기존 계약을 준수하는 데이터 접근 로직
- 정의된 예외 처리 정책의 구현
- 컴파일 오류 및 일반 테스트 실패 수정
- 기존 설계를 변경하지 않는 리팩터링
- 테스트 코드 작성 및 보완
- 명확한 요구사항 범위에서의 성능 개선
- 일반적인 구현 세부사항에 대한 기술적 판단

다음 원칙을 적용한다.

1. 모든 기술적 판단을 Astra에 위임하지 않는다.
2. 기존 설계에서 해결할 수 있는 문제는 Sol이 직접 처리한다.
3. 코드가 복잡하다는 이유만으로 Astra에 전환하지 않는다.
4. 설계의 해석이나 변경이 필요해지면 Astra에 판단을 요청한다.
5. 판단의 근거가 되는 설계가 명확하다면 Sol은 작업을 계속할 수 있다.

## 3. Astra로 전환해야 하는 조건

Sol은 다음 상황에서 Astra에 설계 판단을 요청한다.

### 3.1 설계 모호성 및 누락

- 기존 설계 문서가 모호하여 구현 방향을 결정하기 어려운 경우
- 요구사항에 필요한 비즈니스 규칙이 누락된 경우
- 상세 설계가 없어 중요한 구현 방향을 결정할 수 없는 경우
- 여러 구현 대안 중 선택에 따라 설계 의미가 달라지는 경우

### 3.2 설계 충돌

- 요구사항과 설계 문서가 서로 모순되는 경우
- 서로 다른 설계 문서 사이에 충돌이 있는 경우
- 기존 아키텍처로 요구사항을 충족하기 어려운 경우
- 기존 도메인 규칙을 위반해야만 구현이 가능한 경우

### 3.3 주요 기술적 판단

- 트랜잭션 경계를 새롭게 결정하거나 변경해야 하는 경우
- 동시성 제어 또는 데이터 정합성 정책이 미확정된 경우
- 도메인 경계 또는 데이터 소유권 변경이 필요한 경우
- 외부 인터페이스 또는 데이터 계약의 변경이 필요한 경우
- 모듈 책임이나 주요 아키텍처 변경이 필요한 경우
- 설계에 정의되지 않은 중요한 비기능 요구사항이 발견된 경우

이미 확정된 설계에 따라 트랜잭션이나 동시성 로직을 구현하는 경우에는 Sol이 계속 수행할 수 있다.

### 3.4 오류 및 장애 분석

- 동일 원인에 대한 수정이 반복 실패하는 경우
- 여러 모듈의 상호작용으로 인해 원인 분석이 어려운 경우
- 구현 오류인지 설계 오류인지 구분하기 어려운 경우
- 해결 방법이 기존 설계를 변경할 가능성이 높은 경우

설계 문제가 명확하다면 반복 실패 횟수와 무관하게 즉시 Astra에 판단을 요청한다.

## 4. 모델 전환 시 정보 전달

Sol이 Astra에 판단을 요청할 때는 가능한 범위에서 다음 정보를 전달한다.

- 작업 식별자
- 작업 목표
- 관련 요구사항 및 설계 문서
- 현재까지의 구현 내용
- 발견한 문제 또는 설계 충돌
- 판단이 필요한 질문
- 예상 영향 범위
- 기존에 시도한 해결 방법과 결과
- 작업 진행 상태

Astra는 전달된 정보가 불충분하다면 관련 문서나 코드를 추가로 확인할 수 있다.

전체 프로젝트를 불필요하게 재분석하지 않고 판단이 필요한 쟁점에 집중한다.

## 5. Astra 판단 결과에 따른 처리

Astra의 판단 결과는 다음 네 가지로 구분한다.

### 5.1 기존 설계 내 해결 가능

- 기존 설계를 변경하지 않는다.
- 구현 방향과 판단 근거를 제시한다.
- Sol이 구현을 계속한다.

### 5.2 제한적인 설계 보완 필요

- 설계 누락이나 모호한 부분을 분석한다.
- 기존 승인 정책에 따라 변경 권한을 확인한다.
- 자율적으로 결정 가능한 범위에서는 설계를 보완한다.
- 사용자 승인이 필요한 경우 승인 전 확정하지 않는다.
- 확정된 설계 내용을 Sol에 전달한다.

### 5.3 주요 설계 변경 필요

- 변경 사유와 영향 범위를 분석한다.
- 가능한 대안과 트레이드오프를 정리한다.
- 기존 정책에 따라 사용자 승인을 요청한다.
- 사용자 승인 전에는 설계를 확정하거나 구현하지 않는다.
- 승인된 변경 사항을 설계 문서에 반영한다.
- Sol이 변경된 설계를 기준으로 구현한다.

### 5.4 추가 조사 필요

- 현재 정보로 판단할 수 없는 이유를 명시한다.
- 필요한 조사와 검증 항목을 정의한다.
- 기존 담당 에이전트가 수행할 수 있는 조사는 해당 에이전트에 위임한다.
- 조사 결과를 기반으로 판단을 재개한다.

## 6. Sol의 구현 재개 및 재검증

Astra의 판단이 완료되면 구현 책임은 기존 Sol 담당 에이전트에게 돌아간다.

다음 순서로 진행한다.

1. Astra의 판단 결과를 확인한다.
2. 승인된 설계 및 변경 사항을 확인한다.
3. 기존 구현에 미치는 영향을 분석한다.
4. 필요한 범위의 코드만 수정한다.
5. 관련 테스트를 실행한다.
6. 기존 검증 정책에 따라 결과를 검증한다.
7. 검증이 완료되면 작업 상태를 갱신한다.

이미 확정된 설계 판단을 불필요하게 반복 검토하지 않는다.

모델 전환 이후에도 기존 작업 식별자와 진행 상태를 유지한다.

## 7. 반복 실패 및 에스컬레이션

일반적인 구현 오류는 Sol이 먼저 분석하고 해결한다.

다음 기준을 적용한다.

- 컴파일 오류나 단순 테스트 실패는 Sol이 직접 해결한다.
- 동일 원인에 대해 두 차례 수정에 실패하면 Astra 개입 필요성을 검토한다.
- 설계 결함이 명확한 경우 즉시 Astra에 요청한다.
- 반복 실패 원인이 테스트 환경이나 외부 의존성에 있다면 먼저 해당 문제를 확인한다.
- Astra가 원인과 해결 방향을 분석하면 가능한 경우 Sol에 수정 작업을 재위임한다.

두 차례 실패 기준은 절대적인 제한이 아니라 초기 에스컬레이션 기준으로 사용한다.

## 8. 검증 단계의 모델 선택

기존 검증 정책을 그대로 유지한다.

### 8.1 Sol 자체 검증

Sol은 다음 사항을 확인한다.

- 컴파일 성공
- 관련 테스트 통과
- 작업 완료 조건 충족
- 기존 설계 및 계약 준수
- 일반적인 회귀 영향

### 8.2 Astra 검증

기존 정책에서 독립 검증이 필요한 작업은 Astra가 담당한다.

Astra는 다음 사항을 확인한다.

- 요구사항 충족 여부
- 설계와 구현의 정합성
- 비즈니스 규칙 준수
- 테스트의 적절성 및 누락
- 예외 및 실패 시나리오
- 주요 변경의 영향 범위

### 8.3 검증 실패 처리

- 구현 오류는 Sol에 수정하도록 전달한다.
- 설계 오류는 Astra가 분석한다.
- 중요한 설계 변경은 사용자 승인을 받는다.
- 수정 후 영향을 받은 범위를 다시 검증한다.
- 검증되지 않은 항목을 통과로 처리하지 않는다.
- 실제 실행하지 않은 테스트를 통과했다고 보고하지 않는다.

## 9. 모델 전환 최소화 정책

모델 전환은 작업의 정확성과 효율성을 개선하기 위한 수단이다.

다음 규칙을 따른다.

1. 모델 전환 자체를 목표로 하지 않는다.
2. 기존 모델이 해결 가능한 문제는 계속 수행한다.
3. 동일한 판단을 여러 모델에 중복 요청하지 않는다.
4. Astra에는 필요한 판단 범위를 중심으로 정보를 전달한다.
5. 확정된 설계 판단은 문서로 재사용한다.
6. 불필요한 모델 왕복을 최소화한다.
7. 모델 전환을 줄이기 위해 중요한 설계 문제를 무시하지 않는다.
8. 모델 사용 비용뿐 아니라 재작업과 검증 비용을 고려한다.

## 10. 기존 정책과의 관계

이번에 추가하는 모델 라우팅 정책은 기존 운영 정책을 보완한다.

- 기존 세션 분리 정책을 변경하지 않는다.
- 기존 부모 및 서브 에이전트 구성을 변경하지 않는다.
- 기존 사용자 승인 정책을 유지한다.
- 기존 설계 및 문서 관리 규칙을 유지한다.
- 작업 분할·검토 진입·완료 절차는 [개발 흐름](development-workflow.md)의 현행 기준을 따른다. P09-D 이후 운영 정비는 모델·담당 구조·사용자 승인·필수 검증 수준을 변경하지 않는다.
- 모델 라우팅 정책만으로 새로운 실행 권한을 부여하지 않는다.

기존 정책과 충돌이 발견되면 임의로 해결하지 않고 충돌 내용을 보고한다.

상위 시스템 지침과 실행 환경의 안전·권한 제약을 우선한다.

## 11. 실행 환경의 지원과 제한

정책상 역할 지정과 실제 실행 모델 선택은 별개다. `AGENTS.md`를 읽거나 이 정책을 추가하는 것만으로 현재 세션의 모델이나 추론 수준이 자동 변경되지는 않는다.

2026-10-29 이 작업 세션에 공개된 도구 정의에서 확인한 범위는 다음과 같다. 실제 모델 호출·전환은 이번 문서 변경에서 시험하지 않았다. 이후 실행 시에는 당시 도구의 허용 모델과 권한을 다시 확인한다.

| 기능 | 확인된 지원과 제한 |
| --- | --- |
| Sol 구현 모델 지정 | 일반 개발 담당을 배정할 때 `gpt-6.2-sol`과 `reasoning_effort: high`를 명시한다. |
| Astra 설계·검증 모델 지정 | 설계 판단과 별도 독립 검토 담당은 `gpt-6.2-astra`와 `reasoning_effort: medium`으로 배정한다. |
| 부모의 서브 에이전트 호출 | 호출 도구는 제공되지만 사용자 또는 적용 지침의 위임 허용과 기존 세션 구조를 따른다. 도구의 존재만으로 새 에이전트를 만들 권한이 생기지 않는다. |
| 에이전트별 모델·추론 설정 | 현재 도구에서 명시적 재정의는 `fork_turns: none`으로 시작할 때 가능하다. `all`은 부모 설정을 상속하며 재정의를 받지 않는다. 기존 에이전트의 모델을 제자리에서 바꾸는 기능은 확인되지 않았다. |
| 컨텍스트 전달 | 새 호출의 작업 메시지와 기존 담당자에 대한 후속 작업·메시지 도구가 제공된다. 모델을 명시하는 별도 컨텍스트에는 4절의 인계 정보를 전달한다. 전체 대화가 자동 전달된다고 가정하지 않는다. |
| 현재 부모 세션 자동 전환 | 이 세션의 도구 정의에서 현재 부모 모델을 직접 바꾸는 기능은 확인되지 않았다. 필요한 경우 지원되는 사용자 모델 선택 또는 기존 담당 세션의 인계 절차를 사용한다. 지원되지 않는 자동 전환을 약속하지 않는다. |

전환이 불가능하면 필요한 판단·현재 상태·실행 제약을 기록하고 기존 절차로 인계한다. 중요한 설계 문제를 임의로 확정하거나 Astra의 검증을 실제 수행한 것처럼 표시하지 않는다. 이번 정책 반영으로 실행 환경이나 전역 모델 설정을 변경하지 않는다.
